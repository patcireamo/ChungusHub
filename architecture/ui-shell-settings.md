# UI shell, settings, theming & ambient: architecture & maintenance

**Boot** happens in [`AppShell.svelte`](../src/lib/components/layout/AppShell.svelte) `boot()`, one ordered async chain (comments in the file explain each ordering constraint: settings-spine stores before first paint, library/persona/presets before anything resolves chat context, `chatStore.loadAllChats` after, `initSync()` last). **Its first step waits for the live-sync socket instead of gambling on one attempt**, because a 5s connect cap is a fact about five seconds and not about the server (architecture/client-data-layer.md): a cold dev server, a phone waking on its network and an install still opening its port all heal inside a window that a single attempt loses, and the launch continues by itself the moment the socket opens, with nothing to press. The wait is never silent. The launch card moves from Preparing workspace to Waiting for the server, and past 15s to Can't reach the server, which names the one thing the reader can check; every failed pass also logs its own error. Only an answer that will never heal ends the wait, and `/api/health` is what asks for one between attempts: 403 lands on the denied screen, and a 503 carrying the server's maintenance state lands on a card drawn from the server's own headline and detail (architecture/server-core.md), since an install holding itself for a restore is up and deliberately not serving. A failure after the socket is open is a real bug and lands on the error screen. The data epoch this page was built against is read once the socket is up, so `watchForRestore` never compares against an unknown. The app is one SvelteKit route (`src/routes/+page.svelte` → AppShell) plus `/debug`, the detached prompt-debug window, which runs its own three-line boot over a fraction of these stores (architecture/tokenizer-debug.md). SSR off, prerendered shell.

**Panel choreography** ([`ui.svelte.ts`](../src/lib/stores/ui.svelte.ts), `uiStore`) is the one owner of what's open: chat-area overlays (`chats`, plus `chatsScope`, which of the browser's two scopes it reopens on, remembered across opens the way `libraryTab` is (architecture/chat-sessions.md); `lorebook` / `presetControls` / `storymap` / `memory`), the Settings dock (left) and merged Library dock (right, `libraryTab` characters/personas + centered `libraryEditorId` editor), the debug panel, the free-floating Chungus Assistant (`assistantOpen`, exempt from mutual exclusion), and the welcome landing (`welcomeOpen`, a base layer dismissed only by opening a chat). [`TitleBar.svelte`](../src/lib/components/layout/TitleBar.svelte)'s centred `NAV` cluster raises four of those overlays, and **one of them a setting can retire**: `memory` goes while `featurePromptsStore.memoryEnabled` is off, since the panel would have nothing to run, and the button is filtered out entirely rather than opening a dead surface (architecture/engines.md). Turning it off while the panel is open leaves it dismissible by Escape/click-away but unreopenable. **Steering has no entry here at all**, deliberately: the composer's compass popover creates, scopes, edits and deletes notes on its own, so a second surface over the same rows would be a manager for guidance that is written a few centimetres away (architecture/engines.md). **One of those buttons also carries state**: Memory's, which renders its own glyph through [`MemoryNavStatus.svelte`](../src/lib/components/memory/MemoryNavStatus.svelte) (architecture/memory.md), lights it off `memoryStore.standing` and folds the same line into its `title` and `aria-label`, so a background pass, a backlog or a failure is readable with the panel closed. Its footprint is fixed by construction: the glyph keeps the box a bare icon occupied and the backlog mark is absolutely positioned inside the button, so the cluster's geometry is identical whether or not memory is working. That is the rule for anything else that wants to report state here: the state rides colour, light and a corner mark, because a nav button that grew, swapped its glyph or reordered the row would cost the reader the anchor the cluster exists to be. `chats` has no TitleBar button at all: it is raised from the welcome landing and the composer's hamburger menu. **`stats` has none either, and for the same reason**: the TitleBar cluster is the open chat's own tools, while the stats screen counts the whole library (architecture/stats.md), so it rides those two library-wide doors rather than a sixth nav button whose subject is not the chat in front of it. Rules encoded there: one panel at a time unless a side dock is **locked**; a registered **nav blocker** (used by the Library's unsaved-new-entry trap) can veto any navigation and pulse a warning (`guardBlocksNav()` is the public form for call sites outside the panel methods, e.g. a browse-card pick that exits an open editor); closing the Library releases `workspaceFocus` (the assistant's auto-attach signal; see architecture/chungus-assistant.md). `uiStore` also owns the **New chat flow** (`newChatStep` 'character'/'persona' + `newChatCharacterId`; `startNewChat`/`advanceNewChat`/`clearNewChat`): a two-step wizard that rides the Library panel itself. Welcome's New chat button, Ctrl+N, the chat empty state, and the global Chats view all start it; a character pick advances it, a persona pick completes it (fresh chat via `chatStore.createChat`), and it cancels on `closeLibrary` or any chat opening (`chatStore.selectChat` calls `clearNewChat`). `LibraryView` shows the step banner while it runs. The state machine's transitions and cancel edges are pinned in [`new-chat-flow.test.ts`](../src/lib/stores/new-chat-flow.test.ts) (runs the rune store as a plain class via a `$state` identity shim). [`viewport.svelte.ts`](../src/lib/stores/viewport.svelte.ts) decides dock-vs-overlay (≥76rem, derived; coupling 7), phone mode (≤640px) and `isTouch` (`pointer: coarse`). The last is the one signal for "is there a physical keyboard", deliberately **not** the width query (a narrowed desktop window still has one, a 1024px tablet doesn't), and it is what both composers' Enter-to-send contract, input-history recall and the Settings shortcuts row all read; [`navigation.ts`](../src/lib/services/navigation.ts) is the assistant's deep-link router (routes through the same uiStore/chatStore actions so the nav guard holds; flashes the target).

**Assistant snap geometry** ([`AssistantFloatingWidget.svelte`](../src/lib/components/assistant/AssistantFloatingWidget.svelte)) comes from the rendered shell, never a JavaScript copy of `--chat-col-max`: `TitleBar.svelte` exposes `data-assistant-snap-column` for the shared horizontal chat/dock boundary and `Workspace.svelte` exposes `data-assistant-snap-workspace` for the content bounds below the title bar. A `ResizeObserver` re-fits snapped panels when either anchor changes, covering viewport resize, browser/UI scale, the chat-width setting, and responsive breakpoint changes. At dock widths side zones occupy the exact Settings/Library margins; below the dock breakpoint they resolve to the native centered-overlay column. Snapped surfaces and their preview ghost use sharp corners; the surface also drops floating shadow/all-edge borders and uses the same panel background and seams as native docks/overlays. While attached to a side, the widget publishes transient `uiStore.assistantSnapSide`; `Workspace` folds that into its existing `dock-left-open` / `dock-right-open` classes, so both the chat and welcome tint retract their feather on that side through the same registered `--chat-feather-*` animation as Settings/Library. Floating, centered, narrow, mobile and closed states clear the side without entering panel mutual exclusion.

**Keyboard**: [`commands/shortcuts.svelte.ts`](../src/lib/commands/shortcuts.svelte.ts) is the single list of global keys **and** the matcher (`matchShortcut`), the sibling of `commands/registry.ts` and one file for the same reason: a binding is declared, documented and matched in exactly one place. `Workspace.svelte` `handleKeydown` asks it what a press means and runs it, and the shortcuts sheet renders from the same rows, so a key cannot be bound as one thing and documented as another, nor documented and dead. Three rules hold it. **No shortcut implements behaviour**: every `run` is one call into a store, so a key and the control it stands in for are the same call. **A row without `run` is documentation**: Enter in the composer, ⌘/Ctrl+Enter beside it, the arrows on a turn and the layered Escape belong to whatever has focus, and they are listed because the sheet is the one place a reader looks for a key. Enter is the reason that first pair can never be bound here: every text box in the app owns it, so a window-level match would fire from the assistant's composer, a rename field or a dialog, and living in the composer is also what lets ⌘/Ctrl+Enter read the very gate its menu row reads (architecture/chat-sessions.md). Such a row spells its modifier `'mod'` and the sheet draws the platform's word for it, since `MOD_KEY` lives there and the registry cannot import it back. **A `run` may decline**, by returning false, and the key then reaches the browser untouched: Ctrl+F takes find-in-chat off the browser's own find only while a chat is genuinely on screen (`chatStore.activeChatId && !uiStore.activeOverlay`), since the story map carries its own search (architecture/chat-sessions.md); ⌥↑/↓, which step the keyboard through the story's turns, are guarded on the same fact. Modifiers are compared exactly and never "at least", or Ctrl+Shift+F would also answer to the Ctrl+F row and open find-in-chat over the hint labels. A binding names its keys **either by character (`key`) or by position (`code`)**, and the choice is not a taste: a letter that MEANS something is matched on the character the reader typed, while a cluster that is a shape under the hand is matched on where it sits, because Option on macOS composes characters and ⌥W arrives as `key: '∑'`, so a row spelling itself `'w'` would never fire on a Mac at all. The matcher hands `run` the spelling that answered, since a row bound by position cannot read its own key back off the event. What is left after all that is residue that fails in silence, which is the whole hazard of a keyboard since nothing on screen says a press did nothing, so [`contracts.test.ts`](../src/lib/contracts.test.ts) ("shortcuts") pins that no two rows answer to the same press, that every row sits in a group the sheet renders, and that a bound row runs while an unbound one says what to press. Ctrl+J is the assistant's only door once its floating button is switched off, so that one is not optional garnish. The **Escape ladder** closes one surface per press, top-most first: debug panel, chat-area overlay, then an unlocked Settings/Library dock, and with nothing left to close it hands the keyboard back to the composer (`chatCursor.toComposer()`, architecture/chat-sessions.md). That last rung is why there is no shortcut of its own for the composer: Escape is the way back to the box you type in, from a turn the cursor was parked on or from anywhere else. The handler stands down while a Dialog portal is mounted (`.dialog-portal`) and defers to a microtask so any panel-level Esc consumer (lorebook collapse, message editors, image viewers, the composer's command palette) can claim the key with `preventDefault` first. New Esc consumers must call `preventDefault` or the workspace will also close their host panel. The shortcuts sheet ([`ShortcutsSheet.svelte`](../src/lib/components/ui/ShortcutsSheet.svelte)) is a plain Dialog that owns nothing but the drawing: rows, order, labels and combinations all arrive from the registry, and what stays here is `MOD_KEY` (the ⌘/Ctrl platform string, the app's one `navigator.platform` read, imported by every surface that names a shortcut) and the chips a binding derives into. A row carrying neither a binding nor chips throws rather than drawing a labelled blank. Its open flag lives **with the registry**, as does the hint layer's, and for one reason: both components read that list, so a flag in either of them would leave the file declaring the key that raises a surface importing the surface that imports the list. Both stay outside uiStore's panel choreography either way, since neither a glance at the keys nor a look at the labels may disturb whatever panel is open, which is also why the sheet is a dialog and not a settings page. Both its triggers are global (Ctrl+/ and the Settings root's footer row), so `Workspace.svelte` mounts it, not a panel.

**Hint labels** ([`HintLayer.svelte`](../src/lib/components/layout/HintLayer.svelte), Ctrl+Shift+F) are the app's answer to a target that is visible but far from wherever the keyboard is. A cursor that steps is the wrong tool for a far target and a pointer driven by arrow keys is a slow mouse; what the keyboard has over both is that it can ADDRESS a thing, so every control on screen wears a short badge and typing one presses that control. **Its value is that it needs nothing from the surfaces it labels**: a panel becomes keyboard-reachable the moment its controls are real buttons, so no screen has to be taught navigation of its own for the app to be usable without a mouse. What it cannot label is exactly what it must not hide: a `<div>` with a click handler gets no badge, and that absence is a straight reading of where the markup is not semantic yet. `data-hint` is the explicit opt-in for anything that is reached rather than pressed (the transcript's turns).

**It is a mode, not a gesture.** The labels stay up until they are switched off and re-read the screen after every press, because picking a control is usually the first of several moves and pressing the key again between each of them is the work this exists to remove. What that costs is the letters: while the labels are up they are spellings and not text, and the layer takes the keyboard in the **capture** phase, or every letter would also land in the composer, which still holds the caret. Three rules pay that cost back. **Focus reaching a box that takes text switches the mode off, however it got there** (`handleFocusIn`): a label, a Tab or a click into the composer all leave a caret somewhere, and this is what keeps a standing mode from becoming a keyboard that answers typing with jumps. Reaching a TURN does not, since that is navigation and the next move is usually another one. **A modified key travels on untouched**, the toggle included, so Ctrl+K out of the labels opens Chats and the labels re-read what it put on screen. **The labels watch the page rather than guessing when it changed** (a `MutationObserver` over the body while the mode is up): a press whose act is async, a swipe that reaches the server and re-renders its turn a few frames later, leaves labels standing over controls that are already gone, and re-reading one frame after the press is too early to see it. The observer ignores a batch made entirely of the layer's own badges, or writing the labels would observe itself; and a spelling that still lands on a node no longer in the page puts fresh labels up instead of pressing nothing. And **a re-read keeps the label a control already carries**, dealing fresh ones only when the count crosses into a different spelling length: the transcript scrolls on its own while a reply arrives, and a set reshuffled under a reader who has read a label and not finished typing it sends the press somewhere else. That makes what is on screen an INPUT to what goes on screen next, so the pass reads the standing labels under `untrack`: read as a dependency of the effect that calls it, its own write at the end re-runs the effect that made it and the page dies on a depth-exceeded loop. A re-read also stands down entirely while anything is typed, for the same reason. Escape is always the way out.

Two more rules keep the badges honest. Candidates come from the shared [`visibleTargets`](../src/lib/utils/screen-targets.ts) pass, which filters by an **occlusion test** (`elementFromPoint` at the clamped centre) and not by the rect alone, because panels stack over the chat and every panel scrolls: a control covered by an overlay or scrolled out of its own box still has a rect on screen, and a badge drawn there points at something the press would never reach. **Every label is the same length**, which is what makes them prefix-free ([`utils/hints.ts`](../src/lib/utils/hints.ts), tested): a one-character label that also starts a two-character one could never be typed, since the first press would have to guess whether the reader was finished. The layer sits above every panel, popover and dialog (z 1200).

**The focus keys** (⌥/Alt + W/A/S/D, [`services/spatial-focus.ts`](../src/lib/services/spatial-focus.ts)) move the keyboard one control in a direction, which is the step Tab gets wrong on any screen laid out in two dimensions: Tab walks the document in one, so in a grid of cards or a two-column form the next thing in the markup is regularly not the next thing on screen and the reader has to hold a map of the DOM in their head to predict a press. **A modifier rather than bare letters, and that is what keeps this out of a mode**: the composer holds the caret nearly all the time, so bare WASD would need a state to switch into and back out of at every text box on the screen. **The arrows are deliberately not an alias**: they belong to the control the keyboard is already ON (a slider's value, a list's selection, the caret), and that separation, act inside with the arrows and move between with the letters, is the whole reason the letters exist. The cluster is bound **by position**, per the rule above, which is both what makes it work under ⌥ on macOS and the truer reading of WASD: a place under the hand rather than four initials. ⌥↑/↓ stay what they are, the story's own steps, because those are semantic rather than geometric: they walk the branch a turn at a time, reaching turns the window is holding back and ones taller than the screen, where "up" from the composer would land on its own toolbar. Scoring is pure and tested ([`utils/spatial-nav.ts`](../src/lib/utils/spatial-nav.ts)): distance is measured edge to edge along the way being travelled and stepping OUT of line is weighted heavier than stepping along it, because a nearest-centre search skips a tall card whose edge is right there for a small button below it and walks the press diagonally down the screen. Its candidate list is **narrower than the labels'**, and read off the tabindex ATTRIBUTE rather than the computed `tabIndex`: an element with no tabindex reports -1 exactly like one carrying `tabindex="-1"`, so the computed value cannot tell a transcript turn (focusable, deliberately out of the tab order) from a plain `<div>`, and moving to the second drops the keyboard on the floor. A `role="button"` with no tabindex can be pressed by a label and can never be reached by a focus key, because nothing can focus it. With nothing in that direction on screen it scrolls the box the focus is in by most of a screenful and takes **one** retry, or a panel taller than the window would stop the keyboard dead at its fold; that scroll says `'instant'`, since the transcript's scroller glides by its own CSS and the retry a frame later would otherwise read a position still travelling (architecture/chat-sessions.md coupling 15).

**The first-run greeting** ([`WelcomeDialog.svelte`](../src/lib/components/layout/WelcomeDialog.svelte)) is a plain `ui/Dialog` with a module-level open flag, the `ShortcutsSheet` pattern and for the same reason: a greeting must not disturb whatever panel is open, so it stays outside `uiStore`'s choreography. Two steps and no more. The first is the author's note on why the app exists; the second creates a **persona** and closes the dialog. **The first step carries no feature list**, deliberately: a capability nobody has used yet cannot be taught in a modal (memory means nothing before there is a chat to summarise from), and the app holds far more than any three items, so every shortlist reads as arbitrary. What is not built yet belongs on the roadmap, not on a greeting. **It is the one surface written in the first person**: everywhere else the app speaks in its own voice, and a second personal note anywhere would leave that voice inconsistent rather than warm. **SillyTavern is named once**, in the import note, because that note points at the door that reads a library the reader already has. It **sets up no connection and routes nowhere**: provider, key and model are the Connections page's whole subject, a second copy of that form here would be a second thing to keep in step with the provider list, and a greeting that ends by pushing the reader into Settings buries the one step that matters, the persona. Someone who never opens Connections meets that at the first send, which fails loud.

**It is a gate, and there is no Skip.** The persona step is the reason: the library's floor is one persona (architecture/library.md) and this dialog is the only door that writes it from nothing, so a skip would leave the app in the one state it has no other way out of: no protagonist, and the New chat flow's second step asking for one that does not exist. The gate is expressed as one derived `dismissible`, passed to `ui/Dialog`, **not** as a hidden Escape handler, because the same flag is what removes the dialog's close X, and a dialog that swallows Escape while still showing an X is a button on screen that does nothing. Two states open it again, both stated in the component: a persona already **exists** (so the gate has no subject left, which is what keeps the Settings row from trapping a reader who came back only to re-read), or the persona write **failed** (with the server gone nothing in the dialog can succeed, and holding someone inside a dialog that cannot finish helps nobody). The persona it writes is passed through `confirmNewEntry` before the dialog closes, or the Library's unsaved-new nav guard would trap the very next navigation on an entry the reader already finished. Failures land in `ui/Alert` inside the dialog, never the toast stack (the notification contract). **`maybeGreet` asks two questions, not one**: it opens the dialog while `generalSettings.welcomeSeen` is false **or** the library holds no persona, because "has been greeted" and "has a persona" are different facts and only the second one the app cannot work without. That covers the one way the first can outlive the second: the escape hatch below closes the dialog and sets the flag, so without the persona test a greeting cut short by a failed write would never be offered again. The flag itself **rides the settings spine rather than localStorage on purpose**: the blob is server-side, so setting the app up on a desktop and then opening it on a phone does not greet you a second time, which localStorage would (and would also greet a second browser on the same machine). **`boot()` raises it only once the shell has reached `ready`**: a dialog stacked on a boot state card greets someone whose app has not started. Settings → Developer reopens it (below), which is a page a reader reaches only on purpose: the greeting is written for someone who has never seen the app, so a second door to it does not belong among the pages everybody meets. Reopening never clears the flag: it is a re-read, not a reset. **Every opening starts at the first step**, which is why the step lives beside `open` in the module block rather than in the instance: a re-read that resumed wherever the last one finished would greet the reader with the persona form. A re-read also **ends** on that first step (`leaveHello` closes outright once a persona exists), because that form's only job is the first persona and with one in the library it would mint a duplicate of whatever name was last typed into it.

`ui/Dialog` carries a **`dismissible`** prop (default true) for that gate: false drops the close X and stops Escape and the backdrop from dismissing, all three together, since leaving any one of them would either hand back the exit the gate exists to remove or leave a control on screen that does nothing. Every dismissal route runs through one `requestClose`, so the flag cannot be honoured by one door and forgotten by another. Reach for it only where closing would leave the app in a state it cannot work in, or where an accidental dismissal would throw away work the reader cannot get back (the prompt review, below). A second prop, **`bare`**, hands the whole panel to the child: no padding and no scroller of its own, for a surface that needs a head and a foot standing still around a scrolling middle. The child then owns every edge, scrolling included. Sizes run `sm`/`md`/`lg`/`xl`, plus **`2xl`** for a dialog whose subject is machine text rather than prose, where a narrow measure is not a kindness but a second scrollbar. A third prop, **`fill`**, takes the full height a dialog is allowed rather than the height of the content, for a surface that is a place to work rather than something to read: one that resized itself per request would move its own controls under the pointer between one opening and the next. The room is declared once, as the scrim's own `--dialog-inset`, and both the cap and the filling height derive from it, since a panel that overshoots by a few pixels hands the backdrop a scrollbar over a surface that has nothing else in it.

**The prompt review** ([`PromptReviewDialog.svelte`](../src/lib/components/chat/PromptReviewDialog.svelte) + `PromptReviewCard`, mounted once in `Workspace` beside the shortcuts sheet, since the five gates that raise it live in different places and a request must not lose its review to whichever of them unmounts) is the surface a held request waits on (architecture/prompt-pipeline.md). A `bare`, non-dismissible dialog: head (what is held, the model, the size, the Pretty/JSON switch), a scrolling list of message cards, foot (Cancel and a confirm button wearing the words of the press it releases). Cards open **closed**, with role, position and size on every row, because a prompt is a dozen blocks of which one is usually the whole preset: the list has to answer "what is actually in here" before it is an editor. **Pretty edits what a message says** and can drop one; **JSON edits what the request is**, and parses into the same working copy on every keystroke, so the two views are never two documents and Send is deciding about one thing either way. A document that will not parse names its fault and holds Send. **The JSON view is one field, so it IS the middle rather than something inside it**: the body stops scrolling there and the textarea keeps the only scrollbar, since two of them over one document is the outer one claiming there is more below when there is nothing else there. Its size comes from a flex basis rather than a height, so the dialog opens as tall as it is allowed to be and the field takes what is left; it needs no drag handle, and a handle would have nothing to reach. A message card in the Pretty view keeps the one `autoResize` gives it, because there it is one of many and the body around it really does scroll. The JSON view also carries a **Wrap** switch, on by default: a single system block is one line thousands of characters long, and a horizontal scrollbar over that is not a way to read it. Wrap is remembered while the app is open and is deliberately neither reset per request nor stored as a setting: it is how the reader likes to look at JSON, not a preference the install carries. It is not dismissible on purpose: a backdrop click that threw away five minutes of editing would be the app's most expensive misclick, so Cancel is the only pointer exit, with Escape and ⌘/Ctrl+Enter as the two keys. Both come from this component's own listener, marked consumed and bound on the **capture** phase: the review can be raised over a composer strip that carries its own Escape, and on the bubble phase the older listener would win and close that strip underneath, leaving the request with nothing left to answer it. Token counts are measured once per pause rather than per keystroke, since a whole prompt is the one payload where BPE on every character would be felt. Its glyphs and its confirm wording come from `config/prompt-hold.ts`, where each gate is written down once.

**A control sitting tight inside a clipping box needs the ring on the box.** The app's focus ring is `outline` with a positive `outline-offset` (app.css), so it is drawn OUTSIDE the element it belongs to, and any ancestor clipping at that element's edge cuts it away. A joined pill is exactly that shape: its `overflow: hidden` rounds the group's corners, so a ring on one half survives only as the sliver falling in the seam between the halves, a bare vertical bar saying nothing about which button has the keyboard. The pair that fixes it is the same everywhere and all three of its instances are written alike (the title bar's Settings and Library split pills, the steering note's version pill, the debug panel's segmented control): the group takes the ring through `:has(:focus-visible)`, the segment drops its own `outline` and says it has the keyboard with a wash of the same accent, and the pair sits LAST in its block so the wash beats the open/pinned/selected tints above it. It touches `background` alone, so a state carried in the segment's colour survives having focus. This only became visible once the keyboard could travel anywhere; any new clipping group owes itself the same pair.

**Focus**: hand-rolled overlays that can't be built on `ui/Dialog` (BranchCompareModal, ImageLightbox, PortraitViewer) get Dialog's focus behaviour (initial focus, Tab trap, restore on close) via the [`focusTrap`](../src/lib/actions/focusTrap.ts) action (`{ trap: false }` for non-modal floats like PortraitViewer). **A body-portaled overlay owns its own open/closed condition, and the `$effect` that moves its node must read that state** (`Dialog`'s `open`, `ImageLightbox`'s derived `open`, `BranchCompareModal`'s `leaves`). Never `{#if}` the component from the caller and bind the portal to its lifetime alone. That effect then runs once: after its cleanup detaches the node from `<body>`, nothing re-attaches it, and the overlay reads as open to the caller while rendering nothing at all, permanently. Fast repeat clicks reach that state easily, because a closing transition keeps the old instance alive while the next one mounts. The cleanup keeps its own node reference rather than reading the `bind:this` state, which is nulled on unmount and would skip the removal. An always-mounted overlay also means its `svelte:window` key handler must return early while closed, and any expensive `$derived` behind it must be gated on the same open state.

**One bottom-left corner, two pictures, two components.** [`SpriteLayer.svelte`](../src/lib/components/chat/SpriteLayer.svelte) draws the chat character's sprite ([`sprites.svelte.ts`](../src/lib/stores/sprites.svelte.ts)); [`PortraitViewer.svelte`](../src/lib/components/chat/PortraitViewer.svelte) draws, over it, the portrait a reader opened by clicking a message avatar (`portraitViewerStore`). They share that corner and nothing else, which is what makes them two files rather than one card with two branches. The portrait IS a card (surface, border, shadow, rounded clip, name plate, close button, `focusTrap`, Escape). **A sprite is a cut-out** drawn on a transparent background, so every one of those is a frame the artwork was made without, and a contained picture inside a fixed card letterboxes its own leftover against a visible surface besides. The sprite layer is therefore a bare `<img>` flush with the screen's bottom edge (`bottom: 0`, `object-position: bottom center`), so the figure reads as standing in the room rather than as a picture of one. It is `pointer-events: none` throughout, since it is the chat's own state rather than something the reader opened: nothing on it is clickable but the status dot, which takes its own events back, and everything under it (on a narrow window, the composer) has to stay usable. The overlap is settled by z-order alone: sprite 14, portrait card 15, docked panels 25. **Every avatar opens the portrait card**, the character's own included, because the sprite is ambient and a click is not; closing it hands the corner back.

**Both stand in the bay, and it is two custom properties rather than a number per component.** [app.css](../src/app.css) derives `--picture-bay` (the empty margin beside the chat column: `(100vw - --chat-col-max) / 2`, floored at 18rem for a window with no margin to spare, held under 70vw so that floor cannot swallow a phone) and `--picture-height` (a share of the window, not a pixel size). Deriving the bay from the column rather than tuning it is what makes it follow the chat-width knob and every screen size for free. **Height leads and width follows**: a picture is drawn as large as fits inside bay × `--picture-height` with its own proportions kept, so what decides its presence is the window rather than the file's resolution or shape, and one character is the same size on a laptop and on a 4K screen. The sprite gets that from `object-fit: contain` in a box of exactly that size; its leftover space is transparent and invisible, and centring the picture in the bay is what puts the empty margin evenly on both sides of the figure instead of all of it between the figure and the story. **The card cannot do the same, because it has a surface**: a fixed box letterboxes every picture that is not the shape it expected. So it reads the ratio off the loaded `<img>` (`naturalWidth / naturalHeight`, stamped with the url it was measured from so a ratio cannot outlive its portrait) and takes `width: min(bay, --picture-height × ratio)` with `height: auto`, which is the same arithmetic with the box hugging its result. A picture that has not reported its ratio yet is drawn at 3:4 for that one frame, so the card is never unsized. The bay element itself passes pointer events through: it spans a margin the chat forwards wheel events from, and only the card inside it is clickable.

**The sprite follows the newest reply, and the reading is stored on the turn.** The store answers one question (which sprite the open chat shows) off the newest **assistant** turn on the active path (a user turn waiting for its reply leaves the sprite where it was). Because `messages.sprite_label` holds the reading (architecture/server-core.md), swiping between siblings and walking branches shows each turn's own sprite with **no new call**, and a reload keeps what was already read. `active` (engine on **and** the chat's character has sprites) is what puts the layer on screen, **and a phone never puts it there at all** (`viewport.isMobile`, the gate sitting on the mount in `ChatContainer`): the chat column is the whole screen there, so a standing figure has nowhere to stand that is not on top of the story. That gate lives at the mount rather than inside `active`, because `active` also guards `invalidateMessage`, and a reading that a phone declined to clear would be a stale face on every other device. **What it draws is the newest turn that has been read**, walking back up the branch, not the newest turn full stop. A reply is born unread and its reading lands a second or two later, so keying the face on the newest turn alone would drop the character to their default on every single reply and then swap it, a blink that says nothing happened; instead the face holds what it last knew and changes once, when there is something new to say. A reading whose sprite has since been deleted keeps the walk going for the same reason. The character's `defaultSprite` is the floor under all of that, reached only in a chat where nothing has been read at all, which is why the library guarantees one exists (architecture/library.md). **The layer is what asks** (`ensureRead`, from one `$effect`), so a chat nobody is looking at never spends anything, and a phone spends nothing on sprites at all; in-flight and already-failed message ids are held in memory so a failure retries on the reader's word or the next app start, never on the next render, and a failure toasts rather than sliding quietly onto the default. **The dot in the picture's corner is the engine speaking for itself** (`spriteStore.status`: `read`, `reading`, `failed`, `idle`, with the failed one a button on `spriteStore.retry`). Without it a dead engine looks exactly like a calm one, since the face simply holds the last thing it read, and the guard means it would stay that way until the app restarted. `retry` drops the guard for that one turn and goes through `ensureRead`'s ordinary door, so every other reason not to call still holds. The two collections behind that (`inFlight`, `failed`) are `SvelteSet`/`SvelteMap` for this reason alone: the dot reads them. Everything about the call itself (prompt shape, the JSON answer contract, why the engine ships off) is architecture/engines.md.

**One image viewer, and the caller names the set.** [`ImageLightbox`](../src/lib/components/ui/ImageLightbox.svelte) is the app's only full-size picture viewer (`PortraitViewer` is a different animal: a non-modal float showing one face). It takes `images` plus a bindable `index` and pages that set with arrow keys, on-screen prev/next and a horizontal swipe, and it **never decides what the set is**. Each surface hands it the one set it can name: the assistant panel's tab-wide picture roster (architecture/chungus-assistant.md), a chat message's own attachments (a chat is a tree, so anything wider would have to pick a branch to mean anything), a library entry's gallery, one logged request's images. A new surface answers "which set", not "does it page". Three rules keep it honest. The portal `$effect` reads the **derived** `open`, never `index`, or every step detaches and re-appends the node, replaying the open transition and dropping focus. An index the set no longer holds reads as closed rather than clamping to a neighbour, since a viewer that silently shows a different picture than the one asked for is worse than one that shuts. And the swipe is touch/pen only, ignores a second finger so pinch zoom survives, and is never the only way through: a horizontal drag near a phone's edge is the system's own back gesture, so the prev/next buttons stay on screen whenever the set has more than one picture.

**The destructive-act ladder.** Every delete in the app is gated BEFORE the act and is final after it: there is no undo channel anywhere, and the rung is picked by what the click destroys, never by which screen it happens to live on. **Nothing** for what is not saved work or has its own recovery: toggles, reorders, chips (tags, keyword chips, the IP allowlist's rows, **except the row for the device the reader is on**, which is asked about while the allowlist is the gate, because what that one costs is not saved work but the way back in: it shuts ChungusHub on this device and reopening takes another approved one, or the machine it runs on, which a headless host does not have. Off, it costs nothing and is not asked about, since the switch that would make it bite asks its own question then; see architecture/server-core.md), staged-but-unsaved uploads, steering notes (one line of guidance, stated at the delete button itself), and every edit inside Prompt Builder, whose Discard restores the committed preset. **An armed press** for one saved thing deleted from inside its own editing surface: the first press turns the same button red with "Press again to delete", the second press deletes, and arming a different row moves the arm instead of stacking a second one. `CharacterVersionMenu` (which refuses outright while any chat pins the version) and the alternate-greetings modal are the two instances. **Asked once, with the real numbers**, for anything whose full content is not in front of the reader: every entity delete (character, persona, lorebook, lorebook entry, preset, connection, background, skill, regex rule, chat, assistant session), every bulk delete, restore-defaults over a populated list, and the memory wipe all go through `ui/ConfirmDialog` (portals to body, so it nests fine inside another Dialog; never native `confirm()`), whose message names the thing in quotes and states what goes in real counts. **The heavy rung is a gesture, not a second dialog**: a dialog passes `holdMs={holdMsForBlast(n)}` with the same count its message states, and once the loss reaches `HOLD_THRESHOLD` the confirm button becomes the identical press-and-hold the transcript's subtree delete uses (`ui/HoldToConfirmButton`), so a big loss can never be fired by muscle memory while a small one stays one click. That button carries a `shape`, and a call site picking the wrong one is a visible fault rather than a nuance: `block` (the default) is a row in a stacked menu and takes its column's full width, which in a dialog's right-aligned footer means eating the row and squeezing Cancel down to its own text, at a different height and type size besides. A footer passes `inline`, whose metrics are `ui/Button` size md to the pixel so the two actions read as a pair; the footer grid then settles their width, giving both the width of the wider one, so a long confirm label can neither squeeze Cancel down to four letters nor wrap itself onto a second line. **SecurityPage's three dialogs are the app's only `ConfirmDialog`s that gate a lockout rather than a loss, and none is marked `destructive`**: that flag is what puts a dialog on this ladder and lets the reader's rung skip it, and a skipped question here locks somebody out of their own app. Its hold length is deliberately short (0.63s at the threshold to 1.4s at 100+) because the gesture only has to outlast a reflex, and a cleanup pass of many small deletes must not feel parked. The transcript's message delete is the in-place build of the same two top rungs: menu confirm stating message count and memory impact, hold scaled by the total weight (architecture/chat-sessions.md coupling 3). A post-hoc undo must not come back in any form: a deferred delete dies with the page (the row resurrects on the next boot), lies to every other device for its whole grace window, and hands a real decision to a 5 second timer. The no-undo scan in [`contracts.test.ts`](../src/lib/contracts.test.ts) holds the line.

**Which rung is in force is the reader's to lower, and [`delete-guard.svelte.ts`](../src/lib/stores/delete-guard.svelte.ts) is the only thing that knows.** `hold` (the default) is the ladder above; `ask` drops every hold to a plain click; `off` removes the asking entirely, so a delete fires on the press that reached it. It is **one setting with three rungs, deliberately not two switches**: with asking off there is no dialog left for a hold to stand on, so a pair of booleans would spell one of its four states as nothing at all. Two doors read it and no call site knows it exists: `holdMsForBlast` returns 0 whenever the heavy rung is not in force, which covers every hold in the app at once, and `ConfirmDialog` answers itself the instant it is raised when nothing is being asked. The surfaces that build their own asking read `deleteGuard.asks` by hand: the transcript's delete and replace confirms, and the two armed presses (`CharacterVersionMenu`, `AlternateGreetingsModal`), where the arm IS the asking. **`ConfirmDialog`'s `destructive` is opt-in and must stay that way**: the same component carries cost confirmations (Memory's enable/summarise/rebuild, whose message quotes model calls), assistant approvals and Prompt Builder's discard-draft prompt, none of which are on this ladder, and a default would make the next one of those skippable without anyone deciding it should be.

**A lowered rung is temporary unless the reader insists otherwise.** Picking `ask` or `off` opens a **window**: runtime state in that store, written nowhere, so it dies with the page and never reaches another device; a guard lowered for a cleanup pass must not outlive the pass, still less on hardware the reader isn't holding. Permanence is the second click ("Until I turn it back on"), which is an ordinary settings write. An outage closes any window (every write fails while the server is gone, so the minutes would burn down in an app that cannot delete anything) and deliberately leaves a kept rung alone. The window's clock is part of the decision and not only part of the cleanup, because background tabs throttle timers to minutes and a foregrounded tab would otherwise spend its first second still unlocked. While anything is lowered, [`layout/DeleteGuardBar`](../src/lib/components/layout/DeleteGuardBar.svelte) says so on the standing channel below; `ConfirmDialog` also offers the short window inline, as a checkbox that arms it and opens it only **behind** the act being confirmed, so the dialog can never lose the gate the reader is currently standing on and a delete backed out of leaves nothing lowered.

**The settings spine**: every user preference is a JSON blob in the server `settings` table via `syncedSetting.ts` (see architecture/client-data-layer.md): the live look (`appearance`), the reader's palettes (`customPalettes`), ambient (`ambientConfig`) and background (`backgroundConfig`), each the app-wide copy a chat's own scene stands in front of, general (`generalSettings`: drafts/input-history + its scope and cap/auto-expand-reasoning/settings-split-view/story-map-wheel, plus the two one-time notices' read marks, the first-run greeting's `welcomeSeen` and the assistant cost notice's `assistantCostSeen`; both ride the spine for the same reason, that a thing said once on the desktop must not be said again on the phone, and the second is written by its own Got it and by nothing else, since an appearance is not a reading), advanced (`advancedSettings`: the prompt-debug-panel toggle, the kept delete-confirmation rung, and `developerMode`, which no control writes and only the About row's tap streak flips, see below; a temporary drop of that rung is deliberately NOT here, see the ladder above), the prompt hold's armed gates (`promptHold`, one boolean per gate in `config/prompt-hold.ts`, all of them off until asked for; see architecture/prompt-pipeline.md), regex rules (`regexRules`; see architecture/prompt-pipeline.md for where they apply), browse prefs, lorebook globals, preset-control values, active persona/preset keys, named connections + the flat routing map (`connections` / `connectionAssignments`; see architecture/llm-providers.md). Each store follows the same pattern: `normalize()` coerces the raw blob (clamped numbers, whitelisted enums; a corrupt blob degrades to defaults, deliberately unlike the server's fail-loud state files), `initialize()` reads + registers a `registerSettingsReload` hook, mutations persist via `writeSetting`. **A knob that is dragged writes through [`BurstSettingWriter`](../src/lib/services/syncedSetting.ts), not straight through.** A write is an HTTP round trip AND a broadcast that every other device answers by re-reading every synced setting it holds, so a slider firing an input event per pointer move is a request per frame here and a full settings reload per frame on the phone in the next room. The writer coalesces a burst into one write 250ms after the last of it, and the store's own state is what the screen reads, so nothing waits on it. Its `busy` flag is the other half: a `syncReload` landing mid-drag would hand back a value older than the one under the reader's finger, so a store with a write still owed skips that reload. Ambient and background use it because every knob on both cards is a slider or a switch; a setting whose every value is worth keeping still writes through.

**The only localStorage exceptions**: the sidebar collapse state ([`sidebar.svelte.ts`](../src/lib/stores/sidebar.svelte.ts)) and the assistant widget's rect/launcher position, genuinely per-device viewport geometry. The `clientId` is deliberately not one of them: localStorage is shared by every tab, and it has to be per-page (architecture/client-data-layer.md). **The first-paint cache is not an exception either, because it is not a preference**: `applyTheme()` mirrors its resolved output (every `--theme-*`/`--user-*`/`--msg-*` var plus every attribute it stamps) into `chungushub:paint`, and an inline script in [`app.html`](../src/app.html) reads it back onto `<html>` before the body paints. The look rides the server spine, which nothing can read until `db.initialize()` and `themeStore.initialize()` have both returned, so without it every single load paints app.css's shipped Graphite until the blob lands: a dark flash for anyone reading on a light palette and a wrong-coloured one for anyone on a palette they built. It is a cache of what THIS device last painted and never a source of truth, so a device that has never run the app has nothing there and correctly falls through to the CSS defaults. **The shape is hand-kept between the writer and that script** (`writePaintCache` in `theme.svelte.ts`): a new var or attribute rides along for free, a change to the wrapper object's shape does not. The script deliberately carries no `try`/`catch`, so a corrupt cache throws where the console can say so and the page carries on with the same defaults.

**The Appearance area is two pages and one spine.** [`settings-pages.ts`](../src/lib/config/settings-pages.ts) orders them **Interface → Chat**, and two rules decide what goes where. **A knob sits with the thing it dresses**: the story's own face and measure (story font, text size, line height, paragraph gap, column width) are on Chat, while the frame's font and the app-wide `Corners` are on Interface, since that one rounds every surface there is and the message card's own radius is a multiplier riding on top of it. That is also what settles the two workspace scrims (below): the reading column's shade sits with the column, the background image's dim sits with the image. **A page exists to hold a subject, not to hold a card**: Interface is seven cards (Palette, Accent, Interface Type, Surfaces, Scene, Background, Ambient Effects) rather than pages of two, because a two-control page is a stop on a walk nobody wanted to take, and the cards there are one subject, everything the app draws that is not the story. A page's whole content is one component ([`InterfacePage`](../src/lib/components/settings/InterfacePage.svelte), [`ChatPage`](../src/lib/components/settings/ChatPage.svelte)), each with its own arm in `SettingsPageView`; there is no router component between them.

**Theming** ([`theme.svelte.ts`](../src/lib/stores/theme.svelte.ts) + [`themes/presets.ts`](../src/lib/themes/presets.ts)): palette × accent × knobs (contrast, fonts, scale, radius, chat style, glass, motion, column shade) resolve into `--theme-*` custom properties stamped on `<html>` by `applyTheme()`; `presets.ts` is the single source of shipped palette/accent/font data (app.css keeps only a first-paint fallback), legacy `activeTheme` ids map at read time via `LEGACY_THEME_MAP`.

**A palette is data, not code, and the store owns two things rather than one.** The **look** is the live `appearance` blob, what the app is wearing and the only key a settings control ever writes, so dragging a slider costs one small write per frame. The **palettes** (`customPalettes`) are the ones the reader built, concatenated onto the shipped ones wherever a palette is offered, written when a palette is edited and at no other time. `normalize()` takes the palettes that exist as an argument and the load order in `syncReload` is load-bearing: palettes, then look, or a look built on the reader's own palette fails its own id check every boot and is dragged back to the house default.

**Restore defaults is the only way back to the shipped look, and each Appearance page carries its own.** [`APPEARANCE_SCOPE`](../src/lib/themes/presets.ts) is the table that says which page owns each `AppearanceState` key: it is spelled out key by key rather than derived from a short list of exceptions, so a knob added to the type fails to compile until it says which page tunes it. `restoreDefaults(scope)` writes back exactly the keys that page owns, which is what leaves the other page's look alone, and `isModified(scope)` is what puts the link on screen at all: a page already at the shipped default carries no Restore defaults, rather than a control that would do nothing. That comparison is a plain JSON one and exact for one reason, that both sides come out of `pickScope()`, which walks the table in one fixed order, so two equal looks always serialise to the same string. **It reaches the appearance blob and nothing else**: the background image and the ambient mix are their own stores with their own controls on the same page, so the confirm names what goes and says what it leaves alone. It sits at the foot of the page, past everything it undoes, and it is a `data-setting` anchor like any other control, conditional the way `palette-editor` is.

**The palette editor edits sixteen colors and the app derives the rest.** `applyTheme()` mints roughly seventy-five custom properties out of a palette (the glass tiers, `--theme-border-raised`, the on-accent and on-error inks, the shadows, both scrims), so the derived half can never be dragged out of step with the picked half and the editor stays a short list rather than a spreadsheet. `PALETTE_COLOR_KEYS` (`presets.ts`) is that list. **`overlay` is deliberately not on it**: it is the modal backdrop's scrim, it answers to the mode alone (`OVERLAY_BY_MODE`), and it is the one palette value carrying its own alpha, which a hex picker could not express anyway. **Mode is not a label**, which is why the editor states it: it picks the branch in `glassAlpha()`, the direction every shadow and the story's halo are mixed, the modal scrim, and the phone's status-bar glyphs. The editor [measures itself](../src/lib/utils/contrast.ts) against the pairs the app genuinely puts ink on and **reports rather than refuses**, since a palette is the reader's to build and a number they can see beats a control that argues with them. It appends BELOW the palette grid and never above it, the same rule the ambient mixer follows, so opening it cannot slide the card just tapped out from under the pointer. **`DEFAULT_APPEARANCE`'s pair sits at the head of both lists**, since `activePalette`/`accentColor` resolve an unknown stored id to `palettes[0]`/`accents[0]`: a default anywhere else means a corrupt blob lands on a combination the app does not ship as its own, and the Interface page opens on a first card that is not the one Default returns to. `customAccent`'s default is that accent's own hex, so the "+" swatch (which flips `accent` to `custom` the moment it opens) starts from the color already on screen. **The default palette's `bgPrimary` is copied by hand into three surfaces painted before the store boots**, where a drift shows as a flash of the wrong color: app.css's `:root` block (which mirrors every resolved default var, not just that one), `app.html`'s `theme-color` and `data-theme` id, and `static/manifest.webmanifest`'s `theme_color`/`background_color`, the installed app's splash and task-switcher tint. **The docs site mirrors that same default from outside the app**: `docs/docs.json` carries the Indigo accent's two hexes (`light` is dark mode's, `dark` is light mode's), and `appearance.default` of dark, so a reader arriving from the documentation meets the interface it describes. Nothing enforces it, so a change to `DEFAULT_APPEARANCE`'s palette mode or accent lands there in the same pass. **Typography is deliberately not part of that mirror** and stays on Mintlify's own stack: the app's pair is tuned for a story column, and a reference page of tables, UI labels and inline code reads worse in a serif. Fonts are bundled under `static/fonts/` and lazy-loaded per family ([`fonts.ts`](../src/lib/services/fonts.ts)). Components style exclusively against `--theme-*` vars. Hardcoding a color breaks palette switching. `applyTheme()` also rewrites **two meta tags** in `app.html`, because the phone's own chrome is part of the palette: `theme-color` takes the palette's `bgPrimary`, and `apple-mobile-web-app-status-bar-style` swings on the palette's mode. That second one is not redundant: iOS standalone pins its status-bar glyphs from its own tag and ignores `theme-color` entirely, and `black-translucent` means white glyphs over a transparent bar, which a light palette turns into white on parchment. `default` gives dark glyphs on a light bar instead. The values in `app.html` are only the first paint and match the dark default there.

`applyTheme()` also mints the **message-card layer** the chat components read (`--msg-*`, `--prose-*`, `--avatar-*`, `--user-bubble-width`), so every knob on the Chat page is one `AppearanceState` field → one var → one CSS declaration, and no chat component ever reads the store for geometry. Three of those resolve rather than pass through, and the reasons are load-bearing: **bubble tints MIX into** the palette's own `userBubble`/`assistantBubble` (`color-mix(in oklab, tint N%, base)`) instead of replacing them, so switching palettes carries the tint and the palette's contrast floor survives any hex, whereas **prose accents** (`--prose-quote-color`/`-em-color`/`-strong-color`) use a custom hex **verbatim**, since mixing text color would make the picker lie about what you get. **All three answer one `ProseColorSource`, `off | default | accent | custom`, and the uniformity is the rule**: a row offering fewer answers than the row above it is a card the reader has to re-read on every line, and how much of a page repaints when the accent moves is then their own pick on a sample they can see rather than a ceiling nothing on screen admits to. Quote's `default` still mixes the fixed house hue toward the palette's `textPrimary`, through `proseQuoteDefault()` (`presets.ts`), a function and not a constant because the Story Text swatch shows that same colour under the word "Default", and two copies of the expression would drift into a picker that lies; emphasis and strong fall back to the palette's secondary and primary text, which the card names as live theme vars rather than resolving itself. **`off` resolves to `currentColor` and must never be the `inherit` keyword**. A custom property whose entire value is a CSS-wide keyword IS that keyword for the property itself, so `--prose-quote-color: inherit` on `<html>` inherits from nothing, leaves the property invalid, and every `var(…, fallback)` reader silently takes its fallback, which is the shipped tint: the control turns the accent's own default back on instead of standing down. Nothing may hand a CSS-wide keyword to `setProperty` for the same reason. The rest of each accent is its **face**, and it is **two booleans (`…Bold`/`…Italic`), never one four-value enum**: bold and slant are independent questions, so a cross-product enum would be exactly the fourth value the speaker label/casing split already refused, and it would put a pill on screen whose only job is to name "neither". They are attributes rather than weight/style vars precisely because a var has to spell that neutral answer out: `font-style: normal` on strong text cancels the emphasis it sits inside, and `***word***` is one run wearing both accents. `--prose-shadow` is the card's one whole-story knob, a legibility halo for prose read straight off the workspace (a card faded to nothing, or Manuscript); like the two scrims below it answers to one number and never to a colour, since it is always the counterpart of the palette's own ink. `.prose blockquote`'s left rule is a separate, settings-less piece of chrome and still reads the accent; `bubbleOpacity` is a **multiplier over** `BUBBLE_ALPHA[glass]`, not a replacement, so Glass keeps working underneath it, and it multiplies **every alpha on the card, not just the fill**: `--msg-border-color` and `--msg-shadow` are scaled by it too (`cardAlpha`), so a drag reads as one surface dissolving instead of a fill sliding out from under a full-strength frame, and all three reach transparent together at zero with no branch needed to switch the card off. Widths never move: `--msg-border-width` is the stored outline choice through the whole range, since fading a color leaves geometry alone and a slider crossing zero must not reflow the card mid-drag. The stored outline/shadow choices are never written either, so both return intact as opacity lifts, which is why those two controls stay on screen at zero instead of being hidden; and the tighter corner on the speaker's side (`--msg-radius-notch`) is capped at `--msg-radius`, or sharp Corners × a wide card radius inverts it into the roundest corner on the card. Quote highlighting turns "off" by resolving `--prose-quote-color` to `currentColor`: `markdown.ts` still emits the span, it just stops being tinted, so nothing in the render path changes. **Five knobs are attributes rather than vars, for two different reasons.** `data-speaker-label` (pill/plain) and `data-speaker-caps` (on/off) each swing half a dozen properties, so one selector per state beats a dozen vars. The six story faces (`data-quote-bold`/`-italic` and the same pair for `em` and `strong`) swing one property each, and are attributes because an attribute can declare **nothing**: the `.prose strong`/`em`/`.quoted-text` base rules in app.css ARE the shipped faces and each attribute states only its departure, which is what leaves a nested accent inheriting the one it sits in. Strong's UI-font swap is part of that departure: it exists to give bold its punch on a serif page, so `normal`/`italic` hand the family back rather than leaving a sans run mid-sentence. Those two are deliberately **separate attributes, not one enum**: chrome and casing combine (a pill in small caps is a real choice), and folding casing in as a third `speakerLabel` value would make that combination unreachable. Any settings enum that turns out to be two independent questions should be split the same way rather than grown a fourth value.

**Glass & surface tiers**: the Glass setting (off/subtle/full) drives every surface token, not just the panel shells. `applyTheme()` resolves per-level alphas (the `*_ALPHA` maps) into: `--theme-panel-bg` (Workspace docks/overlays, the only surfaces that pair it with `--theme-backdrop-blur`), the in-flow tiers `--theme-bg-secondary/tertiary/elevated`, `--theme-card-bg`, `--theme-input-bg` (translucent under glass, opaque at off, **never** given their own backdrop-filter; the hosting panel already frosts, and nested backdrop-filters don't re-blur), the chat bubble tokens (high alpha for prose readability), and `--theme-float-bg` for out-of-flow floating surfaces (menus/popovers/tooltips/toasts/dialogs/modals), consumed via the `.surface-float` utility in app.css (bg + `--backdrop-blur` + `--glass-border`). **Every one of those alphas is authored for a dark palette and passes through `glassAlpha()` before it is used, because glass composites the two modes asymmetrically**: a translucent surface moves toward whatever is behind it, so over the workspace photo a dark surface only ever *gains* contrast against light text while a light surface *loses* it against dark text. Measured on the shipped stack (photo under the 35% dim, panel at glass=full) a dark palette holds ~9.7:1 primary and ~5.1:1 secondary on its worst backdrop while an unscaled light one collapses to 4.8:1 and 2.0:1. That is illegible, and structurally so rather than as a palette bug. `LIGHT_GLASS_KEEP` (0.42) therefore keeps a light palette's glass *hierarchy* at a fraction of the transparency; it is one factor rather than a second set of maps so the tuned order (panel < card < tier < float < bubble) cannot drift out of step, and an alpha already at 100 stays there. A new surface alpha must go through `glassAlpha()` or it silently reintroduces the collapse for light palettes only. **A separator drawn on a raised translucent tier uses `--theme-border-raised`, never `--color-border-subtle`**: the subtle token is calibrated against the base surface and has nothing left over once the surface itself has moved toward it, measuring ~1.2:1 on every palette (i.e. absent) on the composer's interior, in dark and light alike. That covers control outlines as much as rules: the composer's rule, the pips between its feature buttons, and the buttons' own borders are all on that tier and all read from the same token. The raised token nudges `borderSubtle` toward the palette's `textPrimary`, which corrects both modes with the same expression because the ink is near-white on a dark palette and near-black on a light one. Its two percentages (80% dark / 65% light) are deliberately **not** one number: the contrast ratio moves less per unit of mix on a near-white surface, so a single figure that reads right on the dark palettes leaves the light one visibly fainter. Split, every shipped palette lands at ~2.3:1. It lives in `applyTheme()` rather than a component custom property precisely because it is mode-dependent, which is not a decision a component should be hand-rolling off `data-mode`. Floating surfaces must use the float recipe, never a plain translucent token (content beneath would bleed through); on-image chrome (chips/scrims over photos) is exempt and stays hardcoded black/white, and MockupTip popovers deliberately use the fully opaque `--theme-bg-solid` instead of the float recipe: animated demos are unreadable over glass.

**Ambient & background**: the mix's whole model is the import-free [`types/ambient.ts`](../src/lib/types/ambient.ts) (the effect list, the four knobs every effect carries in `AMBIENT_BASE_SETTINGS`, the ones it has of its own in `AMBIENT_EFFECT_SETTINGS`, the resolvers over both, and `normalizeAmbientConfig`), the steering model's rule and for the same reason: a mix is stored in two places, so the store that reads the app's copy and the chat feature-state normalizer that reads a chat's own have to agree exactly on what a corrupt value degrades to. [`types/background.ts`](../src/lib/types/background.ts) is its twin for the picture. [`ambient.svelte.ts`](../src/lib/stores/ambient.svelte.ts) is then only state and persistence: the app-wide mix, `config` (whichever mix is IN FORCE), and one private `write` that routes to the settings spine or to the open chat's scene. Rendering lives in `components/ambient/` (`AmbientCanvas` + one module per effect under `effects/`, barrel-exported from `effects/index.ts` and wired into the canvas's `EFFECTS` map). **A renderer bakes everything it can and leaves the context as it found it**, because the canvas runs the whole active stack back to back on one context every frame: textures, gradients, glow sprites and noise tiles are built in `create…State` (a `CanvasPattern`, which needs the live context, is built on first render and cached on the state) and blitted thereafter, `ctx.filter` never runs inside a render loop since it forces a software raster path that costs every effect in the stack its frame rate, and anything that sets a stroke style, a transform or a composite op wraps it in `save`/`restore` or the next effect in the order silently paints with it. `dither.ts` (cached full-screen gradients, radial sprites) and `particles.ts` (cached rgba strings) exist for the first half of that rule. The whole Settings surface is **one card**: `InterfacePage` owns the shell (`data-setting="ambient-effects"`, the head's InfoTip and its Clear all) and [`AmbientMixer.svelte`](../src/lib/components/ambient/AmbientMixer.svelte) is the body, three zones in a fixed order: the **stage** (a live preview of the mix over the real workspace background and its dim, mock bubbles included, since which side of the story an effect paints on is one of the things being decided here; a dashed invite while empty, at the same footprint, so the first pick never moves the box), the **catalog** (toggle pills on labelled shelves, `aria-pressed`, deliberately not `ui/PillRow`, whose radio semantics say only one can be on; shelf membership is `EFFECT_SHELF`, an exhaustive `Record<AmbientEffect, …>` precisely so an effect shipped without a shelf is a compile error rather than a pill that silently never appears, and order within a shelf follows `AMBIENT_EFFECTS`), and the **mix** (one row per active effect, folding open on that effect's whole settings list and open already on the tap that added it, since a knob nobody has seen is a knob nobody knows is there; folding it away again is the reader's). **Everything the selection adds appends BELOW the catalog, and nothing above the catalog may change height with the selection**: a zone inserted above it would slide the tapped pill out from under the pointer mid-gesture. The stage's dim mirror is plain black, per the scrim rule below. [`background.svelte.ts`](../src/lib/stores/background.svelte.ts) picks the workspace background image (bundled default or upload, `/files/`-served) + dim/blur, and routes its writes exactly like the mix; both layer under the chat in `Workspace.svelte`.

**Every knob belongs to one effect, and there is no cluster over the top of them.** Density, speed, visibility and which side of the story an effect paints on are `AMBIENT_BASE_SETTINGS`, four defs every effect carries ahead of its own. One set of sliders across the stack could only ever move all of it together, and a stack of five is regularly four calm effects and one heavy. They share `AmbientSettingDef` with an effect's own knobs deliberately: the mixer draws **one uniform list** per row and the canvas reads the first three out of the same bag it hands the renderer, so nothing has to special-case which kind a row is showing. Two rules hold it. A per-effect def may never reuse a base key, or the row would draw two sliders of the same name and the second would win; [`contracts.test.ts`](../src/lib/contracts.test.ts) refuses it. And a key missing from `effectSettings` IS its shipped default (`effectSetting`), so a mix nobody has tuned stores nothing at all and the slider's own double-click is the way back. **Baking a state is expensive, so `AmbientCanvas` does as little of it as it can and never more than one at a time.** `create…State` is not an allocation: the textured effects bake full-screen offscreen canvases in it (fog draws three, over a hundred gradient blobs each), and particle counts are baked in at creation too, so anything that changes a density has to bake that effect again. Three rules follow. It **remembers the density each live state was baked at**, so one row's slider never re-bakes the rest of the stack. A density still MOVING waits 150ms for the drag to settle, or a slider dragged at pointer rate bakes those canvases tens of times a second and takes the frame rate with it; speed and visibility are read fresh every frame, so those two drags need none of this and stay live. And **the frame decides what is owed while the browser's idle time is where it gets paid** (`requestIdleCallback`, one bake per callback, with a timeout so it cannot be starved): spacing bakes evenly would only distribute the cost, since a bake landing in ANY frame that had work to do costs that frame, while nothing is waiting on weather. A chat opening owns the main thread outright, so a whole scene simply arrives once the story is on screen rather than competing with it. Leaving the mix, which costs nothing, still happens the moment it is noticed. The two checks that gate all of it run every frame on every canvas and allocate nothing.

**A picture reaches the screen only once it is decoded, and then it fades in over the one it replaces** (`Workspace.svelte`). Handing a fresh url straight to CSS decodes a multi-megabyte photo on the main thread at the moment a chat is opening, which is a freeze on top of the work of opening it, and then a hard cut. The outgoing picture stays whole underneath rather than fading out with it, or the crossfade would dip to the bare surface halfway through; the incoming one is promoted on a timer rather than on `transitionend`, which never fires at all under reduced motion; and a swap started while another is in flight cancels it by token, so opening three chats quickly lands on the third. Both layers carry `will-change: opacity` for the length of the fade and neither carries it outside one, so a full-screen photograph is rasterized once rather than on every frame of the fade without leaving a standing hint on a layer nobody is animating. Both wear the live blur, since a blur being dragged has no url change to wait for.

**A stored blob may still carry those four at its top level, where they scaled the whole stack, and `legacyBaseSettings` carries them onto every effect that is playing** (unit-tested and idempotent), so an install reading one looks exactly as it did. An effect that was only parked keeps its own tuning and takes the defaults for the rest: the number that was on screen was never its. A knob the old blob never held is left out entirely rather than seeded with a guess.

**Over or under the story is per effect, so the workspace draws the stack in two canvases** rather than one, and `Workspace` mounts each side only when `effectsPlaced` says it has something to draw: with every effect on the same side, which is the shipped state because an effect ships BEHIND the story (drawing weather over the words is a thing to ask for, never a thing to meet), there is exactly one canvas and one animation loop. Mixed, the cost is a second full-screen layer, and it is the reader's own choice to pay it. Order within a side is the mix's; between the sides it is the z-index, which is what the choice means. The stage previews the same way, one canvas either side of its mock bubbles.

**A chat can wear a scene of its own, and it is a whole scene rather than a patch.** [`chatScene.svelte.ts`](../src/lib/stores/chatScene.svelte.ts) owns that: `chats.feature_state` holds `{ enabled, background, ambient }` (architecture/chat-sessions.md), `active` is that scene while `enabled`, and both settings stores read it ahead of their own copy. **It is keyed on the chat ON SCREEN, never on `activeChatId`**: the id is claimed the moment a row is clicked and the rows land a fifth of a second later, so a scene keyed on it changes the sky at the click and leaves the story that was there sitting under a stranger's weather until its replacement arrives, which reads as a stutter and is really a half-finished transition. Keyed on the loaded chat, the scene and the story arrive together, and the landing screen (which clears the loaded chat outright) is still instant. What DOES start at the click is the picture's own download (`openingBackground`, warmed by `Workspace`), since the rows and the picture are two independent fetches and running them end to end is the sky arriving a beat after the story it belongs to. Nothing else in the app knows: `Workspace`, the mixer, the background picker and the two `data-setting` cards all read `store.config` and call `store.setX` exactly as before, which is what keeps one card editing whatever is on screen instead of growing a second editor for the same rows. **A whole scene is the reason there is no inheritance matrix**: with every field answered in one place, nothing on screen has to say which half of a picture is inherited, and switching a chat onto its own seeds it from what is already there, so the press itself changes nothing and the tuning starts from the look the reader was looking at. **Switching back keeps it** (`enabled: false`), which is what spares this control the destructive-act ladder: the pill is a switch, not a way to lose an afternoon's tuning. The switch lives on the Interface page as its own **Scene** card (`data-setting="chat-scene"`) directly above the two cards it governs, and while a chat scene is in force those two wear a "This chat" chip beside their titles, since the Scene card scrolls off and nothing else would say whose background is being edited. Its note counts the chats an app-wide change will not reach. **Writes to a chat scene are debounced** (250ms, carrying the chat id they started on): a chat row write broadcasts the `chats` scope and every other device answers it with a chat-list refetch, so a slider drag would send one per frame; the pending scene is what the app reads meanwhile, so the drag still paints at full rate, and a chat switch mid-flight lands the write on the story it was made for rather than the one now on screen.

**A chat claims what it can name, and settings panels always speak for the app.** A story can play as its own persona, send on its own connection and pin its own character version. All three are claimed from the [`ChatSetupChip`](../src/lib/components/chat/ChatSetupChip.svelte) in the composer's feature row and nowhere else, because a chat may only claim things it can name to the reader. It stands whenever a chat is open rather than appearing on divergence, since a control that shows up only once something is odd is a control nobody knows exists; its label is the persona and the model this story is running on, truncated, and deliberately NOT derived from the category list, since a label that grew a segment per category would push the composer's own controls off a narrow screen. **The panel is two levels in one place, and the reason is that both axes grow.** More claimable things makes a flat panel longer, and so does a bigger persona library, so a panel that renders every category's list at once is unusable at forty personas and gets worse from both directions. Level 1 is a summary with exactly one row per category (label, the value in force, a chevron, and the "This chat" pill where this story has broken away), so its height is a function of how many categories exist and never of how many items any of them holds: **when a per-chat preset eventually lands it is one more row and nothing else changes**, which is the property to protect. Pressing a row drills IN PLACE, replacing the same panel's contents rather than raising a second floating layer, which a popover anchored inside a composer has no room for. Level 2 is a small header naming the category with a back affordance, the way back to the app pinned above the list (`Follow the app (Tom)`, naming what it resolves to so the reader knows what they are choosing), a search field that appears only once the list is long enough to need one (`SEARCH_FROM`, the same number and reasoning as the import plan's group filter) and stays put with the header while the list scrolls under both, and then the list. **Personas render as a face grid past `PERSONA_GRID_THRESHOLD`** and as portrait rows below it: personas are faces, and a name-only list throws away the one cue that makes a large library scannable. Connections and versions are plain rows; neither has art. Escape at level 2 steps back to level 1, Escape at level 1 closes, both marked consumed per the Esc contract above. Everything a category needs at either level is declared once in the component's `categories` array. There is deliberately **no** settings page for any of it, no scope pill, no counter of the other chats a change will not reach, and no resolution layer between the chat and the app: the whole rule is `chatValue ?? appValue`, with the stored id checked for liveness, so a claim naming something deleted resolves to the app's value and that category says the claim is gone instead of pretending, at level 2 where the reader is deciding about it. It is resolved in one place, [`utils/chat-setup.ts`](../src/lib/utils/chat-setup.ts), asserted by `contracts.test.ts`.

**A persona is stamped from a real choice or not at all.** `createChat` is reached from six doors and one of them (`routeAfterDelete`) mints a chat as a side effect of deleting another, with nobody present, so stamping whatever the app happens to start chats as would write a permanent pin the reader never made. Only two things stamp: the character's own `defaultPersonaId` seed (architecture/library.md), and a persona handed in by the **New chat flow's persona step**, which outranks the seed because somebody just chose it. That step therefore writes the new chat and nothing app-wide; the same press made from the Library outside the flow is still the app-level choice. Every other door leaves the claim null and the story follows the app exactly as it did before. `importSillyTavernChat` and the assistant's chat insert stamp nothing.

**The panels change wording, not subject.** The Connections page's Model routing card keeps routing the app's Primary point and wears the read-only "This chat" chip (the same recipe the Interface page's governed cards use) when the open chat sends somewhere else. Library → Personas keeps the app-wide persona under a name that says what it does: the badge reads "New chats" and the button says a persona is what new chats start as, since it no longer decides what the open story plays as. **The story's `primary` calls are the only ones a chat can claim**: the assistant and every engine stay app-wide, which is what keeps the Connections page honest about the rows it does own. There is no per-chat preset, and that is a decision rather than an omission: three pieces of shared global state (`memoryStore.macroPlaced`, `regexRulesStore.carried`, `presetControlValues`) still assume one preset exists app-wide, so a chat on another preset would spend memory calls against a prompt that never carries `{{memory}}`, render its transcript through the wrong preset's display rules, and share one control value per macro name with every other preset that uses that name.

**The two workspace scrims**, the reading column's shade (`--theme-column-shade` + `--theme-column-shade-opacity`, drawn by `ChatContainer`'s `.chat-center-shell::before` and its twin on the welcome layer) and the background image's dim (`backgroundConfig.dim`, drawn by `Workspace`'s `.background-dim`), are **deliberately independent, and neither offers a colour choice.** They are not the same kind of thing and must not be unified again: the column shade belongs to the app's own surface language, so it is always the palette's tone; the dim is a photographic scrim over a picture the palette has no say in, so it is always plain black and is hardcoded in `Workspace` rather than minted as a theme var. **Each answers to exactly one number, on the page that owns the thing it protects**: the column's shade on Chat, the image's dim on Interface. Colouring both from one enum costs the combination "black column over a theme-washed picture", and splitting a single scrim's colour onto one page and its strength onto another leaves two halves of one control with nothing on either side admitting the other exists.

The column shade is handed to the shell as an **opaque tone plus a strength applied as `opacity`**, never pre-mixed with `transparent`, and that is load-bearing rather than stylistic. The tint's alpha ramp spans only a few 8-bit levels, so it bands; the fix is a noise tile (`--chat-col-noise`, app.css) layered over it as a second `background-image` on the same element. Pre-mixing the tint left that tile painting at full strength with the shade at zero. Since a docking panel animates the element's geometry, the residue was a stripe of film grain visibly sliding across the workspace with the setting turned off. Under one `opacity` the tint and its dither can only move together. **Both shells also grow that element by `--chat-feather-*` on each side**, because the mask only goes solid that far in from the element's own edge: an element sized to the column spends the ramp fading across the column's own extremities, which is exactly where the portrait rail and the composer's shoulders sit, and they end up backed by nothing while the middle of the transcript is fully tinted. Grown, the solid region lands on the content and the melt happens over empty workspace. **A side with a dock glued to it drops its feather to zero** (`.dock-left-open` / `.dock-right-open` in `Workspace`, animated because the two vars are `@property`-registered): the docks sit flush at `50% ± --chat-col-max / 2`, so that side has no empty workspace left to melt into, and the panel is translucent: a ramp tucked *underneath* it does not hide, it shows through as a dark band running down the column's edge. The tint ends hard exactly where the panel's own border begins, which is the one place a hard edge is invisible. The tile is authored for a shade at **full** strength, where the ramp bands worst, so it scales down with the tint it serves. Its ceiling is deliberately low, because the tint is the palette's own surface tone rather than black, a far smaller delta against the backdrop, so it bands far less and needs correspondingly less jitter. Grain you can see is worse than a band you cannot. Anything else layered onto those pseudo-elements inherits the same contract.

**Settings UI** (`components/settings/`): the panel is a **phone-style drill-down**, except in **split view** (below), which takes over at dock widths. [`settings-pages.ts`](../src/lib/config/settings-pages.ts) holds the IA in one place (it lives in `src/lib/config/`, not the component folder; `services/navigation.ts` routes by it, and a service importing from `components/` would be a layer violation): the root groups (Connection / App / Appearance / Advanced / About; one surface for everyone, deliberately no simple/advanced experience mode, and every row always visible but the one that states its own `shown`, which is Developer's and nothing else's) whose rows carry live value previews, `ANCHOR_PAGES` (every `data-setting` anchor → the page that hosts it), and `TAB_FALLBACK_PAGE` (the assistant's `SettingsTab` ids are the deep-link contract and nothing else). [`SettingsPanel.svelte`](../src/lib/components/settings/SettingsPanel.svelte) is the router: it renders the grouped root or one page from `uiStore.settingsPage` (`'root' | SettingsPage`, remembered across opens), with directional fly transitions (reduced-motion aware), a "‹ Settings" back chip, Escape-steps-back (consumed with `preventDefault` per the shell Esc contract, standing down while a `.dialog-portal` is mounted), per-page scroll reset (the scroller's own `scrollTop`, never `scrollIntoView` on the page inside it: that aligns the page's top edge with the top of the scrollport and parks the shell's gutter above it, so every page long enough to scroll would open a gutter's worth down, and it is free to scroll the workspace behind the panel on its way up), and consumption of the one-shot `uiStore.pendingSettingsAnchor`. The chip rides a `.page-head` nav bar that lives **outside** the scroller (`.settings-root` flex column → header + `.settings-shell`), the same fixed-header shape `SettingsContentPanel` has in split view, for the same reason: the way back has to be reachable from the bottom of a long page, and a header that scrolls away is a dead end at exactly the moment it's needed. It renders only while `!split && page !== 'root'`, since split view's dock never leaves the list. Anything new that must survive scrolling (a page title, a per-page action) belongs on that bar, not inside `.page`. The last group is **About**, and its two pages are ordinary pages: they sit in `settings-pages.ts` with the rest, render through `SettingsPageView` like the rest, and split view shows them in the centered panel like the rest. [`AboutPage`](../src/lib/components/settings/AboutPage.svelte) is the app's identity card and its one door out: an identity block (the mark, the name, one line of what the app is, the version pill), then **Updates**, **Help & community**, **This install**, and a closing line naming the licence. Nothing on it changes how the app behaves: every item either states a fact or leaves the app, which is what keeps a page reached from the bottom of the list off the settings spine entirely. **The update check is the one request the app makes that no story asked for**, and the card says so above the button rather than after it: nothing polls, nothing runs at boot, and a reader who never presses it never reaches GitHub. It leaves from the server ([`about.ts`](../server/about.ts), `GET /api/about/latest-release`) and not from the browser, so one address asks instead of one per device, a page extension cannot quietly block it, and the request comes from the machine that would install what it finds; it carries a bare product name as its user agent (GitHub rejects a request with none) and nothing else, which is what lets that promise stand. The **comparison happens on the client**, against the baked number, since the server answers `dev` from source and could not weigh itself against anything; `parseVersion` is strict on purpose, so a tag this build cannot read is a sentence the reader gets to see rather than a number rounded into a comparison that says "you are up to date", and a 404 names both of its causes (no release published, or the repository not public) because an unauthenticated request cannot tell them apart. What a check found is runtime state and is deliberately never stored: remembering it would mean recording which device asked and when, on a spine every device reads. **Help & community is the only door out of the running app**, since the welcome landing carries the same two community links and is gone the moment a chat opens. Every address in it comes from [`links.ts`](../src/lib/config/links.ts), which that landing reads too: one invite, one place to change it. "Report a bug" opens an issue with the report already shaped and the reader's build already written into it (version, build, runtime, platform, browser), which is the part nobody thinks to include and the part that decides whether a report can be acted on; "Copy details" on the install card puts the same lines on the clipboard, for the reports that happen on Discord instead. The "Keyboard shortcuts" opener is the one control in Settings that reaches a dialog instead of a page and is **gone entirely on `viewport.isTouch`** (the sheet lists keys that device doesn't have and its only other trigger, Ctrl+/, is unreachable there, so it would be the single entrance to a dead end; hidden, not shown inert, the same rule the Chat controls follow). GitHub's and Discord's marks come from [`ui/BrandGlyph`](../src/lib/components/ui/BrandGlyph.svelte) and deliberately not from `ui/Icon`: that set is one stroke language on a grid the app owns, and a brand mark is a filled shape belonging to somebody else that nobody may redraw to match. **"Reach me" is the one block in the interface written in the author's voice**, and the confinement is the rule: the welcome dialog speaks as the product and must keep doing so (above), while an About page is the one surface where a first person is the honest register. It exists because every other door out of this card needs an account somebody may not have, so it names the author's own handle, which is **copied rather than opened** since Discord has no address that reliably resolves a person from their name. It carries no second copy of the invite: the server sits one card above and the sentence points at it. The closing **licence line names two, not one**: the app is AGPL-3.0 with its source linked, and the bundled typefaces are not covered by it, each carrying the SIL Open Font License instead. That second half is not garnish, since a page claiming one licence over everything it hands the reader claims one it does not hold, and it is **linked rather than only named**: the notice ships in `static/fonts/` and is served at `/fonts/OFL.txt`, the one address in [`links.ts`](../src/lib/config/links.ts) that never leaves the machine, because a licence the app hands the reader has to be readable from an install with no internet at all. **This install** is `GET /api/about`, asked once when the page opens and never again while it is up: the answer walks every file under the data dir for its size, so nothing may hang it on a render or a sync hint, and a walk that fails takes the card down rather than reporting a folder smaller than the reader has. It states the build (portable or from source), what it runs on, the data dir behind a copy button, and the size as the whole folder plus the share of it that is pictures, since a bare total answers no question anybody has. It also catches the one state the two halves can disagree in: replacing a portable build restarts the server while an open tab keeps running the client it already loaded, so a portable build whose server version differs from the bundle's says so and asks for a reload. From source that comparison is skipped, the server having no number to state. `InstallInfo` is **hand-kept on both sides** ([`about.ts`](../server/about.ts) and [`transport.ts`](../src/lib/services/transport.ts)); nothing type-checks the two against each other, so a field added to one is a field to add to the other. The version, read from [`version.ts`](../src/lib/version.ts), is also the root row's preview, so the number is readable without opening the page. `package.json` is the only place a version is stated and it is never served to the browser, so `vite.config.ts` bakes it into the bundle through a `CHUNGUS_VERSION` define. That is the client's own copy and not the compiled server's (`server/version.ts`), which has to answer `dev` from source because a hand-built binary has no build step to bake anything; the client always goes through Vite, dev included, so it never guesses. **The version is also the only switch for `advancedSettingsStore.developerMode`**: seven taps with no more than 1.2s between two of them toggle it, the streak resetting on that gap rather than on a deadline for the whole run, so a slow deliberate run still lands while a number poked at across a week never opens a page nobody asked for. **Every tap answers**, since a control that reacts only on the seventh reads as a dead one: the number shakes, takes an accent tint, and throws a label off the pill's right side carrying the count still to go. That label **counts down without ever naming what it counts toward**, which is the line this page holds: a stray tap gets a number and no explanation, and the page still advertises nothing. The seventh is the exception and has to be, being the only thing on this page that reports the switch at all, since the row it adds sits in a list one level up. The labels are a **list rather than one element**, so a fast streak stacks several in the air instead of restarting one and showing only the last, and each carries its own sideways offset so two thrown milliseconds apart fan out instead of printing on top of each other. They leave from the **side** and not over the pill, because the only thing a rising label can cross there is empty margin: the tagline sits above, and a number drifting up through a sentence reads as a rendering fault rather than a reward. Both the labels and the shake are cleared **on a timer and never on `animationend`**, for one reason: the blanket reduced-motion rule ends every animation in 0.01ms, so anything whose life depends on its own animation is gone before it is seen. The shake answers that with its tint; the label answers it by switching the animation off outright under **both** spellings of that rule, the app's own `data-motion` attribute and the OS query, which leaves it sitting at its readable base state until the same timer clears it. The attribute selector is marked `:global`, since it rides `<html>` and Svelte prunes an unreachable ancestor along with the whole rule. The toggle itself notifies nothing, per the notification contract: the **Developer** row appears in the list on the same click, and the next streak takes it away. That is what `SettingsRow.shown` is for, read by `SettingsPanel` on every render rather than baked into the config, so the row comes and goes under a list already on screen in split view. [`DeveloperPage`](../src/lib/components/settings/DeveloperPage.svelte) is the workbench: nothing an ordinary reader needs belongs on it, and for now it holds one card, **Notices**, the way back to everything the app says once and then never again. **Each row reaches its notice the only way that notice can still be reached**, which is why the two verbs differ rather than being evened out: the greeting's own trigger is gone the moment a persona exists, so its row opens it on the spot and clears nothing (a re-read, not a reset), while the assistant's cost notice is a view inside the assistant's own panel, so its row **arms** it by clearing `generalSettings.assistantCostSeen` and puts it back there rather than previewing it out of context here. An armed row says so in the button's place, so the state reads as a state the row is in and not as a control that went missing. A new one-time notice belongs here as a third row on the same rule. The flag rides the settings spine like every other preference, so a machine set up for developing keeps it across reloads and hands it to every device the reader opens the app on. **Split view** (`generalSettings.settingsSplitView`, default off): while the panel is docked (`viewport.canDockSettings`), Workspace passes `split` (the dock renders only the root list with the active row tinted, the `.is-active-tint` scoped-mirror idiom; the keyed remount that refreshes previews is kept, its slide and scroll reset suppressed) and mounts [`SettingsContentPanel.svelte`](../src/lib/components/settings/SettingsContentPanel.svelte) as a `chat-overlay-front` surface whenever `settingsPage !== 'root'`: the selected page, wide and centered over the chat, `.overlay-header` identity (row label over group label), body capped at `--settings-measure` (the same cap the drill-down applies), the Library entry editor's pattern exactly (joins `coveringOverlay`; click-away closes the whole panel; the panel's Escape-steps-back closes just the centered page, the next Esc reaches the workspace). Its header carries an always-visible back/forward pair on the left track walking a **page-local** pane history (module state in SettingsContentPanel; each entry is all four nav fields, `settingsPage` + `settingsConnectionId` + `settingsRoutingModel` + `settingsEngineId`; `'root'` is never recorded, replay is guarded so back/forward don't re-record themselves, `HISTORY_CAP` 50), plus a top-right close X that returns to the list (the dock stays; same exit Escape reaches). **A different page is a fresh stack, never an appended step**, so the pair only ever walks the sub-views of the page its own header names (connection list ← editor ← routing, engine list ← detail) and drops the forward half of the page being left behind. **Notifications** ([`toast.svelte.ts`](../src/lib/stores/toast.svelte.ts) + [`ui/ToastContainer`](../src/lib/components/ui/ToastContainer.svelte) + [`ui/Alert`](../src/lib/components/ui/Alert.svelte)). Everything the app has to say rides one of **four channels**, picked by one question: does the reader have to do something about it? **Nothing**: the screen already says it (a row that vanished, an editor that closed, a marker that appeared). This is the DEFAULT, and the reason most acts notify nothing at all: a line repeating a visible change only teaches the eye to skip the corner where the failures land. **Toast**, something happened the screen does not show and no answer is needed: a count the reader cannot see, work that landed off-screen, a consequence somewhere else. **In place**: a failure belongs where the act was, the dialog that raised it or the card that refused it, which is `ui/Alert` and never the toast stack (a toast fired from inside a dialog is a message the reader cannot reach, and that is how a panel ends up growing a bare colored `<p>` of its own). **Standing**: a condition rather than an event; it lasts as long as it is true, so a toast, which leaves while it still is, can never carry one. That channel holds four conditions, one component each, stacked under the title bar in urgency order. [`layout/DataAheadBar`](../src/lib/components/layout/DataAheadBar.svelte) is first: this workspace was last written by a newer ChungusHub than the one serving it (`dataAhead` off the boot config, architecture/server-core.md). It outranks the outage below it because an outage stops writes, which is the safe failure, while this one lets every write through into a shape the running build was never written against, and it is the only condition on the channel that **cannot resolve while the app is open**: nothing the reader does inside clears it, so it offers no control and is not dismissible. Its flag arrives once with the boot config and never changes, so it is a module-level rune in the component (the `WelcomeDialog` pattern) rather than a store. [`layout/ConnectionBar`](../src/lib/components/layout/ConnectionBar.svelte) is second: the server is unreachable, which breaks generations, stops other devices' changes arriving and fails every write, all behind an interface that otherwise looks healthy. [`layout/DeleteGuardBar`](../src/lib/components/layout/DeleteGuardBar.svelte) is third: the destructive-act ladder is lowered, and still is. It and the connection row only ever appear together on a kept rung, since an outage closes any window. [`layout/ImportBar`](../src/lib/components/layout/ImportBar.svelte) is last and least urgent: a SillyTavern folder import is running (`stores/import-run.svelte.ts`, and the Import page below). It is the only one of the four that resolves on its own, and the only one whose subject is work rather than a warning, which is why it wears the accent rather than an alarm colour. Each is a **full-width row in normal flow**, not a corner badge: no corner to contest, zero pixels while the condition is false, identical on a phone and a desktop, and impossible for a panel to cover; the layout shift when it appears is the message. **Only the delete-guard row is dismissible, and dismissal is scoped to the activation that raised it** (the rung plus the window's end, so lowering again or extending says so again) and lives in memory, so a kept rung dismissed today is stated again on the next boot: "not now" is a reasonable thing to tell a warning and "never again" is not. The connection row is not dismissible at all, because nothing the reader does can make its claim untrue. Its signal is the transport's reachability pair, which reports a drop only after a reconnect attempt has failed (architecture/client-data-layer.md). It renders only in the `ready` phase, since the boot failure cards state the same outage in their own words. **Individual write failures stay toasts and must not be folded into it**: the bar says the server is gone, a toast names the one value that did not land, and only the toast tells the reader what to do again once the connection is back.

**A caught error reaches the screen only through [`failureText(act, cause)`](../src/lib/stores/toast.svelte.ts)**, as `toastStore.failed` on the toast channel, and as the same call assigned into a local on the in-place one, so the two channels cannot apologise in two voices. Naming the act is not optional: the thrown text is a symptom ("429 rate_limit_exceeded") and only the call site knows which of the reader's clicks produced it, which is why a wrapper that runs many different actions takes the act as a parameter (`PresetManager.run`). `toastStore.error` is for a sentence written by hand: a validation, a refusal. The rest of the vocabulary lives in that module's header and holds for every surface: things named in quotes, real counts and never "some", **no em dash on any screen**, one sentence carries no trailing period, and **durations belong to the tone** (`DURATION`) rather than to the sentence, so no call site can buy itself a longer stay. The no-em-dash rule is not scoped to toasts: it holds for every string a reader can see anywhere in the app (template text, tooltips, placeholders, labels, empty states), since the character renders as a stray bar in the UI font at message sizes wherever it lands. A rewrite states the same fact with a colon, a comma, parentheses, or two sentences instead. The [`contracts.test.ts`](../src/lib/contracts.test.ts) em dash contract asserts it over **every tracked file**, whatever its type, listed by `git ls-files` so a new file, directory or extension is covered the day it lands. **Text a model reads is held to the same bar as text a person reads**, because a model copies the punctuation it is fed and hands it back inside the story on screen: a system prompt, a tool description and the bundled preset are as much in scope as a button. So are comments, docs and shell scripts, since the repo itself is read. **The escape hatch is per LINE, never per file**: a line that carries the character as data ends with `em-dash: data`, which is greppable, reviewable, and cannot quietly cover the next em dash that lands in the same file the way a file allowlist would. The regex starter pack that softens em dashes is what needs it, along with the fixtures that prove it and one character class. The **en dash** is a separate, narrower rule: it is correct in a range, so a comment or a prompt may spell `seq 4-5` properly, and only text a reader sees is held to the ban. That is why its three scans stay scoped, to `.svelte` non-comment text, to `src/lib/config/`, to the capability describes, and to every failure text `server/llm/` throws or maps a status code to, since the provider layer's message is what `failureText` folds into the reader's sentence verbatim.

**Three more rules hold for every string a reader sees**, each with its own scan in that file under "one house voice". **An elision is `…`, never `...`**: the split showed up worst inside one control class, two search fields side by side with one saying "Search chats…" and the other "Search 12 characters..."; spread is the only other `...` a `.svelte` file can contain and is always followed by an identifier, a bracket or a brace, so a negative lookahead separates them exactly (RegexPage's `\p{...}` flag hint is regex SYNTAX and is exempt). **Title Case names a thing** (panels, settings cards, character fields, sampling parameters) and **everything else is a sentence**: buttons, dialog titles, headings that state a state rather than name a surface. **"When was this" has one answer**, [`formatRelativeTime`](../src/lib/utils/date.ts), which owns the bands, the capitalisation and the Yesterday step; three surfaces used to hand-roll their own and disagreed on all three, so the same row read differently depending on which panel it was in. Likewise **one platform check**: `MOD_KEY` and `shortcutLabel` in [`ShortcutsSheet.svelte`](../src/lib/components/ui/ShortcutsSheet.svelte) are the only place that knows what platform this is, and `shortcutLabel` is the one spelling of a modified shortcut (modifier, a space, the key; never glued with `+`, which is wrong on macOS). A shortcut TABLE puts each key in its own `<kbd>` chip instead; the helper is for shortcuts named inside a sentence or a chip.

**The stack folds repeats and is capped.** Identical lines collapse into the live one with a count chip and a restarted timer, so a loop that fails ten times says one thing rather than ten; past `MAX_VISIBLE` the oldest makes room. `.toast-wrap` sits at **z 1100**, above every out-of-flow surface in the app: dialogs and the lightbox portal to 300, the assistant widget holds 200 and goes full-screen on phones, tooltips reach 1000. `.app-shell` opens no stacking context, so that value competes at the root and the container needs no portal of its own.

The Connections page keeps the Model routing card above the connection list. That list defaults to four visible cards and exposes the rest through a local expand control. New and duplicated connections stay in the overview, auto-expand the list when needed, scroll into view, and pulse with the same shared accent ring/glow used by Assistant navigation.

## Before touching this

- New user-facing message → pick a channel from the notification contract above BEFORE writing the sentence, and if it came out of a `catch`, name the act and hand it to `toastStore.failed`/`failureText`. A raw `Error.message` passed straight to `toastStore.error` is the exact shape this contract exists to keep out.
- **Clipboard writes go through [`copyText`](../src/lib/utils/clipboard.ts), never `navigator.clipboard` directly.** That API is exposed in a secure context and nowhere else, and a phone reaching this server over the LAN is on plain http, so a direct call is `undefined` exactly where copying is hardest to work around by hand. `copyText` falls through to a selection copy that still works there, and **throws when the text did not land**. That second half is the one that gets skipped: a "copied" tick set beside the call rather than after it is a lie the user only discovers at the paste, on the one device that cannot see the console.
- **New delete → put its asking surface on the ladder, and say which rung.** A `ui/ConfirmDialog` needs `destructive` or the reader's setting will never reach it; a hand-built confirm needs a `deleteGuard.asks` check of its own. Neither is inferred, and the failure is silent in the safe direction (the gate simply never lowers), which is why it belongs on this list rather than in a test.
- New user preference → ride the settings spine (`readSetting`/`writeSetting` + `registerSettingsReload` + a `normalize`), never localStorage, never a new persistence path.
- New panel/overlay → add it to `uiStore`'s choreography (mutual exclusion, nav-guard, lock semantics) rather than tracking open-state in a component.
- **A body that scrolls uses `.panel-scroll`, never a bare `overflow-y: auto`.** The recipe (app.css `@layer components`) is `overflow-y: auto` + `scrollbar-gutter: stable`, and the gutter is the whole point: Chromium's scrollbars are classic, so the moment content crosses the panel height the bar appears, the content box narrows by its width and the entire body re-flows sideways. Opening one disclosure row therefore slides everything right-aligned in the panel, which reads as a rendering fault. Reserving the track costs its width permanently and is the right trade on any surface whose content length varies. It is **not** a `*` rule and must not become one: `scrollbar-gutter` reserves on `overflow: hidden` boxes too, and the panel shells (`.chat-overlay-panel`, the docks, every clipped card) are full of those; a blanket rule would hand each of them a dead strip. Layout (`flex`/`height`/`padding`) and scroll-chaining (`overscroll-behavior`) stay with the component; the recipe owns the overflow axis and the gutter only. Applied to every panel/dialog body: both Settings surfaces, Lorebook, Memory, Preset Controls, Steering, the assistant panel + its settings view, Chats, Welcome, the message list, the chat preview pane, the story-map inspector, the branch-compare modal, the debug panel's two panes, the library/persona editor bodies, and `ui/Dialog` (backdrop **and** body; a dialog that grows shifts its own centering otherwise). Deliberately **out**: `max-height` popovers and dropdown lists, code/pre boxes that scroll both axes, and horizontal-only strips (`scrollbar-gutter` would reserve a vertical track on those too). Those still jump on filter-as-you-type; if that gets fixed, it needs its own pass, not this class. A horizontal strip that must not have the bar land on its content reserves the band by hand instead: the assistant tab bar carries `--assistant-tabbar-scrollbar` and pads **both** children by it, because a strip's auto height counts its content and not its bar, and padding the scrolling child alone lifts it half a band off whatever sits beside it.
- **A text field on a touch screen never renders below 16px, and never re-measures itself over a keystroke that wasn't its own.** Two rules, one surface, and both are invisible on a desktop. The floor is an **unlayered** `@media (pointer: coarse)` block in app.css, unlayered because Tailwind's `text-sm`/`text-xs` live in `@layer utilities` and would outrank anything in `@layer components`; `max(16px, 1em)` so a field on a larger surface keeps that surface's size. Below that threshold iOS Safari zooms the page in the moment the field takes focus and stays there, leaving a viewport wider than the screen, a caret that scrolls out from under the thumb, and taps landing off target; raising the floor is the only cure that leaves pinch zoom alone. The measuring rule belongs to [`autoResize`](../src/lib/actions/autoResize.ts), the one action every growing textarea uses: a form rebuilds every field's parameter object on every render, so `update` fires on **all** of them for one character typed into one, and each measurement collapses a box to its content height for an instant. That instant is what clamps a scroll container sitting near its end, and the clamp is not undone when the height comes back, so the view walks away from the caret, once per field per keystroke, worst exactly where the keyboard has eaten half the screen. The action therefore skips a measurement whose value and ceiling are both unchanged, and restores the scroller's position around the one it does take. Neither half is optional, and a call site that wants external value changes honoured must keep passing `value`.
- **Scrollbars are styled with the standard properties only**: `* { scrollbar-color; scrollbar-width: thin }` in app.css, no `::-webkit-scrollbar` anywhere global. Do not reintroduce the pseudo-elements and do not try to serve both: Chromium 121+ gives the standard properties precedence over `::-webkit-scrollbar`, so a global pseudo-element block is dead weight on Chrome/Edge, and the `@supports not selector(::-webkit-scrollbar)` guard that would split the two engines **lies on Firefox 153+**, which answers "supported" for web-compat while still refusing to apply the pseudo-elements' colors. That guard costs Firefox its scrollbar styling outright, and the breakage is invisible on macOS and Android Firefox (overlay scrollbars draw nothing to notice); it only shows on Windows Firefox, which draws a classic bar. So **any scrollbar change has to be checked on Windows Firefox specifically**, not just Chrome. `thin` also equalizes the bar's width across engines, which is what `.panel-scroll`'s reserved gutter is sized against. A few components still carry scoped `::-webkit-scrollbar` rules (`.chats-scroll`, `.nav-cluster`); the width/colour ones are inert for the same reason and are pre-existing.
- **A welcome-landing control that raises a panel is a toggle, never a bare open.** The landing only goes `visibility: hidden` behind a *covering* overlay; a side dock (Settings/Library) leaves it fully visible and clickable, so its buttons are pressed a second time with the panel already open: `openLibrary()` on an open Library is a no-op that reads as a dead button. `Workspace.handleBackgroundMouseDown` treats the landing as backdrop but exempts its own `button`/`a` targets: without that, the backdrop pass closes the dock on mousedown and the button's own click reopens it, so the toggle plays as a reopen animation.
- New settings page → the `SettingsPage` union + `TAB_FALLBACK_PAGE` and the root groups in `settings-pages.ts`; a new *tab* id also needs the server's `SettingsTab` copy (couplings below).
- Settings page navigation → `uiStore.gotoSettingsPage(page)`, never a bare `settingsPage =` write: it also clears the connection editor (`settingsConnectionId`), its in-place Provider Routing sub-view (`settingsRoutingModel`), and the engine detail (`settingsEngineId`), none of which may survive a page switch. The one sanctioned exception is SettingsContentPanel's history replay, which restores all four fields together.
- Colors/spacing → `--theme-*` variables only; new vars are minted in `applyTheme()` + a fallback in app.css.
- **A new palette is authored to the readability floor its siblings hold**: primary ≥ 13:1, secondary ≥ 7:1, muted ≥ 4:1 against its own `bgPrimary`, asserted per palette in [`contracts.test.ts`](../src/lib/contracts.test.ts). Nothing in the type system enforces this and the damage is invisible on a bare page: a palette a stop shallower than the rest looks correct in the picker and only falls apart where glass sits over the workspace photo, which is where most of the app lives. The floor is what makes `LIGHT_GLASS_KEEP` sufficient rather than a patch over a weak palette.
- **The measure is capped on the column, never on a row.** `--settings-measure` (52rem, `:root` in app.css) caps *both* settings surfaces (the drill-down's `.settings-content` and split view's `.content-body`), so a page reads at the same width either way instead of stretching to the full chat column in a wide overlay. Rows fill their card: `.toggle-row` and `.slider-block` carry **no** cap of their own. A per-row cap produces exactly the raggedness it is meant to prevent: a card whose input and pill row run to the card edge while the switch above them stops short of it, invisible until the panel clears the row cap, i.e. only on wide screens, where it reads as a rendering fault rather than a choice. The rule: every control in a card ends at the same right edge; if the measure is too wide, narrow `--settings-measure`, don't shrink one recipe. On top of that, `.toggle-row` carries a hover band (common region beats proximity) and the [`toggleRow`](../src/lib/actions/toggleRow.ts) action hands the whole row to the switch it contains, widening a ~40px target to the full row without adding a second tab stop (it clicks the first `[role="switch"]:not(:disabled)` inside, and ignores clicks that already landed on a control or ended a drag). **The row is the switch, including what it refuses to do**: every other click-the-whole-row surface in the app is a real `<button>` and inherits `user-select: none` from app.css, while this one is a div that borrowed only a button's click, so the action refuses the browser's multi-click selection step by hand. Without that, a double click means two different things three pixels apart (over a word it highlights the word, over the gap beside it it flips the switch twice), and nothing on screen says which one you are about to get. The refusal is the multi-click step and nothing else: a deliberate drag over the label still selects it, and a text field living inside a row (the lorebook globals) still picks a word on double-click, because both handlers exempt controls through one shared rule. A press that travels belongs to the text, a press that lands where it started belongs to the row, and neither asks what is selected elsewhere on the page. The action stamps `data-row-toggle`, which is what the pointer-cursor rule keys off, so rows with bespoke markup (Security's password lock, the assistant's permission cards, the lorebook globals, an engine's identity row) get it too. **Never put it on a row that already means something else when clicked**: the Engines list row drills into a detail page and the Regex rule row expands, and both are deliberately left out.
- **A settings page has exactly two surface tiers: the panel, and the page's own cards.** `.settings-content` (drill-down) and `.content-body` (split view) are the measure and nothing else: no border, no background, no padding of their own; the horizontal gutter is `.settings-shell` / `.content-scroll`'s padding, and the surface beneath is the frosted dock or the `.chat-overlay-panel`. Giving either of them a card treatment makes every page cards-inside-a-card: an extra border plus ~20px per side between the gutter and the first control, and on a page whose whole content is ONE card (the Engines overview, Regex, Advanced), the very same rounded box drawn twice, concentric, with nothing but padding in the gap. In a 21rem dock that middle tier alone costs ~30px of a ~246px content column, and Regex stacks a fourth box on top of it (`.rx-rule`, then `.rx-editor`), which is what wraps the `/pattern/` field's flag row. So: a new page brings its own `section.card`s (or an equivalent bordered group: SecurityPage's `.security-card`, PromptBuilder's `.pb-list`) and never assumes a surface underneath. Content with no card of its own sits directly on the panel, which is correct for the transparent rows (`.reset-row`, the Manuscript `.style-note`) that already do.

- **A control's explanation lives in an [`InfoTip`](../src/lib/components/ui/InfoTip.svelte), never as body text beside the control.** The drill-down pages and the assistant's in-panel Assistant Settings both read as heading → controls, with one ⓘ per card: prose stacked above a control is a wall nobody reads and it costs the vertical space the controls need, which is worst exactly where the surface is smallest. **A call site never picks the bubble's side**. There is no such prop, and adding one back is the bug: a side that fits a 52rem settings column runs off the edge of a 320px assistant panel, so the only correct answer is the one measured at the moment of opening (below). Pass a `trigger` snippet to hang a tip off a chip or badge instead of the ⓘ; it renders as the content of InfoTip's own button, so pass markup, never a button of your own. Explanations that state a rule rather than describe one control (the assistant's frozen-settings rule) belong in the section's own tip, not repeated per card.
- **Every hover bubble in the app is placed by [`anchorTo`](../src/lib/actions/anchorTo.ts): [`InfoTip`](../src/lib/components/ui/InfoTip.svelte) and [`MockupTip`](../src/lib/components/mockups/MockupTip.svelte) alike.** A bubble left in normal flow is offset from its nearest positioned ancestor and **clipped** by its nearest scroll container, and the workspace nests panels inside several `overflow: hidden` docks: the tail of the text is simply gone, with no way to reach it. So the action moves the node to `<body>` and works in viewport coordinates, flips below→above only when below doesn't fit and above does, and clamps into both axes: one 8px gap off the anchor, one 8px margin off the viewport, for every tip in the app. It stamps `data-placement` so a component can point its enter animation the right way and `data-open` a frame later so the CSS reveal has a from-state; geometry is the action's, looks and motion stay in the component. Render the node under `{#if open}`: the node and the action live and die together, which is what keeps a tip clear of the always-mounted portal trap above: there is no `$effect` whose cleanup can outlive what it detached. A `role="tooltip"` element in a component that doesn't reach for the action fails [`contracts.test.ts`](../src/lib/contracts.test.ts), because a hand-placed bubble is a clipped bubble.

**Four shared components carry what a class alone cannot**, because each has structure or state rather than only looks. [`ui/EmptyState`](../src/lib/components/ui/EmptyState.svelte) is the one shape of "there is nothing here yet": the `.empty-orb` disc, a sentence-case heading, one line of copy, and the action that ends the emptiness. **Two sizes and no more**: `md` for a whole panel with nothing in it, `sm` for a state inside a working panel (a filter that matched nothing, a sub-view waiting on a chat), which is smaller because the panel around it already says what surface this is. **The action is the point**: an empty state that only describes the emptiness leaves the reader to go find the button themselves, which is the one thing they cannot do yet, so `actions` is omitted only when the remedy genuinely is not on this screen. A panel reaching for `.empty-orb` directly is building a second empty state by hand; the only sanctioned one is `MemoryView`'s INTRO card, which is not an empty state at all (the panel has a chat and works, it is explaining an engine nobody switched on). [`ui/Spinner`](../src/lib/components/ui/Spinner.svelte) is the one busy indicator, three sizes, and it is `aria-hidden` unless given a `label`: a ring announces nothing a screen reader can use, so the waiting SENTENCE beside it is the announcement. [`ui/Toggle`](../src/lib/components/ui/Toggle.svelte) is the one switch: two sizes (`md` a settings row, `sm` a dense list row) and **one on-state**, so a dense list cannot trade the solid accent for a faint tint and leave the reader deciding per surface what "lit" means; its knob travel derives from the track rather than being hand-tuned per size. Not every two-state control belongs there: the lorebook row's status dot carries THREE natures in its colour (always active / keyword / off) and only happens to click as a toggle. [`ui/Button`](../src/lib/components/ui/Button.svelte)'s `danger` variant paints `--color-on-error`, never white: every palette's error is a light red, so white measures around 2.5:1 on it and a hardcoded ink cannot answer a light palette at all. `--theme-on-error` and `--theme-on-success` are minted in `applyTheme()` by the same recipe as `--theme-on-accent`, for the same reason, and both have a real consumer (the danger button, the assistant launcher's badge). All four are asserted in [`contracts.test.ts`](../src/lib/contracts.test.ts) under "shared UI recipes", together with the rule that no status colour carries a hardcoded `var(--color-error, #…)` fallback: the var is always defined by `@theme`, so a fallback never renders and is simply a second, different red sitting in the source claiming to be the app's.

Repeated micro-recipes live in app.css `@layer components`: `.panel-scroll` (below), `.surface-float` (float frost), `.empty-orb` (the disc `ui/EmptyState` draws), `.section-label` (uppercase micro-label), `.is-active-tint` / `.seg-lift` (canonical active states for tabs/pills/segments), and the settings-page control language: `section.card` (+ `section.card .card-head` / `.card-title` / `section.card .card-body`), `.toggle-row`, `.link-btn` (link-styled inline button, the reset/override affordances), the `.slider-block`/`.slider-top`/`.slider-label-wrap`/`.slider-label`/`.slider-value` scaffolding, and the `input.slider` range skin. Point markup at these instead of re-declaring them in scoped styles; keep only genuine local additions (margins, borders) in the component. A re-declaration wins in a way that does not look like it should: component styles are unlayered, so they beat `@layer components` whatever the specificity reads, and a page-wide one silently reshapes every card on that page to suit the one card that wanted it. Right-edge placement in particular belongs on the element that wants it (`margin-left: auto` on the button), never as `justify-content: space-between` on a shared head: that head also carries a title and its InfoTip, and pushing its children apart strands the ⓘ a card's width from the words it explains. The card and slider recipes are **element-qualified on purpose**: mockups use `<div class="card">` for message cards and `ui/Slider` renders a `<div class="slider">` wrapper, so bare class selectors would leak into them; `.card-head`/`.card-body` are card-scoped because SecurityPage reuses those names for its own drifted dialect. Keep the qualifiers.

One overlay is reachable with **no chat open** and must stay that way: `steering`, since global steering notes have to be editable from the welcome landing (architecture/engines.md). Nothing in the choreography special-cases it (`coveringOverlay` already covers any `activeOverlay`, which hides the welcome layer beneath it), but a future guard that requires an active chat to raise an overlay would silently strand those notes.

Chat-area utility overlays use the shared `.overlay-header` recipes in `app.css`, in **two forms picked by one question: can the TitleBar name this panel for us?** The base form is one left-aligned toolbar row where the **breadcrumb** (`.overlay-crumb`) leads and `.overlay-actions` trails, worn by the panels the nav cluster does NOT raise (Chats, Stats, and the split-view Settings page). Its grammar is fixed: the panel's name as a quiet `.overlay-crumb-label`, a dim `/`, then the SUBJECT as the strong `.overlay-subject`, with dim `.overlay-facts` after it. **A panel with no subject on screen promotes its own name into the strong slot**, so the loudest text on the bar is always the most specific thing in front of the reader, and a panel whose subject IS itself (Chats, Stats) simply starts promoted.

**`.overlay-header--stacked` is the second form, and the four nav-cluster panels wear it**: the panel's name alone on the first line (`.overlay-title`, an `<h2>`), the subject and the controls over that subject on the second, both centred, no breadcrumb label and no separator. The first line **hides itself the moment the TitleBar's own button carries the panel's name**, which is the whole point: those two are the same word on one screen, and the nav button is already tinted to say which panel is open. It is *hidden*, never removed, so a reader navigating by headings keeps it at every width. **Both halves read one attribute with one writer**: whether the labels fit is decided against `--chat-col-docked`, the dock regime's column at the current window width (the equation is spelled once at `:root` in app.css; coupling 7), measured off a hidden probe in `TitleBar.svelte` whose `ResizeObserver` stamps `data-nav-labels` on `<html>` synchronously in its callback, so the flip lands before paint on both surfaces at once. `.overlay-title` hides under `:root[data-nav-labels]`, and a panel needs no container of its own for it. **The bar's rendered width is deliberately not the input, and must never become it**: the bar is capped at `--chat-col-max`, whose room is non-monotonic by design (squeezed toward its floor while the docks are held, back at the content cap the moment they vanish; coupling 7), so a rule that asks the bar's own momentary width turns the labels back on in the middle of a narrowing drag, and a viewport media query is wrong the other way, keeping labels on at a narrow chat-width setting on a wide screen where the cluster has no room. The docked column is the tightest form the current window can take and moves only in the window's own direction, so the labels flip exactly once per direction; below the dock breakpoint the bar is wider than the deciding width, and that slack stays icons-only rather than handing back labels the next few pixels of narrowing would take away again. The threshold (46rem in `TitleBar.svelte`, rem so browser zoom keeps working) is the row's own widest state plus room to spare, erring on the side of dropping labels early; the cluster itself neither scrolls nor shrinks below its content, so if the rule is ever broken the overflow paints where it can be seen. The attribute's name across its spellings and the probe's variable are held by [`contracts.test.ts`](../src/lib/contracts.test.ts). **Everything a header holds speaks one of two shared control vocabularies, and which one is decided by scope.** A control about the SUBJECT rides the crumb: an interactive subject is an `.overlay-switch` (same type as the static form, chevron as the standing affordance, soft pill on approach, a negative margin holding its text at the crumb's own x, `.is-untitled` keeping a nameless subject's muted italics), and a menu of actions ON that subject sits right beside its switcher, because one parked on the far edge of a wide panel is a control the reader has to go looking for: Preset Controls' (`PresetManager compact`, shrinking the trigger to sit inline) and Lorebooks' own, whose trigger is the plain `.overlay-action-btn` wearing `aria-expanded`, which the recipe already lights. **The switcher picks, the menu acts, and neither does the other's job**: a subject dropdown that also carries export and delete makes the reader read every row before clicking one. A control about the PANEL (Stats' poster/recount) rides `.overlay-actions` as an `.overlay-action-btn`: the ghost `.icon-btn` metric plus the states chrome needs (`.is-on` for held tools, `:disabled`, a `--labeled` form), kept a separate recipe so those states never leak into the app-wide `.icon-btn` surfaces. No panel hand-rolls its own header button; per-panel one-off button styles are the drift the recipes exist to prevent. **A stacked header has no trailing track at all**: everything on it is about the subject, and a shortcut into Settings parked on the far edge is exactly the kind of per-panel one-off that leaves two panels with the same shortcut and a third without it. The engine's own page is reached from Settings, and a panel that cannot run says so in its body with the door in its empty state (Memory's off-note). These headers carry no leading icon, **including Chats**, whose subject is the word "Chats" and never the character: whose chats these are is what the scope switch below says, and a crumb that shape-shifted into the character's name would say it a second time, in only one of the two scopes. Its `.chats-identity-row` overrides only padding, the recipe's min-height (it stacks two more rows below the crumb) and the bottom seam, because the controls row below it carries that seam instead. Settings, Library, Lorebooks, Preset Controls, Story Map and the Memory panel deliberately have no in-panel close button; click-away, Escape, and their TitleBar toggles own dismissal. One deliberate exception (owner call): the split-view Settings page panel (`SettingsContentPanel`) carries a top-right X: it steps back to the dock's list, never closing Settings outright.

## Hand-kept couplings

1. `SettingsTab` union ×2. The client declaration lives in [`settings-pages.ts`](../src/lib/config/settings-pages.ts) with the rest of the settings IA, and `types/assistant.ts` imports it rather than re-spelling it in the `NavTarget` setting arm; `TAB_FALLBACK_PAGE` in the same file is a `Record<SettingsTab, SettingsPage>`, so a new tab must land on a real page or it fails to compile. `server/assistant/registry/settings.ts` keeps the second copy (no cross-boundary import) and the two are asserted equal in [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts).
2. Settings anchors: the assistant settings catalog's `tab`+`anchor` ↔ `data-setting="..."` attributes in the tab components ↔ the `ANCHOR_PAGES` map in `settings-pages.ts` (architecture/chungus-assistant.md rule 1); `navigateTo` routes `uiStore.settingsPage` by that map, leaves the one-shot `uiStore.pendingSettingsAnchor` for a later-mounting panel, and flashes by the attribute (retrying across a few frames while the page mounts). All three ends are asserted in [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts): every catalogued anchor must have an `ANCHOR_PAGES` entry AND a `data-setting` somewhere under `src/lib/components`. A catalogued anchor with no page and no attribute is not excused: it is deleted from the catalog.
3. `--theme-*` variables minted in `theme.svelte.ts` `applyTheme()` ↔ first-paint fallbacks in `src/app.css`: add in both. The message-card layer (`--msg-*`, `--prose-*`, `--avatar-*`, `--user-bubble-width`) has a **third** copy: every consuming declaration carries the shipped value as its `var()` fallback, so the transcript paints correctly in the frames before the store stamps anything. All three must agree; a new knob that only lands in `applyTheme()` looks right at runtime and wrong on first paint.
4. A new `AppearanceState` field needs four edits, not one: the type (`types/theme.ts`), the default (`DEFAULT_APPEARANCE` in `themes/presets.ts`), a clamp/whitelist line in `normalize()`, and the var in `applyTheme()`. `normalize()` is the only thing standing between a corrupt blob and the UI: a field missing from it reads as `undefined` and silently degrades every consumer.
5. Ambient effect ids: **one source.** [`AMBIENT_EFFECTS`](../src/lib/types/ambient.ts) is the ordered list; `AmbientEffect` derives from it and `AmbientType = 'clear' | AmbientEffect` (`clear` is the absence of an effect, deliberately outside the effect union; it has no renderer and never appears in the picker). The store's validation set, `AMBIENT_LABELS`/`AMBIENT_DESCRIPTIONS` (both `Record<AmbientType, …>`), the canvas's `EFFECTS` map and `AmbientMixer`'s `EFFECT_SHELF` (both `Record<AmbientEffect, …>`, deliberately not `Partial`, so an effect with no renderer or no catalog shelf fails to compile) all follow from it. 7. **Two regimes, one expression: split in halves while there is room, then hold the docks and squeeze the chat.** While a quarter of the screen is at least `--dock-hold` (21rem), the layout is 50/25/25: the share is the invariant at **every** width from there up, so the proportions never drift with the viewport, on a laptop and an 8K screen alike. Below that the docks stop shrinking and the chat absorbs the rest of the narrowing (`100vw - 2 × --dock-hold`); `min()` of the two terms *is* that rule, and the crossover falls out on its own instead of needing a second breakpoint. The asymmetry is deliberate and is the whole point: the chat is the widest column at every dock width and its content is nowhere near cramped down there, while a panel squeezed past ~336px starts folding its rows: the column with slack gives it up. Everything else follows, including the breakpoint, which is therefore an equation written twice: `DOCK_QUERY` in `viewport.svelte.ts` and the `@media (min-width: 76rem)` branch on `--chat-col-max` in app.css must stay identical, because 76rem is just **`--chat-col-min` (34rem) + 2 × `--dock-hold` (21rem)**, the width at which the squeezing reaches the chat's own floor. Below it there are no docks and the column hugs `--chat-content-max` (below). The column expression itself is spelled once, on `--chat-col-docked` at `:root`, at every window width: the branch assigns it to `--chat-col-max`, and the TitleBar's nav-label probe measures it below the breakpoint too (the stacked-header rule above). The **outer `min(…, 100vw - 28rem)` re-imposes an absolute dock reserve after the chat-width knob multiplies**: without it a knob above 100% would starve the docks the query already promised, and that guarantee is the only reason a plain media query is honest here rather than a JS geometry check. The knob genuinely trades chat against dock (0.75 → docks ~31% each, 1.2 → ~20%), at every viewport width.
   **The column has no ceiling, and must never grow one.** The docks are defined as everything from the column's edge to the screen edge (`50% ± --chat-col-max / 2`), so any absolute cap on `--chat-col-max` hands every pixel past it to the docks: on a 4K screen a capped column renders as a narrow strip between two panels each wider than the story they frame, with the panels' own content stopped at its measure and floating in mostly empty glass. The chat-width knob, multiplying an already-bound cap, moves almost nothing. Width caps belong to **content**: `--chat-content-max` (78rem × the knob, app.css) centers the transcript (`MessageList .message-list-content`) and the composer (`InputArea .input-inner`) inside the column, and it must stay on those content boxes because Portraits and Manuscript rows fill their row: uncapped they stretch to whatever the share resolves to. The surplus a wide column holds past its content stays quiet inside the column that owns it, never handed to a neighbour.
   **The rejected alternative is worth knowing, because it looks more principled.** Giving each dock a fixed minimum and handing the chat every leftover pixel *at all widths* fails in a way that only appears on the screens it matters for: the docks stay pinned at their minimum until the chat reaches its own cap, so a 1464px laptop renders 69/15/15 while a 2560px desktop renders 49/25/25. Same code, opposite layouts. The share must be the invariant while there is room; the dock's width becomes the invariant only once there is not.
   `--reading-measure` (64rem) is a separate thing again and stays a *ceiling*: the text's own cap inside the content column, consumed by `Message.message-bubble-shell-user/-assistant` and `MessageList.memory-boundary`, each multiplying it by `--user-chat-width` so a wider column yields wider text instead of more empty margin. It does not floor the column: 45–75 characters sits far below it, so a 44rem column still reads fine. All three constants are plain app.css declarations, not `applyTheme()` vars, so none needs a first-paint fallback.
   Two consequences that are deliberate, not bugs. The column **drops sharply at the breakpoint** (its content cap → half the viewport), because that is the moment two panels' worth of room has to come from somewhere; and the side margins are a **permanent reservation**, so with nothing docked they are empty background at exactly the dock's width, the price of `.settings-dock`'s promise that the chat never moves when a panel opens. The threshold is rem so it tracks browser zoom and the browser font size the way the column does; a pixel threshold is wrong at any zoom but 100%. **Browser zoom is the reader's size control and the layout must keep honouring it**: every term here is rem or viewport share, so zooming condenses a big screen into the smaller layouts exactly as on any web page. Nothing may read the display size or window size from JS to scale the interface, which cancels the reader's own zoom. Sizing against the screen resolution rather than the *viewport* is the other trap: a 1512px screen is a ~1464px viewport.
