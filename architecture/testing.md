# Testing: architecture & maintenance

This doc owns **how** invariants are enforced and **where**. It does not restate them: every subsystem doc owns its own rules, and this one explains the machinery that keeps them from rotting. The suite is deliberately small in surface and blunt in purpose: it exists to convert the failures that would otherwise be silent (a renamed method that only breaks at runtime, a mirrored union that drifts, a summary that survives a branch it should not) into a red `bun test`.

## What runs

**`bun test`** is the whole runner. Every test file imports from `bun:test` and nothing else: there is no vitest, no jsdom/happy-dom, no testing-library, no playwright anywhere in [`package.json`](../package.json), and adding one would be a dependency decision, not a detail. `node_modules` is not scanned, so the vendored `gpt-tokenizer` test files never run. At the time of writing the suite is **1288 tests across 76 files, 5675 `expect()` calls**, in a handful of seconds, and it is green. Three kinds of file reach outside their own process memory: [`server/llm/openai-compatible.test.ts`](../server/llm/openai-compatible.test.ts) and [`server/llm/net.test.ts`](../server/llm/net.test.ts) stand up scripted endpoints with `Bun.serve({ port: 0 })` (OS-assigned loopback ports, stopped in `afterAll`, never 1420/4242), the database-backed files below, and two files that **spawn the server itself**. The first is [`server/generationSurvival.test.ts`](../server/generationSurvival.test.ts), and it earns the cost: the rule it pins is that a generation outlives the socket that asked for it, and nothing below the WebSocket layer can be handed the situation that breaks it (a phone whose browser is backgrounded has the socket torn down mid-reply). It runs `server/index.ts` as a child against a throwaway `CHUNGUS_DATA_DIR`/`CHUNGUS_BACKUP_DIR` on `CHUNGUS_PORT=0`, reads the assigned port off the child's own banner, and waits on `child.exited` before removing the scratch dir, because Windows will not unlink a file the child still holds. It also passes **`NODE_ENV: 'production'`**: the child is a real server rather than a test process, and `bun test` puts `NODE_ENV=test` in the environment it would otherwise inherit, which is exactly what [`config.ts`](../server/config.ts) reads to decide whether to create the data dirs. Inheriting it boots an install with nowhere to write. Any future spawned-server test owes all four of those, plus the `CHUNGUS_NO_OPEN=1` below. Its scripted endpoint holds the second half of every answer behind a gate the test opens only after cutting the socket, which is what makes the claim provable rather than plausible: the tokens it asserts on are ones that could not exist if the generation had died with its page. Seven tests: the returning page is handed exactly what it missed and no more, **the reply lands in the story with no page ever there to write it**, a second reply for the same chat is refused while the first is still being written, **a page that lost its generation finds it by chat and stops it** (which is what keeps that refusal from being a dead end: the discovering socket never issued the generation, and the endpoint still holds the rest of its answer behind the gate, so nothing but the cancel can be what ended it), an engine call is not reported as a reply being written, a claim on a generation the server never had is answered instead of hanging, and a released one is forgotten. Run it against a `close(ws)` that aborts and the first two go red, which is the check worth repeating before trusting any change in here. The second is [`server/instanceLock.test.ts`](../server/instanceLock.test.ts), which owes the same four things and spawns for the same reason: it pins that a second copy launched against one data folder refuses to start **and that the first is still holding the folder once it has**, since a refusal on its own cannot tell those two apart and a claim that lapsed under the second launch lets it in with nothing said anywhere; and that a copy **killed outright** leaves that folder claimable again. Both copies are read on both streams for as long as they live: a child whose pipe nobody drains blocks on the write, and a claim that faults after it was taken reports that on stderr alone, so reading one stream at the end leaves the interesting half of a failure unread. Only an OS can be asked whether it released a claim, so a unit test of the module would pin nothing that matters. Both instances take `CHUNGUS_PORT=0`, so a port collision can never be what stops the second one. Nothing calls a real provider, nothing reads or writes `user-data/`, and **nothing opens a browser because both files pass `CHUNGUS_NO_OPEN=1`**, which is the fifth thing a spawned-server test owes and the one whose absence is loudest: a server started from source opens a tab unless it is under `--watch` (architecture/build-packaging.md), so forgetting it sprays tabs across a test run. **[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs `bun run check`, `bun test` and `bun run build` on every pull request and every push to `main`**, on Linux and Windows both: this codebase splits on path separators and line endings, so a Linux-only run is a green tick that says nothing about half the users. It pins the same Bun the release builds use, or CI would vouch for a runtime the shipped binary is never built with.

**One file writes real files with no database behind them.** [`server/config.test.ts`](../server/config.test.ts) drives `ensureConfigFile()` against a `mkdtemp` folder, which it can because that function takes the path it works on rather than reading `CONFIG_PATH`. Ten tests cover what a build that has learned a new setting may do to a settings file somebody already has: the missing line is added with its default, every value, note and key order already in the file survives, a misspelled key survives so the boot can still name it, a file already holding every setting is not written at all, and **a file it cannot parse is left byte for byte alone**. That last one is why the file exists: rebuilding a torn config from defaults would drop the line naming where the data lives (architecture/server-core.md). It never sees the repo's own `chungushub.config.json`.

**`bun run check` is two type-check passes**, and neither of them checks the tests: the root [`tsconfig.json`](../tsconfig.json) excludes `src/**/*.test.ts` and [`tsconfig.server.json`](../tsconfig.server.json) excludes `server/**/*.test.ts`, both because test files lean on `any` for the dynamically imported db handle. The server config states the trade in its own header: `bun test` is what keeps them honest instead. Why the passes are two at all (SvelteKit's generated config structurally cannot reach `server/`) belongs to [build-packaging.md](build-packaging.md).

## `src/lib/contracts.test.ts`: the cross-boundary net

[`contracts.test.ts`](../src/lib/contracts.test.ts) is the file nine architecture docs point at. Its subject is **residue**: pairs of declarations that genuinely cannot be collapsed into one, either because the two ends live in modules that must not import each other (server code never reaches into `src/`; the client never imports the server's runtime) or because one end is a TypeScript union and the other is SQL, a `.svelte` file's private constant, or an ordering that carries its own information. Everything that *could* be derived away already has been: the docs that say "**not hand-kept**" are recording exactly that. What is left gets a failing test instead of a comment nobody reads. 59 tests in 25 `describe` blocks. Twelve blocks are not cross-boundary couplings at all and say so in their own comments (`notification contract`, `em dash contract`, `one house voice`, `shared UI recipes`, `destructive-act ladder`, `transcript window`, `transcript scroll writes`, `anchored tips`, `theme custom properties`, `palette readability`, `commands` and `shortcuts`): `palette readability` asserts every entry in `themes/presets.ts` clears the contrast floor its siblings hold, because that invariant has the same shape as the rest. Nothing in the type system enforces it, and a palette that breaks it looks correct everywhere except over the workspace photo (architecture/ui-shell-settings.md). `anchored tips` is the same shape again: it asserts no component hand-places a `role="tooltip"` bubble instead of reaching for the [`anchorTo`](../src/lib/actions/anchorTo.ts) action, because a hand-placed bubble is clipped by its panel's scroll container and the damage only shows on narrow surfaces. `destructive-act ladder` is the third: it asserts no source file re-grows a post-hoc undo channel (`withAction`, `pendingDeletes`, `undoDelete`), because deletion is gated before the act and final after it (architecture/ui-shell-settings.md). A deferred delete dies with the page, lies to every other device for its grace window, and hands a real decision to a 5 second timer. `transcript window` is the fourth: the chat renders a window of the branch, so a surface that resolves `msg-<id>` from the document itself finds nothing for any turn the reader has not loaded back, and on screen that reads as the turn having been deleted rather than as a jump that failed. It scans every shape of that lookup and exempts the two components that own the window (architecture/chat-sessions.md #14). `transcript scroll writes` is the fifth, and it guards the same scroller from the other side: that box glides by its own CSS, so `behavior: 'auto'` defers to the glide rather than overriding it and a scroll meant to land travels instead. It bans the word outright in the two components that scroll it, because the mistake is invisible in the file that makes it and shows up on screen as the story sliding away on its own, and it pins the CSS to that one box in both directions, since the margin wheel rides the same animator (architecture/chat-sessions.md #15). `one house voice` and `shared UI recipes` are the sixth and seventh, and they are the same shape once more: nothing in the type system stops a panel from spelling `...` instead of `…`, hand-rolling its own "5m ago", drawing its own spinner ring or its own switch, and every one of those is invisible in the file that does it and only visible beside the surface it disagrees with. They scan `.svelte` source for the give-aways (a non-spread `...`, a `${n}m ago` template, `navigator.platform` outside `ShortcutsSheet`, `.empty-orb` outside `ui/EmptyState`, a `border-t-transparent` + `animate-spin` pair, `role="switch"` outside `ui/Toggle`, a `var(--color-error, #…)` fallback) with the two deliberate exemptions named in the tests themselves: `MemoryView`'s orb is an intro card rather than an empty state, and the lorebook row's dot carries three natures in its colour rather than two. Both blocks share the `stripComment`/`codeLines` walkers hoisted above them, which the em dash contract already used. `commands` is the eighth, and it reads source for a reason of its own: the composer's command registry reaches the stores, so a runes module cannot be evaluated from a test at all. Three of its failures are silent. A command whose `group` has no section in `COMMAND_GROUPS` is filtered out of the grouped palette, so it exists only for someone who already knows its name; a second claim on a name or an alias shadows the first in the lookup map with nothing saying so; and a spelling carrying a capital, a space or a slash is a row the parser can never produce, readable in the list and impossible to type. Everything else about a command is already derived (the icon type is read off `Icon.svelte`, the group is a union, the palette renders from `COMMANDS` itself), which is why the block is only three tests long (architecture/chat-sessions.md). `shortcuts` is the ninth and the same shape once more, over the key registry beside it: the sheet draws a bound row's chips from its binding, so a key cannot be documented as one thing and pressed as another, and what is left is what fails in silence, which is the whole hazard of a keyboard since nothing on screen says a press did nothing. A second claim on the same combination leaves the later row dead while the sheet still lists it; a row whose group has no section is a key documented nowhere; and `matchShortcut` skips a row with no `run`, so a binding without one is a key the sheet promises and nothing answers (architecture/ui-shell-settings.md).

**Two techniques, and the guard that makes the second one safe.** Where a value can be imported, it is (`PROVIDER_NAMES`, `PERMANENT_TRAITS`, `MACROS`, `AMBIENT_EFFECTS`, `STEERING_ROLES`/`STEERING_SCOPES`, `SYNC_SCOPES`, `PROVIDER_PROFILES`). Where it cannot, the test reads the **source text** and regex-scans it: importing the server's runtime creates its data directory as a side effect, and a `.svelte` file's internals are not importable at all. A text scan that silently stops matching is worse than the coupling it replaced, so both helpers assert they found something before comparing: `scan()` requires at least one capture and `block()` requires the named declaration to exist, each with a "the scan pattern is stale" message. The three whole-tree walks (`src/lib` for settings readers, `src/lib/components` for `data-setting` attributes and for `role="tooltip"` bubbles) assert a non-zero count for the same reason.

The blocks, and the silent failure each one converts:

1. **RPC bridge** (cites `client-data-layer.md #1`, `server-core.md #1`): every `this.call('x')` in [`database.ts`](../src/lib/services/database.ts) must appear in `MUTATION_SCOPES` or `READ_METHODS` in [`server/db.ts`](../server/db.ts). Without it a typo surfaces only at runtime as "Unknown db method". **One-directional on purpose**: the reverse is not asserted, because the server exposes methods the client has no proxy for. The assistant reaches them in-process.
2. **Live sync, scope reachability** (cites `client-data-layer.md #2`, `server-core.md #2`): the vocabulary itself is shared and compiler-enforced, so what this asserts is the thing the compiler *cannot* see: every `SyncScope` in [`shared/sync.ts`](../shared/sync.ts) is broadcast by some mutation or some `broadcastSync` call. A scope nobody broadcasts is dead weight in the client's handler table.
3. **Live sync, reader/reload parity**: the other half of the same failure one layer down. Every file under `src/lib` that calls `readSetting`/`getSetting` must also mention `registerSettingsReload` or `syncReload`; otherwise the write broadcasts, every other device is told, and that one store keeps its boot-time copy until the page reloads. Four of these had accumulated silently before the test existed. **Exempt**: `src/lib/services/database.ts` (it *is* the read) and `src/lib/utils/prompt-builder.ts` (reads per build, so it can never be stale); `.test.ts` files are skipped by the walk.
4. **WebSocket discriminators** (cites `client-data-layer.md #3`, `server-core.md #4`): every `t:` the client transport sends has a matching `msg.t ===` handler in [`server/index.ts`](../server/index.ts). **Exempt**: `'sync'`, which travels server→client only and has no inbound handler by design.
5. **Provider profiles cover the client list** (cites `llm-providers.md #1`): `PROVIDER_PROFILES` names equal `PROVIDER_NAMES`, sorted. Bidirectional.
6. **The server's `ProviderName` union matches the client list**: same equality, read out of the server's type declaration as text.
7. **`ParamPolicy` vocabulary parity** (cites `prompt-pipeline.md #2`, `llm-providers.md #2, #4`): the string literals of `ParamPolicy` + `ResolvedParamPolicy` are compared between the server profile types and `src/lib/types/llm.ts`. A literal on one side only is a policy that mis-branches silently: `'declared'` reaching the client helpers unresolved falls straight through to the `'reported'` path.
8. **Provider allow-list entries are real fields**: every param name in a profile's static `paramPolicy` array is either an `apiField` from [`config/sampling.ts`](../src/lib/config/sampling.ts) or a known non-sampling request field. **Exempt**: the three non-sampling fields `max_tokens`, `max_completion_tokens`, `seed`; the non-profile modules `index.ts`, `types.ts`, `util.ts`, `openai-compatible.ts`; and any profile whose policy is `'reported'`/`'base-only'`/absent, which has no static list to check.
9. **Settings tab union parity** (cites `chungus-assistant.md #1`, `ui-shell-settings.md #2`): the assistant catalog's `SettingsTab` equals the client's in [`settings-pages.ts`](../src/lib/config/settings-pages.ts).
10. **Catalogued settings are routable and highlightable**: every `anchor` in the assistant settings catalog is a key in `ANCHOR_PAGES` *and* appears as a `data-setting="..."` attribute somewhere under `src/lib/components`. Missing the first, the deep link goes nowhere; missing the second, it lands on the right page and highlights nothing.
11. **Ambient render order covers every effect** (cites `ui-shell-settings.md #5`): `EFFECT_RENDER_ORDER` inside `AmbientCanvas.svelte` is compared against `AMBIENT_EFFECTS` **in both directions**, unusually: an effect missing from the order simply never paints, and a stale id left in the order is equally a bug. Everything else about ambient effects derives from the one list; the compositing order cannot, because it carries back-to-front information of its own.
12. **Character field macros are documented** (cites `library.md #1`, `macros.md #1`): every `macro` on a `PERMANENT_TRAITS.character` trait is declared in `MACROS`. Resolution is derived and cannot drift; the macro *reference* is still hand-written, and a field whose macro is missing there resolves correctly but is invisible to every macro-picker UI.
13–15. **Steering vocabulary ×3** (cites `engines.md`, `chungus-assistant.md`, deliberately without numbers): `STEERING_SCOPES`, `STEERING_ROLES` and `STEERING_MODES` in [`server/assistant/registry/workspace.ts`](../server/assistant/registry/workspace.ts) each equal the client list, **order included** (these are `toEqual` on arrays, not sorted sets; the scope ladder's order is meaning). `add_steering` states all three as tool-schema enums and cannot import the client model. `SteeringMode` has no runtime list, so its literals are read out of the type declaration.
16. **The thumbnail convention** (cites `server-core.md #7`): the client asks for a thumbnail by deriving its path from the original's, the server writes it at that path, and the derivation is pure only because the extension is fixed. Both halves declare `THUMBNAIL_EXTENSION` and the test compares them, since the client cannot import server code; a second test holds the client's `THUMBNAIL_TYPE` to that same extension, because bytes of one format under the name of another render fine in an `<img>` and surface nowhere until something trusts the content type. Everything else about the convention was collapsed rather than asserted: the backup inventory and the assistant smoke script call `thumbnailFor` instead of repeating it. A third test in the same block holds both `/files/…` routes to deriving their path through `requestedFilePath` and holds that helper to touching no `node:path`: a URL path is `/`-separated by definition, `normalize` rewrites it into the host's separator, and files.ts refuses that spelling because it reads a thumbnail's location out of the path itself. This one is asserted rather than collapsed because the damage is invisible off Windows: one call turns every picture in the app into broken art there and changes nothing anywhere else, so no reviewer on another OS can see it and no type can hold it.
17. **Per-chat setup** (cites `ui-shell-settings.md`, "A chat claims what it can name", and `prompt-pipeline.md`): what a story runs on is `chatValue ?? appValue`, resolved in `utils/chat-setup.ts` and nowhere else, so the whole block is a scan for second resolutions. Two of its tests list every file that reads an app-wide pointer directly (`personaStore`, then `getActiveEffectivePreset`/`getActivePresetId`) and hold that list to an allow-list of surfaces that are app-wide *by nature*: boot, cross-device reload, the panels whose subject IS the app's answer, the library meters that hold no chat, and the resolver that owns the fallback. Each scan asserts it found something first, or a rename turns it into a test that passes by matching nothing. The persona scan matches the bare **name** rather than `personaStore.`, so the import specifier is itself the reach: counting only call sites lets a chat surface keep the import after its last use goes away, which leaves the next edit one line from speaking as the wrong person. This shape is used rather than a type because the failure is not a type error at all: a chat surface reading the app pointer compiles perfectly and is wrong only in what it says, silently and plausibly, since the persona it names is a real persona and the preset it assembles is a real preset, just not this story's. A third test holds the regex store to taking its preset as an argument (it imports the preset service not at all), which is what stops a preset's rules applying on one surface and not another once "the active preset" has two answers. The rest of the block pins the birth rules, where the damage is a permanent stored pin nobody made: a new chat takes its persona only from the character's seed or the New chat flow, no door pins one to the library's *active* version, and the assistant's chat reads (which run server-side and cannot import the resolver) spell the persona fallback once and reach the app pointer exactly once.
18. **The prompt target** (cites `prompt-pipeline.md #10`): every `AssembleInput` construction site takes its model, budget and post-processing from `resolvePromptTarget` and none resolves a connection itself, and the story generations send on the target they were assembled for. Asserted rather than typed because all three fields are plain values that any site could compute plausibly on its own: the failure is a chat metered against one context window while the send rides another model, with the review dialog naming a third and nothing on screen disagreeing.

## The two-way citation convention

This is a real mechanism, not a formatting habit. **A doc that records a hand-kept coupling links the test that asserts it; the test names the doc and the coupling number back, in its `describe` string.** Both halves are load-bearing: the doc half tells a reader arriving at the coupling that it is enforced and where, and the test half tells a reader watching a red test which doc explains *why* the two declarations exist separately at all. The citing docs are [client-data-layer.md](client-data-layer.md), [server-core.md](server-core.md), [llm-providers.md](llm-providers.md), [prompt-pipeline.md](prompt-pipeline.md), [chungus-assistant.md](chungus-assistant.md), [ui-shell-settings.md](ui-shell-settings.md), [library.md](library.md) and [engines.md](engines.md).

**The hazard is renumbering.** A coupling number is a reference that nothing compiles and nothing validates: insert an item at the top of a `## Hand-kept couplings` list and every `describe` string pointing into that list is now wrong, silently, with the suite still green. Two conventions already work around it and are worth keeping deliberately: `prompt-pipeline.md` appends sub-numbered entries (`1b`, `3b`) rather than shifting the list, and `chungus-assistant.md` numbers its couplings inline in the Maintenance paragraph as `(1)`…`(6)`, which the test cites as `#1`. The steering block cites its two docs with **no** number at all, which is the safe form when the coupling is easy to find by name. Prefer appending, prefer naming; if you must renumber, grep `contracts.test.ts` for the doc filename in the same commit.

## Pure cores: the strategy that makes unit tests possible

Most of the suite is not integration testing at all. It works because subsystems keep their **logic in a pure, injectable module** and their `$state` + persistence in a thin `.svelte.ts` wrapper around it: runes are compile-time macros and nothing compiles them under `bun test`, so anything reactive is untestable by construction. Splitting is what buys coverage, and several source headers say so outright: `calibration.svelte.ts` ("the math lives in `./calibration-core` (pure + unit-tested); this file is only the reactive `$state` + db persistence around it") and `stores/steering.svelte.ts` (resolution lives in the pure `types/steering.ts` "because the generation path resolves the same question against fresh db rows and the two must agree exactly"). The dominant shape is cross-directory (pure logic in `src/lib/utils/` or `src/lib/types/`, reactive wrapper in `src/lib/stores/`), with `calibration-core.ts` the only literal `*-core.ts` in the repo.

**Four files break the rule on purpose**, all by shimming `globalThis.$state` to identity **before** dynamically importing a rune store, which turns its rune classes into plain classes. That is exactly right for pinning state-machine transitions and useless for reactivity, which is not under test. Two of them shim `$state` alone deliberately: a store that grows a `$derived` or `$effect` then fails loudly instead of quietly testing stale values. [`transcript-refresh.test.ts`](../src/lib/stores/transcript-refresh.test.ts) is the exception that shims the whole set it touches (`$state`, `$state.raw`, `$derived`, `$derived.by`), because it loads `chatStore` and the stores around it rather than one lone state machine, and what it pins is the ORDER two overlapping transcript loads publish in (architecture/chat-sessions.md coupling 4), which no derived value takes part in. It stubs the RPC proxy so every read parks on a promise the file settles by hand, since holding two answers in flight and choosing which comes back first is the whole test.

[`chat-setup-birth.test.ts`](../src/lib/stores/chat-setup-birth.test.ts) shims the same set and goes further in one place: `$state.snapshot` clones for real instead of returning its argument, because the library store detaches every entry it hands out through it and an aliasing shim lets a case mutate the store by accident and read its own write back as a pass. It is the client half of per-chat setup driven as a user drives it (architecture/ui-shell-settings.md, "A chat claims what it can name"): one in-memory server behind a stubbed RPC proxy, and then the REAL `chatStore`, `characterLibraryStore`, `connectionStore`, `personaStore`, `presetService` and resolver on top of it, so a birth is `createChat` and a delete is the store method the screen calls. 19 tests over the two rules that fail silently: a character's four New Chat Defaults are SEEDS, so moving one must leave every story already under way where it was and only reach the next chat; and a claim resolves to the app's value while the thing it names is missing without the stored id ever being swept, so restoring a deleted persona, connection, preset or version brings the claim back. The deletes are the real ones (`connectionStore.remove`, `presetService.deletePreset`, `characterLibraryStore.deleteEntry`) and each restore comes back through the door it really would: a settings reload, a re-import under the same name, a row returning to the library.

**A module stub is put back by the file that installed it.** `mock.module` writes into a registry that is process-wide, and one run loads every test file into that one process, so a stub left standing is served to every file that loads after it, in whatever order the platform walks the tree. The failure then lands on one OS and not the other, and inside the file that INHERITED the stub rather than the one that left it, which is the worst shape a failure can take. Three things hold it: each stub is a SPREAD of the real module, so nothing an importer expects can go missing; the restore is registered before the first stub goes in, so a throw during setup cannot leave one standing; and `contracts.test.ts` requires every specifier to reach `mock.module` twice. [`new-chat-flow.test.ts`](../src/lib/stores/new-chat-flow.test.ts) tests `uiStore` that way, and [`prompt-hold.test.ts`](../src/lib/stores/prompt-hold.test.ts) tests the prompt hold gate (what a disarmed gate costs, what an armed one parks, and that a cancel resolves to null, which is every caller's instruction to leave the chat alone; architecture/prompt-pipeline.md). The hold's store answers `fetch` for the length of that file rather than let each switch flip log a failed settings write, and puts the real one back after: what is under test is which gate is armed, not that the write left the browser.

## Tests against a real database

**The real-SQL files are green in a batch, and each one writes to the dir it pinned.** `ServerDatabase` holds ONE handle per process, opened at the first db call, so a file cannot simply pin `CHUNGUS_DATA_DIR` and assume the handle follows: whatever an earlier file opened is still bound to that earlier file's dir. Each of them therefore takes the handle before using it. `serverDb.closeForTests()` runs in `beforeAll` immediately after the dynamic import, which drops any handle left open so this file's first statement binds to the dir it just made; and again in `afterAll` before `rmSync`, because statements against an unlinked database file report `SQLITE_IOERR_VNODE` for the remainder of the run. Miss either call and the failures surface in whichever file happens to run next rather than in the one that caused them, which makes a real regression here read as someone else's. Anything new that opens the real db does the same dance.

These files run the actual SQL rather than a fake: [`server/promptLog.test.ts`](../server/promptLog.test.ts) (5 tests: record/patch/snapshot round-trip, the cap prune, and the boot sweep that settles requests a dead process left in flight), [`server/chatList.test.ts`](../server/chatList.test.ts) (22 tests: chat-list aggregates, the structural fingerprint that must survive an id remap, the search fold that lives half in SQL, and chat duplication), [`server/greetingRefresh.test.ts`](../server/greetingRefresh.test.ts) (19 tests: a card edit reaching the chats that are still nothing but that card's opening, and, mostly, the chats it must refuse to touch, since recognition is the only thing standing between a card edit and text the user wrote) [`src/lib/memory/memory.integration.test.ts`](../src/lib/memory/memory.integration.test.ts) (12 tests: the same pure memory engine with the **real** `MemoryDb` swapped in, driving `memApplyBatch`/`memApplyPromotion`/`memReapEpisodes` through the tree shapes that swipe/retry/branch/delete produce) [`server/personaFloor.test.ts`](../server/personaFloor.test.ts) (9 tests: the last persona cannot be deleted and the active pointer always names a row that exists, driven through `deleteLibraryEntry` because that one method is where both halves live for every caller; architecture/library.md. Its reset helper cannot empty the library, which is the rule under test, so each case builds its cast around the one persona that survives) and [`server/messageSpriteLabel.test.ts`](../server/messageSpriteLabel.test.ts) (7 tests: the server never decides a sprite reading is stale, so a content rewrite, a minor save and a continuation all leave it standing, since re-reading costs a call and is the user's setting; plus that writing a reading is not an edit, and that a duplicated chat carries its readings) and [`server/messageLorebook.test.ts`](../server/messageLorebook.test.ts) (4 tests: a turn's lorebook trace round-trips with its evidence, survives a duplication, and reads as untraced rather than taking the transcript down with it when the cell will not parse) and [`server/importChat.test.ts`](../server/importChat.test.ts) (4 tests: an imported story lands whole in one call, at a size no one plays; and, the half nothing on screen would reveal, that a row which cannot land rolls the whole import back rather than leaving the messages behind under a chat pointing at none of them, which lists with a message count and opens empty. An imported chat is the one write whose size a stranger's file decides, so a per-row loop is both minutes of round trips and atomic in the wrong unit; architecture/chat-sessions.md) and [`server/siblingIndex.test.ts`](../server/siblingIndex.test.ts) (6 tests: a new row's index is asked per chat, so a brand new chat starts its roots at 0 instead of numbering them off the highest root anywhere in the install. Every chat's roots share the same NULL parent, and the leak shows on no screen (an index is read as an ordering inside its own sibling set), which is why it needs a test rather than an eye) and [`server/importSources.test.ts`](../server/importSources.test.ts) (5 tests: the import ledger's SECOND write, which is the one that matters. A source file arrives twice only because somebody asked for it and it becomes a new library entry each time, so the claim has to name the entry that exists now; a first id left standing would point at a deleted row for good and hand the reader that file again on every run, since the confirm card drops a claim whose entry the library no longer holds. Also that a claim carrying no entry cannot blank one already there, and that re-claiming adds no second row) and [`server/defaultCharacters.test.ts`](../server/defaultCharacters.test.ts) (6 tests: the example characters this build actually ships are seeded with their art on disk and their pack labelled from its filenames, and then the rule that matters, that a second boot adds nothing and a deleted one never returns. The ledger keys on the bundle id and the seeder never reads the library, which is what a character the reader writes under the same name pins: it is left alone, not merged with or overwritten by a later boot. A malformed ledger throws rather than re-seeding, since handing back a deleted character is the failure). It runs against the **real** `defaults/characters/` folder rather than a fixture, so a broken card file fails here instead of on a first-run install. It is also the one file that reads `IMAGES_ROOT` out of config instead of the dir it pinned: the database rebinds per file and that const does not, so assuming the pinned dir passes alone and fails in the suite. And [`server/commitGeneratedTurn.test.ts`](../server/commitGeneratedTurn.test.ts) (7 tests: the method that writes a story turn now that a generation outlives the page which asked for it. Every case is a situation the client could not previously reach, because its composer was locked for the length of a generation and these all need a reader who moved on while the model was writing: the leaf stays put when they walked to another branch, a deleted chat lands nothing without being an error, a deleted parent throws rather than leaving a stray root, a second opening claims no root and renumbers nothing, and the one-shot steering note that rode the turn is spent in the same transaction while one edited to permanent meanwhile is left alone. The missing `created_at` this suite caught on its first run is why it exists at all).

Two more of them cover per-chat setup where only real SQL can answer (architecture/ui-shell-settings.md, "A chat claims what it can name"). [`server/perChatSetup.test.ts`](../server/perChatSetup.test.ts) (19 tests: each of a character's four New Chat Defaults rides BESIDE `data` in the entry payload, so none mirrors into a version row or reaches a card export, and each is written only when set, which is what lets an entry that carries none store byte for byte what it stored before the fields existed and spares every install a migration; plus that a chat born with a claim keeps it, which is a claim about the INSERT and fails silently, since the row lands, the chat opens, and the choice the reader made is simply not there). [`server/perChatSetupUsage.test.ts`](../server/perChatSetupUsage.test.ts) (14 tests: the server's own doors. The assistant's `create_chat` answers all four of a character's New Chat Defaults exactly as the composer does: the version pin by the same rule (the character's chat-default version while it exists, else the FIRST version made, never the library's active one), and the other three as claims on the new chat, down to a character naming none of them producing no blob at all rather than a row of nulls. That agreement is the point of the block: answer fewer of the four on one door and the same character started two ways becomes two stories, with nothing on either screen saying why; a duplicate carries the whole feature blob and the version pin verbatim, because a copy that re-derived its setup from the character would answer the CURRENT defaults and play the copy as somebody else; and the persona rule's second spelling in `assistant/registry/chat-reads.ts`, which the server needs because it cannot import the resolver, resolves the chat's own claim first, falls back to the app's when that persona is deleted without ever sweeping the stored id, reads a blob that predates claims (and one that will not parse at all) as following the app, and keeps an orphaned chat's claims when its character goes).

**The backup suites are the exception to that dance and say why in their own headers.** [`server/backup/backup.test.ts`](../server/backup/backup.test.ts) is the only file that checks WHERE a database ended up, since the snapshot code resolves the data dir per call, and releasing the handle settles which dir `serverDb` writes to rather than what a second connection resolves. It therefore builds the real schema through its own connection and re-pins both env vars per test. [`server/backup/restore-swap.test.ts`](../server/backup/restore-swap.test.ts) goes further and never touches `serverDb` at all: a restore replaces the database FILE, and a process that has opened the live handle can never do that (architecture/backups.md), so it reproduces the boot state rather than working around it. `serverDb.createdSince` is covered in `chatList.test.ts`, which owns that singleton legitimately.

**The mechanism that keeps their writes out of real user data is a lazy binding, not a mock.** `ServerDatabase` in [`server/db.ts`](../server/db.ts) holds a `_db: Database | null` and opens it on first *use*, calling `config.resolveDbPath()` at that moment, and `resolveDataDir()` reads `process.env.CHUNGUS_DATA_DIR` on every call rather than closing over an import-time constant. Each test file therefore does the same dance in `beforeAll`: `mkdtempSync` a throwaway dir, assign `process.env.CHUNGUS_DATA_DIR`, `await import('./db')`, and then `closeForTests()`; `afterAll` calls `closeForTests()` once more before `rmSync`. **The two halves answer two different failures and neither substitutes for the other.** Deferring the binding to first use is what stops a path being frozen at import, which would silently send every one of these writes into the real `user-data/`. Releasing the handle is what makes the dir a file pinned the dir that file actually gets, since `bun test` shares one process and the first opener would otherwise hold the binding for the whole run. The migration lines that scroll past during `bun test` are this working: each throwaway database is built by running the migrations. The server calls `open()` at boot so a broken database still fails at startup rather than on first request.

That covers the schema being VALID; it says nothing about what a migration is allowed to do to a database that already holds someone's stories, which is what a backup system rests on: restoring an old snapshot is not a special path, it is the upgrade path a user who did not open the app all year would take anyway. [`server/schema-upgrade.test.ts`](../server/schema-upgrade.test.ts) holds that line with one rule: **a migration only moves data when it was decided there**. Migrations are structure alone apart from an explicit `DATA_MIGRATIONS` list, so one that starts rewriting rows fails the test until someone adds it by name and says why it is safe to run twice, and an entry on that list earns its own case proving what it touches and what it leaves alone. It imports `MIGRATIONS_FOR_TESTS`, which only `backup/backup.test.ts` may import besides.

Note the asymmetry: `DATA_DIR` and everything derived from it (`IMAGES_ROOT`, `PRESETS_DIR`, …) *are* import-time constants in [`server/config.ts`](../server/config.ts). Only the database path is late-bound. Code that needs a redirectable path in a test must go through `resolveDataDir()`.

## The registry smoke script

[`server/assistant/registry/smoke.ts`](../server/assistant/registry/smoke.ts) is the assistant's regression net and is **not part of `bun test`**: it is a standalone `bun` program, not a `bun:test` file, with its own `check()` counter and a `process.exit(fail === 0 ? 0 : 1)`. It seeds a whole workspace (personas, a character with portrait and gallery, a chat with a real message tree, PNG bytes on disk) and then drives every capability plus its edge cases through `dispatch()` exactly as the assistant loop would, across 33 labelled sections: schema and data model, reads/find, orphan binding, validation, create/edit/set, chat reads and paging, memory state, summary rewrites, approval previews, the two save doors and memory pricing, lorebooks, destructive deletes, the settings catalog behind its Navigation gate, skills, navigate, the image consent gate, the capability families, entry-art editing, attachment reaping, character versions, workspace actions, greetings, `create_chat`, steering, connection state, prompt trace, attached files (recognition, the room-bounded reads, session scoping, and that a crafted file cannot forge a freshness claim through a read result), subtree delete, branch awareness, and state freshness (every producer's `stateRevs` stamps, revision motion per editable field derived from `ENTITIES`, and the staleness-note lifecycle). **540 checks at the time of writing.** It reaches outside the registry for exactly two things: `needsApproval` from [`loop.ts`](../server/assistant/loop.ts), because that one function IS the approval policy (a threshold on the read < write < delete ladder, architecture/chungus-assistant.md) and a wrong answer means a call runs having never been shown; and the stamp/check functions of [`server/assistant/freshness.ts`](../server/assistant/freshness.ts), because the per-turn staleness note is otherwise exercised only by the loop, which nothing tests.

It stays outside `bun test` because it is a single stateful narrative, not a set of independent cases: later sections deliberately depend on earlier mutations (the chat-context section reads persona bindings written by the orphan-binding proof; the steering section relies on a version pinned by the versions section), it writes real image files under `IMAGES_ROOT`, and it needs the whole data directory redirected from the environment *before the process starts*, which the lazy-db trick above cannot help with, since `IMAGES_ROOT` is import-frozen.

Run it against a throwaway directory, never the real one:

```
CHUNGUS_DATA_DIR=<tmp> bun server/assistant/registry/smoke.ts
```

It creates the directory tree, so an empty path is fine; delete it afterwards. It starts no server and binds no port.

## What is deliberately not tested

Naming these honestly is the point: they are decisions, and treating them as gaps invites the wrong fix.

- **Everything rendered.** No component, DOM or visual test exists, and no runner capable of one is installed. `.svelte` files are only ever read as *text* (by `contracts.test.ts`, for `EFFECT_RENDER_ORDER` and `data-setting` attributes). [chat-sessions.md](chat-sessions.md) says it outright for the message timer: "UI behavior here has no test coverage: the user tests manually." Anything DOM-shaped is excluded by signature rather than by policy: `findMatchRanges(root: Element, …)` in `utils/chat-search.ts` cannot be reached, so only its pure sibling `buildSearchRegex` is covered.
- **The assistant loop.** No test drives [`server/assistant/loop.ts`](../server/assistant/loop.ts); `smoke.ts` imports exactly one pure function out of it (`needsApproval`) and otherwise covers the registry the loop calls, never the loop's own iteration, cancellation, approval-gate wiring or prompt-cache behavior.
- **Live provider calls.** Nothing in the suite reaches the network. `openai-compatible.test.ts` scripts SSE from a local endpoint to prove framing and inline-reasoning extraction, mounts a fleet of further local servers (`/v1`-only, root-mounted, an HTML-everywhere web UI, an auth wall, a redirecting /models, a chat-only proxy, a movable mount) to prove BYO base-URL resolution, and records one completion body to prove each reasoning dialect becomes its documented wire field and that a request-carried policy cannot override a profile's own; a silent endpoint (accepts, answers never) and a slow-to-start stream carry the other half, which is that nothing but the reader's Stop bounds a non-streamed completion and that a reply which begins late still lands whole, while `net.test.ts` pins the primitives under both (an idle bound that measures silence rather than total time, a headers deadline that is a backstop rather than a verdict); the other providers' profiles are checked only as vocabulary by `contracts.test.ts` and are never exercised against a real API. This is the correct trade: a test that needs a key and a quota is a test that gets skipped.
- **The test files themselves**, by both type-check passes (see above), and `src/service-worker.ts`, which falls through both for reasons [build-packaging.md](build-packaging.md) owns.
- **Packaging.** `bun run package` has no test; the portable build is verified by running it.

## Before touching this

- A hand-kept coupling that gains a test gains a citation in **both** directions in the same commit: the doc links `contracts.test.ts`, the `describe` string names the doc. A coupling collapsed into a single source loses its test *and* its doc entry, and the doc says "not hand-kept" so nobody re-adds it.
- Never let a source-text scan compare without first asserting it matched. Use `scan()`/`block()`; a new whole-tree walk asserts its own non-zero count. A regex that quietly stops matching turns a contract test into a green test that checks nothing.
- Never point a test at the real database. Set `CHUNGUS_DATA_DIR` to a `mkdtemp` dir in `beforeAll`, import the db module **after** it, dynamically, then call `serverDb.closeForTests()`; call it again in `afterAll` before `rmSync`. A static top-level import of `server/db` defeats the lazy binding for that file, and a missing release hands the file whichever dir an earlier one opened.
- Keep the pure cores pure. No db, no stores, no runes, no Svelte imports: the moment logic moves into a `.svelte.ts` wrapper it stops being testable, and the meters-vs-generation class of bug this design prevents comes straight back.
- **A new walk over the message tree gets a case at 100,000 turns**, beside the ones already in `message-tree.test.ts` and `story-map-layout.test.ts` (architecture/chat-sessions.md). A chat's depth is the length of the conversation, so a recursive walk makes stack depth user data and a long enough story throws `RangeError` where nothing catches it. That size is chosen against the engines rather than against any real chat: it is several times the deepest recursion JSC allows and an order of magnitude past V8's, so no recursive implementation can pass it whichever runtime runs the suite. The same case catches the quadratic half (a per-turn `unshift`/`splice`) by running in well under a second.
- **A file that stubs a module puts it back**, as a spread of the real one, with the restore registered before the first stub. The registry is process-wide and the walk order is not, so a stub left standing fails on one OS and inside somebody else's file. `contracts.test.ts` counts the restores.
- A new capability or a change to `dispatch()` semantics belongs in `smoke.ts`; it is the only coverage the assistant registry has.

## Hand-kept couplings

1. **Coupling numbers in `describe` strings ↔ the numbered lists in `architecture/*.md`.** Nothing compiles or validates these references. Renumbering a `## Hand-kept couplings` list (or the inline `(1)`…`(6)` rules in `chungus-assistant.md`) silently invalidates every citation into it while the suite stays green. Append (`1b`, `3b`) or cite by name instead; if you renumber, grep `contracts.test.ts` for the doc filename in the same commit.
2. **The scan regexes in `contracts.test.ts` ↔ the exact source syntax they read.** Reformatting `MUTATION_SCOPES`, `READ_METHODS`, a `ParamPolicy` declaration, `EFFECT_RENDER_ORDER`, `ANCHOR_PAGES` or the mirrored steering arrays can break a pattern without breaking the code. The `scan()`/`block()` assertions turn that into a loud failure. Do not weaken them.
3. **Both exempt lists ↔ reality.** The settings-reader walk exempts `services/database.ts` and `utils/prompt-builder.ts` by path; the allow-list scan exempts `max_tokens`/`max_completion_tokens`/`seed` and skips four non-profile modules by filename. Renaming or moving any of them turns an exemption into a silent no-op or a false failure.
4. **`resolveDataDir()`'s late binding + `closeForTests()` ↔ every db-backed test's `beforeAll`/`afterAll`.** Freezing the db path at import time (or having a test import `server/db` statically) sends that file's writes into the real `user-data/`; skipping the release binds the file to an earlier file's dir and breaks whichever file runs after it, not this one. Every file that does this dance carries the comment explaining why; keep it with the code.
5. **`smoke.ts` ↔ the capability registry.** It asserts exact tool counts (35 with every family on, 32 with the default set) and exact enum contents, so adding a capability fails it until the counts are updated, which is deliberate, since a new tool should be a considered change. It is not in `bun test`, so nothing reminds you: run it.
6. **Test-file exclusion ↔ both tsconfigs.** `src/**/*.test.ts` and `server/**/*.test.ts` are excluded from type-checking on purpose. A test moved outside those globs starts being type-checked and will fail on the `any`-typed db handle.
