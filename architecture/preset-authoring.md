# Preset authoring: architecture & maintenance

Two surfaces over one `PromptPreset`, split by who is holding it. A preset is somebody's work that somebody else downloads, so both halves are built around one idea: **everything the author has to say has a place to be said, and every one of those places is separate from what the model reads.** Item notes, control help, advice badges, option rationales, section descriptions and the preset's own byline are all authored here and none of them reach a prompt. **Prompt Builder** ([`PromptBuilderView.svelte`](../src/lib/components/promptBuilder/PromptBuilderView.svelte), a Settings → Advanced page rendered through `SettingsPageView`) is the authoring half: it edits the item list, the controls, and the per-preset options, and it is the only place any of those can be changed. **Preset Controls** ([`PresetControlsView.svelte`](../src/lib/components/presetControls/PresetControlsView.svelte), a chat-area overlay in `uiStore`'s choreography) is the reading half: it renders the widgets the author published and writes nothing but reader state (their **values** and which setup they adopted as baseline). **Both surfaces always speak for the app**, and neither follows the open chat: each names `getActiveEffectivePreset()`, each switches `activePresetId`, and a chat that has claimed a preset of its own is announced with a `ChatOverrideNotice` at the top of the sheet and changes nothing else here (architecture/ui-shell-settings.md). The claim is made in the composer's setup chip and only there, so no preset surface grows a second door onto per-chat state; the cost is real and deliberate, since tuning the controls of a preset only one chat runs means switching the app onto it first. No item, control or option is reachable from it. Both mount [`PresetManager.svelte`](../src/lib/components/presets/PresetManager.svelte) for the preset **lifecycle**, so a reader can still duplicate, import, export, delete and factory-restore presets; only the authoring verbs are gated. What a preset *is* (the JSON shape, the draft-over-committed rule, assembly, the budget trim, the server-side field whitelist) belongs to architecture/prompt-pipeline.md; the REST endpoints and the `presets/` + `presets/temp/` files to architecture/server-core.md; the settings shell, page routing and the shared CSS recipes to architecture/ui-shell-settings.md. This doc owns the editors.

**The item list** is the builder's primary surface. A `PromptItem` ([`types/database.ts`](../src/lib/types/database.ts)) is `{ id, name, role, content, enabled, note? }` and ordering is array order. There is no sort key. **`note` is the one authored field on this page that assembly never reads**: everything else an author types here becomes prompt, so it is the only place to write "don't touch this unless you know what it does" without writing it to the model as well. It lives at the bottom of the expanded row under a "never sent" label, and a row carrying one shows an annotation glyph so it is findable without opening every item; clearing the box drops the field rather than storing a blank. **The `id` is runtime-only**: `presetService.hydrate` mints a fresh `crypto.randomUUID()` on every load and `strip` drops it before the wire, so item ids differ between reloads and between devices, and nothing may key persistent state on one. `addNewItem` appends an empty `system` item and auto-expands it, `deleteItem` filters it out and closes its row, `toggleItem` flips `enabled` (a disabled row dims via `.pb-row-main.is-off`, leaves the enabled-token total, and never reaches assembly). There is **no per-item duplicate**: duplication exists only at preset level, in `PresetManager`. **Reordering** rides `svelte-dnd-action`'s `dragHandleZone`/`dragHandle` pair: only the lead grip starts a drag, because whole-row dragging was tried first and the library's 3px threshold ate ordinary slightly-sloppy clicks as micro-drags. Items and controls are separate zones with distinct `type`s (`pb-items` / `pb-controls`) so neither list can receive the other's rows. `consider` mutates the working copy only (and collapses just the dragged row, so its placeholder gap stays compact); `finalize` is what writes the draft. `transformDraggedElement` strips `[data-item-body]` from the drag preview so an open row doesn't drag a full editor around.

**The per-item token readout** has two arithmetics behind one button. `showExpandedTokens` is component-local and unpersisted. In **Raw** the row shows `countTokens(item.content, activeModel)` (authored text, no calibration) and the header total is the plain sum over enabled items. In **Expanded** the row runs `resolveItem(item, macroContext, activeModel)`, sums all four buckets and scales by `tokenCalibration.ratioFor(activeModel)`, showing the delta over the calibrated raw size as a separate `+N` (architecture/tokenizer-debug.md owns the calibration); the header total then comes straight from `assemblePrompt(...).breakdown.total × ratio`, which is what keeps it equal to the composer's chip for the same chat. The toggle is wrapped in a `MockupTip` whose [`RawExpandedMockup`](../src/lib/components/mockups/RawExpandedMockup.svelte) carries a note fixed in **both** animation states ("always sent with macros resolved"), because the misread it exists to kill is "Raw means my macros won't resolve".

**The unbound-macro lint** is the builder's other reading of item content. `providedMacros` is `SYSTEM_MACROS` (the engine-owned names, derived from `MACROS`) plus this preset's own non-blank control macros; every name `extractMacroNames` finds outside that set is reported as unbound: a warning icon on the row, a count chip in the section header, and an inline sentence under the textarea saying it will appear literally. Memory-flow macros (`{{batch}}`, `{{episodes}}`, …) are correctly flagged, since nothing fills them in a preset item. The **parameterized history macro** is the one name a set lookup alone cannot judge, so the lint runs `cappedHistoryTurns` first: `{{chatHistoryLast20}}` passes even though it is in no set, and the bare placeholder `{{chatHistoryLastN}}` is flagged, because that is the spelling that ships literal (architecture/macros.md).

**Controls** are the half nothing else documents. A `PromptControl` is `{ id, macro, label, help?, advice?, group?, type }` plus a type-specific tail, and the **`macro` is the entire binding**: an author drops `{{macro}}` into any item's content and the reader's value lands there. Eight types: `text`, `textarea`, `toggle`, `slider`, `range`, `select`, `radio`, `tags`. [`utils/prompt-controls.ts`](../src/lib/utils/prompt-controls.ts) is the one place a control's meaning is decided, and it holds exactly three functions over the same union: `getControlDefaultValue` (the author's default), `getControlValue` (a stored raw value coerced to the control's type, falling back to the default), and `formatControlForPrompt` (the typed value → the string injected into the prompt). The reader UI calls the first two, `resolveCustomControl` in [`macros.ts`](../src/lib/macros.ts) calls the third; forking either side is how the widget and the prompt start disagreeing. Injection per type: text/textarea apply the optional `textTemplate` at its `{{value}}` placeholder and **inject nothing at all when the text is blank**, so a framing label ("Extra rules: …") can never dangle over an empty field; toggle injects `onText` or `offText`; slider applies `sliderTemplate` or falls back to the bare number; `range` carries a `[low, high]` pair along the slider's own `min`/`max`/`step` track and fills `rangeTemplate`'s `{{min}}`/`{{max}}` (bare `low–high` with no template), with `orderedRange` clamping into the track and putting the low end first so no template ever sees an inverted span; select/radio inject the chosen option's `injectedText`; tags join every selected option's `injectedText` with `tagSeparator` (default `', '`), skipping empties.

**Three of a control's fields are addressed to the reader and never to the model.** `help` is free prose at any length (a textarea in the editor, `white-space: pre-line` wherever it is shown) because what an author wants to say about a knob is usually a paragraph, and **it is read from behind an info icon beside the label unless the author asks otherwise**: `helpInline` is the opt-out, absent on every preset that never thought about it. A page whose cards each print a paragraph is a page nobody scans, so the default is the fold and `helpInline: true` is what an author reaches for on the one control whose prose has to be met before it is touched. The icon is drawn **only** when there is prose to open. A blank or whitespace-only `help` renders neither form, since an icon opening on an empty bubble is worse than no icon. It is the shared [`InfoTip`](../src/lib/components/ui/InfoTip.svelte), which is why the bubble keeps `pre-line`: the text inside it is a stranger's paragraph, not our own one-liner. `advice` is one of four badges (`recommended` / `optional` / `advanced` / `troubleshooting`) sitting beside the label, which is the thing preset authors most want to say and previously had nowhere to put. `PromptControlOption.description` is the sentence explaining why a reader would pick that option over its siblings; a radio group whose options carry one **becomes a column of cards instead of a row of pills**, because a row of pills with paragraphs in them is unreadable, while a select shows only the selected option's line beneath it and tags carry theirs as a tooltip. None of the three reaches `formatControlForPrompt`.

**`tags` is the one control that takes text the author never wrote.** With `allowCustom`, the reader's own entries live in the same value array as the option ids and are told apart by lookup: an entry matching an option injects that option's `injectedText`, and an entry matching nothing injects **verbatim** when `allowCustom` is on and **nothing at all** when it is off, which is also what makes a stale id from a deleted option stay silent instead of leaking into the prompt. That is what lets one control be "here are twenty-five phrases I'd ban, add your own".

**Control values are global, not per-chat**: a single `presetControlValues` settings row behind [`presetControls.svelte.ts`](../src/lib/stores/presetControls.svelte.ts), keyed by **macro name**. That is a design decision with consequences an author has to know: one set of values serves every chat and every branch, switching the active preset does not switch values, two presets that happen to use the same macro name share one value, and renaming a macro orphans the old key (the store never prunes, so the old value sits there inert until the name comes back). Five sites read the pair `{ controls, customFields }` into a `MacroContext`: [`prompt-builder.ts`](../src/lib/utils/prompt-builder.ts) (generation, and the only one that reads the settings row **fresh**, via `readPresetControlValues()`), [`live-macro-context.ts`](../src/lib/utils/live-macro-context.ts), `InputArea.svelte` (chat meter), `PromptBuilderView.svelte` (builder breakdown) and `memory/store.svelte.ts`, the last four all off the store's reactive cache, the same deliberate db-vs-cache split lorebook resolution uses.

**A control can never shadow the engine.** `resolveMacro` handles structural, parameterized, system and per-field character macros first and only then falls through to `resolveCustomControl`, so a control named `user` is simply ignored at resolution time. The builder is what makes that visible: `macroError` rejects a blank macro, any name in `RESERVED_MACROS` (**every** `MACROS` entry, flow macros included: `batch` is refused as firmly as `char`), and a name another control in the same preset already took. The error paints a red icon on the row, a red input border and an inline message, but it **does not block saving**: a broken control persists happily and just resolves to nothing.

**Sections are a real thing the preset owns**, not a string that happens to repeat. A `PromptSection` is `{ id, title, description?, icon?, collapsed? }` and `preset.sections` is an ordered array: that array is the order a reader meets them in, the heading text, the sentence under it, and whether it starts folded. The join is deliberately loose: **a control names its section through `group`, which holds a section `id`**, and a group nothing declares still renders, under its own name, after every declared one. That is what lets sections be added to a preset without touching a single control and lets a preset that declares none behave exactly as it always did. There is no migration anywhere, and none is needed. A section's `id` is **read-only once created** (renaming it would cut every control referencing it loose at once, silently), while `title` is free text. Two authoring affordances hang off the same derivation: a declared section no control names shows a warning count and an inline note, since it will never render; and every group the controls use but nobody declared is offered as a one-click "adopt" chip under the list. Deleting a section deletes the heading and **leaves every control's `group` alone**: the grouping survives, it just loses its title. `icon` is not a free registry key but one of the curated names in [`config/section-icons.ts`](../src/lib/config/section-icons.ts): the value arrives inside a downloaded preset, and `isSectionIcon` is what stops a stranger's typo from reaching the icon renderer as an unknown key.

**Setting kits** (`PromptPresetBundle`: `{ id, name, description?, values }`) are named snapshots of every control value, adopted by a reader in one click. They exist because an author with three good configurations was otherwise shipping three near-identical preset files that drift apart the moment one is improved. A kit is only ever made by **capturing**: [`BundleListEditor`](../src/lib/components/promptBuilder/BundleListEditor.svelte) reads every control's effective value through `getControlValue`, so a kit is complete rather than partial (a kit naming only what the author had touched would leave everything else wherever the reader had it, which is not the configuration being vouched for) and can never name a macro no control owns. A control added **after** capture is the one hole that model leaves, so the editor counts each kit's uncovered macros, flags them on the row, and withholds the "Current" state from any kit a recapture would change.

**The reader's page holds exactly one baseline, and the kits grid is its picker.** It is a leading **Defaults** card (every control as the author built it; the defaults are a configuration the author authored too) plus one card per kit, with exactly one lit. It is a `radiogroup` of **equal cells**, not content-sized chips: `auto-fit` columns over a `min(15rem, 100%)` floor with stretched rows, so three kits with very different names and blurbs still read as siblings instead of a stubby box beside a wide one wrapping into a ragged grid. Every card carries the same anatomy (a mark in its own fixed column, then name and blurb in the second), and the mark's slot is held whether or not it is filled, so picking a card never shifts a word of its text. Which one is lit is **stored, never value-matched**: `presetControlsStore.appliedSetups` (settings key `presetAppliedSetups`, preset id → kit id, absent = Defaults). Deriving it from a match would flip the row to "nothing applied" the moment one knob moves and leave reset pointing at two different configurations at once, the failure this whole design exists to prevent. Clicking any card **adopts that configuration wholesale**: the kit's value is written for every macro it names and every other macro this preset's controls own is cleared back to its default (`applyValues(writes, clears)`, one write, one broadcast), so adopting always lands with zero drift and a kit that predates a control puts that control on its default rather than leaving it wherever the reader had it. Only the preset's own macros are touched: values are global, and another preset's are not this page's to clear. Everything that says "changed" then measures against the lit card and returns to it: the status line names the baseline it counted against, per-card Reset re-writes the kit's value where one is named and otherwise `clearValue`s, and Reset-all re-adopts the lit baseline without ever changing which one is lit. A stored kit id naming no bundle (the author deleted it, possibly only in a draft) **derives to Defaults on screen and is never pruned**: pruning would turn an unsaved authoring delete into permanent loss of the reader's selection, while an orphan sits inert until the kit comes back. A kit the author has edited since the reader adopted it shows as drift against the kit's *current* values (the page derives from the effective preset, drafts included); the reader re-adopts with one click, which is the honest alternative to silently rewriting their stored values. There is deliberately **no author-declared starting kit**: the per-control defaults *are* the starting configuration by definition, a freshly imported preset opens on Defaults, and an author who wants readers to start elsewhere writes it into the defaults. A second "initial" source would either auto-write global values on import or light a card whose values are not in effect, both of which reopen the two-baselines confusion.

**The preset's identity** (`PromptPresetMeta`) is author / version / description / writtenFor / cover, authored in [`PresetIdentityEditor`](../src/lib/components/promptBuilder/PresetIdentityEditor.svelte) and read as the header of Preset Controls. **A cover is a 3:4 portrait** (a book cover, not an avatar), and that ratio is declared in three places that must agree: the reader's `.pcv-cover`, the author's `.pi-cover`, and `COVER_WIDTH`/`COVER_HEIGHT` in [`presetCard.ts`](../src/lib/services/presetCard.ts). All three fit the same way (`object-fit: cover` on screen, `cropToPng`'s centre-crop when writing the card), so an author frames a picture once and every surface crops it identically; the upload itself is stored untouched, so re-framing later costs nothing. `cover` is the only non-text field and the only one with a lifecycle: it is a stored image path (`images/presets/…`), so **it is deliberately absent from the interchange document**. A path means nothing on another install, and a cover travels by being the picture a PNG card *is* (architecture/sillytavern-interchange.md). Uploading writes the new path and deletes nothing; `dropUnusedCover` in the view runs on **Save** (drop the one that was replaced) and on **Discard** (drop the one that was never adopted), because the file the draft replaced may still be the committed preset's, and deleting it at upload time leaves Discard restoring a preset whose picture is already gone. `deletePreset` and `restoreDefaults` take covers with them for the same reason: they are files, and the server's row wipe cannot see them. **A bundled default preset ships its cover as the picture lying next to it.** `defaults/presets/` is read as a folder rather than a list ([`server/files.ts`](../server/files.ts)): every `<id>.json` in it is a default preset, and an image file under the **same name** (`<id>.png`, `.jpg`, `.jpeg`, `.webp`) is that preset's cover. A preset with no picture beside it ships faceless, which is a valid thing to ship. The shipped document still carries no `cover` of its own: `ensureDefaultPresets` copies the art into `images/presets/` under a **fresh id** and writes that path into the seeded preset. The fresh id is load-bearing. `restoreDefaults` deletes the covers the wiped presets named *after* the server has re-seeded, so a fixed filename would have the wipe take the new copy with it and leave the restored default pointing at nothing. It writes no thumbnail, and the picture answers thumbnail requests for itself (architecture/server-core.md), which is why a shipped cover belongs at `COVER_WIDTH`×`COVER_HEIGHT`: no surface renders one wider than 10rem, the card writer crops at exactly that size, and a picture shipped larger is carried whole into every slot that draws it.

**A preset carries its own regex rules.** `preset.regexRules` is a `RegexRule[]` shipped inside the document, so a preset that instructs the model to print panels also ships the rules that style them and looks right the moment it is imported. A carried rule is a whole rule, **depth bounds included** (architecture/prompt-pipeline.md), and that is the answer to the cost of a preset that prints story state: the block is a full snapshot, so a prompt-scope rule at `minDepth: 2` sends the newest one and strips it from every reply behind that. It is the one part of such a preset the items themselves cannot express, since a prompt item says the same thing on every turn. [`CarriedRegexEditor`](../src/lib/components/promptBuilder/CarriedRegexEditor.svelte) is where they are authored, through the **same** [`RegexRuleEditor`](../src/lib/components/regex/RegexRuleEditor.svelte) the Regex page mounts for the reader's own rules, one editor with two mounts, since a rule is the same object wherever it is written and a second implementation of the fields would be a second thing to keep in step. A row expands into it, and the list drags (`dragHandleZone` type `pb-carried`), because order is configuration: carried rules run after the reader's own and each sees the previous one's output. Three doors add one (write a blank, copy one of the author's own rules, or import a file), and **the middle one copies, never links**: a preset has to be self-contained, so a later edit to the personal rule must not silently change what everybody downloaded, and the copy gets a fresh id. The picker is an **in-flow disclosure rather than a popover**, for the same reason `MockupTip` portals to `<body>`: this page spends most of its life inside a dock whose ancestors clip, and a list that opens downwards there opens with its bottom half cut off. Removal is inline and unconfirmed, unlike the Regex page's own rules: this one edits a draft, and Discard is the undo.

**The draft is live, and that includes these.** `regexRulesStore.carried` reads `getActiveEffectivePreset()`, which is draft-over-committed, so an author's half-typed carried rule rewrites their own transcript and meters as they type, the same rule the rest of the builder follows, and the reason Discard is a real action. A pattern that cannot compile is skipped by `compile()`, so the live surface only ever moves for a pattern that is valid but unfinished. `normalizeCarriedRules` accepts our own shape or a SillyTavern script through the same parser the settings page uses, but **keeps a declared id** and mints a fresh unique one only for an entry that declares none, because the reader's per-rule switch is stored against that id; it runs at parse time only, so the minted id then travels inside the document and is stable from that moment.

**A carried rule's switch means the same thing on both sides, and the reader's copy of it is a deviation.** The author's switch is the position the rule **arrives in** (ship the optional flourishes off and a reader turns on the ones they want), and `regexRulesStore.carriedOverrides` (inside the `regexRules` settings blob, architecture/client-data-layer.md's settings spine) records only where a reader disagrees. It is **sparse on purpose**: an absent key follows the author's `enabled`, so a preset that flips a default in its next version reaches every reader who never had an opinion, and a flick that lands back on the author's value **drops the key** rather than freezing today's default into this install, the same override contract `continuePrompt` implements one section down. `carriedRuleEnabled` is the one answer both the store and the engine give. Two consequences worth stating: a duplicated preset shares rule ids with its source (`clonePresetBody` keeps them), so a reader's switch follows the duplicate, which is also what lets it survive re-importing v2 of a preset under a fresh preset id; and an override naming a rule the author has since deleted sits inert and is never pruned, exactly like an orphan `presetAppliedSetups` entry. The rules themselves stay the author's: the Regex page renders them as a group under "From «preset»" where a reader may move the switch, open the rule, and copy it into their own list, but never edit the preset's copy. **Opening one mounts the same `RegexRuleEditor` with its fields frozen and its tester live**, which is the honest form of "what is this stranger's find & replace doing to my story". Reading a pattern proves very little, and the tester's "Use the last reply" button puts the chat's own last AI turn in the sample box. **Copy to my rules switches the preset's copy off** in the same click and says so beside the button: a copy that ran alongside its original would apply the same rewrite twice.

**And `PresetControlsView` says the rules exist**, in a strip under the identity block: how many the preset ships and how many of those rewrite what is sent to the model, with a link onto the Regex page. Above the controls rather than among them, because it is something the preset does to every chat whether or not it exposes a single knob, and it is the reason a preset with no controls at all still has something to say on this page. The count is **what the document ships**, not what is currently running: a reader who switched them off already knows, while counting the live ones would tell a reader who never looked that there is nothing here.

**Authoring one control** is [`ControlEditor.svelte`](../src/lib/components/promptBuilder/ControlEditor.svelte), the body of an expanded control row. Label / macro / type / section sit in a self-measuring 2-up grid, then help text with its "show it on the card" switch (offered only once something is typed, since where to read nothing is not a question) and the advice badge, then the type-specific block: default + placeholder + inject template for text; default state + ON/OFF texts for toggle; min/max/step/default + inject template for slider; track + both ends + step + `{{min}}`/`{{max}}` template for range; an option list for select/radio/tags (plus the separator, the free-entry switch and its placeholder for tags). The Section field is a plain input backed by a `<datalist>` of declared sections: typing a new name makes an ad-hoc group, picking a declared one joins that section, and neither needs a second dialog. The macro input **filters as you type** (`value.replace(/[^A-Za-z0-9_]/g, '')`), so the field only ever holds letters, digits and underscores. Case is preserved deliberately: every reader of a macro name matches it verbatim, so folding case would rename the control out from under the items referencing it. Options are `{ id, label, injectedText }`; removing one also clears a `defaultOptionId` that pointed at it and drops it from `defaultOptionIds`, which is the only cleanup the editor does. Every keystroke goes through one `update(patch)` → `onChange` → `updateControl` → `persistDraft` path; the editor holds no local state of its own.

**Rendering one control** is [`CustomControlField.svelte`](../src/lib/components/presetControls/CustomControlField.svelte): a labelled card whose body is the widget, with the **toggle deliberately promoted into the header row** rather than left as a lone switch in an empty card body. It takes the raw stored value and resolves it through `getControlValue` on every render, so a value written under a since-changed control definition degrades to the default instead of breaking; the `baseline` prop (the adopted kit's raw value where it names this macro, `undefined` otherwise) goes through the **same** coercion, so a kit captured under an older definition compares as what it would show, not as its stale raw form. Sliders carry [`rangeReset`](../src/lib/actions/rangeReset.ts): double-click snaps back to the **baseline**, not zero. The range widget is two transparent `<input type="range">` stacked over one shared rail with `pointer-events` on the thumbs only; stacking order follows the thumbs (`lowOnTop` once the low end passes the halfway mark) so two thumbs on the same value can never trap each other. The card's header carries the rest of the conversation between author and reader: the advice badge, and, when the resolved value differs from the resolved baseline (compared serialized, so a range pair and a tag list compare by content), a **modified dot with a one-click Reset** back to that baseline. The view answers the reset: it re-writes the kit's value where one is named and otherwise calls `clearValue`, deleting the key rather than writing the default in, because a stored copy would freeze today's default and stop tracking a preset update. The footer prices the control by running the same `formatControlForPrompt` the assembler runs, so the number is the real one.

**`PresetControlsView` is the preset's face, not a list of switches.** It opens with the identity block: the 3:4 cover at full height on the left, and one column beside it holding the title line (name, version and byline read as a single run rather than three stacked labels), the author's description, and the "written against" note. Top-aligned, because the column is the part that grows and a centred cover would drift away from the title it belongs to as the paragraph runs on. **The description opens clamped** to roughly where the cover ends (line counts tuned per container step against the cover's own height, since that height is `width × 4/3` and the CSS already owns the width), with a Read more toggle that appears only when the text actually overflows, measured by a `ResizeObserver` while clamped and never while expanded, or unfolding would hide the control that unfolded it. Otherwise a preset whose author wrote three paragraphs pushes its own controls off the screen on arrival. Then the baseline picker, then a status line that says how many controls have drifted from the lit baseline (naming it, so the count and the card can never disagree about what was counted against), with a Reset-all beside it and what the whole form costs in tokens, then the sections. Section resolution walks `preset.sections` in order, skipping any whose controls have all gone away, then appends every undeclared group in first-appearance order; every heading is a disclosure button, and **fold state is the reader's**: the author's `collapsed` seeds it, and `seededFor` re-seeds only when the preset id actually changes so a fold never carries across to a different document. A section's cards are laid out as a stack of **rows** (`rowsFor`): a `textarea` control is its own full-width row, and every run between two of them is a pair of **real columns**, one until 700px of the container's own width, two above it. Cards differ wildly in height (a radio group whose options carry rationales is several times a slider), and grid tracks would give every row the tallest card's height and open a hole under every short one, so the columns are independent stacks and the next card starts where the last one ended. **CSS multi-column is deliberately not used for this**, and the reason is a live engine bug rather than taste: Firefox measures a flex box inside a fragmented column against the wrong width and never re-measures it, so a card at a column's head reports a height that omits its own help text and everything below it paints over that text. `break-inside: avoid` does not help, because nothing is being split. The box is measured once, wrongly. Real columns cannot be fragmented, so there is no measure pass left to get wrong. The **split is contiguous, never alternating**: below the breakpoint the pair collapses to one grid column and the two halves stack, and only a contiguous split reads back in the author's order there. **Where it cuts is measured, not counted**: a `ResizeObserver` records each card's rendered height against its (stable) control id, and `balancedSplit` picks the contiguous cut whose two halves come closest to the same total, which is the balance multicol used to do for free. That loop terminates by construction rather than by luck: both columns are the same width, so a card's height does not depend on which one it lands in, and moving cards between columns cannot change the numbers the split was computed from. The observer writes state only when a height actually moves (a sub-pixel tolerance), or it would answer its own write. Before the first measurement (a section that has never been opened renders nothing to observe), it halves by count, which is also what the first paint uses until the observer answers. Its two empty states are different on purpose: no preset at all, versus a preset with no controls. The second explains what controls are and points at the Prompt Builder, since that is a reader's only clue the feature exists.

**Preset options** are the three per-preset scalars, placed below both lists because they change how the prompt is assembled rather than what it says. `pruneEmptyBlocks` is a toggle with a [`PruneEmptyBlocksMockup`](../src/lib/components/mockups/PruneEmptyBlocksMockup.svelte) explainer; `exampleSeparator` is a narrow text field; `continuePrompt` is a textarea with a **Reset** that appears only once the field carries a real override. The two string fields are **not** symmetric, and the difference is easy to trip over: the separator field writes its raw value straight through, so clearing it stores `''`, which resolution reads as a real "no header line" (the `??` fallback to `***` only fires on `undefined`) even though the input's placeholder still shows `***`, while the continue prompt gets the full override dance. That last one implements the override contract literally: `setContinuePrompt` stores `undefined` when the typed text equals `DEFAULT_CONTINUE_PROMPT`, so typing the default back in drops the field instead of freezing this install's copy of it into the preset, while an **empty string is a real value** meaning "send no instruction, leave the reply as a native prefill", which is exactly why Reset has to exist as a separate action rather than being spelled "clear the box". Storage stays override-only for the same reason; export materializes every field at its effective value and import reduces it back to an override. The end-to-end whitelist chain those fields ride is architecture/prompt-pipeline.md coupling 9. `cloneForEdit` here is one of its links.

**The editing model.** The builder never mutates the service's presets: it edits a deep working copy and every mutation writes that copy and then calls `persistDraft`. That copy is the service's own exported `clonePreset`: `cloneForEdit` is an alias for it, not a second implementation, so the per-preset field list exists in exactly one place and a new field cannot survive Save here and then vanish on the next unrelated edit. From the author's chair the lifecycle reads: an edit that materially differs from the committed preset **creates a draft** and the status line appears (amber dot, "Unsaved changes", a Discard link); an edit that ends up matching the committed preset again (text typed and reverted, a drag that lands where it started) **drops the draft**, so the dirty flag can't go phantom; `isDirty` is derived from `presetService.hasDraft` and is never tracked by hand. Save commits the draft, re-clones from the committed result, flashes a fading "Saved" for two seconds and toasts. Discard confirms through `ConfirmDialog` and re-clones from the committed preset. The consequence worth stating outright: **the draft is live for generation, not just for the editor**. `getActiveEffectivePreset()` is draft-over-committed, so an unsaved edit is what the next send uses, which is what makes Discard a real action rather than a formality. An `$effect` keyed on the service's active id **and** its `contentVersion` re-clones whenever either moves (sync from another device, first-boot seeding, a restore-defaults), clearing the two expansion sets only when the id actually changed. `PresetManager` owns everything else (new / duplicate / import / **Export JSON file** / **Copy as JSON** / delete / restore defaults, plus the Save button in the builder and the "Edit in Prompt Builder" jump in Preset Controls) behind a `busy` gate that serializes them, a case-insensitive name-collision check, and a snapshot of the delete target taken before the confirm dialog opens so a sync mid-dialog can't retarget it. **Both preset pickers (the `Select` here and `PresetControlsView`'s own switcher) tag every row `hasDraft` answers for, not the selected one.** A draft is held per preset id, so a preset edited and then switched away from still has unsaved work in it; a tag bound to the selection would go dark on the one preset the reader has to come back for, and the two pickers would answer the same question differently.

**The live breakdown** runs through the same primitives as generation and the composer meter (`buildMacroContext` → `resolveItem` / `assemblePrompt`), which is the whole reason its numbers can claim to match a send. It resolves the character through the **chat's pinned version** (`dataForVersion` with `chat.characterVersionId`), passes `regexRules`, and deliberately passes **neither `steering` nor `continuation`**: it prices the preset, not transient composer or story state (architecture/prompt-pipeline.md couplings 3b, 7 and 8). Because the whole input is drawn from the active chat, Expanded mode with no chat open prices an empty story: no character, no history, no recall. The header carries the two flags from that same assembly: `trimmedMessages` and `overBudget`. They exist because per-row numbers price **what each item resolves to** while the total prices **what fits**, so on a trimmed prompt the rows legitimately add up to more than the total; without the flag the two just silently disagree, and a trim is the one way live story text leaves the prompt with nothing summarizing it.

**Layout and keyboard are container-driven, deliberately.** `.pb` declares `container-type: inline-size; container-name: builder` and every responsive rule queries **itself**, never the viewport, because the builder lives in a ~350–500px Settings dock on wide screens and a chat-column overlay below the dock breakpoint: the Add button drops its label at 379px, the role pill collapses to its initial at 399px, the control row's macro chip disappears at 429px, and the name/role field pair goes 2-up at 430px. `ControlEditor` is its own unnamed container (fields pair at 420px, the min/max/step/default row goes 4-across there, option label/text pairs at 460px) and `PresetControlsView` is `container-name: pcv` (padding steps at 640/960, two columns at 700). Row anatomy is load-bearing: vertical padding lives on `.pb-row-main` and the handle rather than the row shell, or the row's top and bottom strips become click-dead; the lead slot stacks chevron and grip in one absolute position (chevron at rest, grip on hover, **always** the grip under `hover: none`) so disclosure costs no layout shift; delete stays at zero opacity until hover, expansion or `:focus-visible`, and is permanently visible on touch. Keyboard: `.pb-row-main` is a `role="button"` with `tabindex=0` and Enter/Space expand, and the drag handle gets its role, tabindex and keyboard-drag from the library. Any number of item and control rows can be open at once: the two expansion sets are component-local and survive everything except a preset switch. There is no Escape handling and no Ctrl+S in the builder; Save is the button, and Escape belongs to the Settings shell's step-back. [`MockupTip`](../src/lib/components/mockups/MockupTip.svelte) places its popover through the shared [`anchorTo`](../src/lib/actions/anchorTo.ts) action (`<body>`, viewport coordinates, side measured not declared), precisely because the builder is nested inside several `overflow: hidden` docks (architecture/ui-shell-settings.md), and it is opaque rather than the glass float recipe since an animated demo over bleed-through is unreadable. The builder closes with the shared [`MacroReference`](../src/lib/components/ui/MacroReference.svelte), rendered from the `MACROS` registry with this preset's control macros appended as their own click-to-copy "This preset's controls" group.

The `Prompt items` section carries `data-setting="prompt-builder"`, the assistant's deep-link anchor (architecture/ui-shell-settings.md coupling 2).

## Before touching this

- A **new control type** is five edits, not one: the `PromptControlType` union ([`types/database.ts`](../src/lib/types/database.ts)), all three switches in [`utils/prompt-controls.ts`](../src/lib/utils/prompt-controls.ts), the `CONTROL_TYPES` validation set in [`preset-io.ts`](../src/lib/services/preset-io.ts) (miss it and the type fails to import), `typeOptions` plus a settings branch in `ControlEditor.svelte`, and a render branch in `CustomControlField.svelte`. The three switches have no `default` arm, so the compiler catches those; the other three are on you.
- The control runtime is covered by [`prompt-controls.test.ts`](../src/lib/utils/prompt-controls.test.ts): defaults, coercion of a wrong-typed stored value, range ordering and clamping, and every injection branch including the custom-tag rule. Injection formatting lands directly in real prompts, so a change here without a test change is a change nothing is holding.
- Never key persistent state on a `PromptItem.id`: they are regenerated on every load by design. Control ids, option ids, section ids, kit ids and carried-rule ids are the opposite and must stay stable: each of them is either a stored value or something the reader's own state points at (kit ids are what `presetAppliedSetups` holds; regenerate them and every reader silently falls back to the Defaults baseline; carried-rule ids are what `carriedOverrides` holds, and regenerating one silently returns that rule to whatever the author shipped).
- Every builder mutation goes working copy → `persistDraft`. A write that skips it edits a copy nothing will ever save; a write that goes straight to `presetService`'s maps breaks the "no-op edit = no draft" rule the dirty flag depends on. The **cover is the exception that proves it**: it writes a file immediately, which no draft can undo, so its cleanup is deferred to Save/Discard instead.
- A new per-preset field needs `clonePresetBody` in [`presets.svelte.ts`](../src/lib/services/presets.svelte.ts) and the rest of the chain in architecture/prompt-pipeline.md coupling 9. `clonePresetBody`'s **key order is load-bearing**: `strip` drives `sameContent`, which compares serialized output, so two orders read as two different presets and every load would look like an unsaved edit.
- Both views measure their own container. A viewport media query added here is wrong at the dock width by construction, and the builder spends most of its life in a dock.

## Hand-kept couplings

1. **Control values key on `control.macro`, never `control.id`.** `PresetControlsView` reads `presetControlsStore.values[control.macro]` and writes through `setValue(control.macro, …)`; `resolveCustomControl` (macros.ts) finds the control by `c.macro === name` and reads `customFields[name]`. Both ends must move together, and both are why a macro rename orphans a value. Control and option **ids** are stable for a different reason (coupling 2). Do not read `strip`'s id-stability rule as saying values key on them.
2. **Option ids ARE the stored value** for select/radio/tags. `hydrate`/`strip` regenerate item ids on every load but deliberately never touch control or option ids. Regenerating either (or deleting an option and re-adding it with the same label) silently resets every reader's saved choice to nothing.
3. Reserved names and lint-provided names are **two derivations from one registry**, deliberately different: `RESERVED_MACROS` (PromptBuilderView) is every `MACROS` name so a control can never take one, while `providedMacros` is `SYSTEM_MACROS` (engine-only, minus the parameterized placeholders) plus this preset's controls, since flow macros genuinely aren't provided in a preset item. A new macro reaches both with no edit. What no set can express is a parameterized **shape**, so `unboundMacrosFor` calls `cappedHistoryTurns` alongside the lookup, the one hand-kept link between the lint and macros.ts.
3b. **`control.group` holds a `PromptSection.id`.** The reader's grouping, the builder's per-section count, the "declared but empty" warning and the "adopt this group" offer are all four derived from that one string matching on both sides. It is why a section id is read-only after creation and why deleting a section leaves every `group` untouched.
4. The four drag zones' `type` strings (`pb-items` / `pb-controls` / `pb-sections` / `pb-carried`) are what keeps a prompt item from being dropped into the controls list. Duplicate a string and two lists become one pool. The Regex page's own list is a fifth, `regex-rules`, and must stay distinct from `pb-carried` for the same reason: the reader's rules and the preset's are two lists that happen to hold the same shape.
5. `PromptBuilderView` is one of the five character-version pinning sites (architecture/prompt-pipeline.md coupling 3b) and one of the `AssembleInput` construction sites: it must keep passing `regexRules` (coupling 7) and must keep **omitting** `steering` and `continuation` (coupling 8). A new field on `AssembleInput` forces a conscious choice here.
6. `cloneForEdit` ↔ the per-preset field list (architecture/prompt-pipeline.md coupling 9).
7. `presetControlValues` **and** `presetAppliedSetups` reload together, riding the **`settings` sync scope handler** in [`sync.ts`](../src/lib/services/sync.ts), which calls `presetControlsStore.syncReload()` explicitly: the store is deliberately not a `registerSettingsReload` subscriber, and its `initialize()` is a step in `AppShell.boot()`. Both keys must sync or two devices disagree about what Reset means. A new consumer of the values inherits the split: fresh from the row on the generation path, from the store's cache everywhere else; the adopted-setup key has **no generation-path reader**. It shapes only what "modified" and "reset" mean on the reader's page, never what a prompt contains. The values writers funnel through one private `write` (`setValue`, `clearValue`, and `applyValues(writes, clears)`; writes and clears land as one change and one broadcast, not a burst) and `setAppliedSetup` owns the second key.
8. `ControlEditor`'s macro input filter (`[^A-Za-z0-9_]` stripped) must stay no stricter than what reads a macro name: `MACRO_REGEX`, `RESERVED_MACROS`, `preset-io.ts` and `resolveCustomControl` all match verbatim and all accept mixed case. Narrowing it again (folding case, dropping a character class) silently **rewrites** the name of any control the author so much as clicks into, cutting it loose from every item that references it; the shipped default preset is the live example, with `bannedPhrases`, `livingWorld` and `contentRating`.
9. **The reader's switch keys on a carried rule's id.** `regexRulesStore.carriedOverrides` (persisted in the regex settings blob) points at `preset.regexRules[].id`, which is why `normalizeCarriedRules` preserves a declared id while the Regex page's own importer deliberately mints fresh ones. Change either side and every rule the reader had an opinion about silently snaps back to what the author shipped. The map is sparse and prunes on agreement, so "no entry" and "agrees with the author" must stay the same state: writing the author's value in as an entry would freeze it and break preset updates.
10. **A section's `icon` is validated, not trusted.** It arrives inside a downloaded preset; `isSectionIcon` ([`config/section-icons.ts`](../src/lib/config/section-icons.ts)) gates both the reader's render and the author's picker, so the two can never offer and accept different sets, and an unknown name is simply not drawn.
