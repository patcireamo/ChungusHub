# Chungus Assistant: architecture & maintenance

**Shared target highlight**: [`flash-target.ts`](../src/lib/utils/flash-target.ts) owns the accent ring/glow Web Animation used to point at a UI target. Assistant settings navigation and non-Assistant surfaces that need the same visual call `flashTarget` instead of copying the recipe. Pointing at a **message** is not one of them: both doors that do it (`navigateTo`'s `message` arm and the timeline's `scrollToMessage`) hand the id to `messageStore.revealMessage` and stop there, because the transcript renders a window of the branch and a turn behind it has no row to find yet, quite apart from owning the branch switch and the card-not-row rule (architecture/chat-sessions.md coupling 14).

The Chungus Assistant (`server/assistant/`) is an in-app, tool-calling assistant scoped to ChungusHub. It acts **only** through a capability registry (`server/assistant/registry/`), never shell or code. The registry is derived, not hand-written. [`entities.ts`](../server/assistant/registry/entities.ts) is the **single source of truth** for the data model (character / persona / message / lorebook / chat / setting / skill and their fields), and everything else is generated from it: the OpenAI tool schemas ([`schema.ts`](../server/assistant/registry/schema.ts)), the system-prompt data-model section, the turn's workspace note, and the persona-only field restriction. Generic capabilities (`read` / `find` / `create` / `edit` / `set` / `update` / `delete_entity`, plus the bulk `update_entities`, e.g. attribute every orphaned "You" message to a persona in one call) operate uniformly over every addressable entity. Chat/recall reads (`read_chat_messages` pages a thread by tail, anchor window, or an explicit `fromSeq`–`toSeq` range (see *Full-fidelity reads* below); `read_chat_context` presents the chat's cast as it actually is: the bound character in full, the personas stamped on the thread's user messages in full (a deleted one reads as `deleted:true`, unattributed "You" messages are counted and flagged), the persona THIS chat plays as (its own claim while that persona exists, else the app's; `chatPersona` in chat-reads.ts, where the rule in src/lib/utils/chat-setup.ts is spelled a second time because the server cannot import it) as a name **pointer** only (who NEW messages attribute to, never presumed author of history), and lorebook entries as an **index with previews**, over every layer that reaches the prompt: the shelf's globals, the cards' links and the books this chat attached, minus the ones it muted (`chatLorebooks`, the second spelling of `resolveLorebookLinks` for the same reason, and the one the workspace note's chat pointer reads too, architecture/lorebook.md coupling 1); `read_lorebook_entries` reads any book's full entries by id; `read_memory_state` exposes the chat-memory subsystem: enabled/auto flags, the archive boundary DERIVED for the active path, archived vs live seq ranges, the summaries in play each with its **id and the seq range it was written from**, and a count of the ones belonging to other branches; it imports the pure memory core (`src/lib/memory/branching`) so its answer cannot drift from the prompt's, see architecture/memory.md coupling 9. That range is what makes a summary checkable rather than merely readable: `read_chat_messages(fromSeq, toSeq)` fetches the exact turns behind it, and `edit_memory_episode` then rewrites the ones that misremember. **That write reaches the prose and nothing else**: coverage, deletion and re-folding stay the engine's, and the tool refuses a summary the engine has already outdated, since the reap would throw the rewrite away with it) and the lorebook entry ops live as dedicated capabilities ([`chat-reads.ts`](../server/assistant/registry/chat-reads.ts), [`lorebook-entries.ts`](../server/assistant/registry/lorebook-entries.ts)): their windowing and array semantics don't fit the generic field layer. **Operator actions**: `manage_entry_lorebooks` links/unlinks a book to a character/persona: the activation step without which an authored book sits inert, injecting nothing (an emptied link set deletes the key, the stored-entry convention). `set_active_persona` writes the `activePersonaId` settings row + broadcasts `settings`; it never re-labels history. Attribution stays locked at send time. `rename_chat` writes the title via `updateChat` + broadcasts `chats`. `create_chat` (workspace.ts) is a server-side replica of `chatStore.createChat` + `seedCharacterGreetings` (architecture/chat-sessions.md): chat row first with null root/leaf, greetings (First Message + alternates) as RAW root siblings, the chat's record of what the card handed it (`setChatSeededGreetings`, without which the chat silently never follows a later card edit), root/leaf pointers last, all in one transaction, pinned at birth to the version new chats with that character start on (`chatVersionSeed`, a second spelling of the client's rule in architecture/library.md, resolved once so the row and the result the model reads back can never name different variants), and born carrying the character's other three New Chat Defaults as its own claims (`birthClaims`, the composer's rule again: the three claim keys where the character names any, and NO blob at all where it names none, since "claims nothing" has to stay a state the row can be in; architecture/ui-shell-settings.md). Answering fewer of the four here plays the same character, started two ways, as two different stories; the title default mirrors `generateChatTitle` ("<name> - YYYY-MM-DD"; a format change must update both, and this side cannot import the client's `utils/date.ts`), and the result carries a `nav` jump-in button. `add_steering` inserts a **steering note** row (architecture/engines.md): a scope param (`chat` default / `character` / `version` / `global`) resolved against the target chat, with `depth`/`role` omitted meaning "inherit the app-wide placement", the same tri-state the UI writes. It **adds** rather than replaces, because notes stack; and a bound scope with nothing to bind to (no character, no version pin) refuses instead of storing a row that could never resolve. It touches no `feature_state`. `manage_greetings` (greetings.ts) manages `data.alternateGreetings` (an array, outside the FieldValue layer, the lorebook-entries precedent) with 1-based indexes. **Both greeting doors carry a second broadcast**, this one and the `firstMessage` field write in `entities.ts`: `serverDb.updateLibraryEntry` carries a changed opening into the chats that are still nothing but that opening (architecture/chat-sessions.md), and those are message rows, so a non-empty return fires `messages` on top of the tool's own `library` hint. Without it the card moves and the open transcript keeps the greeting it was seeded with. The RPC bridge does the same for the client's own saves (architecture/server-core.md); the assistant reaches the method in-process, so it repeats the hint itself. Asserted in `smoke.ts`. **`delete_entity` carries one for the same reason**: `serverDb.deleteLibraryEntry` refuses the last persona outright and, when the deleted one was active, hands the role to a survivor (architecture/library.md), so a non-null return fires `settings` on top of the `library` hint. That delete also drops the row **before** it sweeps the entry's image files, because the refusal is the only step that can stop it and a sweep that ran first would strip the art off an entry still in the library. Chat memory gives the assistant exactly one write, `edit_memory_episode` (architecture/memory.md coupling 9): the summary's TEXT, never its coverage. That is the same split the panel's episode editor lives by, because prose can neither open a gap in the archive nor move the boundary. The other fix, correcting the messages the summary was written from, belongs to the message tools and **does not combine with it**: editing a covered turn discards its summary and the engine writes a fresh one from the corrected text, so a rewrite of that same summary is thrown away, unless the message went through the quiet door, which is the whole of *Two doors for a message rewrite* below. The `edit_memory_episode` schema says so. `read_prompt_log` / `read_prompt_entry` (prompt-trace.ts) read the server prompt log (server/promptLog.ts): index + one-full-message/full-response paging, never a whole-prompt dump; the index counts a request's **tool definitions** alongside its messages, since those are usually the larger half of an assistant prompt and an overview that omits them answers "what is eating my context" with the smaller one; results state the honest limitation that capture only runs while a device has the Prompt Debug panel open. `read_connection_state` projects the `connections` + `connectionAssignments` settings blobs through an explicit safe-field pick (id/name/provider/model/contextSize/generation, plus `samplingParams` on `openai-compatible` connections only. That list is what a BYO endpoint actually sends, so a `generation` value outside it is stored but inert and must not be blamed in a diagnosis; see architecture/llm-providers.md) so credentials and endpoints can never surface. The settings DOCTRINE holds: app settings stay explain-and-navigate-only, these drive story-workspace state. [`settings.ts`](../server/assistant/registry/settings.ts) is a read-only catalog the assistant uses to answer "what does X do" and to deep-link via the `navigate` tool; both halves of that surface, the `setting` entity kind and `navigate`, ride the opt-in **Navigation** family (see *Capabilities*), so a workspace with it off has no settings surface at all; the client routing lives in [`src/lib/services/navigation.ts`](../src/lib/services/navigation.ts) and the assistant-panel wiring in [`ChungusAssistantPanel.svelte`](../src/lib/components/assistant/ChungusAssistantPanel.svelte). The regression net is [`server/assistant/registry/smoke.ts`](../server/assistant/registry/smoke.ts): run `CHUNGUS_DATA_DIR=<tmp> bun server/assistant/registry/smoke.ts`.

**Assistant Settings** ([`AssistantSettingsView.svelte`](../src/lib/components/assistant/AssistantSettingsView.svelte), gear button in the assistant tab bar) is a full-height view embedded in the existing floating panel, not a dialog or portal. It replaces the chat surface until Back or Escape returns to the conversation; the gear stays available even when no assistant session is open. It is ONE scrollable page of stacked sections (**Instructions**, **Suggested Prompts**, **Skills**, **Approval**, **Capabilities**) under plain headers (a handful of controls never needed a nav rail; a single page means nothing hides behind an unvisited tab), with container-responsive layouts for the widget's resizable width; Escape commits the pending instructions draft before closing. **Approval** ([`AssistantApprovalSection.svelte`](../src/lib/components/assistant/AssistantApprovalSection.svelte), `assistantApprovalMode`) sets the default a new tab is born with; it sits above Capabilities because it governs whether the assistant asks, while Capabilities governs what it can reach. Unlike the other three it is NOT part of the frozen snapshot, so it carries no Apply notice: the mode never touches the prompt or the tool list. **Instructions** holds the user's standing instructions for the assistant (`assistantCustomInstructions` settings key, global, capped at 4000 chars client-side): free text that [`systemPrompt.ts`](../server/assistant/systemPrompt.ts) folds into its own prompt section on every turn (empty → section omitted), read server-side through the session's frozen snapshot in [`loop.ts`](../server/assistant/loop.ts), exactly like the skill index and the capability set (see *Frozen session settings*). It is framed as **authoritative over the built-in reply/tone/language/workflow defaults but never over the Safety discipline section**, and is trusted input (typed by the user) unlike chat/card/lorebook content. **Suggested Prompts** ([`AssistantSuggestionsSection.svelte`](../src/lib/components/assistant/AssistantSuggestionsSection.svelte), `assistantSuggestedPrompts`) is the empty screen's tappable list, in the order it draws them: one settings row holding a JSON array of strings, so every edit writes the whole list, a text change on blur and a structural one (add, delete, move) at once, plus once more when the view is taken away, since Escape, Back and minimizing the widget all remove a focused input without it ever blurring. **The list is held by `assistantSessionStore` beside `approvalDefault`, and both surfaces read that one state**: the editor and the empty screen sit inside the same panel, so two independent reads of the same row would leave a new suggestion invisible on the screen behind the editor until the next load. The editor keeps a draft of its own and follows the store only when nothing on the page is half-typed and the change is not the one it just made, which is what keeps another device's write from replacing a list under the cursor and keeps a save from re-keying every row. **A missing row means nothing has been customized and the shipped set is drawn; an empty array is a real answer and draws none**, which is what lets the list be emptied without the defaults growing back on the next load. The shipped set, the key, the collapse threshold and the read-back rule live in [`assistant-suggestions.ts`](../src/lib/config/assistant-suggestions.ts), the `assistant-approval.ts` precedent: the panel and the editor cannot disagree about what the defaults are. **Add defaults appends only the shipped lines that are missing**, the Skills rule again, so the pristine set is always one press away and a list somebody rewrote is never overwritten to hand back a line they can already read. Like Approval it is NOT part of the frozen snapshot and carries no Apply notice, because a suggestion only fills the composer and reaches neither the prompt nor the tool list. The empty screen shows the first `SUGGESTED_PROMPTS_COLLAPSED` and **expands to all of them rather than to a second fixed number**: the list is its own scroller, capped at about ten rows and at the room the panel has left, whichever is smaller, so a long list is read inside that box and nothing else on the empty screen moves. Three things hold that shape and each fails visibly without the others: the empty block carries `min-height: 0` so it can be squeezed rather than pushing past the panel, everything above the list (mascot, title, hint) and the Show more button below it are pinned `flex-shrink: 0` so the list is the only part that gives, and the ROWS are pinned too, since a flex column with room to compress its children never overflows and therefore never scrolls at all. Show more sits OUTSIDE the scroller, so scrolling the rows can never carry it out of reach. The rows are held off the bar by **padding on both edges, never by a reserved gutter**: where the OS hides scrollbars until they are used the bar is an overlay, `scrollbar-gutter` (and therefore `.panel-scroll`) reserves nothing at all, and the bar paints over the last row; padding is the one inset both kinds of bar respect, and equal on both edges keeps the box on the centre line the mascot and the title share. The rows are rendered UNKEYED: nothing dedupes the stored list, and two rows holding the same text must be the user's business rather than a crash.

**Generation is not configurable here, and none of it is app-owned.** The assistant is an ordinary consumer of the connection assigned to the `assistant` surface (Settings → Connections, architecture/llm-providers.md): its model, provider, every sampling knob, its output cap, its context size and whether it streams are all fields of THAT connection, used verbatim. A turn resolves them client-side in [`assistantSessions.svelte.ts`](../src/lib/stores/assistantSessions.svelte.ts): `llmService.resolveConnectionParams('assistant')` for sampling (the same `getGenerationParams` a chat send builds, after warming the model cache so the capability filtering is real), `getGenerationTuning` / `routingFor` / `sendsImages` for the rest, and the connection's `contextSize` + `generation.streamResponses` read straight off it. An unassigned surface throws before the request instead of sending empty ids. `contextSize` is the number the server's context trim and pre-flight fit check budget against (see *Loop hygiene*), so a small one simply trims a tab sooner. `streamResponses` off means the loop passes the providers no `onToken`, which is how both provider implementations decide streaming (architecture/llm-providers.md): each model step becomes one non-streamed request that lands whole: no reply/reasoning deltas, no running tool rows, the activity line and the settled steps carrying the turn.

**What that costs is stated once, and it takes the whole panel to say it.** [`AssistantCostNotice.svelte`](../src/lib/components/assistant/AssistantCostNotice.svelte) is a full-height view inside the assistant panel, the `AssistantSettingsView` shape and mounted as the panel's **outermost branch**, ahead of the settings view and everything else: one short screen of copy and one button, with nothing beside them to read instead. It states the mechanic the panel's shape hides, that one message is a turn of up to `MAX_ASSISTANT_ITERATIONS` model requests each carrying the whole conversation and the entire tool block, then asks for the one precaution that actually holds, a spending limit on the key. A quieter last line points readers who already know the shape at agentic coding tools, and it is quieter precisely because it lets exactly those readers stop reading. It quotes **no numbers**: what a turn costs is the model's price against the job's size, so a figure here would be wrong for everyone reading it. **It is in the panel and not over the app**: a modal would put a cost the assistant owns in front of a reader who came for something else. **Only its button marks it read** (`generalSettings.assistantCostSeen`, written by nothing else), so it comes back on every open until Got it is pressed: an appearance is not a reading, and a panel somebody minimized again taught them nothing. The panel derives its branch off that same flag, so Settings → Developer's re-arm (architecture/ui-shell-settings.md) puts the view straight back, open panel included, and the drop overlay stands down under it rather than painting a drop hint over a notice. The mark rides the settings spine, so the app says this once per install and not once per device.

**The prompt names families; the schemas describe tools.** `# Your tools` is one generated line per family ([`groups.ts`](../server/assistant/registry/groups.ts) → `describeToolFamilies`): family, its tool names, one clause on when to reach for it. It is the only thing the tool list itself cannot supply (35 flat schemas have no families) and it replaced 1.7k tokens of prose that restated those same schemas almost verbatim, sitting beside them in the identical cached prefix, where moving a sentence from one to the other gains exactly nothing. Two facts had nowhere else to live and were rehomed rather than deleted: the settings doctrine (answer from the catalog, `navigate` to the control, never change an app setting yourself) rides the Navigation family line, and the two-tool *make a character from this picture* recipe rides `edit_character_images`. The rule that keeps it 150 tokens forever: a new capability adds its NAME to a family line and writes nothing else here.

**One fact, one home, and that rule runs through the schemas too.** The 35 schemas and the prompt are the same cached prefix, so a rule stated in both is paid for twice and improves nothing. Which one owns a fact follows from what kind of fact it is. **General doctrine belongs to the prompt**: a chat is a tree and a `seq` is a position on the branch it was read from (the `chatBlock` says it, so `read_chat_messages` only reports the `activeLeafId` it walked), where an explicit `chatId` comes from (so those params say only *which* chat), when a delete is legitimate and what `confirm` must equal (Safety discipline says it, so `delete_entity` states the mechanics its arguments need), and *leave versions alone* (the family index line says it, so neither version schema repeats it). **A tool's own contract belongs to its schema**, stated ONCE: an argument's meaning lives in that argument's `describe`, never in the summary as well: `add_steering`'s four scopes and `delete_entity`'s two message scopes are on the params, and the summary says what the tool is FOR. A rule two schemas share is written out on the one the model reaches for first and referenced from the other, but the reference still carries the operative test, never just a pointer: `edit_entity`'s `minor` holds the quiet-save rule with its worked example, and `set_entity`'s keeps the criterion (meaning, not size) and the safe default while citing it, because a flag that decides whether a memory summary survives must be decidable from the schema in hand. And nothing on a schema is there to persuade a human: rationale, restated examples and value judgements ("core to keeping a long roleplay consistent") come out. Applying that pass took the tool block from 8.6k to 7.8k tokens with no rule lost.

**Skills** ([`skills.ts`](../server/assistant/registry/skills.ts)): procedural guides the assistant reads **on demand** instead of carrying in its system prompt: the prompt embeds only a one-line index per **enabled** skill (`describeSkillIndex()`; the whole section disappears when none are), and the assistant pulls a body with `read_entity kind:skill` when the task matches. **Every skill belongs to the user** and there is no privileged class among them: one flat list in the **Skills section of Assistant Settings** ([`AssistantSkillsSection.svelte`](../src/lib/components/assistant/AssistantSkillsSection.svelte); served by `/api/assistant-skills` GET/PUT), every row editable, toggleable and deletable, the ones the app ships included. A disabled skill is invisible to the assistant entirely (index, `find_entities`, and `read_entity` all exclude it). State lives in `assistantSkills.json` under the data dir: the list verbatim, ids and all, rewritten whole on every save (the section always sends the full list, in order). A save reaches new sessions immediately and an open one when the user applies it (*Frozen session settings*); the BODY is always read live, so only the prompt's index line is frozen. A corrupt file is backed up to `<file>.corrupt-<ts>` and logged before the bundled catalog is read, never silently emptied (the next full-set save would have made the loss permanent). For the same full-set reason a save broadcasts the `assistant` scope (skills do not earn their own; the sessions reload it also fires is one cheap read): a Skills section left open on a second device would otherwise save its stale list back over the change. It refreshes through `registerSkillsReload`, a no-op while Assistant Settings is closed, and `applySkills` keeps expansion, in-progress drafts and unsaved cards across the refresh. Instructions and Capabilities read the settings table directly, so each registers its own `settings` reload for the same reason.

**What ships is a catalog, not a class of skill.** `defaults/skills/` holds one `<id>.json` per bundled skill in the same format an export writes, **read as a folder** (`listDefaultSkills()`), so shipping another is dropping a file in and nothing else: no id list, nothing to fall out of step. The id is the FILENAME stem, which is why a shipped skill wears a readable `character_creation` in the prompt index while a user's own wears a uuid. The folder is **read-only at runtime and never written back to**: the first read of a fresh install seeds `assistantSkills.json` from it, the **Defaults** browser copies out of it on demand (`GET /api/assistant-skills/defaults`), and that is the whole answer to *what if the user rewrites or deletes one*: the pristine copy is always one dialog away, so nothing in the app has to defend a shipped skill from its owner. A missing or empty folder throws rather than yielding an empty list: it is a packaging mistake, and silence would hide it behind a browser that simply shows nothing (`scripts/package.ts` copies the folder, architecture/build-packaging.md coupling 4). The two it holds are **worked examples, not an attempt at a complete set**: the sets worth having are the ones users write and trade, so shipping more of them is a decision, never a todo.

**Getting skills in and out** ([`AssistantSkillPickerDialog.svelte`](../src/lib/components/assistant/AssistantSkillPickerDialog.svelte), file format in [`shared/skills-file.ts`](../shared/skills-file.ts)): four buttons head the list: **Defaults**, **Import**, **Export**, **New skill**. Three of them ask the same question, so they share one dialog (rows with a live count and All / None), and the two that bring skills IN share one code path, because they differ only in where the entries came from. **The rule that makes the whole thing safe is that bringing a skill in never overwrites one you have**: a file carries no ids, a shipped skill keeps its readable id only while that id is free, and anything else is minted fresh, so re-reading your own export, or taking a default you have already customized, ADDS a second card you can compare against and delete, and no dialog anywhere needs a destructive branch. What keeps that from being a duplicate factory is the tag: a row whose NAME is already in the list is marked *In your list* and starts **unticked**, so the reflex click takes exactly what is missing. The file is `{ type: 'chungushub.assistantSkills', version: 1, skills: [...] }`, each skill carrying name / description / body / enabled; the shape, the writer and the parser live in `shared/` because the server reads the same format out of `defaults/skills/`. Export writes each skill's SAVED text and lists only saved cards: the file has to carry what the assistant actually reads, and a never-saved draft is not a skill yet. An import or a Defaults pick lands in ONE save; a failure reloads from the server, which drops all of them, so nothing is left half-added and the source is still there to retry. The parser takes our envelope, a bare array, or a single skill object, skips an entry missing name/description/body, and throws when nothing usable survives: a file that yields no skill says so, it never no-ops quietly.

**Capabilities**: consent is granted by FAMILY, never per tool. [`groups.ts`](../server/assistant/registry/groups.ts) partitions the 35 capabilities into ten (Core, Navigation, Writing, Deleting, Lorebook, Memory, Story operations, Versions, Images, Diagnostics) and that one table gates the tools, generates the prompt's tool index, and fills the settings page. **Images is the LOOKING family only** (`view_character_images`): it is a consent-and-cost question about sending pictures to a model. Writing owns `edit_character_images`, because copying a picture the user already owns sends none of it anywhere. Filing it with the reads would take *make a character from this picture* away from every default install. **Navigation owns pointing at the app**: the `navigate` tool and the `setting` catalog KIND ride it together (`EntityDef.group` in entities.ts; the generic reads refuse a kind whose family is off, and `describeDataModel` drops it from the prompt), so switching it off leaves no settings surface at all rather than a catalog with a dead button. **Three families are not in the defaults** (`DEFAULT_ENABLED_GROUPS` takes every family that is neither): Images and Navigation are opt-in (`defaultOff`), and Deleting is **experimental** (`experimental`): badged on the Capabilities page, excluded from the defaults AND from every preset because its deletes still misfire, so a person switches it on knowingly, per workspace; `src/lib/contracts.test.ts` fails any preset that hands an experimental family out. **Core never closes**: reading the workspace is what the assistant IS, and an agent that cannot find an id is not a narrower agent, it is a broken one. The three file reads ride Core for that same reason: the user attaching a file IS the consent, exactly as it is for a hand-added workspace attachment, so there is nothing here for a switch to ask. A family of their own would have cost more than it bought and been wrong in every direction: a stored capability set never contains an id that did not exist when it was saved, so a new family ships OFF on every workspace that has ever opened the Capabilities page, while `describeToolFamilies` renders it to the model as "SWITCHED OFF by the user": a feature nobody can find, described by a sentence that is not true. A closed family is enforced **twice**: `buildTools(permissions)` leaves its tools out of the list, and `dispatch()` refuses them even if the model somehow produces one: the two guards deliberately asked about DIFFERENT sets (the list about the session's frozen one, dispatch about the effective one, see *Frozen session settings*), which is what lets a family switched off mid-session bite at once without the tool list moving. A capability belonging to no family throws at both guards rather than becoming quietly ungatable, and `src/lib/contracts.test.ts` asserts the partition so that never ships. The chosen set is one settings row (`assistantCapabilities`, a JSON array of ids) the page writes over the normal db bridge and the server reads directly; the CATALOG (labels, tool lists, presets, the experimental badge, and what each family costs the prompt) is served by `GET /api/assistant-capabilities` rather than duplicated client-side, and its token figures come from the same estimator the loop's context budget uses, so the page and the budget cannot quote different numbers for the same schemas. Presets (Simple / Standard / Full) are presentation, not storage: only the set is stored and whichever preset it equals lights up, because a stored preset name and a stored set can disagree. **They nest**: Simple is the story families (Writing, Lorebook, Memory, Story operations, Versions), Standard adds Images, Full adds Navigation and Diagnostics, so a step up the ladder only ever grants; a preset that dropped a family would take away a tool the user had just been working with. `smoke.ts` asserts the containment, and `src/lib/contracts.test.ts` the rest of the preset rules. **Images** carries a second guard of its own that no switch relaxes: an image path only ever comes out of a database row, either an entry's stored art (portrait / `identity.gallery`) or the user's own uploads, and never from the model. `view_character_images` is a **batch**: no selection → portrait + newest gallery images (5 max); an explicit comma-list ("portrait, 1, 3") up to a hard cap of 10 per call. **What art an entry OWNS is not part of this family.** Every `read_entity` on a character or persona reports `images: { portrait, gallery }` (`readEntryImages`), gated by nothing: counting pictures sends no bytes and needs no vision model, and it is the only way `edit_character_images` can be pointed at one: a read that stayed silent would leave the assistant unable to use art the user can see in the library, which is the whole reason this family can sit off by default without crippling the write. With the family on, that same read (and `read_chat_context`) also **auto-attaches the portrait(s)**, so "look at this character" is one call, not two. Tools return `injectImages` on their `ToolOutcome`: the loop attaches those paths as a user turn AFTER all of the iteration's tool results (a message wedged between tool results is a protocol violation) and **dedupes against images already in the conversation**, so repeated reads never re-inline the same bytes.

**Images in the assistant chat**: the panel's composer can attach/paste images (uploaded to `images/chat/`, persisted on the user turn via `assistant_messages.images_json`). What an attachment may be (its format, its resolution and its size) is not this panel's to decide: it asks `imageRejectionReason` and uploads through `imageService`, the one gate every model-facing image in the app passes (architecture/server-core.md), so the composer here, the chat composer and the library's portrait/gallery pickers cannot drift apart on what they accept. `AssistantRequest` carries `connectionId` + `routing` (the assistant surface's connection) alongside `images` (this turn's paths) and `sendImages`, the same provider-media-policy + model-modality gate the main chat computes (`llmService.sendsImages('assistant')`). Image *paths* always persist in the session context; each request strips them when `sendImages` is false, so switching to a vision model later makes past attachments visible again. When a turn carries images the model can't receive, the loop wedges an internal note saying so, because an assistant silently describing a picture it never got is the worst outcome. Providers expand paths to real bytes at request time (`LLMToolMessage.images` → OpenAI content parts / Anthropic image blocks).

**Attached files: reference material, never a workspace object.** A user can hand a tab a file (`.md`, `.json`, a `.jsonl` chat export, a character card) and the assistant READS it: three Core capabilities ([`registry/files.ts`](../server/assistant/registry/files.ts)): `list_files` (the tab's roster: id, name, what each one turned out to be, its length, what reading it whole would cost), `read_file` (a 1-based line range, line-numbered) and `search_file` (substring matches with their line numbers). There is no write, no edit and no import: a file is material the assistant works FROM, and turning one into a character is `read_file` plus the ordinary `create_entity`, which keeps one door for authoring instead of two. **Nothing is ever injected.** A file's content reaches the model only through a tool call, the same discipline `read_chat_messages` pages a thread by, because any real world-info export or chat log would swallow the tab whole if the composer dumped it in.

**The reads answer to the room the conversation has left, and that is the whole safety story.** A tool result is persisted verbatim and `trimConversation` cannot split one turn (see *Loop hygiene*), so a read that overshoots does not fail one request: it leaves the tab unable to send anything ever again, with the user's whole conversation stuck inside it. So the loop hands the tools `AssistantContext.roomTokens()`, asked LIVE at the moment of each call (two reads in one model step must not both spend the same room) and measured against the TRIM ceiling rather than the raw window: that fraction is the headroom the loop already lives by, and a read allowed to fill the window outright would hand the next persist a conversation it can only fit by dropping every earlier turn. Two ceilings follow, and the split is what makes "read it all" possible without a `force` flag anyone could regret: **no range is not a request for any particular size**, so it may only take `INLINE_CONTENT_TOKEN_LIMIT` (registry/schema.ts, the same number a full workspace attachment may occupy, because it is the same question: how much may land unasked), while **an explicit range is a deliberate size** and may spend the room itself. A user who says "read the whole thing" therefore gets it in ranges, across as many calls as it takes, and the tab degrades by trimming its oldest turns rather than by dying. `search_file` asks the identical room, or a one-character query over a 10 MB file would be a whole-file read wearing another tool's name. Every refusal states the size, the room, and the way forward; the warning surface when the user should decide is `ask_user`, which needs no new UI.

**Line numbers are the address, and they never drift**, unlike a chat `seq`, which is branch-relative. An attached file is read-only for its whole life, so a range read in one turn still names the same lines twenty turns later, which is why the schema tells the model never to re-read a range it already holds and why files carry no `stateRevs` claims at all: there is no staleness to announce. That permanence is bought at ingest, where normalization happens exactly once ([`files-core.ts`](../server/assistant/files-core.ts), pure and unit-tested): a BOM goes, CRLF folds to LF, and **JSON is re-printed**. That last one is not cosmetic: a world-info export or a card is routinely one line of several hundred kilobytes, and against one line a range read returns everything and every search match reports line 1.

**What a file IS gets decided by shape, never by its name**, the rule the SillyTavern boundary already lives by (architecture/sillytavern-interchange.md), so a card renamed `notes.txt` still reads as a card. The kinds are deliberately few (`shared/assistant-files.ts`): every one is a shape that can be checked, which is why there is no `markdown` or `csv`: any text "is" markdown and a comma is not a format, and a guess dressed as a detection would put a claim in the assistant's first look that nothing can stand behind. Ingest **recognizes but does not convert**: no ST mapper is ported server-side, and a `.png` is unwrapped to the document inside it (`chara`, then `chungus_preset`) because the readable content of a card is that document and not its pixels. Refusals are loud and store nothing: over 10 MB, not decodable as UTF-8, or a picture carrying no document at all.

**The first look is free.** A per-request internal note ([`describeAttachedFiles`](../server/assistant/loop.ts)) states the tab's files (name, id, kind, lines, what reading each costs) and the room left. It is rebuilt on every model step and **never persisted**, which is the only way the room figure can be usable: a number written into the stored context would still be claiming "48k left" ten turns after it stopped being true. It is the file twin of the image roster (`describeAttachments`) and sits in the same slot, after the conversation, so it costs no prompt cache.

**Where a file lives**: `assistant_files` + `assistant-files/` under the data dir, owned by the row, cascading from both the session and the user turn, swept at boot; architecture/server-core.md owns the storage, the endpoints, and the reason those bytes have **no static route** (an attached `.html` served from the app's own origin). Client-side the panel stages a real row rather than a pending upload (`store.files`, mirrored from the server whenever the transcript is read), so a staged file survives minimizing the widget, and a staged one can still be thrown away while a sent one belongs to its turn. The composer's attach menu holds both kinds as separate rows (**Image…** and **File…**) because they are separate questions: a picture is LOOKED at (Images family, a cost-and-consent question) and a file is READ. The panel and the chat composer both take **drops**: the whole assistant panel accepts either kind, the chat composer accepts pictures only and names what it refused. A dropped `.png` is the one ambiguous case and MIME type cannot settle it, so the client reads its chunks (`isDocumentPng`) and a card goes to the file path while a photograph goes to the image path. Routing on type alone would make the likeliest file of all unattachable by the gesture built for it. Chips: staged ones in the attach bar, sent ones under their user bubble, and either opens the same read-only viewer ([`AssistantFileViewer.svelte`](../src/lib/components/assistant/AssistantFileViewer.svelte)), which pages the text through the JSON API a window at a time (a 10 MB file must never reach the DOM in one string) with the SAME line numbers the tools speak, so a line the assistant quoted can be checked.

**Writing entry art**: `edit_character_images` is the write end of the image trio (know → look → **edit**): `set_portrait` / `add_to_gallery` / `remove_from_gallery` / `clear_portrait`, on any character or persona. **Two arguments say which picture, and the split is what makes art movable between entries.** `image` names it in the only vocabulary there is, the user's uploads (`"attachment N"`, or a bare `"attachment"` for this turn's) and an entry's own art (`"portrait"`, or a 1-based gallery number oldest-first, the same vocabulary `view_character_images` uses), while `sourceId` says which ENTRY those last two resolve against, defaulting to the target. An id belongs in an id-shaped argument rather than packed into the reference string: `argNotes` strips ids from an approval card precisely because a person cannot act on one, so a reference carrying an id would put the unreadable half of the call in the field the card shows. `sourceId` is **refused, never ignored**, where it cannot mean anything (`remove_from_gallery`, `clear_portrait`) or contradicts the reference (`"attachment N"`): a quietly dropped argument files a picture from somewhere nobody named; pointing it at the target itself simply means the target's own art, so the no-op guards still fire. So *"make a character from this picture"* is `create_entity` + `edit_character_images`, *"give Mira the portrait of Aria"* is one call, and *"promote her third gallery image"* is one call.

`run` and `preview` share **one plan** (`planEdit`): it validates the action, resolves the source entry, the reference and the file, and READS that file, so a broken picture fails before anything is written and before the card promises a copy. Every refusal the call would make is therefore a refusal the card shows, and a cross-entry copy is named on it by the entry it comes from ("Copies Aria's gallery image 1 into Mira's own art"), never by an id. It lives in **Writing**, not Images: Images governs looking at library art (sending bytes to a model, at a cost) while this only rearranges pictures the user brought or already owns and sends nothing anywhere. Since Images is off by default, filing it there would dead-end the two-tool recipe on every fresh install. Three shapes of the call are priced rather than waved through (`escalates`): clearing a portrait, dropping a gallery image, and **replacing** a portrait, all of which leave the entry naming one picture fewer with nothing in the app to put it back. The preview raises those to `delete`, which is the permanent mark their card rows wear. Setting a first portrait, or adding to a gallery, takes nothing away and stays an ordinary write.

**Character versions**: every variant OPERATION lives in exactly two dedicated tools (`versions.ts`); every other tool reads and writes the entry's live `data`, which is always the active variant. One exception, and it is informational: a `read_entity` on a versioned character folds in `versionSummary` (versions.ts), `activeId` plus the roster, because a read that stays silent hands the assistant one variant as though it were the only card, and it then edits blind. A character with no variants gets no roster, since saying "unversioned" on every read is noise. `edit_entity`/`read_chat_context` still never mention versions. *Leave versions alone unless the user brings them up* is stated once, on the family's own index line in [`groups.ts`](../server/assistant/registry/groups.ts): no data-model entity, no prompt section, and not repeated in either schema. `read_character_versions(characterId[, versionId])` lists the roster (id/name/active) or reads one parked variant's fields (via `characterVersionFields` in `entities.ts`, the same projection a character read uses minus the unversioned identity fields); it is characters-only and reports `versioned:false` for an entry with no rows. `manage_character_versions(characterId, action, …)` does the mutations: `switch` (point the entry at another variant's `data`; existing chats keep their pin), `create` (fork the live data into a named variant, and on the FIRST fork of an unversioned character materialize an "Original" baseline + `pinUnpinnedChatsToVersion`, then broadcast `library` **and** `chats`), `rename`, `delete` (refused while chats are pinned via `pinnedChatCount`, or if it's the only variant; deleting the active one falls back to another variant first). It replicates the library store's version lifecycle (`characterLibrary.svelte.ts`) directly against `serverDb` because the assistant runs server-side: the store's client orchestration isn't reachable, so the invariants (mirror-on-save keeps the outgoing row current, so a switch needs no explicit park) are hand-honored here. The first fork's four writes run in one transaction, so a character never ends up half-versioned.

**Attachment lifetime**: files under `images/chat/` are owned by the rows that reference them. `deleteChat` / `deleteAssistantSession` / the message deletes collect their paths and hand them to `dropOrphanedChatImages()` ([`db.ts`](../server/db.ts)) once the rows are gone: a file is unlinked only when NO message and no assistant message points at it any more (branching and forking a message *copy* its attachment list, so one file can have several referrers). The sweep is hard-scoped to `images/chat/`, which is exactly what the copy-on-adopt rule below buys: a portrait made from a chat attachment survives the chat it came from. Entry art is the mirror image: a library entry owns every copy under `images/characters/` / `images/personas/`, so deleting one takes its portrait and gallery files with it, in the store and in the assistant's adapter alike. **What the row names is the whole set**: an upload made in the editor is on the entry the moment it is picked (architecture/library.md), so there is no staged copy to hunt for, but no sweep anywhere reaches those folders (the boot sweep is scoped to `images/chat/`), so a file either delete path forgets outlives everything that could name it.

Every delete is immediate and final, and sweeps its files inline with the rows; the gate is the confirm BEFORE the act (the destructive-act ladder, architecture/ui-shell-settings.md). A library entry owns three sets of pictures and `delete_entity` names all three (portrait, gallery, sprites; architecture/library.md), since nothing else sweeps `images/characters|personas/` and one set left out sits on disk forever. Session deletion is asked in the history list's confirm dialog, which names the session, states its message count, and says when a running turn will be stopped. The store (`assistantSessions.svelte.ts` `deleteSession`) then stops the turn first (session-level, so a turn merely adopted from another device or an earlier page load cannot run on against a deleted row) and deletes server-first, so a failed delete changes nothing on screen and only toasts.

Two invariants hold it together. **Ownership**: a source is always *copied* into `images/characters/` or `images/personas/` (`copyImage(path, category)` in [`files.ts`](../server/files.ts), carrying the thumbnail when the source has one) and never aliased, so clearing the chat can't blank a portrait and dropping a gallery image can't blank the portrait promoted from it; a removal only *unlinks*, so dropping a gallery image leaves its bytes on disk for the entry's other references. **Stable numbering**: `AssistantContext.userImages` is built by `collectUserImages()` from the persisted `assistant_messages` transcript, not the model-facing context: the context is trimmed at ~120 messages, which would silently renumber the roster and hand the assistant the wrong picture. User turns are never deleted (only a failed *assistant* turn is, on retry), so the list is append-only and `"attachment 3"` means the same image for the tab's life. Each request states the roster in an internal note (`describeAttachments()`), which also carries the not-vision-capable warning when the model can't receive the images at all. **The panel's viewer pages that same roster**, and this is the one coupling worth honoring by hand: `AssistantTurnTimeline` rebuilds the list by the identical walk (user turns in order, their `images` concatenated) and hands it to `ImageLightbox` with the counter reading "Attachment 3 / 7", so the address the assistant answers to is the address on screen and a picture it names can be swiped to. That is also why the viewer is scoped to the TAB and not to the bubble it was opened from: a per-message set pages one turn's pictures and leaves "attachment 3" unreachable. Its order is the transcript's order, so next always means further down. **Missing files heal, they don't brick**: before each turn, `healMissingImages` (loop.ts) drops context image paths whose files no longer exist (an entry deleted from the library, a swept attachment) and wedges a system note naming them: one dead path must not fail every future request of a long-lived tab. Only THIS turn's fresh uploads stay strict and fail loudly. The roster numbering never shifts (numbers are the invariant); resolving a healed number in `edit_character_images` fails loudly while the call is planned, which is also when its approval card is drawn. A **refused** image is dropped at the other end of the same turn: an injected attachment that no request ever carried (the provider rejected the request: an image format it cannot decode, typically) is stripped in the loop's catch, keeping the message and naming the files, because a provider that refuses those bytes refuses them identically every later turn and persisting them would dead-end the whole tab with no way back. An abort is not a rejection, so a stopped turn keeps its attachment.

**Nothing the assistant does can be undone.** There is no undo button, no revert payload on a tool result, and no checkpoint: a capability's write is durable the instant it runs. The safety surface sits BEFORE the work instead (see *Approval* below): what the assistant is about to do is what the user gets to see and refuse, at the one moment refusing still costs nothing. Three consequences worth naming. `this_only` message deletes are **refused outright** when the target heads a branch and holds replies, because the re-parent would merge them into the fork (the rule lives in `serverDb.deleteMessageOnly`, so this adapter inherits it rather than repeating it; the thrown message names the fix, and `dispatch` hands it to the model as a normal tool failure). Deleting the turn the user is reading leaves the chat **readable**: the db retreats the chat's leaf to the nearest surviving turn as part of the delete (`repairChatPointers`, architecture/server-core.md): this door has no transcript behind it to re-home the view, and a leaf left naming a deleted row renders the chat empty with every message still in the table. And every delete sweeps its own files inline, the way the rest of the app does: the assistant has no reason to keep bytes alive past their rows.

**Approval: the safety surface, and it sits before the work.** One ladder decides everything. `RiskClass` in [`types.ts`](../server/assistant/types.ts) is **read < write < delete**, every capability declares the rung it sits on (`Capability.risk`), and the two per-TAB modes are two answers to one question (`APPROVAL_THRESHOLD` in [`loop.ts`](../server/assistant/loop.ts)): **Manual** asks from `write` up (everything that changes anything, reads untouched) and **Auto** asks about nothing, deletes included. A mode is one line and nothing else, which is what makes it predictable: no per-tool list to learn, no size at which a write quietly becomes a question, and nothing between reviewed and not. The whole policy is `needsApproval`, exported so `smoke.ts` can assert it, because a wrong answer there means a call runs having never been shown. And the loop **refuses a mode it does not recognize** instead of reading it as "no threshold": the wire is hand-assembled, so this gate has to degrade loud, never open. A page whose build predates the current mode set gets an error naming the fix (reload), not a silently unreviewed turn.

**The mark and the gate are the same number.** `ApprovalCall.risk` is both what paints a row as a delete and what decided the row is on the card at all, so a call the card shows as permanent can never be one the mode waved through. **Where a call sits can depend on its ARGUMENTS**, and those capabilities carry `escalates`: `manage_character_versions` only deletes when its action says so, `manage_greetings` only on `remove`, `edit_character_images` only when it clears a portrait, drops a gallery image, or REPLACES one rather than setting a first. Declaring the whole tool `delete` would stamp a plain version `switch` with the permanent mark, so the floor stays `write` and the `preview` raises it (`ApprovalPreview.risk`, raise-only). The gate runs **once per model step**, before any of that step's calls: a cheap name-only pass asks the CEILING (`riskCeiling`: `delete` for anything that escalates, and for an unknown tool, since guessing low is the one direction that could run something unseen), `previewCall` prices the survivors, and the same threshold is then applied to where each call actually landed. `src/lib/contracts.test.ts` fails a capability that declares no rung, one above `read` with no `preview`, and one that escalates without a preview that raises.

A bulk `update_entities` sweep is a `write` however many rows it reaches: it replaces values the card shows and the timeline keeps a diff of, and its `limit` param (500 hard cap) is what bounds it. No row count raises its rung, deliberately: a size at which an edit turns into a question is a line nobody can predict, and predictability is what the ladder exists for. Manual therefore shows it as one row stating its size, and Auto runs it like any other write.

**The mode never reaches the model.** It is not in the system prompt, not in the tool list, and not in the session's frozen settings: it rides each request's body instead ([`transport.ts`](../src/lib/services/transport.ts) `approvalMode`, whose payload literal is typed against the request shape, so a required field cannot silently fall off the wire), so switching it costs no prompt cache and no resend, and there is no Apply notice attached to it. Per tab and in MEMORY only: a tab loosened for one long job falls back to the standing default (`assistantApprovalMode`) on the next load, which is the safe direction to forget in. A running turn keeps the mode it was sent with: the threshold is read once, at the top of the turn.

**Manual ships as the default**, and Auto is chosen knowingly. [`assistant-approval.ts`](../src/lib/config/assistant-approval.ts) is the one home for how the two read to a person: label, the sentence for the settings page, the menu-width line for the composer's pill, the standing badge (*No review*, in the Capabilities page's badge shape), and the confirmation Auto shows **every time it is picked**, on both surfaces. A stored value outside the pair reads as Manual (`readApprovalMode`), the safe direction. The copy states what a mode does and does not review and where the record of the work is, never a warning about the reader's judgement: the point is a deliberate choice of working style, not a scare. Manual has no confirmation: tightening a safety switch needs no ceremony.

**The card is built by the capabilities, not by a second opinion.** `Capability.preview(args, ctx)` describes a call it has not run; `previewCall` (registry/index.ts) assembles the row from it. **Every capability above `read` has one**, and `src/lib/contracts.test.ts` asserts it, because a write with no preview falls back to its tool name and its raw arguments, which is a row asking the user to trust a change nobody described. The previews reuse the **same pure derivations their results carry afterwards** (one branch check, one memory pricing, one save-door rule), asked before the write, since a deleted row has no coverage left to price; where a preview and its `run` would otherwise resolve the same target twice, the resolution is one shared helper (`bulkPlan`, `resolveSteeringScope`, `loadPersonaToActivate`, `findEntry`, …), so **every refusal the call would make is a refusal the card shows** instead of a promise the tool then breaks. `update_entities` is the sharpest case: a card that priced "847 rows" for a call the tool then refuses would be lying about the one number it exists to state. A preview must not mutate and may throw: a throw becomes a `Could not preview: …` warning line on the card rather than killing the turn, and the call fails with that same error the moment it is approved. `previewCall` asks the SAME family guard `dispatch` does, so a call from a family switched off mid-turn is shown as "switched off and will not run" instead of being offered for approval.

**A row names the thing, the card names the deed once.** The preview splits what it knows four ways, and the split is what keeps a twenty-row card readable. `act` is the deed without its target ("Delete message") and `actNotes` are true of the deed however many rows repeat it (how far a delete reaches, which save door an edit takes); `label` and `notes` are this row's own: which turn, what it costs, whether it lands off the branch. What is true of every call on the card is said by NEITHER: nothing the assistant does can be undone, so permanence is the delete-class row's mark and never a sentence. A line stating it on twenty rows is one the reader learns to skip, and it crowds out the part that differs. Rows sharing `tool` + `act` + `within` collapse under one heading that states the act, the count, the container and, from each row's `at`, the stretch of chat they cover ("Delete message · 20 · in The Tower · turns #41 to #60"); 4+ rows start folded, and a folded row is one clipped line of the text at stake, one click from the whole of it. Grouping is render-time only, exactly like the timeline's batching: `ApprovalCall.index` is the server's ordinal and every answer is addressed by it, never by row position. Two things follow. **A message is named by where it sits and who said it** (`describeMessage` in chat-reads.ts: "Turn #42 · Aria", or "Off-branch · Aria"), because a message has no name and "user message" identifies nothing on a card holding twenty of them; one path walk answers both the position and the branch check, so a preview asks it INSTEAD of `offPathWarning`, never as well. **And a delete shows the text that is about to go**, as a diff to nothing: the same inline diff an edit gets. The card speaks to the PERSON: the branch warning has two wordings, `offPathWarning` for the model (which ends in an instruction about what to report) and `OFF_PATH_NOTE` for the card, kept side by side so neither moves alone. **A capability module writes for both audiences in one object literal**, and which field a string sits in is the whole of the difference: `label`, `act` and a note's `text` are read by a person, as is every `ToolError` message (`dispatch` draws it as the failed row), while `summary` / `describe` / `whenToReach` / a result's `note` are prompt text. So the no-em-dash rule (architecture/ui-shell-settings.md) is asserted here per FIELD rather than per file, in `src/lib/contracts.test.ts`.

**Arguments are the floor, and the floor leaves out what a person cannot use.** Every capability above `read` predicts, and reads are never shown, so raw arguments now reach only the two rows whose preview could not speak: a tool switched off mid-turn, and one whose preview threw. `argNotes` drops the ids and the `confirm` token (an anti-accident handshake between the model and the tool, not a decision input), and the label is the tool name as a sentence. The developer's name for it still sits in the mono chip beside the row.

**A pending row can be looked at before it is answered.** `ApprovalPreview.target` names where the thing lives in the app, and the card routes it through the same [`assistant-targets.ts`](../src/lib/services/assistant-targets.ts) the settled timeline rows use: one routing table, since the two surfaces point at the same places and a private copy in either would drift. Both minimize the full-screen mobile widget first: the destination renders below it, and the tap would otherwise look dead. [`assistant-icons.ts`](../src/lib/config/assistant-icons.ts) is shared for the same reason: a tool wears the same mark on the card that approved it and on the row that reports it.

**Waiting is safe, which is the point.** The pending card lives on `LiveTurn.pending` (server/index.ts), never on a socket, and is broadcast to every open page: the answer may come from any device with the tab open, the first one wins by `askId` (`settlePending`, the one settle path), and `assistantStatus` hands the card back to a page that reloaded mid-wait. **That slot is ONE, and it is a union**: approval calls, or the questions `ask_user` asked (see *Asking the user* below). A turn runs its calls in order, so it can only ever be waiting on one of them, and "both pending" must not be representable: one wait, one settle, one recovery, one first-answer-wins, and every reading of "is this tab waiting?" asks a single thing. The two cards keep their own components and their own wire events, because they ask different questions and are answered differently. The wait is unlimited by design: nothing has been written, so a turn abandoned here (the user walks away, the server restarts) loses only work that never happened, and the row simply becomes `interrupted`. A Stop settles the card as a refusal of everything on it, the reading Stop has everywhere else. **Refusing one call drops that call only**: it returns to the model as an ordinary tool failure ("the user reviewed this call and refused it"), the turn carries on, and the model says at the end what it did not do. Client-side the card is `runtime.pending` ([`AssistantSessionRuntime`](../src/lib/types/assistant.ts), the same union), rendered by [`AssistantApprovalCard.svelte`](../src/lib/components/assistant/AssistantApprovalCard.svelte) directly above the composer and **never as a modal**: the user has to be able to read the chat behind the panel while deciding. Rows answer one at a time, a whole group at once (and a group's pair only ever answers what is LEFT, so a row decided by hand is never flipped by a gesture aimed at its neighbours), or the whole card in one gesture; a row-by-row pass sends nothing until the LAST row is decided, because the server takes exactly one outcome per card and a half-answer would refuse what the user had not reached yet. `ApprovalCall.index` is the call's absolute ordinal in the model step, **not** the card's row order, and the card echoes it back untouched: that number is what `loop.ts` matches a refusal to its `tool_call_id` by. A turn held on a card announces itself in three places and none of them takes the screen: the activity line stops moving and reads *waiting for you* (motion means working, and here nothing is), the tab strip marks that tab, and the closed launcher badges, scoped to OPEN tabs, since a badge has to point at something answerable, and a card left on a closed tab is recovered by reopening the session from history.

**Asking the user** ([`ask.ts`](../server/assistant/registry/ask.ts)): `ask_user` is the one capability whose answer comes from a person rather than the workspace. It is a **tool**, not a loop state, and that is the whole design: the turn stops on a card, the answers come back as an ordinary tool result, and the SAME turn carries on and acts on them. Ending the turn to ask in prose instead would make the user's reply a new turn, which re-primes the context and throws away everything the assistant had lined up. It rides **Core**, so it never switches off (an assistant that cannot ask is one that guesses), and its rung is `read`, so no approval mode gates it, **including Auto**, deliberately: that mode is a choice not to review writes, not a choice never to be spoken to. It reaches the person through `AssistantContext.ask`, threaded loop → `askQuestions` (server/index.ts) → the same `LiveTurn.pending` slot the approval card uses. A context with nobody on the other end (a preview, the smoke script) has no `ask` and the tool refuses loudly rather than inventing an answer. Because it waits, `Capability.run` may return a promise, and `dispatch` **awaits** it inside its try: a bare `return` would let the rejection past the catch and kill the turn instead of failing one call.

**One question per card, a series the user steps through** ([`AssistantQuestionCard.svelte`](../src/lib/components/assistant/AssistantQuestionCard.svelte)). The question sits ABOVE the scrolling options rather than inside them (capped, so a pathologically long one still leaves the options on screen): four long options scroll, and a question that scrolls away with them leaves the reader picking an answer to something they can no longer see. One call carries 1 to 6 questions (more is a form, not a conversation, and every one of them blocks the work); each is its own card, stepped through with one pair of arrows and a counter, and answers and typed text live outside the card, so stepping back shows what was chosen there. **A single-choice pick advances the series by itself**: one tap has answered that whole card, so asking for a second on the arrow is a step that decides nothing. A multiple-choice card is not finished by its first tick and never auto-advances, and the last card of either kind stays put: the send is the one gesture that commits. **Nothing is sent until every card is answered and the user says so**: the server takes exactly one outcome, and the assistant asked because it needs all of them. Independent questions belong in one call; a question whose options depend on an earlier answer belongs in a later one. **The free-text box is the panel's, not the model's**: it is on every card, which is why the schema *forbids* an "other" option (the model spending one of its four slots on a door the card already has). In a single-choice question it behaves like the classic "Other:" radio (typing deselects the options, picking one releases the box without erasing what was typed), and in a multiple-choice one it rides ALONG with the ticks, because "these two, plus this" is how the answer actually comes out. **Every option carries a button that drops its words into the box**, because the commonest answer of all is one of the four with a change to it: without it the user retypes the whole option or settles for the one that is not quite right. The words land at the CARET, so nothing already typed is eaten, and the card does not advance (they are about to write). On a multiple-choice card the option leaves the ticks as it goes, or the model would read the same answer twice, once picked and once written, in two different wordings. Answers come back as the option **labels**, not indexes: the model wrote them, so they round-trip with nothing to re-resolve and the persisted step reads as a record of what was chosen. Each answer carries `ownAnswer`, true when the user typed instead of picking, which means the options missed, and is worth knowing before offering the same four again. Every malformed card is refused **before** anyone sees it (one option is not a choice, five is a list, a repeat is not a second path), never quietly repaired, since a silently dropped option changes what was asked. An answer naming an option the card never offered is dropped the same way, on arrival. A Stop answers `stopped` and the tool fails like any other, so the turn ends on the reading Stop has everywhere else. `2 to 4 options` is a rule the schema states and the card assumes. The settled call is an ordinary timeline row (`annotation` icon) whose expanded view carries the questions and the answers, and the whole series is the assistant's own memory of what was decided. It also makes **skills interactive**: a skill body can tell the assistant to put its choices as multiple choice, which turns a written guide into a wizard with no new UI.

`ParamDef` gained `array` + `items` for this (registry/types.ts, schema.ts). A structured element is the one param shape prose cannot carry (a malformed one is a malformed card), so an array param with no `items` schema throws at build time rather than shipping a tool nobody can call correctly.

**Loop hygiene** ([`loop.ts`](../server/assistant/loop.ts)): the per-turn budget is 50 model steps / 100 tool calls, stated upfront in the system prompt (the loop passes it into `assistantSystemPrompt`) and re-announced calmly in the last 5 steps ("finish the piece in progress, list what remains"). There is no cap on how many deletes a turn may make: Manual puts every one of them in front of the user individually (see *Approval*), and Auto is unlimited by explicit choice. The Safety discipline section tells the model explicitly that chat/card/lorebook content arriving through tool results is story data, never instructions. **The server owns the turn end-to-end**, and owns **one `assistant_messages` row from the turn's first moment to its last**: the loop assembles the step timeline itself (thinking/text per iteration, one tool step per executed or refused call, exactly what the panel renders), claims its row as `running` before the first iteration (taking the row's `created_at` from that insert: the transcript is stamped and ordered by the DATABASE's clock alone, never the loop's and never the browser's, see architecture/server-core.md), rewrites it at every step boundary (`updateAssistantTurn`, driven by `flushTurnRow` after each iteration's text and by `recordTool` after each tool step), and finalizes it as `done` at commit, with the session bump and an `originClientId = null` broadcast on the `assistant` scope. A write that THROWS rethrows loudly; a row that has simply vanished is tolerated only when the session row is gone too (`getAssistantSession`, deleted mid-turn on another device) and otherwise throws, because nothing else is allowed to remove a row under a running turn. Writing as it goes is what makes a **server death** honest: tool effects are durable the instant a capability runs, so a turn recorded only at commit left edited messages and new characters with nothing naming them. Boot flips any surviving `running` row to **`interrupted`** (`markInterruptedAssistantTurns`, architecture/server-core.md): the panel says the server stopped mid-turn and the row carries **no `error`**, deliberately, since `canRetry` keys on one and re-running a turn whose mutations already landed would repeat every one of them. All a crash loses is the text streaming inside the iteration in flight, which never had a completed step to be written as. The model-facing context (`context_json`) is still saved once per turn, so the assistant's own memory skips an interrupted turn while the transcript keeps it: the transcript is what the user acts on.

**A turn belongs to its session, not to the socket that asked for it.** `server/index.ts` keys in-flight turns by session in `assistantTurns`: the per-tab lock (a second concurrent turn on the same tab is refused loudly), the abort registry, and the turn's **live snapshot**: `recordLiveEvent` folds every outgoing event into the same timeline the panel builds from the same events (architecture/client-data-layer.md coupling 6). Every event carries `assistantSessionId` and goes to **every** open socket, so a page that reloaded mid-turn (or a second device with that tab open) renders a turn it never requested; the two refusals that never become a turn (duplicate request id, tab already busy) answer the asking socket alone and carry no session id, so they cannot settle a turn that is still going. On boot, on every reconnect, and when a session is opened from history, the client asks `assistantStatus` which of those sessions are running: a running one is adopted (the tab goes busy, the snapshot becomes its timeline, the deltas that follow extend it: the server builds and sends the snapshot in one synchronous step, so nothing slips between it and the next frame), and a session with nothing running drops any stale busy state and re-reads its transcript, which also closes the race where a turn finishes between the boot read and the socket opening. A `running` row is filtered out of the rendered transcript (`loadMessages`), since the runtime slot is already drawing that turn. `assistant-cancel` matches by request id or `assistantSessionId`, and the store's `stop` falls back to a session-addressed cancel when this page holds no request of its own, so Stop lands after a reload and from another device (the deferred session delete's final abort goes the same way). A dropped socket rejects the pending as `detached` and the tab **stays busy** with the timeline it has until the reconnect's status query says otherwise. A Stop already in flight settles as a clean abort instead. `syncReload` skips a tab's transcript refresh only while a turn started on THIS page is in flight (that window holds local writes a db read would race: the optimistic user bubble, a retry's row delete); a turn running elsewhere makes no local writes, so its tab refreshes normally.

The `assistant-done` / `assistant-error` events carry the persisted row as `committed`; the store *adopts* it (`absorbCommitted`, deduped against the sync reload, runtime settled in the same tick so the turn never renders twice) and commits nothing itself for a finished turn: a client-side error bubble (`commitLocalError`) exists only for failures that never reached the server (pre-flight throws, lock/duplicate-id refusals). A page that started the turn settles it through its own promise; every other page settles it from the event feed, which is the only path that can tell it a turn it merely watched has ended. **An empty finish is an error, not a shrug**: a turn ending with no reply and no action throws, naming the finish reason (`length` gets the raise-max-tokens hint), so the panel gets a real error and a Retry. Warnings are PERSISTED on the committed row's reply, not lost in transit: output-limit cut (`length` on any iteration), abnormal provider finish with partial output (content filter and kin), a failed context save (`persist()` logs AND warns, never silent), plus the budget-capped `⏸` and stopped `⏹` notes; `capped` survives inside `usage_json` even when a provider reports no token usage, so Continue always appears when it should. Each iteration reports `contextTokens` (last iteration's prompt+completion, real provider-reported tokens); the blob feeds the **context meter** against the Assistant connection's `contextSize`, and stopped/failed turns keep their reading (5s stop-grace for the server's final accounting). A tool result is **never shortened**, but the context IS bounded (see the trim below); the meter shows where the tab stands against that context size and offers "New tab" inline past 80%. Tool-call arguments that arrive as invalid JSON (max-tokens truncation, provider glitch) are **refused loudly without running the tool**. Tool-call *progress* is what makes a long write visible while it happens (see *Watching a call write itself* below). Transient provider errors (429/5xx/timeouts) retry up to 2 times with backoff, but only while nothing of that attempt has streamed; mid-stream `{"error":…}` events from the provider layer throw with the unwrapped upstream message (see architecture/llm-providers.md). Persistence: tool results are stored **verbatim at any size**, never shortened, never cut (a cut corrupts the JSON the model replays and silently degrades every later turn; the context meter is the management surface, by explicit owner decision). **Every budget here is measured against the request's fixed head, never against the raw window.** That head is the system prompt PLUS the tool schemas (`overheadTokens` in loop.ts, estimated over the serialized schema list). The tool block is normally the larger of the two, and a budget blind to it let a small connection pass the fit check and then 400 at the provider on that turn and every turn after it. So the conversation's budget is `contextSize − head`, and the persisted context is bounded in BOTH units against it: past ~120 messages, or past ~70% of that budget in estimated tokens (conservative ~3.5 chars/token + flat 1000/image), the oldest whole turns drop at **real** user-message boundaries (never at the loop's own image-injection user messages, never splitting a tool_call from its results) down to 80 messages / ~55% of the budget (hysteresis: the cache prefix shifts rarely, not every turn), with a cumulative `(memory note: N older messages were trimmed…)` system line prepended so the model knows. Before the first iteration the loop re-fits the stored context to the CURRENT window (lowering Context Size, or pointing the surface at another connection, can shrink it under a tab) and refuses the send with an actionable message rather than letting the provider 400 forever, with the two cases named apart, because they have different fixes: a conversation that cannot be trimmed small enough (one giant turn) says so, while a head that alone outgrows the window says THAT, since no amount of trimming touches it. A failed turn can be retried (`retry: true` on the request): the server re-runs the last turn without appending the user message again. The retry match skips the loop's own image-injection user messages, so a turn that died right after one still retries clean. Corruption degrades loudly, not fatally: a corrupt `assistant_messages` row loads as a visible error bubble instead of bricking the tab (`getAssistantMessages` runs at every turn start via `collectUserImages`), with its `images_json` parsed in its own try, so the attachment roster never silently renumbers (an unrecoverable images cell says so in the bubble), while a corrupt/non-array `context_json` throws with an actionable message naming the session. Panel-side, runs of 3+ consecutive tool actions auto-collapse into one expandable row (`groupSteps` in [`AssistantTurnTimeline.svelte`](../src/lib/components/assistant/AssistantTurnTimeline.svelte)): grouping is render-time only, so the persisted step array is untouched; running rows are outside it, since they are not steps. **Every non-diff step is auditable**: the loop stamps `args` (skipped when a diff already carries the payload) and the tool's whole result as `resultPreview` onto the uiResult, and the timeline's expand chevron shows them. That display copy is **never cut**, the same rule the model's copy follows, for the same reason: a trail that stops at a fragment cannot answer what the assistant actually read, which is the only thing it is for, and the panel scrolls it. Steps recorded while a 2KB cut existed still carry `resultChars`, so the timeline labels them `cut · N of M chars` instead of passing a fragment off as the whole result. The assistant session also remembers the chat it most recently worked against (`assistant_sessions.chat_id`, stamped by `commitTurn` latest-non-null): the history popover renders it in the meta line so "which chat was this about" reads at a glance; the composer (draft + staged uploads) lives in the store per session, so minimizing the widget keeps a half-typed message, and a boot-time sweep reaps uploads whose send was abandoned (architecture/server-core.md). The composer needs no pre-created session: the first send/attach lazily creates one (`orphanDraft` holds the pre-session text), the empty state carries tappable example prompts, and Enter keeps the chat composer's touch guard (coarse pointers never send on Enter).

**Watching a call write itself** (the whole mechanism exists only while the Assistant connection streams; with Stream response off no deltas arrive and a call is simply invisible until its step lands): when the model calls a tool that writes a lot of text (a message rewrite, a character field, a lorebook entry), that text streams as tool-call ARGUMENTS: nothing has run yet and there is no result to render, so the panel would otherwise sit dead until the call returns. The provider layer's `onToolCallDelta` closes that: the loop derives one display line from the accumulated arguments ([`toolProgress.ts`](../server/assistant/toolProgress.ts)) and sends it as `assistant-tool-progress` `{index, name, text}`. Three rules hold it together. (1) **Throttled and derived, never raw.** Providers re-send the FULL accumulated arguments on every delta (quadratic traffic over a big edit), so a call emits at most one frame per ~150ms, and a frame whose line is unchanged is dropped (a call whose long value has closed would otherwise repaint the same text for the rest of its arguments). What rides the wire is ~200 characters of readable text, not the JSON. (2) **The line is the LONGEST string VALUE in the fragment**, whitespace-collapsed, tail-marked with `…`. The fragment is a complete prefix but normally unterminated, so it never goes through `JSON.parse`; a hand-written scan reads it, keys are tracked only to tell key position from value position, and a value under ~40 characters yields an empty line: ids, enums and field names are not work worth watching. Picking "whatever is being written right now" instead would flip a 3000-character rewrite over to a 12-character trailing argument in the call's final frames. It is display only: whether a call actually RUNS is still decided by a real parse of the finished arguments. (3) **One row that matures, never two.** The panel keeps these on `AssistantSessionRuntime.running`, deliberately NOT `AssistantStep`s: a call with no result has nothing to persist, and the step array is exactly what the server commits. A row wears the same icon and row furniture a finished action gets, in the place that action will occupy, and **nothing about it moves**: it is content, its liveness belongs to the activity line at the foot of the turn (see *One live element*); when the result lands, the oldest running row hands its place to the new tool step (results arrive in call order). **A call draws a row only once it has a line to show.** Short arguments (an id, an enum, a name) derive nothing by design, so a row for one of those would be a bare tool name repeating what the activity line already says and the settled step is about to say properly. The call is still fully visible, as that line's motion and phrase. A row therefore appears mid-call, the moment a long value opens, which is why the panel's scroll-follow counts rendering rows (`liveToolRows`) rather than running calls. The list is cleared when the model step ends (`assistant-iteration`: call ordinals restart, and an aborted or action-capped call never reports a result) and when the turn settles. It is **ephemeral**: `recordLiveEvent` does not fold progress into the live snapshot, so a page that reloads mid-call re-draws the row from the next frame (at most one throttle period away) rather than the durable timeline carrying state that can never be committed. Rendering rules the row is built to keep, all of them load-bearing at ~7 frames a second: its footprint is FIXED (the text is one clipped line, never wrapped, so nothing below it ever moves, and the panel's scroll-follow tracks only the row COUNT, never the text), the text is `aria-hidden` (announcing it would machine-gun a screen reader; the tool's name carries the meaning), and only the text node changes between frames. Exactly one live element is on screen at a time, and it is never this row: see *One live element* below.

**One live element** ([`AssistantActivityLine.svelte`](../src/lib/components/assistant/AssistantActivityLine.svelte), with [`assistant-motion.ts`](../src/lib/config/assistant-motion.ts) for the map and phrases and [`AssistantWorkMotion.svelte`](../src/lib/components/assistant/AssistantWorkMotion.svelte) for the glyphs): a running turn carries at most ONE moving thing, the activity line at its foot, present for the whole turn and never conditional: a turn always has a state, so the line always has something true to say. A settled conversation keeps the same mark, held still (`still` on the glyph, its resting frame), and so does a turn stopped on an approval card: the panel has one constant presence at its foot, and whether it moves is the whole message. Every row that can appear there shares one glyph rail (the action row's own inset, which the reasoning header and both marks match), so nothing shifts sideways as a turn starts, runs, and ends. Everything above it is content and holds still: settled actions, the streaming reply, the reasoning block (whose own pulse is gone: a second indicator beside its title was the same word twice), and the running call's row, which wears the static icon it will keep once its result lands.

The line answers two different questions, and the split is the whole design. **What is happening** is its head: one of eight family motions while a call is in flight (`sift` / `read` / `write` / `make` / `cut` / `bind` / `look` / `go`: every entry in `CAPABILITIES`, split the way `TOOL_ICONS` already splits them), the cursive while the reply is arriving, the ellipsis (`idle`: three dots that part and gather, resting as the gathered point so a frozen frame is still one solid mark) while the model itself is working, plus a phrase from `WORK_WORDS` rotated every ~4.6s and never repeated twice running. Reasoning is the one phase with no phrase at all: the block above it is already titled "Thinking…", so the glyph and the trail carry it alone (the streaming reply has no such label, which is why writing keeps its phrase). **A turn held on an approval card is the one phase that does not move**: it outranks every other reading (nothing is in flight by definition), the glyph is frozen at its resting frame and the phrase is a single fixed line, *waiting for you*. Motion here means the assistant is working, and a breathing head over a card that needs answering reads as "leave it alone", which is the one thing that must not happen. A phrase is only ever on screen while its work is genuinely in flight, which is what lets it describe rather than guess; the moment a result lands the line moves to the waiting phase, because a phrase that outlived its call would claim finished work, and a fast tool spends far longer waiting than working, so that stale claim would be the state the user mostly sees. **Whether anything is actually happening** is its trail: a fixed strip of ticks whose head advances one notch per burst of real activity (reply tokens, reasoning tokens, tool-call argument frames, a step landing), throttled to ~110ms, plus a beat of its own for as long as a call is IN FLIGHT. That beat is load-bearing, not decoration: short arguments (an id, a name) derive no progress line at all and server-side execution emits nothing, so an entire call would otherwise pass with the trail frozen, which reads as a hang. The one state that keeps no beat is waiting on the model, where nothing is observable by definition, so a stalled provider shows a frozen trail instead of a spinner turning over a dead socket. The head keeps breathing while the trail is frozen, deliberately: motion means alive, an advancing trail means productive, and a completely still row would read as a crash during an ordinary wait.

`idle` doubles as the fallback for an unmapped tool; the row's tool name sits beside its glyph, so that reading never collides with the line's. **No step counter rides the line**: the timeline growing is the progress signal, and a number next to a phrase was clutter; the one thing lost is a turn that loops without acting, where nothing new appears. The phrase and the trail are both `aria-hidden` next to a visually-hidden "Working" (they are flavour and evidence; the fact is the label), and both intervals live and die with the component. Rendering is bounded by construction because this sits on the ~7-frames-a-second path: a fixed tick count with only opacity changing, one clipped phrase that never wraps, and throttled advances, so no amount of streaming can resize the row or move the timeline above it. Every glyph's RESTING state is a readable pictogram, because `prefers-reduced-motion` freezes it there permanently. The four whose rest state would be nothing (a lone card, two stacked dots, a bare dot, an unstruck block) carry an explicit static pose for that case, while the trail keeps working and merely stops easing.

**The panel's face** ([`AssistantMascot.svelte`](../src/lib/components/assistant/AssistantMascot.svelte)): a raccoon in spectacles, wherever the assistant names itself: the widget header, a session tab, the empty state, and the closed launcher, which is why none of them carries a generic icon or a bitmap. The app ships the same animal whole in `static/mark.svg` and as a bare head in `static/icon.svg` (architecture/build-packaging.md); this is a third drawing of it, and it is **self-contained**, sharing no data with either, so redrawing them leaves this face alone. The spectacles are the whole of what tells the assistant apart from the app's own icon, which is why they are not a detail to simplify away. It is chrome and never a status: it does not animate, because motion in this panel means work is happening. Three invariants keep it honest. It is a two-tone print, `--mascot-paper` over `--mascot-ink`, and **both tones are pinned**: tinting the ink with the accent is the obvious idea and it fails, since the paper is a constant near-white and the pale accents (sage, silver) then put light lines on a light face. The paper is three shapes, the face and the two ears, and they are **not this drawing's own contours**: its outline is two bands that enclose the face only together, so there is no inner edge here to lift. They are separate data, and what licenses putting them under this ink is that they are **inset from it the whole way round, measured on every radius rather than eyeballed**, so no cream can show past the line at any size. Redraw the ink and that has to be measured again. And the drawing is line work rather than a filled silhouette, so **below roughly 20px the lenses close over the eye patches** and it becomes a face-shaped smudge: at the two sizes that cross that line, the tab and the header, it sits beside its own label and may never be the only thing naming the panel.

**The assistant is the app's second delete-and-edit surface, and it pays the same memory debt as the first.** architecture/chat-sessions.md coupling 3: the transcript states, before a delete or an in-place save lands, which summaries die, how many pause behind the hole and how many turns must be re-read. `memoryCostOfMessageChange` (chat-reads.ts) asks the identical question through the identical pure functions (`changeImpact` for the numbers, `describeMemoryImpact` for the sentences), so the two doors cannot drift, and it is asked BEFORE the write, since a deleted row has no coverage left to price. Message deletes and content edits carry it: the panel row gets the short count (`memory: 1 summary dropped, 4 turns re-read`), the model gets the numbers and the transcript's own wording. A chat with memory off, or a change that touches no coverage, reports nothing: the common case stays silent.

**Two doors for a message rewrite, and the assistant picks with `minor`.** The transcript offers a person a quiet save for the commonest rewrite of a folded turn (a typo), because paying a model call to re-read a comma is the tax that stops people fixing typos (architecture/memory.md coupling 8). `edit_entity` / `set_entity` take the same door as a boolean, refused outside a message's `content` so it can never look like it buys something elsewhere, and threaded to the storage adapter through `WriteOptions` rather than smuggled into the field patch. The criterion the schema states is **meaning, not size**: typos, grammar, rephrasing and flow are quiet; anything that changes what happened is not, however few characters it moves: renaming Mahmut to Mehmet is one word and heavy, because the summaries say Mahmut too. Nothing infers it from the text, in either surface. Which door a write went through is in the result and on the panel row, and it decides one more thing: a heavy edit does NOT combine with `edit_memory_episode` (the engine's re-read throws the rewrite away), while a quiet save does, and that pairing is the only cheap way to carry a rename all the way into memory.

**The branch is part of every chat answer.** A chat is a tree, and every read here walks root→`activeLeafId` (`activePathMessages`), so a `seq` is a position on THAT branch and nothing more. Three things keep that from becoming silent corruption. The turn's workspace note stamps the branch (`branchStamp`: message count + leaf id): it sits after the user turn, so it costs no cache, and the model watches it change in its own context the moment the user swipes. Every branch-derived read (`read_chat_messages`, `read_chat_context`, `read_memory_state`) reports the `activeLeafId` it answered from, and the rule itself (target by `id`, treat a seq from a different stamp as stale) is stated once, in the prompt's `chatBlock`, since it holds for every one of them. And every message WRITE derives whether its target is still on that path (`offPathWarning`, or `offPathMessageCount` for a bulk sweep: one path walk per chat, so hundreds of rows cost one read): off-path it lands anyway, because fixing an abandoned branch on purpose is legitimate work, but the tool result carries the warning and the panel row says *off the active branch*, since otherwise the user watches an edit report against a thread that never moved. `find_entities kind:message` deliberately still sees every branch: the danger is touching one blind, not seeing one.

**Freshness: how an earlier read stays trustworthy.** The conversation is the ledger: every read or write of tracked story state stamps its model-facing result with `stateRevs`, one `{"kind:id": "<content revision>"}` claim per thing it handed over, and before each turn the loop re-checks every claim in the persisted context against the workspace ([`freshness.ts`](../server/assistant/freshness.ts); the hash, the claim scan and the note format are the pure, zero-import [`freshness-core.ts`](../server/assistant/freshness-core.ts), reachable by `bun test` without the database). Claims come from three places the scan reads by shape: tool results carrying `stateRevs`, state notes (which re-claim what they announced), and the workspace note's header line, which claims what a full attachment injected: header line ONLY, because that note's body quotes story text and a forged token there would suppress a re-read (see *Hand-added attachments*). Anything that moved (the user editing in the app, another device or tab, a version switch, the roleplay carrying on) is named in ONE `(state note: …)` system message pinned after the user turn beside the workspace note; nothing moved means no note and zero tokens, the common case. The note fires only for changes that were not the assistant's own, and it says so in one sentence (not yours, they stand, name a collision instead of undoing it), because told only "this moved, re-read it", a model can read the user's hand edit as damage and restore its own earlier version over it. The prompt states the one rule (re-read what a note names; everything else is exactly as read, so never re-read it), and `read_entity`'s summary phrases its own precondition per CONVERSATION, never per user message: a re-read obligation bound to a message boundary is a standing order to re-read everything every turn. A revision hashes state **as the assistant can see it**, never timestamps or invisible metadata (a persona rebind bumps no clock; an `isFavorite` toggle means nothing to what the model read): character/persona = identity + data + version rows (tags, greetings, art, links, a roster change and a version switch all fire), message = its five visible fields, chat = title + binding + pin + ALL message rows + the active leaf (a swipe fires like an edit, the staleness signal for a chat the workspace note is NOT stamping; the branch stamp keeps owning where the user is reading now), lorebook = name/description + the entry projection the reads hand out, `memory:chatId` = episodes + flags + the structural tree inputs the boundary derives from (disabled memory hashes its one fact, so a dormant chat's churn says nothing). Five properties hold it together. **Claims live in the context and nowhere else**: the trim drops them with the turns that made them, so the scan and the model forget together, and a crash that loses the context save leaves that turn's own writes reading as foreign, which re-reads them, the safe direction. **The note is its own dedupe**: every named item carries a `[kind:id rev:…]` token the next scan reads back as a claim, so one change is announced exactly once and the next change announces again. **Writes re-claim what they moved**: a message write stamps the message, its chat and its memory key; entry writes re-stamp the book; greetings, art, links and version ops re-stamp the entry; a bulk message sweep re-stamps the touched chats (honest because bulk refuses text fields: what it wrote is the short values the model itself set); deletes stamp `gone`, so the assistant's own work is never announced back at it as a foreign change. **Unstamped degrades safe**: a read that claims nothing merely forfeits the saving (the read-before-edit rule still forces the read), and a missed write re-claim costs one true self-note, never a stale act. **The check is per turn**, the branch stamp's granularity, and because a turn can run for minutes while the user keeps working, the write doors carry their own in-turn guards: `edit_entity`'s find/replace fails loudly against moved text, and the blind whole-value overwrites (`set_entity`, and every `manage_greetings` mutation, `add` included, since an ungated add's honest re-stamp would launder a stale claim for the `set` after it) ask ONE shared claim gate (`assertClaimFresh`, registry/util.ts) that refuses when the conversation's claim for the target no longer matches the workspace, telling the model to re-read and redo against the current text. The gate reads the turn's LIVE ledger (`AssistantContext.claims`): the loop seeds it after the pre-flight fit, from the context exactly as the request sends it (a trim that dropped a claim drops it here too), and folds each landed result's stamps back in through the same `collectStateClaims` scan, which is what lets the model's own re-stamping writes pass on the very next call; a ledger frozen at the turn's start would refuse the second write to a thing the first just re-stamped. No claim, no gate: the model never read the thing, the prompt's read-before-edit rule owns that case, and untracked kinds carry no claims at all. Both `run` and `preview` ask it, so the approval card shows the same refusal the call would make. Two reach limits are deliberate: an intervening write that honestly re-stamps the same entity (an art, link or version op) refreshes the claim, so the gate covers the direct read-then-overwrite path rather than every interleaving; and a thing held only through a WIDER claim (a message via its chat, a lorebook entry via its book) is not gated on that claim, because sibling motion inside it would refuse writes to targets that never moved. Deliberately untracked, each with its reason: skill bodies (read live at need, by the prompt's own read-before-use rule), the settings catalog (static per build), `read_connection_state` and the prompt log (point-in-time diagnostics), the active-persona pointer and steering notes (no standing knowledge to protect), and list/find results (indexes, not knowledge: acting on a row still requires the read, and the read claims). The net: the state-freshness section of `smoke.ts` asserts every producer's stamps, drives revision motion per editable field DERIVED from `ENTITIES` (a field added to `entities.ts` is asserted the day it lands), walks the note lifecycle end to end, and drives the overwrite gate both ways over a live ledger: a read then two writes in one turn never refuses, a foreign change under a held claim refuses in the call and on the card alike; [`freshness-core.test.ts`](../server/assistant/freshness-core.test.ts) covers the pure half under `bun test`.

**Full-fidelity reads** (`read_chat_messages` in [`chat-reads.ts`](../server/assistant/registry/chat-reads.ts)): message content is **always complete**: no per-message budget, no shortening markers, no byte cuts anywhere in the read path (a cut feeds the model corrupt JSON and triggers shrink-until-it-fits read loops; the panel's context meter is the cost surface instead). The only bound is **paging**: tail (`limit`, default 30), anchor window (`aroundMessageId` + `before`/`after`: their COMBINED span is clamped to the cap, `before` kept, `after` shrunk, with a note), or an explicit `fromSeq`–`toSeq` range, all span-capped at 100 messages per call: a cap on how many messages one call returns, never on their content. User rows are stamped with the `personaId` they were sent with (null = unattributed, renders as "You", noted in the result) and a `personas` legend resolves the slice's ids to names (a dangling id reads "(deleted persona)"). Attribution is locked at send time, so the assistant must never re-label history with the currently-active persona; ST-imported chats carry `personaId` null throughout, which is exactly the slice where dropping the stamp from the read would hand the model a whole history to mislabel. A nonexistent `chatId` throws ("No chat with id…") instead of reading as an empty chat, both here and in the message entity's list path (`find_entities` / `update_entities`). Labels state exactly what the model received ("Read messages 61 to 85 of 85 from *chat title*"): a label that overstates its slice is what sends the model reading in circles. The three **list reads** (`list_chats`, `find_entities`, `search_chats`) page on that same principle and share one rule: a small default page, `offset`, **no constant ceiling on `limit`**, the real total, and a `note` naming what was left out plus the exact call that fetches it. `list_chats` (30 default) and `find_entities` (20) clamp `limit` to the row/match count itself; `search_chats` cannot know its total without scanning every message, so it clamps to `NO_CAP` (util.ts) and collects one match past the page to say `more exist` honestly rather than promising a count it never computed. Both halves are load-bearing: an unbounded default writes every row of a large library into the tab's context, which every later turn then resends, while a hard cap leaves the assistant unable to return everything at the moment the user asks for exactly that. `update_entities`' 500 cap is NOT one of these: it bounds how many rows a single call MUTATES, a safety limit rather than a reading one, and it stays.

**Frozen session settings** ([`sessionSettings.ts`](../server/assistant/sessionSettings.ts), `assistant_sessions.settings_json`): the user's standing instructions, the skill index, and the enabled capability groups all shape the **system prompt and the tool list**, the front of every request, where the cache breakpoint sits (architecture/llm-providers.md). Read live, one settings edit re-prices the whole conversation from scratch, on a surface whose sessions are long and read-heavy. So a session snapshots all three on its **first turn** (`settingsForTurn`, lazy: the insert path is untouched, which is also why there is no data to migrate and why a session that has never run is never "stale") and keeps using that snapshot; a corrupt cell re-freezes from live rather than bricking the tab. The user re-syncs deliberately: the panel shows an **Apply** notice above the composer whenever `settingsStale(sessionId)` reports drift, and applying re-freezes and costs one full-price resend, stated in the button's tooltip. Drift is re-checked when a tab gains focus and when Assistant Settings closes (the only local surface that edits the three); a change made on ANOTHER device therefore surfaces on the next tab focus, not instantly (accepted, since the alternative is polling). Deliberate holes in the freeze, both so the user is never stuck: skill **bodies** stay live (`read_entity kind:skill` reads the file, so a skill written mid-session is usable, just not advertised in the frozen index), and switching a capability family OFF takes effect on the very next turn: the loop intersects the frozen set with the live one (`offered` vs `effective`), so the tool list stays put while `dispatch` refuses, and a one-time `(capability change: …)` system note (prefix-matched so it is announced exactly once, and self-healing if trimming ever drops it) names the dead tools via `revokedToolNames`, which is derived and therefore generalised to every family for free. Switching one ON is NOT retroactive (those tools genuinely are not in the frozen list), and doing so says nothing to the model, which is the safe direction to be wrong in. Endpoints: `GET/PUT /api/assistant-session-settings`, and `GET /api/assistant-capabilities` for the catalog.

**No ambient chat**: there is no "current chat" a tool can fall back to. `AssistantContext` carries no `chatId`, every chat-scoped tool takes an explicit one through `requireChatId` (chat-reads.ts) and refuses without it, and ids reach the model **only** through the **workspace note**: one system message pinned right after each user turn (`buildWorkspaceNote` in loop.ts), built from that turn's attachments alone, carrying the open chat's branch stamp beside its id, and **omitted entirely when there are none** (nothing open, or the user muted the chip). A note that announces an absence is both a claim the model can act on and tokens spent every turn to say nothing; the rule for working without one is stated once, in the prompt. The request's `chatId` never enters the note (it only stamps the session's last-worked-on chat), so muting the chat chip genuinely takes the chat out of the model's view. Two reasons the prompt stays out of it, both load-bearing. **Cache**: the system prompt is the cached prefix of every request (the breakpoint sits at its end, architecture/llm-providers.md), so a value that moves as the user navigates would invalidate the whole session's cache on every chat switch; the prompt therefore states only the *rule*, which holds with or without a note. The note itself sits AFTER the user turn and is persisted with it, so its presence or absence never disturbs that prefix. **Correctness**: the panel's chat is the app viewport's, not the session's: every assistant tab mirrors the same `chatStore.activeChatId`, so a fallback let a write land on whatever the user had switched to since. A wrong explicit id is visible in the tool result and in the approval card that precedes it; a silent retarget was neither.

**Hand-added attachments are reads, and the sent message shows what actually rode.** A chip from the Add picker asks for `full: true`; what each attachment actually gets is RESOLVED in `buildWorkspaceNote` alone (the size limit, the already-in-context check and the chats-stay-pointers rule all live there, never in the composer), with five honest outcomes. **full**: the entry's fields plus its art counts and version roster, the same projection `read_entity` hands over, because "treat this as read" must not claim more than was sent; a chat selection rides here too, quoted verbatim. **clipped**: a highlight past the selection cap, which arrives already shortened: its own mode rather than `full`, since the block tells the model it is partial and a chip claiming otherwise is exactly the overstatement this record exists to prevent. **pointer**: every auto item, and every chat or lorebook however attached. A chat never goes in full, since any real thread blows the limit and a prose dump would break the seq/branch discipline `read_chat_messages` pages with; its one pointer line carries title, id, bound character, the books that actually reach its prompt (`chatLorebooks`, never the character's link list) and the branch stamp. **oversize**: a full request past 5k estimated tokens (`ATTACHMENT_FULL_TOKEN_LIMIT`, measured with the same estimator every other assistant budget uses; flat by owner decision, no second ceiling against the window) degrades to a pointer that says so and names `read_entity`, never a cut block, because a half-injected card the model believes it holds whole is the worst possible outcome. **known**: the conversation already claims the entity at its current revision, so nothing is re-sent and one line says to use what it has; the context trim dropping that claim re-sends automatically, the safe direction. A full block is a genuine read: the note's HEADER LINE carries the same `[kind:id rev:…]` claims a read stamps (`WORKSPACE_NOTE_PREFIX`, shared with freshness-core.ts), so the standing re-read rule and the per-turn staleness check govern attached content exactly like read content, and `collectStateClaims` reads only that line of a workspace note, because the body quotes story text (a selection, card fields) and a forged token there would register a claim that suppresses a re-read. The read-equivalence instruction itself rides the "Attached in full" section header (one line, present exactly when a full block is), never the cached prompt, which would pay every session for a note most turns never carry. Full-mode items resolve before pointers, so the auto slot pointing at a hand-attached entity can never displace its full block.

The RESOLVED record is `SentAttachment` ([`shared/assistant-attachments.ts`](../shared/assistant-attachments.ts), the one shape both sides speak; a second copy on either side would let a chip state a mode the server never produced). The loop writes it onto the user row the client inserted (`setAssistantMessageAttachments`, `attachments_json`, server-only like `updateAssistantTurn`) and announces it with a one-shot `assistant-attachments` event the store folds onto the optimistic bubble; the event is deliberately outside the live-snapshot mirror, because the row is persisted before any page could ask for a snapshot, so a reload reads the truth from the transcript (architecture/client-data-layer.md coupling 6). The timeline renders the record as chips above the user bubble, in the composer's own chip language (solid means content went, dashed means a pointer went), each wearing its mode as a visible text tag (never hover-only), and each routed on click through the same `assistant-targets.ts` every other assistant surface uses: a selection chip lands on its anchor message, a lorebook chip opens the book through the one-shot `uiStore.pendingLorebookId` the Library's Lorebooks shelf consumes. **Hand-added chips are consumed by the send**: the store clears them once the user row is in, so a chip rides exactly one message and sending it again is a deliberate re-add. Retry and Continue pass only the auto slot: a matched retry reuses the persisted note server-side anyway, and Continue's canned line is not a message the user composed, so neither may eat chips staged for their next real one.

**Auto-attach** (what "open in the workspace" means): the panel derives one auto slot from, in priority order, the live chat selection → the library entry in focus → the open lorebook → the active chat. It is a SINGLE slot and the note's only source of the open chat, so a library entry in focus deliberately displaces the chat pointer: with the chat unnamed, the assistant reaches one through `list_chats`/`search_chats` like any other, which is the same discipline as a missing id anywhere else. The library-entry focus lives in its own tiny store ([`workspaceFocus.svelte.ts`](../src/lib/stores/workspaceFocus.svelte.ts)), deliberately not in the Library view's component state: the signal has to survive the Library overlay unmounting, which is exactly what happens when the assistant opens beside it. Its lifetime is the merged Library dock's: the open Library view mirrors its edited entry into the focus, and `uiStore.closeLibrary()` releases it, so once the user closes or navigates away from the Library, the assistant stops seeing that entry. The **lorebook focus** is the same store's second slot, mirrored by the Lorebook view from its selected book and released by that view's own unmount: the view exists exactly while its overlay is open, so unmounting IS the user navigating away, and without the release the assistant would keep pointing at a book long since closed. It is pointer-only like everything in the slot: a book's entries can be enormous, and `read_lorebook_entries` reads them properly. The Chungus Assistant is a free-floating widget that only *reads* this focus; opening or closing it never displaces the Library or touches the focus. Mutes are per-item (attachment key), never a sticky per-tab flag.

**Floating widget snap** ([`AssistantFloatingWidget.svelte`](../src/lib/components/assistant/AssistantFloatingWidget.svelte)) measures the shell's explicit layout anchors (`data-assistant-snap-column` in `TitleBar.svelte`, `data-assistant-snap-workspace` in `Workspace.svelte`) instead of duplicating responsive chat-width formulas. Side snaps therefore occupy the same margins as native docks, center snaps occupy the same column as chat-area overlays, and every snapped zone starts below the title bar. The anchors are resize-observed so zoom, viewport, breakpoint, and chat-width changes re-fit an attached panel automatically; free-floating rectangles retain their independent clamp, radius and shadow. **Resize handles are live in both states**, and a drag on a snapped panel sizes it from exactly where it sits and releases it from its slot on the first real movement (the press alone changes nothing, so a stray click on an edge cannot undock it). It has to leave: the anchors would re-fit a hand-sized rectangle away on the next layout change, and flush dock chrome claims a seam a resized panel no longer sits on. A side attachment publishes transient `uiStore.assistantSnapSide`, letting `Workspace` reuse the native dock tint-overhang animation for both chat and welcome; every non-side or hidden state clears it. The snap preview has the same sharp geometry as the attached panel. The panel's placement persists as a `SavedPlacement` (`assistant-widget-rect` = rect + `snappedZone` + the remembered free size): reopening restores the snap slot instead of demoting a docked panel to a free window wearing the dock's dimensions. The **header uses the same 6px drag threshold as the launcher**: a plain click on a snapped header focuses it; only real movement tears it out of the dock (restoring the remembered free size under the cursor). The **closed-state launcher can be switched off entirely** (Settings → General, `generalSettings.assistantLauncher`): it hides the BUTTON and nothing else: sessions, a running turn, the approval card and every assistant setting are untouched. Which is why **Ctrl/⌘+J is load-bearing rather than a convenience**: with the button gone it is the only door into the panel, so the shortcut and the toggle must never be separated (architecture/ui-shell-settings.md). Two consequences the widget hard-codes: the running / waiting-for-approval / just-finished marks all ride that button, so a hidden launcher shows them only inside the panel; and the "just finished" badge neither arms nor survives while hidden, since re-enabling the button would otherwise announce a turn that ended hours ago. The **launcher is draggable** while shown: horizontally it snaps to the left or right edge (those two sides only, never top/bottom), but vertically it slides freely along that edge and stays exactly where dropped. Side + vertical offset persist in `localStorage` (`assistant-launcher-pos` = `{side, y}`, re-clamped to the viewport on load/resize); a press under the 6px threshold is a plain click that opens the panel (a drag sets `suppressClick` to swallow the trailing click, auto-cleared after ~350ms because touch drags fire no click at all); `touch-action: none` keeps a touch drag from scrolling the page. **Z-layering**: the widget sits at z 200 (full-screen `inset:0` on mobile), which is why every assistant-initiated deep link (the top of `navigateTo`, the timeline's `navigateToTool` and `scrollToMessage`) minimizes the widget on phones first: the destination renders below z 200 and the tap would otherwise look dead. Any portalled overlay that must appear over it (the `AssistantDiffModal`/`Dialog` diff view at z 300 in `Dialog.svelte`, and `ImageLightbox` likewise at z 300) is raised above it; below that it renders behind the mobile panel and reads as "the overlay vanished". The history/attach pop-overs close on an outside press via a `svelte:window` pointerdown handler: a fixed backdrop cannot cover the app from inside the widget, whose `backdrop-filter` makes it the containing block for fixed descendants. The panel message list (`ChungusAssistantPanel.svelte`) auto-follows a stream only while the user is pinned near the bottom (~120px, direction-tracked with a `programmaticScroll` guard): an upward scroll releases the follow so streaming can't yank the view back mid-read. **One effect owns where that scroller sits**, and it holds four rules. It follows reply AND reasoning text (every non-tool step's length), because an opened thinking block fills exactly like a reply and a follow blind to it sits still while the text scrolls off the bottom. It follows the **count** of running-tool rows, never their text (see *Watching a call write itself*). The `programmaticScroll` guard is armed **only when the snap will actually move the scroller**: a write to a scroller already at the bottom fires no scroll event, so the guard would stay armed and swallow the user's next real scroll-up, leaving the follow convinced they are still pinned. And a **settling turn never scrolls**: `absorbCommitted` swaps the live timeline for the persisted one in a single tick, so a pinned reader is already at the bottom and one who scrolled up to read must not be thrown to the end by the turn's last frame. Switching tabs is the one move that re-pins, so a newly opened tab opens at its latest.

**Attached files, maintenance:** a new recognized KIND is one entry in `shared/assistant-files.ts` (the union and its label, both read by every surface) plus one structural test in `detectFileKind`, and it must be a shape that can be CHECKED, not a guess from an extension. A new file capability goes in `registry/files.ts`, the `CAPABILITIES` array, and Core's tool list in `groups.ts`, and it **must ask `ctx.roomTokens()`** if it returns any part of a file: a read that answers only to a constant is the one way back to a tab that can never send again.

**Maintenance:** most app changes need **no** assistant edit: it operates on data + the catalog, not implementation. You only touch it to: add a data-model field (one `FieldDef` in `entities.ts` → reachable everywhere automatically; if the field is stored outside `traits`, also update the entity's storage adapter), add a new assistant-managed entity (one `EntityDef`; give it `group` when a capability family should gate the KIND: the generic reads then refuse it and the data model drops it while the family is off, the way `setting` rides Navigation), add a non-CRUD action (one `Capability` in its family module under `server/assistant/registry/`, its name in the `CAPABILITIES` array in `capabilities.ts`, and its name in one family’s `tools` list in [`groups.ts`](../server/assistant/registry/groups.ts), **and nothing at all in `systemPrompt.ts`**: a new capability owes the prompt no second description of itself, only membership in a family line; it owes its own schema exactly one home per fact, see *One fact, one home*; and it MUST declare its `risk` rung, plus a `preview` for anything above `read`: `src/lib/contracts.test.ts` fails without either, since an undeclared rung cannot be placed against a mode and a call the approval card can only describe by its arguments is a call the user is asked to trust blind), or add/adjust a skill (one entry in `skills.ts`). A capability that hands the model tracked story state, or writes it, spreads `stampState(...)` / `stampGone(...)` into its result (freshness.ts, see *Freshness* above; forgetting a read stamp forfeits re-read savings, forgetting a write stamp costs one true self-note, neither ever a stale act); one that overwrites a whole tracked value with model-composed content asks `assertClaimFresh` (registry/util.ts) in both `run` and `preview` before it lands, the way `set_entity` and `manage_greetings` do; and a new tracked KIND is one resolver in freshness.ts, asserted by the smoke script's freshness section. The hand-kept couplings to remember: (1) the settings catalog duplicates each setting's `tab` + `anchor`: update it if you move / rename / remove a setting, add a matching `data-setting="..."` attribute in the page component for the highlight, AND map the anchor to its hosting page in `ANCHOR_PAGES` (`src/lib/config/settings-pages.ts`, the whole panel is drill-down); all three ends are asserted in `src/lib/contracts.test.ts`, so a catalogued setting that cannot be routed to or cannot be highlighted fails `bun test`; `navigateTo` routes `uiStore.settingsPage` by that map, hands the anchor over via the one-shot `uiStore.pendingSettingsAnchor`, and `flashSelector` retries a few frames while the page mounts; (2) a new `navigate` target kind must change in **three** places: `NAV_TARGETS` (server, `navigate.ts`), the `NavTarget` union (`src/lib/types/assistant.ts`), and the `navigateTo` switch (client); (3) the `SettingsTab` union exists in **two** places: `src/lib/config/settings-pages.ts` on the client (the `NavTarget` setting arm imports it; the live UI state is `settingsPage`) and `server/assistant/registry/settings.ts` on the server, since neither side imports the other; a new settings section updates both plus `TAB_FALLBACK_PAGE` and `SETTINGS_GROUPS` in `settings-pages.ts`, and `src/lib/contracts.test.ts` asserts the two unions agree; (4) the two memory capabilities read through `serverDb.memGetState/memListEpisodes` and DERIVE both the archive boundary and each summary's seq range by calling `resolveCoverage`/`episodeSeqRanges` from the pure client core: that import is deliberate (one derivation, not two), so keeping `src/lib/memory/branching.ts` + `config.ts` free of `$lib` value imports is a server build requirement (architecture/memory.md coupling 9); the one place that states what the assistant may do to memory (the `edit_memory_episode` schema) moves with the tool surface, and `edit_memory_episode` writes through `memUpdateEpisodeContent` + a `memory` broadcast, so an open Memory panel on any device redraws; and (5) `add_steering` states the steering vocabulary as tool-schema enums it cannot import (server code never reaches into `src/`), so `STEERING_SCOPES` / `STEERING_MODES` / `STEERING_ROLES` in `workspace.ts` are hand-mirrored from `src/lib/types/steering.ts`, and `src/lib/contracts.test.ts` asserts all three lists stay equal. A new tool with no `TOOL_ICONS` entry in `src/lib/config/assistant-icons.ts` just falls back to a default icon, and with no `TOOL_MOTIONS` entry in `src/lib/config/assistant-motion.ts` to the ellipsis: cosmetic in both cases, but a genuinely new KIND of work wants its own family (one line in the map, one phrase list in `WORK_WORDS`, one glyph in `AssistantWorkMotion.svelte`).

**File layout**: server-side, [`capabilities.ts`](../server/assistant/registry/capabilities.ts) is only the ASSEMBLY (the `CAPABILITIES` array, in the order the model sees them): the definitions live one module per family in `server/assistant/registry/`: `entity-ops.ts` (the 7 generic ops + their shared helpers), `images.ts` (the look tool, the entry-art write with its shared `planEdit`, and the read-side `readEntryImages` / `portraitAttachment`), `versions.ts`, `navigate.ts`, `chat-reads.ts` (list/search/read_chat_messages/read_chat_context/read_memory_state/edit_memory_episode + `activePathMessages`/`requireChatId`/`memoryCoverage`), `lorebook-entries.ts` (+ `loadLorebookBook` + `manage_entry_lorebooks`), `workspace.ts` (orchestration: `create_chat`, `set_active_persona`, `add_steering`, `rename_chat`, `read_connection_state`), `greetings.ts` (`manage_greetings`), `prompt-trace.ts` (`read_prompt_log`, `read_prompt_entry`), `files.ts` (`list_files`, `read_file`, `search_file`, the reads over attached reference material, bounded by `ctx.roomTokens()`), `ask.ts` (`ask_user`). A new capability goes in its family module AND the `CAPABILITIES` array. The rest of the folder is plumbing, not families: [`index.ts`](../server/assistant/registry/index.ts) is the registry's whole public surface (the loop imports nothing else), with `buildTools` / `dispatch` / `revokedToolNames` / `previewCall` and the derived `riskCeiling`; `schema.ts` is the derivation layer (capability params → OpenAI JSON Schema, `ENTITIES` → the prompt's data-model section); `types.ts` holds `Capability` / `EntityDef` / `FieldDef` / `ParamDef`; `util.ts` holds `ToolError`, the argument coercers (`str`/`requireStr`/`strList`/`boolArg`/`clampInt`), `applyFindReplace` and `ok`; `settings.ts` and `smoke.ts` are the catalog and the regression net above. [`rows.ts`](../server/assistant/rows.ts) is the assistant's ONE set of raw serverDb row shapes (`RawLibraryEntry`, `RawMessage`, `RawChat`, `RawLorebookBook/Entry`, `RawCharacterVersion`): entities, capability modules and the loop all cast through it; a storage-shape change updates rows.ts and the compiler flags every consumer, which a per-file cast written at the use site never would. [`toolProgress.ts`](../server/assistant/toolProgress.ts) is a pure, unit-tested string function with no imports (see *Watching a call write itself*), kept out of `loop.ts` so `bun test` can reach it without the database. Attached files split the same way and for the same reason: [`files-core.ts`](../server/assistant/files-core.ts) is the pure half (recognition, normalization, the line math, search) with `bun test` coverage in `files-core.test.ts`, while [`files-ingest.ts`](../server/assistant/files-ingest.ts) is the container half that knows about PNG wrappers, bytes and the database, and [`shared/assistant-files.ts`](../shared/assistant-files.ts) holds the row shape, the kinds and the size limit, since both sides speak all three. Client-side, `ChungusAssistantPanel.svelte` is the shell/composer only; the limbs are [`AssistantTurnTimeline.svelte`](../src/lib/components/assistant/AssistantTurnTimeline.svelte) (turn rendering, tool rows, running rows, batching, navigate/diff + their modals; the navigation itself is `assistant-targets.ts`, shared with the approval card; an edit's diff renders through [`AssistantDiffInline.svelte`](../src/lib/components/assistant/AssistantDiffInline.svelte), with `AssistantDiffModal.svelte` as its expanded view. **Neither of them draws the untouched text**, because a whole-field write is mostly untouched text and rendering all of it turns reading one edited sentence into scrolling the entire card. Both condense through `condenseLines` ([`src/lib/utils/diff.ts`](../src/lib/utils/diff.ts)), which replaces every run of unchanged lines with a gap naming HOW MANY it hides and WHERE they sit in the uncondensed array; the inline view is height-clipped and additionally leads with the first change, while the modal draws each gap as a button that puts exactly those lines back. The +/− counts are measured over the FULL diff in both: the header states what changed, never what is currently on screen; the turn's one live element is `AssistantActivityLine.svelte`, drawing its nine glyphs from `AssistantWorkMotion.svelte` and its map and phrases from `src/lib/config/assistant-motion.ts`), [`AssistantHistoryPopover.svelte`](../src/lib/components/assistant/AssistantHistoryPopover.svelte) (owns its outside-press dismissal; the toggle opts out via `data-history-toggle`), [`AssistantAttachBar.svelte`](../src/lib/components/assistant/AssistantAttachBar.svelte) (Add picker + the attach menu + manual AND auto chips + the tab's approval-mode pill, one row; the two triggers lead it, before anything they can produce, attach is a MENU on the chat composer's recipe (`paperclip`, one Image… row) rather than a direct file-picker trigger, since images are only the first attachable kind, and the pill is pinned to the far end so a wrapping line of chips never displaces the one control the user needs to find in a hurry), [`AssistantApprovalCard.svelte`](../src/lib/components/assistant/AssistantApprovalCard.svelte) (the pending calls, above the composer, see *Approval*), [`AssistantQuestionCard.svelte`](../src/lib/components/assistant/AssistantQuestionCard.svelte) (the assistant's own questions, in that same slot, see *Asking the user*), and [`AssistantContextMeter.svelte`](../src/lib/components/assistant/AssistantContextMeter.svelte). Attachment DERIVATIONS (auto slot, mutes, what gets sent) stay in the panel: send() needs them.
