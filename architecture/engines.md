# Engines: architecture & maintenance

Engines are the app's built-in AI machinery: **Chat Memory**, **Opening Scene**, **Steering**, **Spellcheck**, **Impersonate**, **Sprites**. Each is its own deep system; what they share is an identity: declared model use, an app-wide on/off switch, editable prompt templates, honest debug labeling, and one config surface, the **Engines page in Settings**.

## The registry and the page

- [`registry.ts`](../src/lib/engines/registry.ts) is pure data: `EngineDef { id, name, icon, summary, description, makesCalls, prompts, enabled }`. `makesCalls` says whether the engine calls a model at all (`false` only for Steering, whose text rides the story generation; nothing to route). Every calling engine is a **routing point**: its connection is assigned directly and visibly on the **Connections** page's Model routing card (`connectionStore.assignments`), and resolution is a straight map lookup (no roles, no groups, no defaults-following, no pins, and no quality warnings); a fresh install routes everything to the one Default connection and re-pointing a row is the user's own explicit choice. The point list itself is registry-derived (`ASSIGNMENT_IDS` in [`connections.svelte.ts`](../src/lib/stores/connections.svelte.ts) = `primary`, `assistant`, then `ENGINES.filter((e) => e.makesCalls)`), so Steering never gets a row and a new calling engine gets one for free. There is no `ENGINE_SAMPLING` table either; see the sampling rule below. The `id` doubles as the engine's `source` label on LLM calls, which is what the prompt debug panel badges each call with (in `sourceColor`); the Engines page deliberately does **not** repeat that label, since the panel already writes it next to every call. `summary` is the engine's one-line row copy and `description` is the InfoTip beside its name in the detail view: what it does and when it fires, in a sentence or two. There is no cost/trigger chip on either surface: "On demand" and "No model call" told the reader nothing they act on, so an engine that spends tokens unasked says so in its own `description` instead. `prompts` (key/label/hint, plus an optional `requires` list of macros the template is useless without) is the **single source for the inline prompt editor**: `requires` drives the editor's "missing {{batch}}" warning and is the gentler half of a rule the owning engine also enforces by refusing to run (architecture/memory.md coupling 1). `enabled` is the engine's app-wide switch, and **every engine has one** (each accessor wraps a flag in the `featurePrompts` blob: `memoryEnabled`, `openingSceneEnabled`, `steeringEnabled`, `spellcheckEnabled`, `impersonateEnabled`, `spritesEnabled`); the registry never grows its own persistence.
- [`EnginesPage.svelte`](../src/lib/components/settings/EnginesPage.svelte) + [`EngineDetail.svelte`](../src/lib/components/settings/EngineDetail.svelte) are a **Settings page** (App group in the drill-down root) in two layers. The page itself is a calm **overview list**: every engine is one row (icon disc, name, one-line `summary` and its on/off `Toggle`), with no lede, no InfoTips and no inline disclosure. A row (not its toggle) drills into the **detail view** via `uiStore.settingsEngineId`, the connection editor's exact pattern: cleared by `gotoSettingsPage`, peeled by the drill back chip ("‹ Engines") and Escape before the page itself exits, recorded/replayed by the split view's history and named in its header (the engine's name over "Engines"); the root settings list previews the page as "N of M on", both figures counted off the registry (`enginesSummary` in `settings-pages.ts`, so a new engine never leaves a stale total on screen). The detail is three cards: **identity** (icon orb, name, the `description` on an InfoTip beside it, Toggle), **Model** (the read-only resolved `connection · model · provider` with a "Change on Connections" link via `gotoSettingsPage('connections')`; Steering instead states it makes no model call), and **Prompts**, plus the one Steering adds for itself (below). Prompts are templates on the shared `.input-base` recipe whose `rows` follow the template's own line count (clamped 3–20; the `rows` attribute, never a JS-written height: dragging the resize grip writes an inline height that wins from then on), per-field draft-based `Modified` badge + Reset, and click-to-copy **flow-key chips derived from `FEATURE_PROMPT_DEFAULTS`** (not a hand-kept list; the keys survive you deleting one from your own edit). **Prompt edits auto-save** on a 600ms debounce and flush on unmount, the same live-write contract as the rest of Settings: no Save button, nothing lost by leaving, and Reset (to the shipped default) is the way back. The page **assigns nothing**: every connection choice in the app lives on the Connections page's Model routing card. Off engines read muted rather than hidden.
- The page is **app-wide config only** for every engine: switch + prompt templates (+ the read-only model line), plus, for the two engines with something app-wide beyond a template, one extra card each: Steering's default placement and Chat Memory's defaults for new chats. Neither card reaches an existing chat or note; both are the bottom of an inherit/seed chain whose per-item end lives on that item's own surface. Memory's per-chat panel (`MemoryView`) lives in the **Memory panel** (`memory/MemoryPanel.svelte`, the chat-area overlay `memory`; architecture/memory.md), raised by the TitleBar's Memory button, and `memoryEnabled` is the one engine switch that also edits surfaces outside its own page: off drops that button from the nav cluster entirely and hides the Memory ghost fade slider on Appearance → Chat, since neither has anything left to act on (architecture/ui-shell-settings.md). Opening scene keeps its per-chat behaviour on its own surface (the chat UI, not this page): its three doors fire it.

## The six engines

- **Chat Memory** (`memory`): the extract/promote pipeline, fired from the memory store as the story scrolls past the context horizon; templates `memoryExtract` / `memoryPromote` (shipped defaults originate in `memory/prompts.ts`). App-wide switch `memoryEnabled` (default **on**): the memory store folds it into `memoryStore.active = enabled && featurePromptsStore.memoryEnabled && macroPlaced`, and the extraction and promotion passes read `active`, not `enabled`. It is a `$derived` the whole memory surface hangs off (ghosts, panel stats, recall preview, token meter), so flipping this switch moves all of them in the same tick; `getRecall` checks the flag directly at generation time. Off = the engine goes inert everywhere (no recall injected, no extraction, no ghosts, full live history in the prompt, and the TitleBar's Memory button and the ghost fade slider both gone), while every chat's stored summaries and per-chat flag stay in the db. It also owns the one card on this page that is not a template: **Starting defaults**, the five `MemoryConfig` tunables (`featurePrompts.memoryDefaults`, `MEMORY_CONFIG_FIELDS` in `memory/config.ts`, shared with the chat panel's own sliders). They are **copied into a chat when memory is switched on for it**, never resolved through afterwards, so no card here can move the layer caps under a story already summarised against them; only fields moved off the shipped default are stored, so an untouched card seeds nothing at all. Double-click resets a slider **here** to the shipped default, this card being the bottom of the chain; the same `rangeReset` gesture on the chat panel's own sliders resets to this card instead, one rung down. Everything else about it, including why copying beats layering: architecture/memory.md.
- **Opening Scene** (`opening-scene`): a way for a story to open, written through the **full prompt pipeline**: `generateOpeningScene` in [`messages.svelte.ts`](../src/lib/stores/messages.svelte.ts) rides `{ engine: 'opening-scene' }` for BOTH the call and `buildPromptMessages`' `target`, so its assigned connection's model, budget, and post-processing apply end to end; template `openingScene`. The direction rides that template as **`{{idea}}`**, a call-site substitution key, deliberately NOT a MACROS entry; it is the pattern Steering's `{{steering}}` and the composer transforms' `{{draft}}` follow too. It is deliberately NOT `{{scenario}}`: that name would shadow the real `{{scenario}}` macro, which belongs to the character card's scenario field and resolves normally inside this template alongside `{{idea}}`.
  - **The scene is a root SIBLING, and the engine has no emptiness precondition.** A card's greetings are root-level siblings and multiple roots are legal, so an opening is one more row of the same kind: with ten greetings the new scene reads "11 / 11", the ten stay reachable by the same arrows, and every surface that walks the tree carries it without being told. What the store owes that contract (the sibling index, `rootMessageId`, the leaf) is in architecture/chat-sessions.md, and what it costs the seeded-greetings mirror is there too: nothing, and deliberately, since a beginning the reader asked for is theirs.
  - **Three doors, one call, and none of them spends before a press.** `MessageList`'s empty-state card is the door for a card that ships no greeting at all; a sparkle beside the pager cluster on every root assistant turn (`Message.svelte`) is the door where the greetings are, which is where the hand reaching for another one already is; and `/opening <direction>` (`commands/registry.ts`) is the keyboard's, and the only one that reaches the act mid-story without scrolling to the root. A root turn of the reader's OWN gets no sparkle: their first line is not a greeting, and the command covers that chat. All three are refused while `messageStore.isStreaming`, app-wide rather than per chat, since one generation holds the one abort controller.
  - **The question is one box, not a mode.** [`OpeningScenePopover.svelte`](../src/lib/components/chat/OpeningScenePopover.svelte) is a direction field and a Generate button, mounted against whichever trigger opened it. There is no Random/Custom pair because **leaving the box empty IS the random answer**, and a choice that answers itself does not earn a step; the store turns a blank direction into the surprise line, so no caller spells a sentinel. The direction is component state and is deliberately never persisted: a direction is not a draft, and one typed and abandoned must not come back later as a request.
  - **The scene streams alone.** `chatStore.startStream(id, { openingScene: true })` marks the stream, `ChatContainer` hands the flag down, and `MessageList` then paints the streaming bubble by itself with the path suppressed: a new beginning is not a turn after the ones on screen, and leaving them up would read as a reply to them. It is also what gives an opening a visible stream and a reachable Stop, since the composer is no longer behind a modal. A stop that kept text lands it as the opening, exactly like any other generation.
  - App-wide switch `openingSceneEnabled` (default **on**): off hides the empty-state trigger and the sparkle, `/opening` says why in place of its description, and `generateOpeningScene` fails loud if called anyway.
- **Steering** (`steering`, `makesCalls: false`; makes no call, nothing assignable): guidance injected into the story prompt, never into chat rows. It is a **library of scoped notes**, not one textarea; see the section below. Template `steeringWrapper` frames each group's text. `{{steering}}` is a call-site substitution key (the opening scene's `{{idea}}` pattern), deliberately NOT a MACROS entry. **No model calls of its own**: the injected text rides primary generations as fixed-cost context (assembly semantics in architecture/prompt-pipeline.md). Switch `steeringEnabled` (default **on**) gates the composer popover, the chat meter's steering input, and prompt-builder's generation gate, which is now the only gate the spend needs: with the switch off no note is resolved, so nothing is named to be spent. Its detail view carries one card of its own: **Default placement** (a 0–20 depth slider + a role `PillRow`), the bottom of the inheritance chain below.
- **Spellcheck** (`spellcheck`): on-demand draft correction from the composer hamburger menu; template `spellcheck` (`{{draft}}` flow key). Runner is [`composerTransformService.ts`](../src/lib/services/composerTransformService.ts) → `complete({ engine: 'spellcheck' }, …, source: 'spellcheck')`; unlike a background sidecar it PROPAGATES errors (foreground action; the panel renders them). The result only ever lands through the approve/reject in [`TransformPanel`](../src/lib/components/chat/TransformPanel.svelte), read as a word-diff redline (`utils/text-diff.ts`); closing leaves the draft untouched, approve records the original into input history first. It has nothing to configure, so its menu row IS the press and the panel opens mid-call, **except while its prompt hold is armed**, where it opens in `setup` like Impersonate's and the press that spends is the one on the strip: a review arriving over a strip the reader never saw would put the whole prompt on screen as the answer to a menu pick, and cancelling it would land them on a button that had not existed yet. Switch default **on** (no ambient cost: runs only when triggered); the service throws if called while off. Both transforms pass their built messages through the prompt hold before the call (architecture/prompt-pipeline.md), inside the service rather than the panel so the request is never built twice; a cancelled review comes back as **null**, which the panel reads as "nothing was spent" and lands in `setup`, the same place a stop lands, and the strip says it is waiting for a review rather than claiming work that has not started.
- **Impersonate** (`impersonate`): expands a short draft into a full message written from the user's perspective; template `impersonate` (`{{draft}}` + `{{perspective}}` flow keys, engine macros like `{{char}}`/`{{user}}` resolve from live context). **The prompt seats the model on the user's side structurally, not by instruction**: chat history rides as native turns with the roles SWAPPED (the character's turns arrive as user, the user's as assistant, self-refs expanded exactly like injected story turns), and the filled template closes the prompt as the final user turn, task and draft right where generation begins. The swap is what makes small models write as the user at all: an unswapped history conditions the assistant seat as {{char}} for the whole context, and a system line at the top loses that fight, so the engine writes the character no matter what it is told. The shape (and the engine connection's own post-processing, which applies here because this is the one engine sending a multi-turn history) lives in the pure [`utils/composer-transforms.ts`](../src/lib/utils/composer-transforms.ts), tested in `composer-transforms.test.ts`; the grammatical person is the per-chat `impersonatePerspective` in the same `feature_state` blob, edited from a pill row in the panel. Same runner, fail-loud, and approval contract as Spellcheck, on its own engine connection: the two can sit on different models. **It calls nothing until the perspective has been chosen**: the panel opens on that pill row with the price of the call beside it and a button that is the only thing that spends, since the whole branch rides this request untrimmed and a call fired before the user could pick is a paid answer to a question they were never asked. Picking a perspective persists it and calls nothing, ever.

- **Sprites** (`sprites`): reads the newest assistant turn and answers with one of the chat character's own sprite labels, which is the picture the bottom-left sprite layer then draws (the sprites themselves are library data; architecture/library.md). Runner is [`spriteService.ts`](../src/lib/services/spriteService.ts), split the same way as the composer transforms: a pure `buildSpritePrompt` and a `readSprite` around `complete({ engine: 'sprites' })`. Template `sprites`, with **one** call-site key, `{{labels}}` (the character's own labels, the only legal answers). **The excerpt is not this engine's invention**: it comes from the ordinary history macros resolving against the path handed in, so how much story the model reads is the author's decision. The shipped template writes `{{chatHistoryLast3}}` and swapping in `{{lastMessage}}` is how someone makes this engine as cheap as it goes. A per-engine excerpt builder would have been a second, hidden way to do what `{{chatHistoryLastN}}` already does, with its own idea of how a turn is labelled. What the template does assert is **where** to look: the character's state at the **end** of the last turn, since a mood moves inside a paragraph and the sprite shows where it landed. **The path handed in must END on the turn being read**: the store truncates it there, because every history macro treats the newest entry as the latest thing said, and a user turn sitting after an unread reply would aim the question at the wrong line. Only `{{labels}}` is in `requires`: the history macro is a choice, and naming one of them would make the editor warn about an author's own valid edit. **Output is JSON** (`{"sprite": "<label>"}`) through the shared [`parseJsonObject`](../src/lib/utils/json-extract.ts), and the answer contract is the pure, unit-tested `pickLabel` in [`sprites.ts`](../src/lib/utils/sprites.ts): fences and preamble are tolerated, casing is normalized to the character's own spelling, and **a label outside the pool is a failure, never a near match**. A fuzzy fallback would put a confident wrong picture on screen instead of saying the engine is not working. **A reply is read once, and re-reading it is the user's call.** Its detail view carries a card Steering's siblings don't: *Read a reply again*, two switches (`spritesRereadOnEdit` / `spritesRereadOnContinue`), **both off**. An edit or a continuation does leave the stored reading describing text that is gone, but fixing that costs a second call on a turn already paid for, and only the author knows whether their edit moved the mood or fixed a comma. The gate sits at the two `messageStore` call sites that already hand an in-place rewrite to chat memory (`invalidateSpriteFor` beside `invalidateMemoryFor`, in `editMessage` and `continueMessage`), and `spriteStore.invalidateMessage` is the sprite half of `memoryStore.invalidateMessage`: it clears the row's reading, drops the failure guard, and the layer's next tick reads the turn again. A reading that FAILED has a second door of its own, the status dot in the picture's corner (`spriteStore.retry`, architecture/ui-shell-settings.md): the guard exists to stop a broken engine re-asking on every render, not to stop the reader asking once. **The server clears nothing** (architecture/server-core.md): a rule in the SQL would apply to every door regardless of the setting, which is the one thing this must not do. A MINOR save never re-reads under either switch, the same assertion that spares memory's summary. A regenerated or swiped reply needs no switch at all: that is a different turn, born unread. Switch `spritesEnabled`, **the one engine that ships OFF**: it spends a call on every reply, and unlike Memory that call buys presentation rather than the story's own continuity, so it is a cost the reader opts into rather than discovers. The Sprites section in the character editor names that fact and deep-links here, which is where someone who uploaded pictures and saw nothing happen is actually standing. When and where it fires: architecture/ui-shell-settings.md.

**Continue is not an engine.** Extending the newest reply in place is preset behaviour, not app machinery: the instruction it appends is the preset's own `continuePrompt` (edited in Prompt Builder → Preset options, saved and exported with the preset), and the call rides the primary connection exactly like a send. It has no registry entry, no app-wide switch and no Connections row, only a source label in the debug panel, so a continuation is still tellable apart from an ordinary turn. Assembly semantics live in architecture/prompt-pipeline.md ("Continuation tail"), the store flow and join rules in architecture/chat-sessions.md.

## Steering notes

A steering note is a first-class row (`steering_notes`, architecture/server-core.md), not a field on a chat, and its **scope** is data on the row, which is the only reason four reaches cost the same as one. The pure model lives in [`types/steering.ts`](../src/lib/types/steering.ts) (tested in `steering.test.ts`) and is import-free on purpose: the generation path resolves it against fresh db rows while the chat meter resolves the store's cache, and the two must agree exactly or the meter prices something the send doesn't inject.

- **The scope ladder**: `global` (scopeId null, always), `character` (= `chat.characterId`), `version` (= `chat.characterVersionId`, so the note goes inert the moment the chat is repinned), `chat` (= `chat.id`). `noteApplies` is the one matcher; a null `scopeId` is never a wildcard and a **dangling** scopeId is inert rather than an error (the dangling-lorebook-link doctrine, architecture/lorebook.md). Injection order is broad → narrow, then oldest first (`sortSteeringNotes`), so the most specific guidance lands closest to the reply; there is no manual reordering.
- **Notes stack.** Several apply to one reply, each with its own `enabled` flag. `activeSteeringNotes` (enabled + non-blank + in scope) is THE definition of active, shared by generation, the meter and the composer readout; `scopedSteeringNotes` is the superset the note lists render, so a rule you switched off stays on screen. `steeringTargetForChat(chat)` is the one place a chat row becomes a `SteeringTarget`: six callers go through it, and a mismatch there is a note that injects on one surface but not the other.
- **Placement inherits.** A note's `depth`/`role` are tri-state, `null` = inherit from `featurePrompts.steeringDefaultDepth`/`-Role` (Settings → Engines → Steering). Same idiom as the lorebook knobs, and it is **shown** the same way: `resolvePlacement` feeds the two Advanced rows, so each names the value the prompt will use and marks it only where that DIFFERS from the default (`ui/OverrideMark`, architecture/lorebook.md); a depth typed back to the default's own number is not a change. Never let either row go blank to mean "inherited", and never put an option called "inherit" among the roles: a reader would have to hold the defaults in their head to know what the note does. The disclosure stays closed by default because inheriting is what a note normally wants, not because the rows have nothing to say. An explicit `0` depth is an override, not "unset": `resolvePlacement` checks `=== null`, never falsiness. **Depth is SillyTavern's author's-note depth**: turns back from the end of the injected chat, 0 (the shipped default) meaning right after the newest turn. `clampSteeringDepth` bounds it to 0–`MAX_STEERING_DEPTH` (100) on every write, and the Engines slider only reaches 20: the wider range guards stored and assistant-written values, the slider guards what a drag can reach. It always lands inside the story, never after the preset's post-history blocks; assembly semantics in architecture/prompt-pipeline.md.
- **`once` vs `pinned`.** A `once` note is deleted after the generation it rode and its text pushed into that chat's `steeringHistory` (still in `chats.feature_state`: the reuse list is the one genuinely per-chat piece left; last 10, most-recent first, exact repeats moved rather than duplicated). **The spend belongs to whoever persists the turn**, and after a persisted success alone. A reply and an opening scene are written by the server, so their notes are deleted inside the same transaction (`serverDb.commitGeneratedTurn`, architecture/server-core.md); continue still writes its own turn and so still spends through `messageStore.spendOneShotSteering`. Both spend **by id**, from `BuiltPrompt.oneShotSteering`, never by re-resolving the scope at spend time: a note added while the model was writing never rode that prompt, and one edited to permanent meanwhile is no longer the reader's to throw away, so both are left standing and only the ids actually deleted come back to be recorded. A global `once` note fires in whichever chat generates next; accepted, since forbidding it costs more explanation than it saves.
- **Grouping is assembly's job.** Notes sharing a role AND a depth are joined (blank line between) and wrapped ONCE (`buildSteeringMessages`), so a stack of five is not five system turns scattered through the prompt. Groups keep the caller's injection order, macros in the guidance expand after the join so one note's trailing macro can't swallow the next, and a group whose wrapped result is blank is dropped rather than sent as an empty turn.
- **One surface, and the editor inside it.** [`SteeringNoteEditor.svelte`](../src/lib/components/chat/SteeringNoteEditor.svelte) is one note's whole editor (name, guidance, scope, lifetime, advanced placement, delete), mounted by the popover in place of its list. Everything in it writes through immediately except text/title, which ride the store's debounce: a click must never sit in a timer. The **name field sits above** the guidance box (a title under its body reads as a caption) and its placeholder is a plain "Name", not the derived `noteLabel`: a placeholder reading "Empty steering" reads as a heading rather than as something to fill in. `noteLabel` still owns the LIST label, where "Empty steering" is the right thing to say. **The word "note" stays out of the copy on every steering surface**, since it reads as a chat-adjacent scribble rather than as prompt state: the create action is "New Steering", the list deletes are "Delete steering", and the editor's own is a bare "Delete". The domain type is still `SteeringNote` and this doc still says "note": renaming the model was never the point.
  - Its guidance box **auto-grows with no resize grip** (`autoResize`'s `grip: false`, `rows` = floor, `maxHeight` = ceiling: 180). The rule the grip breaks: a native handle lives on the bottom-right and the browser maps pointer-down to height-up, which only tracks the finger when the surface is anchored at its TOP. The popover is `absolute bottom-full`, so the extra height is absorbed upward and the handle sits still while the pointer walks away. The composer's own textarea is `resize-none` + auto-grow ([`InputArea.svelte`](../src/lib/components/chat/InputArea.svelte)) for exactly this reason; same for the popover's quick-add box (`maxHeight` 140, `grip: false`).
  - [`SteeringPopover.svelte`](../src/lib/components/chat/SteeringPopover.svelte) (the composer's compass) is the engine's **only** surface, and therefore a complete one: the stack with per-note switches and a per-row delete, the editor, a quick box and the Recent reuse list. Everything a note can be has to be reachable from here, so a second surface is never the answer to something this one cannot do. **It is capped (`min(26rem, 60dvh)`) and scrolls inside itself.** It hangs above the composer and grows upward, so an unbounded panel pushes its own head, and the stack with it, off the top of the screen with nothing to scroll back to; both lists therefore share one `.panel-scroll` body while the head, the quick box and the foot stay outside it. That is also why **Recent sits above the quick box** rather than below: the box is the cheapest action here and must never be the one you have to scroll for, and the reuse rows now sit against the box they fill. The editor scrolls in the same body. The **quick box is the cheap half of exactly one axis**: always `once`, always the inherited depth/role, bound to the open chat (or globally when there is none). It carries no controls at all (no lifetime pills, no commit button), because every one of those would duplicate the editor sitting one click away behind "New Steering", and a mode picker there would make the throwaway action look like the expensive one. Write, it rides the next request, it deletes itself. It commits on Enter and on the popover's own close: the box is component state, so without that commit a line typed and then abandoned for the composer would steer nothing at all. Only an EXPLICIT close commits (`commitQuick`, called by InputArea before it unmounts the panel); a chat switch still discards, because it would bind to the story you just left. **`/steer` is the quick box reached from the keyboard, and therefore its second writer**: it creates a note with the identical shape (`once`, inherited placement, the open chat or global) from [`commands/registry.ts`](../src/lib/commands/registry.ts), so a change to what the cheap half means is two edits or the two doors quietly start writing different notes. It is not a second surface and must not grow into one: anything a note can be that the command cannot reach belongs to the editor one click away, exactly as it does for the box (architecture/chat-sessions.md). InputArea keeps only the trigger, its dot and that commit-and-flush-on-close.
  - **The popover lists the notes bound to the open chat**, which is every note that can steer the reply being written. A note bound elsewhere (another character, another version, another chat) is inert here and is edited from the chat it belongs to; one whose binding is gone entirely stays in the database, inert, until a chat matches it again. There is deliberately no second surface listing them all: a manager for rows that cannot fire is a page nobody opens twice, and everything it would offer is one chat switch away.
  - **Deleting is a list action**, a hover/focus-revealed trash on the popover's rows, with **no confirm dialog**: the editor's own Delete has never asked either, and the two would otherwise disagree about how dangerous the same row is. A note is one line of guidance; drilling into an editor to throw it away was the bigger cost.
- The store's 400ms debounce (`scheduleEdit`/`flush`) lives in [`steering.svelte.ts`](../src/lib/stores/steering.svelte.ts) rather than in the component, so generation can force a pending edit to commit before it reads the rows. Scope labels are single-sourced in [`utils/steering-labels.ts`](../src/lib/utils/steering-labels.ts) (`scopeChoices` / `scopeIdFor` / `bindingLabel` / `bindingIsForeign` / `versionChoices` / `versionLabel`), store-sourced, and a missing row is **labeled** ("Deleted character") rather than hidden.
  - **Two vocabularies, kept apart.** `scopeChoices` names the RUNGS and nothing else: a fixed `Global / Character / Version / This chat`, each with its own hint, and unavailable rungs disabled rather than hidden. Naming what a rung currently resolves to reads as a courtesy and isn't: a picker saying "Global / Sephiroth / Sephiroth · v2 / This chat" hides which pill is the character and which is the version. `bindingLabel` names what ONE note is bound to, and belongs where one binding shows at a time: the popover's row subtitle and the editor's foreign line, which **names the binding** ("Bound to X. Inert here until the chat matches. Re-pick above to move it.") since the pills can't.
  - **`version` is the one rung whose id is a choice.** Every other scope reads its id off the open chat; a character can hold several versions, so the editor's Version pill is **split**: the face picks the rung, the chevron opens a list of that character's versions (`versionChoices`, creation order, the chat's own pin tagged "pinned here"). Picked once, the face reads `Version · <name>` and re-picking the rung after a detour through another scope reuses that version silently (`strandedVersionId`, remembered on the way OUT; the note's row only ever holds its current binding). Only the chat's pinned version leaves the note active; any other is **legal and inert**, which is why the pin is marked and the foreign line fires. `scopeIdFor('version', target)` stays the pin and is what every non-editor caller wants; the editor is the one place that overrides it.
- **Lifetime reads `Every reply` / `Next reply`**, a symmetric pair, and lives only on the editor's Lifetime row: the quick box has no mode picker at all. The pair must stay symmetric: the picker has no off, only the other mode, and the note's own enable switch is the thing that turns it off.

**Templates + switches** live in [`featurePrompts.svelte.ts`](../src/lib/stores/featurePrompts.svelte.ts): `FeaturePromptKey`, `FEATURE_PROMPT_DEFAULTS`, overrides-only persistence riding the settings spine (`featurePrompts` blob). The app-wide switches (`memoryEnabled` / `openingSceneEnabled` / `steeringEnabled` / `spellcheckEnabled` / `impersonateEnabled` / `spritesEnabled`) ride the same blob, all default **on except Sprites**: an engine ships off only when it spends unasked-for tokens on something other than the story itself, which today is Sprites alone. Two engines add their own knobs to that blob rather than growing storage of their own: Steering's `steeringDefaultDepth` / `steeringDefaultRole`, and Sprites' `spritesRereadOnEdit` / `spritesRereadOnContinue`.

## Hand-kept couplings

1. A new engine = a registry entry (incl. `summary`, `description` and an `enabled` accessor) + a `FeaturePromptKey` with a `FEATURE_PROMPT_DEFAULTS` default + a colour in `SOURCE_COLORS` ([`debug/format.ts`](../src/lib/debug/format.ts)): the registry `id` IS the source label, and that map is a `Record<EngineId | 'chat' | 'assistant' | 'continue', string>`, so a missing colour fails to compile instead of quietly rendering gray. (Gray remains the honest fallback for a caller that passes no engine label at all.) The Engines page renders the whole row and its opened detail (switch, chips, model line, flow keys, and inline prompt editor) from the registry alone; no per-engine wiring anywhere else.
2. The Engines page is shell-wired like any settings page: the `SettingsTab` union ×2 (`settings-pages.ts` on the client, `server/assistant/registry/settings.ts` on the server) + `TAB_FALLBACK_PAGE` and the root groups in `settings-pages.ts` (`src/lib/config/`) + the page arm in `SettingsPageView.svelte` + a `SETTINGS` catalog entry with a matching `data-setting` so the assistant can explain/deep-link it (architecture/ui-shell-settings.md couplings #1 and #2, both test-asserted).
3. Prompt field descriptors are registry-owned and read in exactly one place: `EngineDetail` reads `engineById(id).prompts` for its inline editor. Edit labels/hints in the registry; there is no second mount to keep in sync (the Memory panel's gear deep-links into this same detail rather than growing its own editor).
4. EVERY calling engine calls `llmService.complete({ engine: '<id>' }, …)` so its own routing-point assignment resolves, and the one full-pipeline engine (Opening Scene) also passes `target: { engine: '<id>' }` to `buildPromptMessages`, so assembly (model, token budget, post-processing) follows the same connection the call rides. Calling `complete('primary', …)` from an engine silently ignores the user's routing for it, the one way to break this quietly.
5. **Engines never override their connection's sampling.** There is no `ENGINE_SAMPLING` table anywhere: `complete()` builds params from the resolved connection's own `generation` block, so a connection you assigned is a connection whose settings apply. If an engine needs different sampling, that is a different connection, not an app-owned constant. The rule has no exceptions left in the app: the Chungus Assistant, which is not an engine, rides its own assigned connection the same way (architecture/chungus-assistant.md).
6. Steering's vocabulary is mirrored on the server (`STEERING_SCOPES` / `STEERING_ROLES` / `STEERING_MODES` in `server/assistant/registry/workspace.ts`, for `add_steering`'s tool-schema enums; server code never imports from `src/`). All three are asserted equal to the client model in [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts). A new scope is: the union + `SCOPE_RANK` + `noteApplies` + the `STEERING_SCOPES` array in `types/steering.ts`, the server mirror, and `scopeChoices`/`scopeIdFor`/`bindingLabel` in [`utils/steering-labels.ts`](../src/lib/utils/steering-labels.ts). Only three of those seven are exhaustive (`SCOPE_RANK`'s `Record`, `noteApplies`' switch, `bindingLabel`'s switch), so the compiler names three and the other four are on you; the mirror is the one the contracts test catches.
7. Every engine's `enabled` accessor wraps a flag in the `featurePrompts` blob (`memoryEnabled` / `openingSceneEnabled` / …); the registry never grows its own persistence. The switch only gates when its runtime actually reads the flag: a new engine's `enabled` must be wired into that engine's execution path (see the per-engine gates above), or the toggle is a lie.
