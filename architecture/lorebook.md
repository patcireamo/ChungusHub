# Lorebook: architecture & maintenance

World info in the SillyTavern sense: standalone books of keyword-triggered entries injected into the prompt via the `{{lorebook}}` macro. Books are first-class db records (`lorebooks` table); characters and personas **link** to them by id (`data.lorebookIds`), so a book can be shared, exported, re-imported alone. **Two more layers reach a prompt that no card names**: a book can be switched into every chat (`book.global`), and **one chat can attach books of its own** (`ChatFeatureState.lorebooks`, claimed from the composer's setup chip, architecture/ui-shell-settings.md). Nothing links either one, nothing lists them on a character, and they are in the prompt anyway. Every reader of the link list therefore goes through `resolveLorebookLinks` (coupling 1) rather than walking `lorebookIds` itself, and a caller that short-circuits on an empty link list drops exactly those books. **The chat layer ADDS and never replaces**: what a story attaches rides on top of what its cards bring, which is the one thing about it that differs from the four claims it sits beside in that chip.

**A chat can also take a book back out** (`ChatFeatureState.mutedLorebooks`, the same chip), and that is the ONE exception this app has to every layer above it. A book in every chat is otherwise in every chat, and a character's book is otherwise in every story with that character, so without this the widest two switches are decisions no single story could stand outside of, and the only way to exempt one was to stop using the switch. It is applied **last and to the finished list**, so it outranks the globals, the cards and the chat's own claim alike: a subtraction run before any adding layer would simply be undone by it. **An id may never sit in both lists**, because it would read on screen as a book this story carries while reaching no prompt at all, so attaching a muted book clears its mute and muting an attached one clears the attach. The rule is a property of the pair rather than of either list, so each door writes through its own pure transform (`withLorebookClaim` and `withLorebookMute`, [`types/chat.ts`](../src/lib/types/chat.ts)) and a door that edited one list by hand is the door that loses it. A deleted book leaves dangling ids behind **on purpose**: every reader resolves links against existing books and skips misses (`lorebookStore.resolveBooks`, prompt-builder, the assistant, the link picker), and the id drops the next time that entry's links are edited, an ordinary save carrying it since it sends `data` whole (see the comment on `deleteLorebook` in [server/db.ts](../server/db.ts)). **A count is a reader too**: the editor header's Lorebooks chip and the picker's foot both resolve before they count, since a number taken off the raw id list makes a link to a deleted book read as a live one, and on a shelf with one book left it reads as a link to that book, whose row is then one press from really being linked. Both count through `resolveLinkedBooks` and never through the chat resolver beside it, which answers with books nothing links: a chip reading that one claims links the card has not made.

**Domain model** ([`types.ts`](../src/lib/lorebook/types.ts)): entries use SillyTavern's native World Info field names **verbatim** (`key`, `keysecondary`, `selectiveLogic`, `constant`, `disable`, `order`, `probability`, `caseSensitive`, `matchWholeWords`, `scanDepth`, `triggers`, the `match*` source flags, `sticky`, `cooldown`, `delay`, `group`, `groupOverride`, `groupWeight`, `useGroupScoring`, `position`, `depth`, `role`, `excludeRecursion`, `preventRecursion`, `delayUntilRecursion`) so import/export is passthrough; everything not modelled (`characterFilter`, `automationId`, `vectorized`, …) rides untouched in `entry.rest` / `book.extensions` for lossless round-trip. A book itself is a name, an optional **cover** and those activation knobs: a `description` arriving from a card's `character_book` (or from our own export) is unmodelled too, so it rides in `book.extensions` and leaves the same way. The cover is `book.cover` (a stored `images/lorebooks/<file>` path) plus `book.coverFocus` (the app-wide portrait framing, architecture/library.md), both absent on every book made before it and on every book that never gets one. It never reaches a model and **never travels in an export**, since a World Info file is JSON and the picture is a file, which is the same line a character's framing is on. Neither exporter can leak it: both build an explicit shape. Activation knobs resolve **entry → book → global**: tri-state fields (`null` = inherit) fall back to book-level, which falls back to [`settings.svelte.ts`](../src/lib/lorebook/settings.svelte.ts) (`lorebookGlobalSettings` settings row: scanDepth, recursion, match defaults, budgetPercent, crossBookRecursion) through `resolveBookActivation`. **Two settings have no book layer**, and for the same reason: they describe the whole scan rather than any one book, so an override could not work. Each is drawn where it is real and named where it is not, in the smallest way that stays honest: the pass cap keeps a foot line under the Scanning card it belongs to, saying where it is set, while the budget simply is not drawn in book scope at all, since a section heading whose only content is "not here" is a section about nothing. `budgetPercent` caps all lore in one prompt at once. `crossBookRecursion` decides whether recursion reaches across the books in play, which two books cannot disagree about. That store registers a `settings` reload: these values steer real prompt assembly, so a device that kept a boot-time copy would quietly build different prompts than the one where they were changed.

**Engine** ([`engine.ts`](../src/lib/lorebook/engine.ts)) is pure, injectable-RNG and tested (`engine.test.ts`). `scanLorebooks` reads a list of **scan sources** rather than one joined string: `messageScanSources` turns the chat path into one source per turn carrying its distance from the newest (depth 0), `fieldScanSources` adds the cards' own text, and recursion appends the content of entries that already fired as sources of their own. That is what lets every entry read its own slice AND lets every match name where it was found. **The slice is per entry, not per book** (`sourcesFor`): the chat clamped to `entry.scanDepth ?? the book's`, plus only the card fields that entry opted into, plus everything recursion pulled in, which is never windowed. Per entry rather than per book because a depth override may reach *further* back than its book's. It fires constant entries always and keyword entries on primary+secondary logic (AND ANY/ALL, NOT ANY/ALL), applies the Trigger% roll once per entry (never re-rolled during recursion), and recurses within the book when the book says to, returning the survivors sorted by `order` ascending, which is where SillyTavern's own descending sort plus unshift lands too. **What recursion feeds back in is macro-expanded**, with the caller's own expander: an entry writing `{{char}}` is read as it reaches the model, the same rule the card fields follow, and a scan that read the braces instead would match on the macro's spelling rather than on the story. Before any of that runs, one `gate` answers everything an entry's settings and its own past decide without reading a word: switched off, nothing to inject, the wrong kind of generation (`triggers`, `firesOnTrigger`), a chat too short for its `delay`, or a `sticky`/`cooldown` window still open. Those verdicts do not depend on the sources, which is why recursion may only overturn the three the keys themselves reached (`REVISITABLE`). `renderLorebookBlock` macro-expands each entry's content and admits entries greedily in that order under the optional token budget (`budgetPercent` share of the prompt budget), pricing each entry WITH the separator that joins it to what it lands in, so the rendered text cannot outgrow the allowance by its own glue. Titles (`comment`) are never sent to the model.

**Matching is decided per key, not per entry.** A key is the smallest thing a lorebook gets wrong, and one bad key used to drag the whole entry with it: an acronym that has to be case-sensitive would force every other key on the entry to be, and an inflected stem that has to tolerate suffixes would force the rest to tolerate them too. So each chip carries its own mode and case, and the entry's two switches are only what a chip that sets nothing falls back to (`resolveKeyMatch`, the one resolver both the scan and the chip's picker read). Four modes: **anywhere** (a plain substring), **whole word**, **word start** (the key plus the rest of the word, which is what makes `ejderha` match `ejderhanın` and `dragon` match `dragons`), and **regex**. Two rules keep this from changing what existing books match. A key with whitespace never *inherits* whole-word, matching SillyTavern, which applies that flag to single-word keys only; picking the mode explicitly still applies it to a phrase. And **a regex key is its own text**: a chip written `/pattern/flags` IS one, exactly as SillyTavern writes them, so it needs no stored rule, answers only to its own flags (the entry's case switch has nothing to say about it), and crosses the interchange boundary untouched. `compileRegexKey` is the ONE compile, shared by the scan and the chip, so a pattern the editor accepts can never be one the scan refuses; a pattern that will not compile matches nothing and the chip goes red where it is written, rather than taking a generation down mid-send.

**A scan can read the cards, not only the chat.** `LOREBOOK_SCAN_FIELDS` is one table of five (description, personality, scenario, persona, creator's notes), each row carrying the SillyTavern flag that names it in both interchange shapes, and that single table drives the engine's sources, the editor's toggles and both import/export mappings. Opt-in per entry and off by default: a constant-sounding word in a description would otherwise fire half a book on every turn. Field text is macro-expanded with the same expander as entry content, so a card writing `{{char}}` is scanned as it reads, and field sources sit in FRONT of the chat in the source list, which is searched backwards, so a key present in both is reported against the turn the reader is looking at.

**Recursion is one relationship with two directions, and the entry sets both ends.** SillyTavern's three flags are carried verbatim (`excludeRecursion`, `preventRecursion`, `delayUntilRecursion`) and read through the single `resolveEntryRecursion` in [`types.ts`](../src/lib/lorebook/types.ts), which also answers for rows stored before the fields were modelled by falling back to either spelling still sitting in `rest`. The editor collapses them into what an author actually decides: **what may wake this entry** (the chat and other entries, the chat only, or other entries only) and **whether it wakes others**. The pair that cancels out (waiting for recursion while refusing to be woken by it) is a real SillyTavern state and a dead entry in both engines, so it is named where it stands and never offered as a choice, and the engine gives it its own `neverFires` status rather than letting it read as an entry that merely went unmatched. A waiting entry can name the **level** it waits for, SillyTavern's own recursion level, carried in the same `delayUntilRecursion` field (`true` is the first). Levels open one at a time, lowest first, and the next one opens only when the passes below it wake nothing new, so a book staged into waves arrives a wave at a time. Every opened wave costs a pass against `maxRecursionSteps`, which is what keeps a book with many levels from looping past a cap that was set to bound it; with no cap the whole chain still arrives, so the staging shows in *when* an entry is admitted rather than in whether it is. **An entry that waits for recursion reads other entries and nothing else**: it asked to be woken by lore, so the story text it would otherwise have matched is not an answer to that, and this is the one place the engine departs from SillyTavern, which re-reads the whole buffer once any recursion pass has run. An open `sticky` window overrules all three, because it is a decision an earlier turn already made. And a delay applies to constant entries too, which is what lets an always-active preamble arrive only once some lore has; such an entry fires on the first recursion pass without evaluating keys, rolling its Trigger % there instead.

**How far recursion reaches is one setting, and it is global.** `selectFromBooks` runs over a *pool*: one book, or every book at once when `crossBookRecursion` is on. The pool shares the sources and the loop and never the settings, so each entry still matches under `resolveBookActivation` of the book it was authored in (its scan depth, its case and whole-word defaults). A book whose own `recursiveScanning` is off stays out of the recursion economy entirely: it is neither woken by another entry nor able to wake one, which is what keeps the book-level switch meaningful while the loop is shared. **Crossing is off by default**, because turning it on widens what an existing setup injects and makes the per-book pass cap inert (one shared loop can be capped only once, so the global `maxRecursionSteps` governs), and the panel dims that row and says so rather than leaving a number on screen that does nothing. An entry scan source carries its book's name, so a match woken from another book names it (`LorebookTraceList`), and a match from the reader's own book does not, since that is the part they can already see.

**An entry's own past can speak before its keys do.** Three windows, all measured in generations and all read off the traces earlier turns stored rather than a counter: `delay` holds an entry back until the chat itself has that many messages (the whole chat, not the entry's scan window, which would answer a question about the story with a number about itself), `sticky` keeps it in for that many generations after it fires, and the `cooldown` that follows shuts it out for that many more. **The record is what makes this branch-correct for free**: a branch IS a path through turns, so `lorebookHistory` walking the active path backwards already sees only this branch, where SillyTavern's mutable per-chat counter set would carry a discarded swipe's activation into the reply that replaced it. Two rules keep a window honest. It is measured from the entry's last **natural** firing only (`lorebookFiredNaturally`: `constant` or `keyword`, never `sticky`), so a sticky entry cannot renew its own window and never let go. And a sticky turn skips the keys AND the Trigger % roll, because both were already earned on the turn that opened the window and re-rolling would make the window fray at random.

**An inclusion group is one slot, not a pile.** A group label names a set of alternatives for one idea, so a scan that admits three of them has quietly turned a choice into a list. `resolveGroups` keeps one entry per label, **across every book at once** (two books carrying alternatives for the same label is exactly the case), and narrows in four steps: a sticky candidate wins outright (it is in because an earlier turn decided, and re-running the contest against it every generation is how a sticky window becomes a flicker), then `groupOverride` (Prioritize), then group scoring (most keys matched, asked of the group rather than of each entry so one contest is judged one way), and whatever survives goes to the weighted roll on `groupWeight`, which is the point of a group: variety across turns. An entry naming several labels has to survive all of them. **Every loser's record names the group it lost and the entry that took it** (`lostTo`), because a feature whose whole effect is an absence is invisible without that line. Groups are resolved after the scan, so a loser's content may still have pulled another entry in during recursion; the trace says so (that match names the entry that lost), and closing it would mean running the contest inside every recursion pass of every book.

**Every scan says why.** Both steps produce one `LorebookEntryRecord` per entry ([`types.ts`](../src/lib/lorebook/types.ts)): its `status` (`constant`/`keyword`/`sticky` reach the prompt; `noMatch`, `filtered`, `rolledOut`, `delayed`, `neverFires`, `trimmed`, `disabled`, `empty`, `offTrigger`, `cooldown`, `tooEarly`, `groupLost` are the reasons an entry's text is not in it), the keys that matched with the turn, card field or entry they matched in and an excerpt of it, the chance a lost roll failed, and `placedAt` where an entry did not go into the block. `buildLorebookTrace` reduces that list to the storable `LorebookTrace`: the records worth keeping plus a **count** of the entries that stayed silent, because their reason is uniform and a book of two hundred entries would otherwise weigh more than the reply it rides with. The two surfaces split accordingly: a reply carries its own trace (`messages.lore_json`, architecture/server-core.md) and the chat renders it, while **Test scan** on this page (`LorebookScanTester`) runs the same engine over text the reader types and shows the complete record list, silent entries included. That division is deliberate. A stored trace answers "what shaped this turn"; the entry that is failing to fire is precisely the one a stored trace has nothing to say about, so debugging it belongs to a live box where the reader supplies the text (one line per turn, oldest first) and Trigger rolls are pinned to pass. The box hands the engine text and nothing else, so it tests matching alone: the card fields are empty there, the kind is always a send, and the typed turns carry no traces, which means an entry gated on a card field, a generation kind or a sticky window reads there as whatever that gate says rather than as a keyword verdict. It also scans the open book alone, so a wake that would come from another book is not reproducible there even while books recurse together; macros are not expanded there either, so an entry whose content is written in macros wakes nobody in the box that it would wake in a real turn.

**Placement is two real places.** Most entries join the block the preset placed at `{{lorebook}}`; an entry can instead ask to sit **at a depth inside the chat**, as its own turn, wearing a role (system, user or assistant). That is SillyTavern's `position` 4 with its `depth` and `role`, carried verbatim. Its other six positions describe SillyTavern's own prompt skeleton (its author's note, its example-message block), which this app does not have: they are kept, they export unchanged, and they read here as the block. The editor names such a position rather than showing it as one of ours, so an imported entry never quietly reads as something it is not.

An at-depth entry stops being part of a macro's string and becomes a **contributor to assembly**, exactly like steering, through the same `DepthSplice` and the same `placeSplices` (architecture/prompt-pipeline.md). Three things follow. Entries sharing a role AND a depth join into ONE turn, so a stack of five is not five turns littered through the story. The block and the at-depth groups are admitted under **one budget allowance**, in `order` sequence, because `budgetPercent` caps everything lore injects at once and two allowances would let a book spend it twice. And a caller that cannot splice says so: `resolveLorebooks` takes `placeAtDepth`, which only `buildMacroContext` sets, and only when the enabled preset actually renders `{{chatHistory}}`. Everywhere else those entries fold back into the block, because an entry that asked for a position nothing renders must still reach the prompt.

**`resolveLorebooks` is the one door.** It scans and renders in a single call and every MacroContext builder goes through it: `buildMacroContext` (generation and the meters), `buildLiveMacroContext`, and the memory store's own context. Each hands it the same four things: the chat path, the cards' scannable text (`lorebookScanFields`, one derivation for all three), the generation kind (absent = a plain send, which is what the meters price) and the path's own earlier traces (`lorebookHistory`, likewise one derivation), which is what the sticky and cooldown windows are measured against. The block lands on `MacroContext.lorebook` as plain text and `{{lorebook}}` only prints it, exactly like `{{memory}}`. Two things fall out and both are load-bearing. Selection happens **once per assembly** rather than once per resolve, so the budget trim's re-resolves can't hand a probabilistic entry set a fresh roll each pass, and the trace stored on a turn names exactly what was sent. And the recursion guard is structural rather than a special case: entry content is expanded against the context as it stood **before** the lore was added, so a stray `{{lorebook}}` inside an entry resolves to nothing.

**Store** ([`store.svelte.ts`](../src/lib/lorebook/store.svelte.ts)): reactive book list, mutate-in-place + debounced write-through on the shared `DebouncedWriter` (500ms, keyed per book, committed on tab-hide by the writer itself), `flush()` before navigation/sync-reload. **Typing debounces, a picture does not**: `setCover` and `setCoverFocus` are discrete acts and go out at once through `writeNow`, which cancels the book's pending write because it sends the row whole (a timer left standing would repeat the same book to every device a moment later). `setCover` saves the new file BEFORE it drops the old one and clears the framing either way, since coordinates chosen for one picture mean nothing on the next; a write that fails puts the book back and drops the file it just uploaded, because nothing but `deleteLorebook` reaches `images/lorebooks/` and a file no row names sits there forever. **Every write resolves its book by id rather than taking one it was handed** (`writeNow`, the same shape as the debounced `writeBook`): a caller crossing an await of its own, an upload being seconds on a phone, would otherwise send a copy a `refresh` has already detached from the list on screen. `refresh` flushes first and then keeps any book whose in-memory copy is newer than the row that came back: typing carries on through both awaits, and adopting the refetch wholesale would rewind an open entry under the caret. **Interchange** ([`sillytavern.ts`](../src/lib/lorebook/sillytavern.ts), tested) parses both SillyTavern shapes: native World Info (entries as uid-keyed object) as near-passthrough, and Character Card V2/V3 `character_book` (renamed spec fields) with real mapping. It exports native World Info, stashing ChungusHub-only book overrides in `extensions` so our own re-import recovers them. [`io.ts`](../src/lib/lorebook/io.ts) is just Blob/File plumbing.

**Whether two books are the same book is one question with one answer** ([`identity.ts`](../src/lib/lorebook/identity.ts), pure and tested). SillyTavern keeps a shared book as a `worlds/` file AND inside the `character_book` of every card that uses it, so an import meets the same book many times over and needs to recognize it rather than shelve each meeting (architecture/sillytavern-interchange.md). `bookFingerprint` is what recognizes it: each entry's title, keys, text, `constant`, `disable` and `order`, sorted so neither the entry order nor the storage order can speak, and **the book's name deliberately left out**, since the two shapes name the same book differently. It reads only fields both entry parsers land on identically, defaults included, which is what lets a book arriving as a card's copy match the world file it came from. **A book with no entries fingerprints as null and never matches**, not even another empty one: nothing identifies it, so it can only be itself. `createBookIndex` is that answer plus SillyTavern's own `world` name link, built fresh at the start of an import and grown as it lands books, so it is never asked a stale question. **Every judgement call here favours a miss over a hit**: a miss costs one duplicate book on the shelf, while a false hit binds a character to somebody else's book and drops the one that arrived, and there is no way back from that.

**Books are browsed in the Library and read one at a time.** The shelf is the Library's third tab (`LorebooksView`, architecture/library.md), and a press there opens that book in `LorebookView`, wide and centered over the chat, exactly the split the character editor and its browse list use: `uiStore.lorebookEditorId` names the open book and `uiStore.libraryTab` names the shelf, so a shelf press and an assistant deep link are one act. **There is no lorebook overlay and no nav-cluster button**, for the reason Characters and Personas have neither (architecture/ui-shell-settings.md): the Library pill is the door, it reopens on the shelf it was left on, and Ctrl+B goes straight there. At most ONE centered editor stands at a time (`uiStore.openEditor`), or a Bound-to chip would stack a character editor on top of the book it was pressed in.

**UI** (`src/lib/components/lorebook/`): `LorebooksView` (the shelf: the browse toolbar, the three layouts, the pager, bulk selection) and `LorebookShelfRow` / `LorebookGridCard` / `LorebookGalleryCard` (one book, in each of them), `LorebookView` (the open book: header, the book's title, the one settings strip, the entry list), `LorebookEntryRow` (editing over the store's debounced mutations), `LorebookActivationPanel` (both layers of the cascade, written once: hand it a book and the rows edit that book, hand it none and they edit the defaults; it also carries the two rows that belong to one scope only), `LorebookScanTester` (the Test scan strip, a second collapsible section under Activation), `LorebookTraceList` (**the one wording of a scan's outcome**, shared by that tester and the chat's own reading, so an entry that fired for a reason here cannot read as a different reason there; a new `LorebookStatus` is a compile error until it is worded), `LorebookLinkPicker` (attach books to characters/personas, from the card's side), `LorebookBindPicker` (the same links from the book's side, plus the chats that attached it), `LorebookTransferPicker` (where a selection of entries is going, the body of both transfer buttons), `LorebookStatsBar` (the open book's foot: what it holds), `KeyChipInput` (the keyword chips, each opening its own mode/case picker through the shared [`anchorTo`](../src/lib/actions/anchorTo.ts) action; a chip states only what it does *differently* from the entry it sits in, so a book that follows its defaults wears no marks at all). The entry row folds the rare knobs under **Advanced**, ordered as the entry lives: what it reads (scan depth, extra sources, then the two recursion rows, Woken by and Wakes others), when it fires (generation filter, timing, inclusion group), where it lands (placement, last). **Woken by** and **Fires on** sit two rows apart and answer different questions (what may wake this entry, versus which generations it may join), so neither may be renamed into the other's vocabulary. The fold's own line names whatever is set inside it, in that same order: a knob that works invisibly reads as a broken entry. Inside it, each knob's explanation rides an `InfoTip` on its name instead of a paragraph under its controls, since six stacked descriptions turn the fold into a wall nobody reads. **One line stays on screen, and it is not help**: an entry carrying a SillyTavern position this app has no place for says so under the placement control, because that is a fact about the entry rather than about the knob. Character-side linking is part of the library editor (see architecture/library.md). Keyboard: `/` or Ctrl+F focuses the entry search (Ctrl+K is deliberately left to the workspace's Chats shortcut, and Ctrl+F reaches this view only because `chatOnScreen` counts a centered editor as covering the chat, architecture/ui-shell-settings.md), Ctrl+S force-flushes pending debounced writes; Escape cascades select-mode → expanded rows → **close the editor**, and open popovers consume it via stopPropagation before the view sees it. That last rung is the editor and not the Library under it, because the editor is the top-most surface and the ladder closes one surface at a time; it only holds while the press is marked consumed (`preventDefault`), or the workspace's own Escape takes the whole panel with it (architecture/ui-shell-settings.md).

**The shelf offers what a shelf of books has a subject for, and nothing else.** It wears the Library browse bar (search, Filter & sort, a ⋯ menu holding Import World Info and Select multiple, New) and the Library's own selection bar (Export, Delete), so the gesture that selects three characters selects three books. It wears the Library's **View options** too, the same disclosure holding the same three sections: Layout (Grid, Gallery, List), Card size while the grid is up, and Per page. One popover narrows the list and the other only changes how what is left is drawn, which is the split both other tabs draw. It deliberately has **no token figure on a row**: pricing a book is a BPE pass over every entry in it, so an archive would pay for every row on every keystroke, and the number belongs on the page where one book is decided about.

**Three shapes, one book** (`LorebookShelfRow`, `LorebookGridCard`, `LorebookGalleryCard`, each the Library card of that name to the geometry). **List is the default**, because a shelf is scanned by name far more often than it is browsed by cover and most books carry none. What a row states is what a shelf is scanned for: its name, its entry count, and how many characters and personas carry it, since a book nothing carries never reaches a prompt. Gallery lays that same line over the cover; Grid drops it, since name-only density is the whole reason that mode exists. **A book with no cover wears the open book's own tinted plate**, never an empty hole, so a grid of an archive nobody has illustrated still reads as cards. **Every frame a cover is drawn in is 3:4**, the rail's plate and all three shapes alike, down to the list row's own 60x80: that is the shape it was authored and framed in, and it is what makes the Lorebooks list scan as the same list as the Characters one rather than as a shorter one beside it. So one framing answers every surface, and what it is for is aiming a picture whose own shape is not 3:4. A book switched into every chat wears **Every chat** beside its name in all three shapes, written once in `LorebookGlobalBadge` rather than as a pill copied three times, since three surfaces naming one state three ways is how a shelf stops being one list. **Show** is that same question as a filter, one axis with three answers (In every chat, Linked, Unlinked) held out of the list independently, which is what makes both dead weight and the books every chat is carrying findable in one press. **Global outranks linked** there rather than sitting on an axis of its own: a book in every chat is already in every chat, so which cards also link it is not what that filter asks. The search reads the book's name plus its INDEX, its entry titles and keywords, never entry content: a shelf answers "which book holds the Charizard entry", while prose is what the open book's own search and its Elsewhere section are for. That index is folded once per book and kept until the book is edited, or every keystroke would fold the whole archive. **One casing rule serves both views of the shelf** (`foldForSearch`, shared with the Library's browse views): the dotted/dotless I family folds together, so a query that finds a book in the shelf cannot miss it in the link picker.

**The defaults are the shelf's own page, and the door to it is a row rather than a menu item.** **Global Settings** sits under the toolbar wearing the toolbar's own bar plus the strip vocabulary the open book's Activation strip wears (`.strip-head`, architecture/ui-shell-settings.md), so its line already states what the defaults hold before it is pressed: a layer every book falls back to is worth stating on the shelf, where a row folded into the ⋯ menu would be a setting that has to be hunted for. **It is drawn with no books too**, since how books will behave is decidable before there is a book to try it on, and reaching this through one book's editor is exactly what made it unreachable on an empty shelf. A press swaps the toolbar for a way back and the list for `LorebookActivationPanel` with no book; Escape steps back out of it before the workspace may close the Library. It is a page rather than a fold, because seven settings in three cards push the list off screen anyway, and its top row sits exactly where the toolbar was so the two pages line up under the tabs instead of jumping. Opening a book closes it, so a book never stands over a shelf that has lost the list it came off.

**The entry list has one toolbar row**, the library browse bar's own shape: the search takes the room, and Filter & sort, select and New end the same line. Two settings strips sit above it as one stack, and the space under them is several times the space between them, because that gap is where the page stops being about the book and starts being about its entries. The funnel carries both questions the list answers, worded as the Library words them. **Sort by** is one list of finished answers (Order, Reverse order, A → Z, Z → A, Longest, Shortest, Most keys, Fewest keys) and never a field plus a separate direction, which asks the reader to combine two choices in their head to name one. **Show** holds any of the three natures out of the list, each wearing the dot its rows wear. The badge counts what is *narrowing* the list and never the order: an order is not a filter, and a badge that counted it would read as entries gone missing. A list left empty says which narrowing emptied it and offers the way out of each one that is on, because "Nothing matches" over a list the funnel emptied sends the reader to clear a search that was never in the way. **The list itself sits on one plate**, the card the two strips above it wear: a collapsed row is a title, a keyword line and two small number fields, all of it small text, and with the glass theme up over a blurred backdrop it was being read against whatever picture the panel was standing on. The surface belongs to the LIST and not to each row, so the rows still read as lines of one thing rather than a stack of separate chips, and its padding is what keeps a hovered or open row off the plate's own rounded corners. An open row goes on carving itself out of it, unchanged.

**Entries move between books from the selection bar, and the verb is pressed before the destination is picked.** Selecting rows offers Enable, Disable, **Move to…**, **Copy to…** and Delete in that order: what changes the entries in place, then what sends them elsewhere, then what destroys them. Both transfer buttons open the same `LorebookTransferPicker` over every book but this one, and each prints its own verb and count at the head, since a panel that only listed books would leave the reader to remember which press opened it, and those two presses are not equally easy to take back. That panel carries a search and three of the shelf's own orders (A → Z, Z → A, Recently edited) whenever there is more than one destination, because finding one name in an archive of two hundred is the entire difficulty of the press, and a list of one has nothing to search or order. Both wear their words at every width rather than collapsing to icons, the way Enable and Disable beside them do: two glyphs nobody can tell apart is not a saving on a phone. A move leaves selection mode, because the rows it was made of are no longer in this book, while a copy stays, since sending the same entries on to a second book is a run of presses. Neither button is drawn while the shelf holds nothing else, the rule the composer's setup chip follows for its own lists, and the picker cannot mint a book for the same reason the editor cannot: that is an act on the archive. **Merging two books is this and nothing else**, select everything and move it, so there is no second door that joins books and no second answer to what happens to an entry on the way.

**One cascade, shown as one.** The activation settings exist at three levels and are edited through a single vocabulary, so a change can't land on the wrong layer: every cascading row carries the value that will actually be used, plus a star ([`ui/OverrideMark`](../src/lib/components/ui/OverrideMark.svelte)) where that value differs from the one the row would inherit, and clicking the star clears it. **The star reads the difference, never the storage**: a field typed back to the default is not a change, and marking it as one sends the reader hunting for a difference that isn't on screen. Following the defaults is the quiet state and says nothing at all. Never reintroduce a second panel carrying the same settings under another heading, a "Global (on)" option inside a value list, or a blank field that means inherit: all three make the layer a thing the reader has to infer. **Two rows in that panel are not cascade rows at all and exist in one scope only**: **Use in every chat** (book scope, the switch that puts this book in every chat with nothing linking it) and **Books recurse together** (global scope). Neither wears a star, because neither has a layer to differ from. The switch lives here rather than beside the name because it is one more thing the book DOES, and the strip's folded line prints *every chat* first when it is on, which is what stops the widest thing a book can be doing from hiding behind one press. **The layer is decided by the surface, never by a control inside the panel**: `LorebookActivationPanel` writes to the book it was handed, or to the defaults when it was handed none, so a change meant for one book cannot land on all of them by a switch left in the wrong position. That is also why the defaults live on the shelf and not inside a book (below): a layer every book falls back to is a property of the archive, and reaching it through one book's editor put an app-wide change under the name of a book it was not about, and put it out of reach entirely while the shelf was empty. A row whose value is real but has nothing to act on right now is **dimmed and says why**, never hidden and never left looking live: the book's pass cap while books recurse together is the one case, and the collapsed strip prints the cap that will actually run rather than the one the book stores. **`OverrideMark` is app-wide**, not a lorebook part: steering's placement rows speak the same language through it (architecture/engines.md), the composer's setup chip marks a claimed row with it (architecture/ui-shell-settings.md), and a second way to mark a changed setting is the split this replaced. **`onRevert` is optional and the star is a plain mark without it**, for a caller whose row is already a button: nesting a second interactive thing inside one hit target is a mis-tap that silently changes a setting.

`LorebookView` wears the **shared editor header** (`.editor-header`, architecture/ui-shell-settings.md), the bar the character and persona editors wear, and not a utility-overlay one: it stands in their slot over the chat, and two editors in one slot wearing two bars read as two surfaces. Sharing it costs one thing and the header pays it back: a glyph before the name (`bookOpen` here, `users`/`user` there) says WHICH editor this is, since the bar is otherwise identical and the reader would have to read the page under it. So the open book's name leads as plain text, the Lorebook actions menu (vertical dots) trails as the view's own `BrowsePopover`, holding **only what happens to this book** (Export World Info, Delete lorebook), and the close X ends the row behind a divider, since an editor with no nav button of its own needs a way out that is not a keypress. **The name is read-only here and picking another book is the shelf's job**, exactly as it is for a character: the shelf is docked beside this bar, so a picker on it would be a second browse list one press from the first. **Making and importing books belong to the shelf, never here**: they are acts on the archive, and a menu over one book that can mint another is the same category error as a Delete that could reach a second row.

**The page is one scroll and, past 860px of panel, two columns**: what the book IS on the left, what it HOLDS on the right, the split the character editor's identity pane already uses. The rail carries the cover plate and the book's identity, and only those: it sticks while everything beside it scrolls, so what is in it is what should not move. **Activation and Test scan take the wide column**, above the entries, because three cards of settings and a scan box with its result list have nothing to spend a 17rem rail on. Stacked they land exactly where they always did, since the rail's contents still come first down the page; only the wide layout changes, which is the whole reason the move costs nothing on a phone. The column takes its width whole, since a measure of its own would leave a wide panel empty, and the rule between the two is drawn on its side and only side by side. **The plate is the cover, authored exactly as the other two editors' portraits are**, which is what makes the three rails one shape (architecture/library.md): a press picks a picture, the corner X drops it and its file, the corner crop button opens the shared `PortraitFramingDialog`, and those two ride the same `.portrait-frame` rule that keeps them reachable on a touch screen. Empty it keeps the book glyph rather than a photo one, since a plate with nothing on it should still say what kind of thing the page is about, and only that state carries a label. A press is the **one** thing the plate does, so nothing else may be nested in it. The flip is a **container query on the panel and never a viewport one**, because this panel is as wide as the chat column: a wide window with both docks open has a narrow panel in it, and `lg:` would give that panel two columns it cannot hold. Where the strips are narrow a summary takes its own line under the name rather than being clipped to three words, since that line is the whole reason a fold may stay folded. **They carry their own size container** and never the column's: the entry rows sit in that column too, and their popovers measure themselves against the viewport, which a containment context there would quietly redefine.

The identity is a **labelled Name field, the character editor's own, to the class**, and then, under a rule, what carries the book. The name is a field and **never a second heading**: the bar above already says it, and the same string in two sizes an inch apart reads as a page that has lost track of its own title. The rule under it is what keeps the block below from reading as one more field of the name: what a book is CALLED and what carries it are two questions, and only the first is typed into.

**What the book is MADE OF is the page's foot** (`LorebookStatsBar`, the app-wide `.editor-stats` recipe the two library editors wear, architecture/ui-shell-settings.md): its entry count, its natures, how many keywords can wake something in it, and an upper bound in tokens. It sits under the scroller rather than in the rail, for the reason the library editors' own feet do: what a thing amounts to should be on screen whatever part of it is being edited, and it is stated there ONCE, since the same numbers an inch apart in two type sizes is a page arguing with itself. A fact with nothing to say is not a row, so the natures are spelled out only where the book holds more than one, since "3 entries · 3 keyword" says one number twice. **There is no prompt figure beside the token one, and there cannot be**: what a book injects is decided per turn by the scan, so the honest number is everything enabled firing at once, and a real answer is what Test scan is for.

**Binding is offered from the book as well as from each card and each chat, and all three write the same rows.** A link has two ends and the book is the end the question gets asked from most often, so **Bind to…** opens `LorebookBindPicker` over the three things that can carry one: a character, a persona (`data.lorebookIds`) and a chat (`ChatFeatureState.lorebooks`). It writes through the doors those surfaces already use, `characterLibraryStore.updateData` and `chatStore.toggleChatLorebook`, so a binding made here is the same row, the same sync scope and the same resolution as one made there; a write of its own would be a second answer to what carries a book. The panel stays open across presses, since binding a book to three chats is a run of them, and it rides the app's [`anchorTo`](../src/lib/actions/anchorTo.ts) idiom (portalled to the body, measured, Escape consumed before the view's own ladder sees it), because the rail scrolls inside a panel that clips and a picker left in flow would lose its own list. What it writes for a character is that character's **active variant**, exactly as the character editor's own picker does, so a chat pinned to another variant is playing that one's link list. Under the button, **Bound to** lists what carries the book, cards first (the durable binding) then the chats that took it for one story, each chip wearing that card's own portrait under its own framing, or the kind's glyph in the same round frame where there is no picture, so a mixed row is still one shape. **At most `CARRIER_LIMIT` chips stand**, the rest behind one press: a rail that grew to forty chips has lost the page it is a rail for. **Bound to appears only when something carries the book**, its absence reading as *Not linked* in its place, and that line is held back while the book is switched into every chat, here and on every shelf shape alike: a book reaching every chat must not read as one reaching nothing. A link count still shows where a card also links it, which neither line says on its own. **A chat chip is the one place this page navigates away from itself**, so it flushes the book's pending writes, lowers the editor and drops the Library where it cannot dock beside the chat it just opened, which is the recipe the Library's own character pick follows.

**Off stores as nothing**, so a book nobody switched on keeps the row it always had, and the switch **never travels in an export**, unlike the activation overrides: it is a decision about this install's whole setup, and a shared book that turned itself on in a stranger's library would rewrite every prompt they send. Nothing the page states is stated in a menu too, and nothing else about a single book lives in the page's body, which is activation and entries only. **A book with no name lands with the caret in its Name field**, which is what makes the shelf's New a single press; the book is read inside the `tick` rather than as a dependency of that effect, since every keystroke anywhere in the book reassigns the store's list and an effect tracking it would yank the caret back to the title on each one. A book that goes while it is open (deleted here, from the shelf, or on another device) closes the editor rather than leaving an empty document over the chat.

Two small couplings to the assistant ride these two surfaces. The editor mirrors the open book into `workspaceFocus.setLorebook` (the assistant's auto-attach signal) and releases it on its own unmount: it exists exactly while a book is open, so unmounting is the user navigating away, and a focus left standing would keep the assistant pointing at a closed book. And the **shelf** consumes the one-shot `uiStore.pendingLorebookId` deep link (an assistant chip pointing at a book), the same shape the two library views use for theirs: an id that names a book opens it; one that names nothing is dropped once the shelf has books, rather than left armed to open an editor over a book that is gone.

## Before touching this

- A new act on the ARCHIVE (make, import, a bulk anything) belongs to the shelf; a new act on ONE book belongs to the editor's actions menu. **Binding is the exception that proves it**: it is an act on one book AND on one card or chat, so it is offered from both ends and stored once. A third door is fine on the same terms and never on its own row: write through `characterLibraryStore.updateData` or `chatStore.toggleChatLorebook`, or that door's bindings are a second kind of binding that only it can see. Put an archive act in the editor and it reads as something that happens to the book whose name is beside it. **A setting follows the same line**: one that every book falls back to is the shelf's Global Settings page, and only what a single book overrides may appear in that book's Activation strip.
- A selection can only download as ONE file: a browser blocks a burst of downloads, so `downloadLorebooks` zips anything past a single book ([`io.ts`](../src/lib/lorebook/io.ts), the same STORE-method writer the library's bulk card export uses). Names are deduped there, by probing what is already taken rather than by counting, because nothing dedupes book names and two books called the same thing would silently land as one file.
- **A transfer writes the DESTINATION first and cuts the source only once that write has returned** (`lorebookStore.transferEntries`), the rule `setCover` follows: a failure between the two is then a duplicate the reader can see and delete, where the other order is entries that left one book without arriving in the other. Each write puts its own book's entry list and timestamp back if it throws, because a book left holding rows the server never took wins the next `refresh` on its fresher stamp, and the failure the reader was just told about would come true on the next edit. **The destination never appends an id it already holds**, so retrying that duplicate finishes the move rather than landing a second copy: one book carrying an id twice is a delete that takes both rows, an edit that reaches only the first, a repeated key in the list, and one sticky window shared by two entries. Driven end to end in [`transfer.test.ts`](../src/lib/lorebook/transfer.test.ts).
- **A copied entry takes a fresh id; a moved one keeps its own.** Sticky and cooldown windows are measured per entry id across every book at once (`lorebookHistory`) and a scan's records are keyed by it (`selectFromBooks`), so a move carries an entry's own timing along with it, while two entries sharing one id would share one window and collapse into a single record in the trace. The copy keeps its title verbatim: it lands in a book that has no entry of that name, so there is nothing for a "(copy)" to tell it apart from, unlike the duplicate the row menu makes beside the original.
- Deleting is `lorebookStore.deleteBooks`, one reassignment of the reactive list however many books go, and every delete in the app funnels through it. Loop the single-book call instead and a fifty-book selection is fifty re-renders of the shelf drawing it.
- **The cover file is swept by `serverDb.deleteLorebook` itself**, not by either caller, because both doors reach that one method: this store over the RPC bridge, and the assistant's `delete_entity` (server/assistant/registry/entities.ts). Nothing else can reach `images/lorebooks/` (the boot sweep is scoped to `images/chat/`), so a file missed there sits on disk forever, and a rule the assistant can walk around is not a rule. **That sweep may not cost the delete**: the row is gone and autocommitted by the time the unlink runs, so a file the OS holds (EPERM/EBUSY on Windows) is logged and stepped over, or the throw escapes the bridge and the `lorebooks` sync hint, the backup stamp and the rest of a bulk selection all go with it. And **the path it unlinks is gated at the write**, `images/lorebooks/<file>` with no separator in the filename (`insertLorebook`/`updateLorebook`, server/db.ts): a row naming another category would make deleting a book destroy a character's portrait.
- **A write that finds no row is a failure, loudly** (`updateLorebook` throws when the UPDATE changes nothing). A book deleted on another device otherwise takes an edit in silence, and in `transferEntries` that is the destination write appearing to land, after which the source is cut and both copies of the entries are gone. **A payload that will not parse costs its own book and nothing else**: `mapLorebook` reports it and answers with no book, leaving the row untouched, since one torn row would otherwise take the shelf, every generation in the install and the row's own delete with it.
- The one wording of what a delete costs is `lorebookDeleteMessage` ([`types.ts`](../src/lib/lorebook/types.ts)), read by the shelf's row menu and the open book's own menu. A second copy is how the menu standing beside the book's name becomes the one that forgot to say who carries it.
- The engine must stay pure (no db/stores/Svelte): the real prompt and the live token meters share it, and `engine.test.ts` guards behavior. Run `bun test` after any engine change.
- A new reason an entry can end up in or out of a prompt is a new `LorebookStatus`: the engine must write it, `lorebookWasInjected` must place it, `buildLorebookTrace` must decide whether it is worth storing, and `LorebookTraceList` must word it. The last two are compile-checked (`Record<LorebookStatus, string>`), the first two are not.
- A new way for a book to reach a prompt, or to be kept out of one, belongs **inside `resolveLorebookLinks`** and nowhere else. Every surface that prices or builds a prompt already calls it, so a rule added there reaches the send, the two token meters, the memory context and the prompt builder at once; added beside one of them it reaches that one, and the other four quietly disagree with what was sent.
- **Muting is a decision about one story, so it is offered in the composer's chip alone.** Binding is offered from both ends because a link has two, but a book's own page listing the chats that muted it would be a page about somebody else's stories, and a card that could mute would be muting on behalf of every chat it plays in, which is what the link list already is with the sign flipped.
- **A new per-book field lands in the server's payload whitelist too.** `insertLorebook` and `updateLorebook` (server/db.ts) name every key they store; the client sends the book whole, so a field they do not name round-trips fine in the tab that set it and is gone the moment any device reloads. A cover that never persists is what that looks like.
- New per-entry or per-book field? Decide modelled vs `rest`/`extensions`. A modelled field touches: types.ts (+ tri-state inheritance), engine resolution, sillytavern.ts import AND export mapping, and the editor UI. An unmodelled field just rides along, so prefer that unless the engine needs it.
- Keep SillyTavern field names verbatim in the model; translation happens only at the character_book boundary.
- A new generation that builds a prompt must name its `LorebookTrigger` (`PromptBuildContext.lorebookTrigger`, or `buildLiveMacroContext`'s option). Leaving it out is not an error, it silently reads as a plain send, so an entry limited to Impersonate would fire there too.
- Entry fields added since the first release are OPTIONAL (`keyRules`, `scanDepth`, `scanFields`, `triggers`, `sticky`, `cooldown`, `delay`, `group`, `groupOverride`, `groupWeight`, `useGroupScoring`, `position`, `depth`, `role`, `excludeRecursion`, `preventRecursion`, `delayUntilRecursion`): stored rows predate them and are never rewritten, so absent must keep meaning "inherit / all". Nothing normalises a book on load. The three recursion fields are the ones whose absent value is answered by `rest` rather than by a default, which is why they are only ever read through `resolveEntryRecursion`.
- Writing one recursion field writes all three and clears both legacy spellings from `rest` (`withoutStoredRecursion`). Writing one alone would leave the other two answering from `rest`, and clearing `rest` alone would drop settings the reader never touched.

## Hand-kept couplings

1. Link resolution order: **one implementation.** `resolveLorebookLinks(books, links)` in [`lorebook/types.ts`](../src/lib/lorebook/types.ts) answers what a chat plays with, widest layer first: the books switched into every chat, then `resolveLinkedBooks`'s order-preserving dedupe of what the cards link (`links.cards`), then the same over what the chat itself attached (`links.chat`), deduped across all three, and finally **minus what the chat muted** (`links.muted`), taken off the finished list so the subtraction cannot be undone by a layer running after it. **Every key of `LorebookLinks` is required rather than optional**, so a surface that assembles a prompt has to answer every question: a key it could leave out is a layer it can drop in silence, and the type is the only thing standing between a new call site and a meter that prices a prompt the send does not build. `lorebookStore.booksForChat` calls it over the store's cached books (meters/UI) and prompt-builder calls it over a fresh `db.getAllLorebooks()` (generation). **The two store methods are two questions**: `booksForChat` for anything that prices or builds a prompt, `resolveLinks` for anything that counts an entry's own links. The two differ only in where the books come from, which is deliberate: generation never trusts the store's cache. Fork the resolver and the meter starts lying. **Globals lead the list and are ordered by `createdAt`, never by the array they arrived in**: the store's cache and the server's read are the same query at two moments, so an edit that moves a book in one and not the other would have the meter and the send lay lore down in a different order. Each layer trails the one it narrows, so nothing a card or a chat names can reshuffle the baseline under it. The five call sites read the chat's own two layers through `chatLorebookClaim` and `chatMutedLorebookClaim` ([`utils/chat-setup.ts`](../src/lib/utils/chat-setup.ts)), except the memory store, which carries both on its `ChatCtx` like every other claim (architecture/memory.md). **The assistant carries the only second spelling** (`chatLorebooks` in server/assistant/registry/chat-reads.ts, which cannot import this module): leave any card-less layer out of it and `read_chat_context` describes a scene the story is not playing, once for the books that are in every scene, once for the ones this story alone was given, and once for the ones it took back out. Pinned by `contracts.test.ts` and driven end to end in `server/perChatSetupUsage.test.ts`.
2. Book-over-global resolution is `resolveBookActivation` in [`lorebook/types.ts`](../src/lib/lorebook/types.ts) and lives **only** there: `selectFromBook` selects with it, `LorebookActivationPanel` shows and labels its rows from it, and `LorebookEntryRow` reads its match defaults out of it. Fork it and a row starts naming a value the scan won't use. **The collapsed line above those rows is one wording too**, `activationSummary` beside it: the book's Activation strip prints its resolved values against the defaults, and the shelf's Global Settings row prints the defaults against themselves, so the same setting cannot be named two ways one press apart and the root layer lights nothing (a part is lit only where the resolved value differs from what it would inherit). Its `global` argument prints *every chat* at the head of the line and is the one part the shelf can never carry, since that switch belongs to a book: it exists because the switch now sits inside the fold, and a folded strip that did not say it would hide the widest state a book can be in. Entries resolve their two tri-state fields on top of that result, in the engine and in the row. A new inheritable knob lands in the resolver, in the engine's use of it, and as a row in the panel.
3. ChungusHub book-override extension keys (`max_recursion_steps`, `case_sensitive`, `match_whole_words`) are written by `bookOverrideExtensions` and read by `liftBookOverrides` (sillytavern.ts). Rename in pairs.
4. `budgetPercent` is applied in `buildMacroContext` / `buildLiveMacroContext` (both build the `LorebookBudget` from the prompt budget). A budget-shape change lands in both.
5. A key's effective mode is `resolveKeyMatch` in [`lorebook/types.ts`](../src/lib/lorebook/types.ts) and lives **only** there: the engine matches with it and the chip's picker labels its rows from it (including which row reads "entry", the one a chip lands on when it sets nothing). `compileRegexKey` beside it is the one compile both sides run. Fork either and a chip starts naming a mode the scan won't use, or the editor accepts a pattern the scan refuses.
6. The card text a scan may read is `lorebookScanFields` in [`lorebook/types.ts`](../src/lib/lorebook/types.ts), called by all three context builders. Fork it and an entry scanning the scenario reads a different scenario at the meter than at the send.
7. The path's earlier traces are `lorebookHistory` in [`lorebook/types.ts`](../src/lib/lorebook/types.ts), called by all three context builders over the same path they scan. Fork it and an entry's sticky window is a different length at the meter than at the send.
8. `LOREBOOK_SCAN_FIELDS` carries BOTH SillyTavern spellings per row (`native` flat, `card` snake_case). A new source is one row; renaming a spelling without its twin silently drops the flag on one of the two import shapes.
9. An entry's recursion settings are `resolveEntryRecursion` in [`lorebook/types.ts`](../src/lib/lorebook/types.ts) and live **only** there: the engine gates with it, the entry row labels its control from it, and both exporters write through it. It is the one reader that knows a stored row may still keep these under either SillyTavern spelling in `rest`, so a second reader silently loses every setting an older import carries. `RECURSION_FIELDS` beside it is the one table pairing each flag's two spellings, read by both importers and both exporters; renaming a spelling without its twin drops the flag on one of the two shapes.
10. Book **display** order is `sortLorebooks` in [`lorebook/types.ts`](../src/lib/lorebook/types.ts), applied only where a list is rendered: `LorebooksView` derives its own ordered copy, `LorebookLinkPicker` derives one and then stably re-sorts linked-first over it, `LorebookTransferPicker` derives one and is also the second surface that WRITES the preference, and all three read `order` off [`stores/lorebookViewPrefs.svelte.ts`](../src/lib/stores/lorebookViewPrefs.svelte.ts). That picker offers three of the seven orders and takes its labels from `LOREBOOK_SORT_OPTIONS` by id rather than writing its own, since a fourth wording of A → Z is how two views of one shelf start naming one setting two ways; a shelf left on one of the other four lights none of its chips, which is honest, and pressing one adopts that order everywhere. **`lorebookStore.books` is never reordered.** Coupling 1 resolves links over that order and it decides what reaches the prompt first, so sorting the store to tidy the lists would let a display preference silently rewrite the prompt. One preference rather than one per list, because the shelf and the picker are two views of the same shelf; the layout, card size and per-page beside it belong to the shelf alone, since the picker is a popover with one shape. **That store's settings key is still `lorebookSort`**, the name it had when the order was all it held, because that is what sits on every install: a bare string there is read back as the order rather than dropped. **Every order ends on the same tie-break**, `createdAt` newest first, and never `updatedAt`: nothing dedupes names on import, so a last-edited tie-break makes a duplicated pair swap rows the moment either one is touched. The counting orders need it most, since a shelf where nothing has been written yet is one long tie.
11. Entry **display** order is `sortEntries` in [`lorebook/types.ts`](../src/lib/lorebook/types.ts), applied only where the list is rendered, and the chosen order plus the natures held out of it are the single preference in [`stores/lorebookEntryPrefs.svelte.ts`](../src/lib/stores/lorebookEntryPrefs.svelte.ts). **`book.entries` is never reordered**, for the same reason coupling 10 protects the shelf: the engine returns survivors in `order` sequence and both the block and the at-depth groups are admitted in it, so sorting the stored array to tidy the list would let a view preference decide what reaches the model first. Every order ends in a tie-break on `order`, because two rows the chosen order cannot separate would otherwise sit in whatever sequence the book stores them in and swap the moment one is edited, with nothing on screen admitting the swap. The preference is one for the whole app rather than one per book: per book would mean writing a view choice onto stored data every install already holds.
12. An entry's nature is `natureOf` in [`lorebook/types.ts`](../src/lib/lorebook/types.ts) and lives **only** there. `partitionEntries` buckets by it, the entry row's behavior switch reads it, and the list's Show filter matches on it, so a row the toolbar files under one kind cannot open showing another. `disable` outranks `constant`: an entry that is both reads as **off** everywhere, since a disabled entry is inert whatever else it says, and hiding Off has to take it along.
13. A book's identity is `bookFingerprint` in [`lorebook/identity.ts`](../src/lib/lorebook/identity.ts) and lives **only** there: both import surfaces ask it through `createBookIndex` (the folder migrator and the Library's own card picker). Its field list is paired with the two entry parsers in [`sillytavern.ts`](../src/lib/lorebook/sillytavern.ts): a field whose DEFAULT differs between `fromNativeEntry` and `fromCharacterBookEntry` must never be added to it, or one book read out of the two shapes stops matching itself and every card shelves its own copy again. Adding an entry field to the model is not a reason to add it here; only a field a reader would call part of what the book says is.
