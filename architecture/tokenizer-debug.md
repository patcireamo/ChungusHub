# Tokenizer & prompt debug panel: architecture & maintenance

## Tokenizer (`src/lib/tokenizer/`)

Every token number in the app comes from one entry point: [`index.ts`](../src/lib/tokenizer/index.ts) exporting `countTokens`/`countMessages` (pure and rune-free, in [`count.ts`](../src/lib/tokenizer/count.ts)) and `tokenCalibration`. Only two local BPE encodings ship ([`encodings.ts`](../src/lib/tokenizer/encodings.ts): gpt-tokenizer's o200k/cl100k, resolved by model-id **family** rules, never a per-model table). Everything non-OpenAI counts under o200k as a **base estimate**, and the calibration layer corrects it: after every real generation, `tokenCalibration.record(model, ourEstimate, provider prompt_tokens)` folds the actual/estimate ratio into a per-model EMA (pure math in [`calibration-core.ts`](../src/lib/tokenizer/calibration-core.ts), clamped + small-prompt-guarded, tested in `tokenizer.test.ts`; persistence + `$state` in [`calibration.svelte.ts`](../src/lib/tokenizer/calibration.svelte.ts), `tokenCalibration` settings key, re-read on every `settings` broadcast so devices share what they learn instead of each drifting on its own copy).

**The two spaces rule**: prompt assembly counts in base-estimate space; the context budget is computed in real-token space and divided by `ratioFor(model)` before being handed to the assembler (`llmService.getPromptTokenBudget`), so budget trims, lorebook budgets and meters all compare like with like. `record()` is called from `messageStore.generateResponse` / `continueMessage` / `generateOpeningScene` with the exact messages sent. If you add a new generation path, feed calibration the same way or the model's factor goes stale.

## Prompt debug panel (`src/lib/debug/` + `components/debug/` + `server/promptLog.ts`)

This panel answers what a request WAS. The other half of that question, what one is about to be, belongs to the prompt hold and its review surface (architecture/prompt-pipeline.md): a different subject (an `LLMMessage[]` on its way out, not a captured record), a different contract (editable, and gone the moment it is answered), and so a deliberately separate component that only borrows this one's visual language. What the hold releases is captured here like any other request, so the log still tells the truth about a hand-edited send.

The log is **server-side, durable, and shared**: `server/promptLog.ts` captures every LLM request/result at the server chokepoint (completions in `handleLlm`, assistant iterations via the loop's `recordPrompt`/`recordResult`) into the SQLite `prompt_log` table (opaque JSON rows, server-internal db methods that are deliberately NOT on the RPC bridge), so the log survives server restarts and reaches every device whenever it connects. Bounded at 500 entries, oldest pruned on insert; a corrupt row throws on snapshot rather than being dropped. Capture happens only while at least one device has the panel enabled (`debugSockets`); `patchResult` returns false for a request that was never captured, and callers skip the broadcast then. That keeps request/result pairs intact when debugging toggles mid-flight.

A captured entry holds **everything that rode the request**: the messages verbatim (each with its `images` paths, never bytes), the `tools` array, `params`, `tuning` and `routing`. That is the panel's whole contract: a field that is sent but not captured is a field the panel cannot show, so a new request field is wired into the entry shape at the same time it is wired into the wire body. Each entry also stores the **response**: `responseContent`/`responseThinking` (completions and assistant steps) and `responseToolCalls` (assistant steps, wire-shape). Lifecycle is `pending` → `done`/`error`/`cancelled`, per completion and per assistant iteration. A user stop RESOLVES in the provider layer with everything it streamed (architecture/llm-providers.md), so both capture sites derive the status from `finishReason === 'cancelled'` instead of filing a stopped request as a clean one, and the loop settles a still-pending entry from its catch block via `pendingPromptId`. Boot runs `settleInterrupted()` beside the assistant's own interrupted-turn sweep: an entry left `pending` by a process that died becomes an error naming the cause, because "in flight" forever is indistinguishable from a request that is genuinely still running.

The client ([`promptLog.svelte.ts`](../src/lib/debug/promptLog.svelte.ts)) subscribes to the transport's prompt-log bus for live events, backfills over `GET /api/debug/prompt-log` when enabled, de-dupes by id on reconnect, and offers selection + a two-entry compare set. Clear (`POST .../clear`) wipes the stored log for every device. Enablement is the Advanced-tab toggle → `advancedSettingsStore.promptDebugPanel` → `promptLogStore.setEnabled` → the WS `debug` message. On phones (`viewport.isMobile`, 640px, matching the panel's own media query) it shows one pane at a time: list ↔ detail with a back button; picking the second compare entry keeps the list visible.

**The panel shows the whole request, or it is lying.** [`PromptDebugPanel.svelte`](../src/lib/components/debug/PromptDebugPanel.svelte) is a list plus a detail. The detail's fixed head carries identity (source + assistant step, model, resolved model, provider), the Pretty/Raw switch and a copy-the-whole-record button, then a row of labelled figures. The switch and the copy button are one group (`.dh-tools`) that takes its own full-width line on a phone, with the copy button dropping its label there: sharing the identity line squeezes both down to unreadable stubs, and the model name is what may shrink, never the controls. Then (status, prompt, completion, cached, total, started, duration, finish) and the error when there is one. Its scrolling body is four sections:

- **Request fields**: `requestChips` renders `params`, the stream mode, and the `tuning`/`routing` objects flattened key by key, so a knob those shapes gain later appears here with no edit.
- **Tool definitions** ([`PromptToolCard.svelte`](../src/lib/components/debug/PromptToolCard.svelte)) are collapsed by default but fully **readable**: name, description and the exact JSON Schema per tool, with the set's size and share of the request in the header. Reducing them to a count hides the largest part of an assistant prompt from the view whose entire job is reading it.
- **Messages** ([`PromptMessageCard.svelte`](../src/lib/components/debug/PromptMessageCard.svelte)): every message whole, with its wire fields (`name`, `tool_call_id`), its tool calls, and its **image attachments as thumbnails with filenames**, opening the shared `ImageLightbox`. An image listed here provably rode the request: the send gate strips images BEFORE this capture point, so the log only ever holds what went out. The panel owns the single lightbox, hands it this entry's whole image list (`entryImages`) so it pages the request rather than the one card the thumbnail sat on, and stands down from its own Escape while it is open.
- **Response**: synthesized `thinking`/`assistant` cards. A settled request with no body states which case it is (failed / stopped / empty) instead of dropping the section.

Raw is `JSON.stringify(entry)`, the captured record itself, never a hand-picked subset. Nothing in either view previews, clips or samples content. Folding is owned by the panel (keys scoped to the entry id; messages default open, tool definitions default closed, `Fold all` touches messages only), so a card's chevron and the fold-all control can never disagree.

**One token number.** `promptSize` ([`format.ts`](../src/lib/debug/format.ts)) returns the provider's reported `promptTokens` when there is one and the base estimate otherwise, with a `reported` flag the panel spells out (`prompt · reported` vs `prompt · estimated`, the estimate also marked `~`). There is deliberately no estimate-vs-real split anywhere: the model was handed one prompt, so the panel states one figure and says which kind it is. A zero prompt count is not a report and falls to the estimate under the estimate's label. The estimate counts message text, the tool-call payloads messages carry, AND the tool definitions. Leaving the schemas out understates an assistant turn by more than half. It cannot price images, so the panel says so in words whenever it estimates a request that carried any. Estimates are memoized by entry id (a captured request's half never changes), or the list would BPE-encode the whole log on every event. `format.ts` imports `$lib/tokenizer/count`, the rune-free counter. The panel states a BASE estimate and labels it as one, so it needs no calibration layer.

Presentation helpers: [`format.ts`](../src/lib/debug/format.ts) (source/status/role colors, where a new query `source` label gets its color; sizing; `requestChips`), [`diff.ts`](../src/lib/debug/diff.ts) (real LCS line diff, abandoned past `DIFF_LINE_CAP` lines), [`CopyButton.svelte`](../src/lib/components/debug/CopyButton.svelte) (takes a getter, not a string, so the payloads are only serialized on click; a blocked clipboard shows on the button instead of being swallowed). `PromptCompareView` diffs each message's **wire envelope plus its text** (role, `name`, `tool_call_id`, image paths, tool calls) and compares the tool definitions as their own block. A compare that reads only `content` would call two requests identical while one of them carried a different picture or a different tool set. When the LCS is skipped for size the block is badged `coarse`, since a whole-block diff reports every line as changed.

**Detached window.** The **Pop out** button is desktop-only (`viewport.isMobile`): a phone has no second screen to move the panel to, and the named pop-up is either blocked or lands as a tab that replaces the app. Where it is shown, it opens `/debug` ([`+page.svelte`](../src/routes/debug/+page.svelte)) as a named window and closes the in-app copy, so the log can sit on a second screen while the workspace stays whole; clicking it again raises the window already out rather than opening a duplicate, and a blocked pop-up surfaces as a toast instead of doing nothing. That page is deliberately **not** a second app instance: it boots the socket (`db.initialize`) and the theme, calls `promptLogStore.setEnabled(true)`, and stops. The log is server-side and shared, so it needs nothing from the window that opened it, and since capture runs while ANY socket is listening it keeps logging with the app window's Advanced toggle off. It skips `initSync()`, whose handlers would reload a dozen stores this page never initialized, and drives the one scope it needs by hand: a `settings` hint calls `reloadAllSyncedSettings()`, or a palette change in the app window leaves the detached one painting the old theme. The panel's `standalone` prop is what drops the pop-out and close buttons there: closing the window is the way out, and its Escape branch is already inert because that page's `uiStore.debugPanelOpen` is false.

Entries carry a `source` label: `'chat'`, `'continue'`, `'opening-scene'`, `'memory'`, `'spellcheck'`, `'impersonate'` passed to `llmService.complete` by the caller, plus `'assistant'` which the loop sets itself; label new callers or the server stores them as `'completion'` and they render gray. `SOURCE_COLORS` is keyed `EngineId | 'chat' | 'assistant' | 'continue'`, so an engine without a color is a compile error. `'steering'` has one but never logs, since it makes no call of its own.

## Before touching this

- Never count tokens with anything but `countTokens(text, model)`; never introduce a second calibration path.
- The debug log must stay zero-cost when disabled (capture gated server-side) and must never contain raw image bytes (paths only).
- **Nothing on this path shortens, samples or previews.** Not the capture, not the panel, not a copy button. If a bound ever becomes unavoidable, it is labelled where it applies (the compare view's `coarse` badge is the pattern).
- **Known capture boundary**: the chokepoint records what our layer hands the provider. `openai-compatible` sends those messages one-for-one (it only expands `images` paths into content parts and places `cache_control`), so the panel is exact for 13 of 14 providers. `anthropic-native` then reshapes for the Messages API (leading system turns hoisted to top-level blocks, later system turns demoted to user, empty turns dropped, a placeholder first user turn added), so an Anthropic entry's transcript is what we handed the provider, one structural step before the wire body.
- `bun test` covers calibration math + counting, `src/lib/debug/format.test.ts` the panel's sizing and request-field rules (tool definitions inside the estimate, reported-vs-estimated), and `server/promptLog.test.ts` the log's record/patch/prune/boot-sweep persistence against the real db.

## Hand-kept couplings

1. The entry/message/event shapes exist in **three** places: `server/promptLog.ts`, `src/lib/services/transport.ts` (request half named `PromptLogRequest`), `src/lib/debug/types.ts` (`PromptLogEntry`, re-exporting transport's `PromptLogMessage`). Keep them structurally identical. A request field added to the WS `llm` message or to `AssistantRequest` belongs in all three plus its capture site (`handleLlm`, `loop.ts`), or the panel silently omits something that was sent.
2. `source` label strings: producers (messages store, memory store, composer transforms, assistant loop) ↔ `sourceColor` in `format.ts`.
3. Calibration feeding sites ↔ generation paths (the three in `messages.svelte.ts`); the assistant loop reports usage per turn and deliberately does not calibrate.
4. The panel's open-state is part of `uiStore`'s panel choreography (architecture/ui-shell-settings.md); the enable-toggle is a synced setting.
5. The `/debug` route's boot ↔ `AppShell.boot()`. It initializes the smallest set the panel actually reads, so a store the panel (or the tokenizer under it) starts depending on has to be added there too. Otherwise it works in the app window and throws only in the detached one.
