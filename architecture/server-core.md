# Server core & persistence: architecture & maintenance

One Bun process ([`server/index.ts`](../server/index.ts)) does everything: serves the built SvelteKit PWA from `build/`, exposes the REST API under `/api/*`, serves user images under `/files/*`, and runs a single WebSocket (`/ws`) that carries cross-device sync hints, LLM token streaming, assistant turns, and debug-panel prompt logs. There is no other backend. The client never touches the filesystem or SQLite directly: every persistent byte flows through this process.

**Paths & config** ([`config.ts`](../server/config.ts)): everything lives under one data dir: `CHUNGUS_DATA_DIR` env override, else `dataDir` from the settings file below, else `./user-data` (next to the exe when compiled: `IS_COMPILED` detects `bun build --compile` via the bunfs mount in `import.meta.url`, **decoded first**: a file URL escapes the `~` of the Windows mount to `%7E`, and an undecoded check answers false in every Windows portable build, rooting the whole install at the working directory instead of at the executable). `resolveBackupDir()` sits beside `resolveDataDir()` and is late-bound for the same reason (architecture/backups.md). `config.ts` creates the data dirs **at import time**, so merely importing it (or anything that imports it) touches disk. `ensureDirs()` also drops the two privacy markers ([`privacy-notice.ts`](../server/privacy-notice.ts)): `DO-NOT-SHARE-THIS-FOLDER.txt`, which names what the folder holds, and a `.gitignore` of `*`, so the folder survives being dragged into a repo or having `git init` run over the install without anything in it being staged. Both are written **only when absent**, never overwritten: an edited notice keeps the edit, a deleted one comes back next boot. The backup store gets the same pair (architecture/backups.md). Key env: `CHUNGUS_PORT` (**default 4242**, chosen to sit clear of what this audience is already running: SillyTavern 8000, koboldcpp 5001, ComfyUI 8188, a Stable Diffusion UI 7860, Ollama 11434. A collision costs a reader their first launch, which is the launch they judge the app on), `CHUNGUS_HOST` (default 0.0.0.0), `CHUNGUS_ALLOWLIST` (comma-seeded always-allowed IPs, never persisted).

**Process settings are a file, and the split is what keeps them findable.** `chungushub.config.json` (`CONFIG_PATH`, beside the executable when compiled, beside the repo from source) holds the five things this process has to know before it can answer anything and that nothing inside the app can fix once they are wrong: `port`, `host`, `dataDir`, `backupDir`, `openBrowser`. Everything the app can change about itself is an app setting and lives in the `settings` table instead; a new knob picks its side by that question alone. **It is the only configuration surface the docs name.** The `CHUNGUS_*` variables still work and still outrank it, but they serve the test suite and the dev server rather than a reader, so two documented places can never disagree about one value. `openBrowser` is the one with two readers: `index.ts` for a launch that is somebody's whole launch, and `vite.config.ts` for the dev server, which owns the tab in two-process dev because it alone knows :1420 and starts once (architecture/build-packaging.md). **It cannot live under the data dir**, being the thing that says where the data dir is. Precedence is **env > file > default**, and the env half is load-bearing rather than legacy: the test suite pins throwaway dirs through the environment and has to outrank whatever the machine running it carries. A variable winning over a key the file **also states** is pushed to `CONFIG_OVERRIDES` and printed in the boot banner: an edited line silently doing nothing is the one failure an undocumented second surface can still cause, and an install that read the old docs may still carry one. Relative paths resolve from the config file's own folder, **except `backupDir`, which resolves from the data dir** so its `../backups` default is exactly the sibling rule `resolveBackupDir()` has always applied, including for a data dir moved elsewhere by env. `ensureConfigFile()` writes the file on a first run with the **plain defaults and never the values this launch resolved**: an env override already outranks the file, and baking one in would hand the next launch a path meant to live for one shell. Every run after the first **backfills**: a file already there keeps every value in it and gains only the settings it lacks, so a key added in a later version reaches installs that already exist rather than being one the reader has to hear about somewhere and type in. `CONFIG_DEFAULTS` is the single list the first write, the backfill and the unknown-key check all read, so they cannot disagree about what a complete file looks like. Three rules make rewriting a hand-edited file safe: **a file it cannot parse is left byte for byte alone** (rebuilding one from defaults would drop the line naming where the data lives, and boot has already refused to start on it), a missing key is written with its **default and never the resolved value**, and nothing missing means **nothing written**, so the file is touched once per new setting. What is there is edited as the object it parsed to rather than rebuilt from a template, so notes, key order and a misspelled key all survive; only the indentation is normalised. The write is temp-then-rename like `security.json` and `allowlist.json` and for a stronger reason: a torn one stops the next boot with the data dir line gone. [`server/config.test.ts`](../server/config.test.ts) pins all of it. A value it cannot read (bad type, unusable port) is collected in `CONFIG_ISSUES` rather than thrown, because `vite.config.ts` imports this module too; boot reads that list and stops on it through `fatal()`, and import-time `ensureDirs()` is skipped while it is non-empty so a refused launch leaves no data folder at a path nobody chose. **A key that is not a setting goes to `CONFIG_NOTICES` instead and only prints**: nothing is being substituted for it, and stopping the boot would wall off going back to an older ChungusHub after a newer one backfilled a setting into the file, which is a move the app allows for the database. `DEFAULT_PORT` is exported for [`scripts/package.ts`](../scripts/package.ts) alone: the zip ships without a settings file, so its README states what a fresh install will listen on rather than the build machine's port.

**One running instance per data folder** ([`instance-lock.ts`](../server/instance-lock.ts)). Nothing underneath enforces it: `bun:sqlite` takes no file lock, so two processes on one database both write it, and the images, presets and snapshot store beside it have no locking at all. Until the port became a setting the only thing in the way was two copies wanting one port, which is not a guarantee and never was. The claim is **a listening socket, not a lock file**: a named pipe on Windows, and a unix socket elsewhere, both named by a hash of the canonicalised data dir path. That choice is the whole design, because the kernel releases the socket the instant the holder dies however it dies, so there is no stale claim to sweep, no heartbeat to keep writing and no pid to guess at. **The socket is never put inside the data folder**, tempting as that is for something scoped to it: two `fs.watch` handles sit on that directory for the life of the process, and on Linux a watcher that meets a new socket there opens it, gets `ENXIO`, and ends the process. It is not `os.tmpdir()` either, which follows `TMPDIR` and is per-user on macOS, so two launches disagreeing about it would each find their own address free and both run; `/tmp` is the one place both platforms agree on. Those watchers now report a fault instead of raising an unheard `error` event, which is what made a stray socket fatal in the first place: a watcher that dies costs the live-edit of `security.json` and nothing else, and the server has no business stopping over it. **A stale socket is removed only for the two error codes that mean nobody is there** (`ENOENT`, `ECONNREFUSED`); any other failure to reach it says the folder may well be held, and deleting it then is how two copies end up writing one database, so it stops the launch instead. **A refusal counts only once it has repeated**, four asks a few milliseconds apart: a unix socket server refuses the odd connection while it is alive and listening (on Linux about one connect in two hundred, with or without a backlog of its own), and a refusal is the single answer that deletes the address, so taking the first one at its word hands a running copy's folder to the copy starting beside it and both then write one database. An address that is genuinely dead refuses every ask, so a crashed copy's residue is still swept, a few milliseconds later. **A starting instance connects rather than binding**: reaching the address is proof enough, the holder answers with its pid and live port so the refusal can name it, and binding to find out is the one call Bun cannot report on a contended pipe (it aborts the process instead of raising). **A holder is waited out for the same few seconds the port is**, and for the same reason: a process that panicked and relaunched itself is racing its own corpse, and refusing on the first answer would move that failure one line earlier instead of fixing it. The claim is taken **before the restore swap and before any database is opened**, since everything past that line writes into the folder. Every way it can fail goes through `fatal()`, including the one where it cannot tell either way, because carrying on there is exactly the guess the mechanism exists to refuse. Two launches inside one event-loop tick can both find the address free; nothing closes that window, and closing it would take a second lock with the staleness problem this one exists to avoid.

**Data written by a newer build is announced, not refused.** Migrations only ever run forward, so a folder whose `_migrations` high-water mark is above `LATEST_SCHEMA_VERSION` was upgraded by a newer ChungusHub, and this one would read a schema it was never written against and write rows the newer build may not accept back. `schemaVersionOnDisk()` is read **once**, after the restore has decided which database this is, and feeds both `snapshotBeforeUpgrade()` and the `dataAhead` flag. The boot says so on its own output and `GET /api/config` carries the same flag to every device (the reader deciding whether to keep writing is not necessarily at the machine the warning printed on; the bar it raises is architecture/ui-shell-settings.md). It is deliberately **not** a refusal: the alternative is an install that will not open the only copy of someone's work, and the snapshot the newer build took before upgrading still holds the data as it was. Bundled assets come from the repo, not the data dir: `defaults/presets/` seeds `user-data/presets/` on first boot ([`files.ts`](../server/files.ts) `ensureDefaultPresets()`, which also copies a default preset's bundled cover art into `images/presets/` under a fresh id, see architecture/preset-authoring.md), `defaults/backgrounds/` is served **directly** from the repo at `/files/backgrounds/<file>`, so dropping a file there ships it.

**Network access is not a gate, it is the socket.** `security.json`'s `networkAccessEnabled` (default **off**) is the only thing `bindHostname()` reads, and `Bun.serve` is opened on `HOST` or on `127.0.0.1` accordingly, so with it off a device on the network finds no port rather than a page that turns it away. That is the whole point of it existing beside an allowlist that could refuse the same device: refusing still answers. Flipping it from Settings persists, then `rebindNetwork()` queues a rebind that stops the old server with `stop(true)` and serves a new one on the other address; the POST handler defers that by a tick so its own reply is on the wire before the socket it travels on closes. Every connection dies with the rebind, including the host's, which is why no `kickAllSockets()` is needed there. **An edit made to `security.json` itself reaches the same rebind**, so a machine with no browser on it is opened up with a text editor and no restart. **Rebinds are serialized through one promise chain and each link re-reads the switch instead of carrying the value it was queued with**, which is not a nicety: two flips arriving together would both find the address stale, both close the socket, and race each other onto the port, and the loser's `EADDRINUSE` takes the process down with nothing listening. A double tap on the toggle is enough. Re-reading also means a burst collapses to whatever the last flip asked for rather than thrashing the socket once per click. A rebind that fails anyway is fatal on purpose: the old socket is already gone, there is nothing honest to fall back to, and a process that stays up serving nobody is worse than one that stops. **`vite.config.ts` cannot move its socket** (a listening address is fixed for the life of a process), so dev always binds the LAN and `allowlistGate()` enforces the switch at the socket instead: while the switch is off, every non-loopback connection is destroyed before a byte of HTTP is read, re-checked per connection, which makes the switch live in both directions with no restart. It must never answer with a page instead: a page refusing the device still says ChungusHub is here, and a device on the network finding nothing is the whole point. **A boot that cannot open the socket stops in words rather than in a stack trace.** `bootServer()` catches the bind: a taken port is answered with the port and the `"port"` line to change in the settings file, and every other bind failure goes the same way instead of being re-raised, since an uncaught throw here is the one failure nobody gets to read. **Both it and `applyBinding()` bind through `serveWhenFree()`, which waits out an `EADDRINUSE` for a bounded few seconds** and says on screen that it is waiting. A port is not free the instant its holder stops, and the two cases that matter are exactly this: a process that crashed a moment ago and relaunched itself (Bun's own `--watch` does that after a panic, and the relaunch races the corpse), and this process's own socket, which `stop(true)` can still be tearing down when the rebind arrives. Without the wait a crash costs a restart by hand; with it, a port genuinely held by something else still ends at the same sentence a few seconds later, so nothing is hidden. It hands that to `fatal()`, **the single exit every boot failure takes** (the pre-upgrade backup snapshot and a failed rebind included), which prints and then **holds the console while `IS_COMPILED` and stdin is a TTY**: a portable build's window belongs to the process and closes with it, so a reason printed on the way out is a reason nobody sees. Piped and terminal-less runs fail that test and exit on their own, which is what keeps a scripted or service start from waiting on a prompt nobody can answer. Anything new that gives up at boot belongs behind `fatal()` for both halves of that.

**Request gates, in order** (the `fetch` handler in `index.ts`): (1) effective client IP = socket address, except X-Forwarded-For is trusted **from loopback only** (the Vite dev proxy case, see `vite.config.ts`); (2) IP allowlist ([`access.ts`](../server/access.ts)): loopback always passes, file-backed list + env seeds, toggleable off via [`security.ts`](../server/security.ts); denied attempts are remembered in-memory (capped, newest-first) and surfaced by `/api/access` as a one-click-allow waiting list, with the 403 page auto-retrying every 5s so an allowed device falls straight through (in dev the Vite gate blocks LAN devices before they reach this process and reports them via the loopback-only `/api/access/record-denied`); the same snapshot carries `online`, the IPs currently holding a live WebSocket (from `SocketData.ip`, stamped at upgrade), which the settings UI renders as green presence dots, and **`yourIpAllowed`**, which is `isAllowed(clientIp)` rather than `allowed.includes(yourIp)` because that list holds the file's entries alone and both loopback and the env seeds pass a gate they never appear in. Settings asks before switching the allowlist **on** from a device that answers `false`, and the reason it has to is that the combination is a one-way door: the switch drops every connection, this device's next request lands on the waiting page, and clearing it needs a device that is already approved. The host machine is always one, so this only ever fires over the network, and a headless host has no such device at all. **The confirm allows this device first and switches the gate on second**. Reversed, the allow is refused between the two calls and the second never lands. That dialog is deliberately *not* marked `destructive`: the rung that would let a reader skip it is the one thing that would put the lockout back (architecture/ui-shell-settings.md). **The device list is the same on every screen by construction**: the machine ChungusHub runs on takes a pinned first row, allowed by being that machine rather than by sitting in the file and filtered out of the rows under it so adding `127.0.0.1` by hand cannot show one machine twice, then the file's entries in the server's sort order, with only the "This device" marker moving from screen to screen. Every one of those entries can be removed, the reader's own included, and that one alone asks first, on the same terms and for the same reason; (3) password gate: argon2id hash + session tokens in `security.json`, sliding 1-hour idle window (mirrored in `vite.config.ts`'s dev gate, keep in sync), loopback exempt, `/api/auth/login` rate-limited 5-fails-30s per IP; the lock is a separate `passwordEnabled` flag that keeps the hash while switched off, so it re-enables without retyping a password. Tightening either of those two calls `kickAllSockets()` so open apps must re-pass the gates on reconnect. Recovery from lockout = delete `security.json` (which also closes the port back down to loopback, since off is the default it restores). **The file is written out on first boot when it is absent**, which is what makes the switches reachable on a machine with nothing to browse from: the settings page needs a browser on the host, the file needs only a text editor. Written *only* when missing, so an upgrade or a restart never overwrites settings already there, and deleting it still restores the defaults next boot. It is then **watched and applied while the server runs**, as is `allowlist.json`, both through [`watch-file.ts`](../server/watch-file.ts): the data *directory* is watched rather than the file, since every write here replaces it by rename and a watch bound to the file it opened with goes deaf; edits settle for 150ms; and the callback is told only that a write happened, so each side re-reads and compares before believing it, or a server that rewrites its own file on a timer would read itself as an edit. `allowlist.json` needs nothing beyond swapping the set in place, because every gate reads it per request: an address that leaves the file fails that device's next request, which is what removing it with the button does too. `security.json` adopts only the four switches, never `sessions`, which stay this process's own and are what keeps its once-a-minute idle-window writes from reading as somebody's edit; and a change routes to `rebindNetwork()` or `kickAllSockets()` exactly as the matching switch in Settings does. A file that will not parse **while running** is reported and dropped instead of fatal (the state in memory is good, and dying over a half-saved edit would take every connected device with it), while booting on a broken one still throws, which is where refusing matters. Settings → Security re-reads the switches on its 5s poll, so its toggles cannot sit showing positions the server has already moved past. `access.ts` and `security.ts` both **throw on an unusable state file** rather than falling back to defaults (fallback would either lock everyone out and then persist the empty list over the real one, or silently disable a password). That covers the file's SHAPE, not just its syntax, and the shape half is the one that bites: a `passwordHash` holding a number parses perfectly and reads as "no password", so every field is type-checked and anything unexpected throws naming the field. Both are also **written out on first boot when absent** (`[]` for the device list), so the pair of files is always there to be edited rather than appearing only after the first click in an app nobody can open. Both also **write through a temp file and rename**, since a torn write is refused on the next boot and the only cure for that is deleting the file, which deletes the password or the device list with it; `security.json` is rewritten about once a minute per active device to slide its idle window, so that window is not small, and the rename is also what keeps `vite.config.ts`'s per-request reads from ever seeing half a file. Follow all three for any new state file. Every HTML response also carries the CSP from `htmlHeaders()` (`connect`/`img`/`font`/`media` pinned to this origin, plus `ws://`/`wss://` to the request's own host for browsers that don't match a same-origin socket against `'self'`), so a page that starts pulling an external asset breaks visibly instead of leaking traffic off-box.

**SQLite** ([`db.ts`](../server/db.ts)): `bun:sqlite`, WAL, foreign keys ON. The handle opens lazily on the first db call, resolving `CHUNGUS_DATA_DIR` at that moment via `config.resolveDbPath()`, never at import time, so no test file's import order can silently point db writes at the real user-data (the memory integration test relies on this to bind its throwaway dir); `index.ts` calls `serverDb.open()` at boot so a broken database or migration still kills the server at startup. Schema is versioned migrations in the `MIGRATIONS` array, tracked in `_migrations`, each applied exactly once in a transaction: one baseline holding the whole schema, and every later change appended after it. Never `IF NOT EXISTS` guesswork, and **never edit a migration that has already been applied anywhere**, the baseline included: a database carrying it never runs it again, so the edit reaches new installs alone and the two schemas drift apart for good. Append a new version instead. **A migration is structure unless it is named in `DATA_MIGRATIONS`** ([`schema-upgrade.test.ts`](../server/schema-upgrade.test.ts), architecture/testing.md), which holds the ones that deliberately rewrite rows and forces each to earn a case proving what it touches and what it leaves alone. There is one: `44: backfill_chat_default_version`, which copies a versioned character's `activeVersionId` into the `defaultVersionId` that decides what new chats with it are born pinned to, for entries written before that field existed. It never overwrites a default already there, skips an unversioned character and one whose active pointer names a version that is gone, and is idempotent by that same WHERE, so a second run changes nothing. **Its JSON reads are wrapped in `CASE WHEN json_valid(...)`, and that is load-bearing**: `json_extract` raises on malformed JSON and the order `AND` terms are evaluated in belongs to the query planner, so a bare `json_valid()` term standing beside them is a boot that dies on somebody's torn row instead of leaving it alone for the library read to fail loud on. Tables: `chats` (`seeded_greetings` is the greeting texts the character card handed this chat when it was created, as a JSON array. A chat still holding exactly these and nothing else is a mirror of the card, so a card edit reaches it (`refreshSeededGreetings`, architecture/chat-sessions.md); NULL means no claim was ever made (imported chats and everything older than the column), and those never follow. Written by every seeding path through `setChatSeededGreetings` and read by the refresh alone: `mapChat` deliberately does NOT carry it and no client type mentions it, so the parse can never fail a chat read. `is_favorite` is the chats panel's star, same shape and meaning as `character_library.is_favorite`; `updateChatFavorite` deliberately leaves `updated_at` alone so starring can't reshuffle an activity-sorted list. `feature_state` is per-chat feature state as an **opaque JSON string** the server never parses (the spent-one-shot reuse history, the Impersonate perspective, the chat's own scene, and the connection, persona and preset it claims): `insertChat`, `mapChat`, `updateChat` and `duplicateChat` all pass it through verbatim, which is what lets the client add a key to it with no schema change and no migration. The insert half is load-bearing on its own: a chat can be BORN with a claim (a persona stamped from a real choice, architecture/ui-shell-settings.md), and an insert that dropped the column would lose it silently, since the row still lands and the chat still opens, so a corrupt blob can't fail a chat read (`getAllChats` maps every row in one query), and the client's `normalizeChatFeatureState` in `src/lib/types/chat.ts` is the only reader, degrading corruption to defaults; same contract as the `settings` table. Steering does not live here: the assistant's steering tool writes `steering_notes` rows, and no server path authors this blob), `messages` (a tree via `parent_id` + `sibling_index`; `ON DELETE CASCADE` from chats, children's `parent_id` → `SET NULL` if a parent row is deleted directly. **A chat's three tree pointers may never name a deleted row**, and no FK enforces that (`root_message_id` / `active_leaf_id` / `canon_leaf_id` are plain columns), so every delete here (`deleteMessageOnly`, `deleteMessageAndDescendants`, `deleteDescendants`) repairs them via `repairChatPointers` inside its own transaction: the leaf and the canon marker retreat to the nearest surviving ancestor, and the root recomputes from the surviving parentless rows. It belongs to the db and not to a caller because the transcript is drawn by walking root→`active_leaf_id` and that walk stops dead at a missing id. A chat left pointing at a deleted turn renders EMPTY with every one of its messages still in the table, and the caller that forgets is the one with no UI behind it (the assistant's `delete_entity`). It is the floor, not the policy: a caller with a better answer, like the transcript re-homing the view to a same-role sibling for continuity, simply sets the leaf again afterwards. A chat that still holds turns always names one; only an emptied chat gets a null. Covered by `server/chatList.test.ts`. **A turn carries no character-version stamp of its own**: a chat plays against exactly one variant, the one its composer chip pins on the chat row, so a per-turn stamp would describe a distinction that does not exist, see architecture/library.md. `minor_edited_at` is the second of two edit stamps: `edited_at` is the systemic staleness signal chat memory compares its summaries against, so a save the user marks as minor (a typo, punctuation) advances THIS column instead and the summary covering that turn survives, while the transcript still marks the turn as edited from either stamp. The mode is the caller's assertion and is never inferred, since no diff of two strings can tell a typo from a retcon (architecture/memory.md). `sprite_label` is the label the Sprites engine read an assistant turn as (architecture/engines.md), NULL for every turn nobody read: user/system rows, and replies written with the engine off or against a character with no sprites. It holds the **label** and never an image path, so a re-pointed or deleted sprite leaves the reading intact and a label with no sprite behind it is inert rather than broken. Written only by `updateMessageSpriteLabel`, which touches nothing else: a reading is not an edit, so `edited_at` stays put and chat memory has no summary to invalidate, the same contract `updateMessageBranchLabel` has. **Nothing here ever clears it**: a rewritten turn's reading describes text that is gone, but re-reading costs a call, so whether that happens is a user setting and the decision belongs to the client call sites that know about it, the same division chat memory's summary invalidation already uses (architecture/engines.md). `updateMessageContent`, `applyMessageContinuation` and `refreshSeededGreetings` all leave the column alone; pinned by [`server/messageSpriteLabel.test.ts`](../server/messageSpriteLabel.test.ts), which also covers a duplicated chat carrying its readings. `generation_ms` is the wall-clock duration of the live generation that produced an assistant turn, NULL for everything else, written by the generate paths alone: `commitGeneratedTurn` at birth for a reply or an opening scene, accumulated by `applyMessageContinuation` when a continue extends the turn. That method also rewrites content/thinking/token stats while deliberately leaving `edited_at` alone, see architecture/chat-sessions.md. `first_token_ms` and `reasoning_ms` sit beside it: the wait before the model said anything (request start → first streamed token of either kind) and how long it spent reasoning. Both NULL wherever nobody measured them, which includes every non-streamed call, since no token arrives to be the first one. **`first_token_ms` is deliberately absent from `applyMessageContinuation`'s patch**, so no continuation can touch it: it records WHEN the turn started speaking, which happened once, on the run that created it, while the other two record HOW MUCH the turn cost and therefore accumulate. Fold it in with them and every continued turn reports a wait that never happened. All three are measured by whoever writes the row: `handleLlm` for a turn this server commits, since it is the one side present for every frame of a generation that outlived its page, and [`transport.ts`](../src/lib/services/transport.ts) for the turns the client still writes itself (architecture/llm-providers.md), and an imported turn carries the exporter's own figures instead (architecture/sillytavern-interchange.md). Pinned by [`server/messageTimings.test.ts`](../server/messageTimings.test.ts), which also covers a duplicated chat carrying them. `lore_json` is the lorebook scan that produced an assistant turn (which entries reached the prompt, which keys pulled them in and from which turn, and why one that could have fired did not). JSON the server carries and never interprets, NULL wherever no scan ran: user/system rows, seeded greetings, imported chats, everything older than the column. It is **parsed defensively** (`parseJsonColumn`, which answers null rather than throwing) because this is a debug record and a corrupt cell must never cost the reader the transcript it is attached to, the same reasoning that keeps `chats.feature_state` an opaque string. It lives on the TURN and not in a per-chat counter set because the conversation is a tree: a swipe is its own generation with its own probability rolls, and a record hanging anywhere else could only ever describe one of them. `applyMessageContinuation` deliberately leaves it alone, like `first_token_ms`: it records the scan that opened the turn. Pinned by [`server/messageLorebook.test.ts`](../server/messageLorebook.test.ts), including the corrupt cell and the duplicated chat), `settings` (key/value strings, shared by client stores AND read directly by the server, e.g. the assistant's `assistantCapabilities` set), `connection_credentials` (per-connection API key + base URL, keyed by the client-generated connection id. `getConnectionCredentials`/`setConnectionCredentials`/`deleteConnectionCredentials`/`copyConnectionCredentials` bridge it; copy duplicates a row under a new id entirely db-side, so duplicating a connection carries its key without it riding the wire; and the registry reads it by id per request), `character_library` (+ `character_versions`), `lorebooks`, `steering_notes` (the Steering engine's scoped guidance notes, architecture/engines.md. `scope`/`scope_id` are real **columns** rather than payload keys so a chat delete can reap its own notes with one statement and a scope lookup is an index hit; title/text/enabled/mode/depth/role ride `data_json` through the same explicit-whitelist writer the lorebooks use. **No FK on `scope_id`**: depending on the scope it names a chat, a library entry or a character version, so no single table can own it. A dangling id is inert by design, never an error. Two chat operations reach in here because they cannot be forgotten anywhere else: `deleteChat` deletes the chat's own notes (they can't cascade) and `duplicateChat` re-mints them under fresh ids bound to the copy, both riding their existing `chats` broadcast, so another device keeps stale note rows cached until its next `steering` refresh, which is harmless, since a note whose chat is gone never resolves), `assistant_sessions` (`chat_id` is the roleplay chat the session most recently worked against, stamped by the assistant loop at commit time; display-only, NULL when no chat was open; `settings_json` is the Assistant settings the session is frozen on, written by its FIRST turn and never by the insert, so a session that has not run is simply NULL, architecture/chungus-assistant.md)/`assistant_messages` (`status` is `running` / `done` / `interrupted`, defaulting to `done`. The assistant loop owns one row per turn from its first moment: it claims the row as `running`, rewrites it at every step boundary, and finalizes it as `done`. Boot flips anything left `running` to `interrupted`, because a turn's tool effects are durable the instant they run while its transcript would otherwise only appear at commit. A process that died mid-turn left edited messages and new characters with nothing naming them. `updateAssistantTurn` and `markInterruptedAssistantTurns` are deliberately NOT bridged: the loop and boot are the only writers. `attachments_json` is the workspace attachments that actually rode a USER turn, each with the mode the loop's note builder resolved it to (`SentAttachment`, shared/assistant-attachments.ts); NULL = nothing rode. Written only by `setAssistantMessageAttachments`, guarded by session id + user role so a bad id cannot scribble on another session's transcript, and NOT bridged for the same single-writer reason: the truth of what was sent belongs to the side that sent it. In `getAssistantMessages`' corrupt-row fallback it gets its own guarded parse beside `images_json`, so a corrupt cell elsewhere in the row does not silently strip the chips. **`insertAssistantMessage` stamps `created_at` itself and returns it (a caller may not supply one)**, and `getAssistantMessages` reads `ORDER BY created_at ASC, rowid ASC`: the transcript's order is the order its rows were appended, and its two writers sit on different clocks (a browser inserts the user's message, the loop inserts the turn answering it milliseconds later). Let each stamp its own row and any drift between those clocks puts the reply above the message it answers, permanently), `assistant_files` (the read-only reference files attached to a tab. The row is the file's OWNER: it is created by the upload, so one staged in a composer and never sent has `message_id` NULL, which is exactly the set the composer's remove button and the boot sweep act on. Both foreign keys cascade (session and user message), so no row can outlive what it belongs to, and `deleteAssistantSession` collects the paths before the cascade so the bytes go with it. `text_path` is the NORMALIZED text and the only thing stored: the upload itself is still on the user's disk, and it is that text a line number addresses, which is why normalization happens once at ingest and never per read. It is also the one column that never leaves the server, see the assistant-files paragraph under File-backed storage), `memory_state`/`memory_episodes` (episodes are the whole store: there is no fact tier and no stored cursor. The archive boundary is DERIVED from the episodes' own `source_message_ids` against whatever path is active, which is what makes memory branch-aware, and nothing may reintroduce a stored one. **Nor may an episode record the ids of the episodes it replaces**: the same transaction deletes them, so such a column can only ever hold dangling references, and `copyChatMemory`'s fail-loud remap throws on every duplicate that hits one. Every write to `memory_episodes` is guarded by `memAssertNoOverlap` (no two episodes of a chat may cover the same message), which is what makes a derived boundary well-defined. `memSetState` **merges** `config_json` rather than replacing it: the client sends only the field it changed, so two devices editing different memory sliders don't write each other's change away. See architecture/memory.md), `chat_drafts`, `input_history`, `import_sources` (one row per source file an import has brought over, keyed `sillytavern:<path inside the picked folder>`. It is what keeps a second run of the same folder from duplicating the first, and therefore also what lets a **stopped** import be continued by simply running the folder again, with no resume position stored anywhere: a position would not survive a reload, would not notice a row deleted since, and would say nothing about a folder that has grown. A path and never a hash of the bytes, so a card edited on the SillyTavern side is that character arriving twice rather than a new one. `entity_id` is populated for the two kinds that become a **library entry**, character cards and personas, and it does two jobs. A later run skips a card but still has to bind that card's chats and sprites, which name it by filename, and without the id it would fall back to matching on display name, the exact collision filename matching exists to avoid. And a claim naming an entry the library no longer holds **stops counting**, so a character or persona the reader deleted by hand is offered again instead of being skipped under a card claiming they still have it (`importRun.known`, architecture/sillytavern-interchange.md); the kinds that point back at nothing keep NULL, cannot be asked, and stay claimed. `recordImportedSources` takes a batch and is written every 20 files rather than once at the end, so a run that is stopped keeps the claims it earned. **A second claim on the same file refreshes `entity_id` and leaves `created_at` alone** (upsert, not `INSERT OR IGNORE`), and that is what makes the rule above terminate: a file arrives twice only because the reader asked for it and it becomes a NEW entry each time, so a first id left standing would name a deleted row for good and hand the reader the same file on every run forever. A claim carrying no id cannot blank one already there. Pinned by [`server/importSources.test.ts`](../server/importSources.test.ts); it rides the `library` scope because an import writes library entries around it, not because another device draws anything from it. See architecture/sillytavern-interchange.md), `prompt_log` (the debug panel's durable log: one opaque JSON row per captured LLM request, written/read only by `server/promptLog.ts` through server-internal db methods that are deliberately NOT bridged, capped at 500 with the oldest pruned on insert (`server/promptLog.test.ts` covers the round-trip and that prune); see architecture/tokenizer-debug.md), `message_tombstones` (the delete half of the message delta protocol below: chat_id + message_id + the rev the delete advanced to; never pruned, since a row is two ids and an integer, and the chat's own delete cascades them). Rows are snake_case; the `map*` methods convert to the camelCase domain objects the client expects. A new column needs its mapper updated too. Two whole-chat operations live here rather than in a client store because they must be atomic and must not ship message bodies over the bridge: the "CHAT LIST AGGREGATES" block (`getChatListStats`, `getChatContentGroups`, `searchChatMessages`, `getChatMemoryFootprint`; one pass each, everything the chats panel renders a row from), the "USER STATS" block (`getUserStats` alone, the whole-library aggregate behind the stats screen: one STREAMED pass over every message, folding the effort totals, the story totals, the activity buckets, the cast tallies, the shape counts and the measured spend at once, since a second pass would be a second read of every body. **Message reads are versioned, so a refresh costs what changed rather than the transcript.** `chats.messages_rev` counts the chat's message writes; every write to a `messages` row carries the value `bumpMessagesRev` (or `revForMessageWrite`, for writers holding only a row id) hands it, in the row's `rev` column, and every delete records the ids on `message_tombstones` at that rev, inside the same transaction. `getMessagesDelta(chatId, sinceRev)` answers the rows past `sinceRev` plus the tombstoned ids and the rev the answer stands at. A `sinceRev` of null (a fresh open) or one AHEAD of the counter (a database restored under a client that kept its cache) answers the whole transcript rather than guessing, and a missing chat answers null. **The invariant: no message write may skip the stamp.** A writer that forgets leaves every other device silently holding the old row until something else touches the chat, the same failure class as a mutation that forgets `broadcastSync`. One exemption, stated at the statement: `duplicateChat` copies rows at rev 0, because the copy is a fresh chat id no device holds a rev for, so its first open reads full like any other chat. [`server/messageRev.test.ts`](../server/messageRev.test.ts) pins each write door's delta AND scans this file for an unstamped statement. The client end is `chatStore.freshMessages`/`fetchMessages` (architecture/client-data-layer.md); `getMessagesByChat` remains for the readers that genuinely want a one-shot full read (the preview pane, the assistant, tests).

**The RPC bridge** is the single seam between client stores and SQL: `POST /api/rpc/db` with `{ method, args, clientId }` → `callDbMethod` dispatches onto the `ServerDatabase` instance, allowlisted by `ALLOWED_DB_METHODS` (= `READ_METHODS` + keys of `MUTATION_SCOPES`). **Adding a db method is a three-place change**: the method on `ServerDatabase`, an entry in `MUTATION_SCOPES` (mutations: the value is the sync scope broadcast to other devices) or `READ_METHODS` (reads), and the client-side proxy in [`src/lib/services/database.ts`](../src/lib/services/database.ts). Forgetting the allowlist entry = "Unknown db method" at runtime; forgetting the scope = other devices silently go stale. `getAssistantContext`/`setAssistantContext` are deliberately NOT bridged: only the server-side assistant loop uses them.

**A write whose size the user's data decides belongs on this side of the bridge, as one method.** A round trip is also an autocommit and a sync broadcast, so a client loop over a per-row method turns one act into thousands of each, and it can only ever be atomic per row: stopped partway it leaves a state nothing later cleans up. `duplicateChat` and `importChat` are both that shape and both wrap their whole write in `inTransaction`, which nests via savepoints so a callee opening its own transaction stays safe inside. `importChat(chat, messages)` lands an imported story whole: the chat row first with its pointers nulled, then every message parent-first, then `updateChat` claiming `root_message_id` / `active_leaf_id`, because those two are foreign keys into `messages` and cannot be written before the rows exist. That ordering is exactly why the atomicity matters rather than being a nicety: half an import is a chat holding thousands of rows and pointing at none of them, which lists with a message count and opens empty. It carries the `chats` scope for the same reason `duplicateChat` does (architecture/chat-sessions.md). Pinned by [`server/importChat.test.ts`](../server/importChat.test.ts).

**A story turn is written on this side too, and for a different reason: by the time it exists, the page that asked for it may not.** `commitGeneratedTurn` lands the two generations that CREATE a turn (a reply, an opening scene): the row, the chat's pointers and the one-shot steering notes that rode it, in one transaction. It is called by `commitGeneration` in `index.ts` when a generation carrying a `commit` placement ends, and it is deliberately NOT bridged, the same single-writer rule the assistant's own methods follow: two writers on one turn is a chat holding the same reply twice. Every other call keeps its result client-side, and the line is what the loss costs rather than what is convenient. Chat memory refires on the next turn, a sprite is re-read, a spellcheck is a button press, and a continue extends a turn that is already safe on disk and re-continues with one click; a lost reply is a story the reader cannot get back. Three rules live in the method, and each covers something the client could not previously reach, because its composer was locked for the length of a generation. A **deleted chat** answers null: there is nothing to land and nothing that went wrong. A **deleted parent** throws, since the FK would refuse the insert anyway and a turn with nowhere to hang is a real failure. And **the leaf moves only when it still names what the request left it on**, because a reader who reloaded and walked to another branch must not be yanked back to a reply on the branch they left; the row still arrives as a sibling they can swipe to. `created_at` is stamped here rather than taken from the caller, for the same reason `insertAssistantMessage` stamps its own: the user's turn was written by a browser and this one by the server, and two clocks that drift put a reply ahead of the message it answers. `index.ts` broadcasts `messages` after it lands (plus `steering` when a note was spent) with **no origin**, since the page that started the turn may be gone and the one still here needs the hint as much as the others, and it does so **before** the `llm-done` frame so a page told the turn is done reads committed state. There is also **one committing generation per chat at a time**, refused in `handleLlm`: a reader whose tab was discarded can reopen a story that looks idle because the reply has not landed yet, and the composer's own lock belongs to a page that no longer exists. **The known gap is that the refusal is all such a reader gets**: a freshly loaded page has no request id to claim with, so nothing tells it a turn is under way and its composer reads as free until it is answered. Closing that needs a chat-keyed adopt query, the shape `assistantStatus` already has. It is narrow rather than harmless: a generation is seconds to a minute and a tab is discarded after minutes of being away, so by the time the reader is back the reply has almost always landed and is simply there. Pinned by [`server/commitGeneratedTurn.test.ts`](../server/commitGeneratedTurn.test.ts) and [`server/generationSurvival.test.ts`](../server/generationSurvival.test.ts).

**Cross-device sync** is hint-based, not data-push: after a bridged mutation the server broadcasts `{ t: 'sync', scope }` to every socket **except the originating clientId** (which identifies a page, not a device: two tabs on one machine must each hear the other); clients re-fetch whatever that scope covers (see [`src/lib/services/sync.ts`](../src/lib/services/sync.ts)). Scopes in use: `chats`, `messages`, `settings`, `drafts`, `inputHistory`, `library`, `lorebooks`, `steering`, `assistant`, `memory`, `presets`. One method carries one scope, so a method that writes across tables picks the one another device has to act on: `duplicateChat` touches chats, messages and (on request) memory but broadcasts `chats`, because that is what reloads the chat list: the copy is never any device's open chat, so its messages and memory load on first open like any other chat's. **Two library methods carry a second scope**, and both are the exception that proves the rule: neither is expressible in a table that maps one method to one scope, because whether the second write happened is only known once the method has run, so each **returns** it. `updateLibraryEntry` returns the ids of the chats whose seeded greetings the save moved (`refreshSeededGreetings`, see architecture/chat-sessions.md), and when that list is non-empty the bridge follows the `library` hint with a `messages` one addressed to **every** client, the writer included: the device editing the card is the likeliest to have one of those chats open beside the library, and its own `library` hint deliberately skips it. `deleteLibraryEntry` returns the persona that took over when the deleted one was active (the persona floor, architecture/library.md), and a non-null answer follows the `library` hint with a `settings` one, to every client for the same reason: the writer's own copy of who "you" are is the one that just went stale. The in-process assistant reaches both methods without the bridge, so its two greeting doors and its `delete_entity` repeat the second hint themselves (architecture/chungus-assistant.md). File-side endpoints that mutate shared state broadcast too (`/api/images` → `library`, preset/draft PUT/DELETE/default restore → `presets`); assistant-loop mutations broadcast with `originClientId = null` so **every** device including the originator refreshes.

**WebSocket protocol** (all JSON, `t` field discriminates): client→server `llm` (completion request; `id` correlates), `llm-cancel`, `llm-attach` (claim a generation started before this socket, carrying how much of each stream the page already applied), `llm-release` (the answer has been taken; stop holding it), `llm-status` (which of these `chatIds` have a reply being written, and for how long), `assistant`, `assistant-cancel` (carries `assistantSessionId`, with or without an `id`), `assistant-approve` (answers one approval card with `assistantSessionId` + `askId` + the approved call indexes), `assistant-answer` (answers one question card with `assistantSessionId` + `askId` + one answer per question, in the order they were asked), `assistant-status` (which of these `sessionIds` have a turn running), `debug` (on/off, registers this socket for prompt-log capture), `ping`. Server→client: `llm-token` / `llm-thinking` / `llm-done` / `llm-error` / `llm-attached` / `llm-attach-miss` / `llm-status-result`, assistant events (see architecture/chungus-assistant.md), including `assistant-approval` / `assistant-question` / `assistant-ask-settled`, plus `assistant-status-result`, `sync`, `prompt-log` / `prompt-log-clear`, `pong`. The approval, question and settled events are the assistant events that are not deltas: either of the first two says the turn has STOPPED, and the card stands until the settled one says someone answered it. Frames that parse to non-objects (`null`, numbers) are dropped before dispatch, and a duplicate in-flight `id` is refused (it would orphan an AbortController), and that check is **global** because the generation map is: two sockets sharing an id collide exactly as one socket reusing it does. **A generation outlives the socket that asked for it.** `generations` is one map keyed by request id (`LiveGeneration`: the controller, whoever is listening right now, everything that has streamed, and the answer once it lands), and `close(ws)` **detaches** rather than aborts. The failure that rule exists to prevent is the ordinary mobile one: a phone that backgrounds its browser has the socket torn down by the OS mid-reply, and a generation bound to that socket died with it, taking the call and every token the reader had already watched arrive, because the only copy of a streamed reply lives in the page that asked for it until the call resolves (architecture/chat-sessions.md). So the work continues with nobody listening, and a page that comes back claims it with `llm-attach`, which is answered with the remainder of each stream alone (never a repaint from the start, which would duplicate what a page that never reloaded still has on screen) followed by the ending if the call has already finished. A claim on a generation this process has never had is answered `llm-attach-miss` rather than left hanging: the asking page has a composer locked on it. **A page that lost its record of a generation cannot use any of that**, since `llm-attach` needs the request id and the id lived in the page that is gone. `llm-status` answers by CHAT instead (`handleLlmStatus`: which of these chats hold an unsettled generation carrying a commit placement, and how long each has run), which is how a reload finds the reply being written for the chat it opens and can Stop it by the id that comes back (architecture/chat-sessions.md). Without it that chat reads as idle, the send is refused by the single-flight rule below, and nothing on screen can end the reply that is refusing it. It reports no tokens and deliberately does not touch `gen.ws`: claiming the stream would point it at the asking socket and cut off whichever page is still watching. Only calls that write a turn are reported, since only those hold that rule. **A settled generation is held until it is claimed**, for `CLAIM_WINDOW_MS` (10 minutes) or until an `llm-release` says a page has taken it, because a socket looking open at the moment the last frame was written proves nothing about a frozen tab having read it; past the window the answer is dropped with a line in the log rather than in silence. A restore is the one place they are killed outright (`quiesceForRestore`): the database those answers are for is about to be replaced. Pinned by [`server/generationSurvival.test.ts`](../server/generationSurvival.test.ts). Assistant turns survive their socket for the same family of reasons and go one step further: they live in the session-keyed `assistantTurns` map (which doubles as the per-tab lock, holds the turn's live snapshot, and holds the one card it is blocked on: calls to approve, or questions to answer), **survive a socket close**, keep working headless, and commit their result server-side. `assistant-cancel` matches by request id or session id, so a Stop lands even across a reconnect or from another device, and settles a waiting card as a refusal of everything on it. Every event of a turn is therefore addressed to the **session**, carries `assistantSessionId`, and goes to every open socket: a page that reloaded mid-turn never issued the request at all, and the socket that did may be gone. The two refusals that never become a turn (a duplicate request id, a tab already running one) deliberately answer the asking socket alone and carry no session id, so they cannot settle a turn that is still going. LLM prompt logging ([`promptLog.ts`](../server/promptLog.ts)) is server-side and durable (SQLite `prompt_log`, 500-entry cap), captured only while at least one device has the debug panel enabled (`debugSockets`), backfilled over `GET /api/debug/prompt-log`.

**File-backed storage** ([`files.ts`](../server/files.ts)) holds what isn't relational: images under `user-data/images/<category>/` (categories fixed: `characters`, `personas`, `backgrounds`, `chat`, `presets`; each with a `thumbnails/` subdir. **Every thumbnail is webp and its path is a pure derivation from its original's** (`thumbnailFor`, the only spelling of that convention server-side: the backup inventory and the assistant smoke script call it rather than repeating it, and the client's copy is held to it by [`contracts.test.ts`](../src/lib/contracts.test.ts), coupling 7 below). A fixed extension is what keeps reading one a derivation instead of a lookup, and webp is the extension because **a thumbnail must not change what the picture IS**: jpeg has no alpha, so a cut-out came back with its removed background filled in black, which is the one thing the stored-format gate below refuses to let happen to a stored file. The reason the two formats differ is the audience: stored art is what a model receives, a thumbnail is only ever drawn by this app's own tab. **A thumbnail request that names no file is answered with the original beside it** (`resolveImageFile`, which every `/files/images/…` request goes through): a thumbnail is an optimization rather than a distinct asset, and three ordinary states reach that case (an upload whose thumbnail failed to encode, a picture stored before thumbnails were webp, a category that never wrote one). Each of them is otherwise a broken-image icon drawn over a picture that is safe on disk. That rule is also what lets a seeded preset cover ship as one file (`seedDefaultCover`). **Every path in this module is spelled with `/` on every platform**, and `absFromRelative` throws on a backslash rather than joining it, because the derivations above look for `/thumbnails/` *inside* a path: a host-shaped one leaves each of them unmatched on Windows alone, which turns the fallback into a 404 and every picture in the app into broken art. `serveImage` is the only caller that can produce one (`node:path`'s `normalize` answers in the host's separator) and converts back after the traversal segments are stripped. **Re-encoding a thumbnail is a client job**, since the browser holds the app's only image encoder: `GET /api/images` lists every stored original and `POST /api/images/thumbnail` stores one (`saveThumbnail`, which drops every other extension under that name first, so two generations cannot sit beside each other and ride every backup together). The pair exists for the rebuild control in Settings › Advanced, which walks the list and re-encodes each picture from this tab (architecture/ui-shell-settings.md). Neither broadcasts a sync hint: no row changes, and the file lands at the path every device already asks for; DB stores the relative `images/<category>/<file>` path and serving, copy and delete derive the category from it, with one exception: a copy may **name** a target category, which is how a picture changes owner across folders (a chat attachment adopted as character art, a persona made from a character, see architecture/library.md); `Bun.serve`'s `maxRequestBodySize` is raised to 64 MB for those uploads; **one gate decides what a model-facing image may be**, and it lives in [`imageService.ts`](../src/lib/services/imageService.ts). The three categories whose files reach a model (`characters`, `personas`, `chat`) all pass through `toStoredFormat`, so chat and assistant attachments, portraits and gallery art are normalized by the same rule and no upload surface carries numbers of its own. `backgrounds` and `presets` are outside it and keep their original bytes (nothing reads those but the app itself, and a 4K wallpaper as png costs megabytes for nothing). Five parts, each with its own failure to prevent. **Stored art is png**: a browser decodes formats the consumers downstream cannot (local llama.cpp servers refuse webp outright), so one format settled at the door beats every consumer guessing. **Resolution is capped at a 2048px long edge**: providers scale anything larger down on their side, so those pixels are uploaded, paid for and then discarded upstream. **A stored file must clear ~3.5 MB**, because it is base64'd into the request (a third larger again) and providers refuse one carrying an image past ~5 MB. Since png is lossless, a photograph misses that budget at any resolution a model can still read, so the encode **falls back to jpeg** rather than shrinking the picture until png fits. **A picture carrying transparency may not take that road**: jpeg has no alpha, so the fallback would not degrade a sprite's cutout, it would fill the removed background back in with black and hand back the very thing the user cut away. Those shrink toward the budget instead (75% a step, floor 256px) and throw if they still miss it, since losing pixels is recoverable and losing the cutout is not. This is the one place in this gate where a picture is shrunk until png fits, and the reason is that for these two the format IS the content. **`imageRejectionReason` is the one refusal**, exported so every upload surface asks it before starting a spinner and `toStoredFormat` asks it again at the door: a file that is not an image, or past the 25 MB source limit, is refused in one wording from one number, and a surface that forgets to ask still cannot get one through. Re-encoding is skipped only for a png already inside every budget: sending a palette png back through the canvas would re-emit it as 32-bit RGBA, several times its own size, for nothing), presets as JSON files under `presets/` (+ `presets/temp/` for unsaved drafts). The user's assistant skills live in the same data dir as `assistantSkills.json` (seeded from the bundled `defaults/skills/` on its first read), but are read and written by [`assistant/registry/skills.ts`](../server/assistant/registry/skills.ts), not by `files.ts`. Preset files are written through an **explicit field whitelist**, held in exactly one function: `presetFileShape` names `name`/`items`/`controls`/`sections`/`bundles`/`meta`/`regexRules`/`pruneEmptyBlocks`/`exampleSeparator`/`continuePrompt`, and `ensureDefaultPresets`/`readPresetDir`/`writePresetFile` all route through it while both preset PUT handlers in `index.ts` type their body as the exported `PresetFileData`. A new per-preset field added to the client but not there round-trips fine in the browser and is silently dropped the moment the server rewrites the file (see the coupling in architecture/prompt-pipeline.md). The shape is structural only: the server never interprets what a section or a carried regex rule means. Image ownership rules (copy-never-alias, chat-attachment refcount sweep scoped to `images/chat/`) are documented in architecture/chungus-assistant.md. `dropOrphanedChatImages` in `db.ts` is the enforcement point (LIKE needles are wildcard-escaped). Two loud-recovery behaviors live beside it: `sweepAbandonedChatImages` runs once at boot and reaps `images/chat/` files no row references (uploads whose send was abandoned; one-hour age guard, aborts entirely if any row fails to parse), and a corrupt `assistantSkills.json` is backed up to `<file>.corrupt-<ts>` before the bundled catalog is read instead of being silently emptied and re-persisted. Boot has two more sweeps beside those, in the db rather than the filesystem, both logged when they find anything: `markInterruptedAssistantTurns`, and `promptLog.settleInterrupted()`. A captured LLM request left `pending` by a dead process becomes an error naming the cause, so the debug panel can never show a request that never returned as one still in flight (architecture/tokenizer-debug.md). File-backed writes sit outside `MUTATION_SCOPES`, so each one broadcasts by hand and forgetting the call is invisible until a second device disagrees: presets → `presets`, image upload → `library`, skill saves → `assistant`. **The assistant-file endpoints deliberately broadcast nothing**, and that is a decision rather than an omission: a staged upload is local to the page that made it and carries nothing another device could draw, and once a file rides a turn the transcript announces it on the `assistant` scope the loop already fires.

**Assistant files** (`user-data/assistant-files/`) are the one file store with **no static route**, and the absence is the whole security posture. An attached file is arbitrary user text, so serving it under `/files/…` the way images are served would hand back an attached `.html` or `.svg` with a content type guessed from its name, executing it as a page **on the app's own origin**, the origin holding the session cookie, on an install reachable from other devices. Images escape that only because `saveImage` whitelists what can land in their folders, and nothing equivalent can exist here: the point of the feature is that any text is acceptable. So the bytes leave the server through JSON alone (`GET /api/assistant-files/text`, paged by line), which has no content type to get wrong. Two more rules ride with it. The stored path never leaves the server: `publicFile` strips it from every response, so a file is addressed by id on every surface and nothing downstream is ever tempted to name a location. And a row **owns** its bytes outright: `assistant_files` cascades from both its session and its user message, `deleteAssistantSession` collects the paths before the cascade takes the rows and unlinks them, and `sweepAbandonedAssistantFiles` reaps files no row references at boot (one-hour age guard, like the chat-image sweep). A file still staged in a composer is never swept: its row exists, and a half-typed message that survives a restart must not lose its attachment. Ingest refusals (over 10 MB, not decodable as UTF-8, a picture carrying no document) throw before anything is stored, so there is never a half-file to clean up (architecture/chungus-assistant.md).

**Type-checking.** `server/` is checked by its own [`tsconfig.server.json`](../tsconfig.server.json) (`strict`, Bun globals, server tests excluded), which `bun run check` runs after svelte-check. It has to be separate: the root config extends SvelteKit's generated one, whose `include` covers `src/` only, so anything outside `src/` is invisible to it. Fold this config away and every "mirrors the client type" comment in here goes back to being worth nothing. Two consequences worth knowing: the `Raw*` row shapes in [`assistant/rows.ts`](../server/assistant/rows.ts) are `type` aliases rather than interfaces (only an alias gets the implicit index signature that `serverDb`'s `Record<string, unknown>` row parameters need), and the reader type in [`llm/net.ts`](../server/llm/net.ts) is written structurally because the global `ReadableStreamDefaultReader` name resolves to Bun's declaration, not the one a fetch body hands back.

**Boot order** is not a list of chores, it is a sequence with two hard constraints, both from architecture/backups.md. A **job child** re-invokes this executable with `CHUNGUS_BACKUP_JOB` set and answers at the very top, before anything opens a database. Then `assertBackupDirUsable()`, then `resumeInterruptedRestore()` (a restore swaps the data folder HERE and only here, since this is the one moment nothing holds the database file), then `snapshotBeforeUpgrade()`, which must land before `serverDb.open()` because opening runs the very migrations it protects against. Only then `open()`, the sweeps, and the socket. **`runBootSweeps` in [`boot-sweeps.ts`](../server/boot-sweeps.ts)** is the repair set a freshly opened database needs (interrupted assistant turns, pending prompt-log rows, the two file reaps, `ensureDefaultPresets`); the same call covers the boot that follows a restore, whose database was written by a process that is long gone and carries exactly the marks a crash leaves. It ends with `ensureDefaultCharacters`, the one step there that is a seed rather than a repair and the one that must **not** repeat: it writes the example characters into the library once per id, ledgered in the `seededDefaultCharacters` setting, so a deleted one never comes back (architecture/build-packaging.md). Reaching it after a restore is correct and not an accident: the ledger is a row in the database that was restored, so a snapshot predating a shipped character is given it and a snapshot taken after its owner deleted it is not.

**Maintenance mode.** While a restore is claimed, the `fetch` handler turns everything away below the two security gates: 503 for `/api`, `/files` and `/ws`, `maintenancePage()` for a navigation. The 503 body carries the same headline and detail that page shows, flagged `maintenance`, because an app booting from a precached shell never sees the page and draws its own card from this instead (architecture/ui-shell-settings.md); a card naming the state without saying what to do would be worse than the outage it reports. Two reads stay open (`GET /api/config` and `GET /api/backups`, because the Backups page is the only surface left that can say what is happening), plus the one POST that cancels the claimed restore, because it is the mutation that ends the state. `/api/config` also carries `dataEpoch` (a settings-table row a restore rewrites, architecture/backups.md), which every client compares on reconnect and reloads on a change, and `dataAhead`, read once at boot and never changing while the process lives.

## Before touching this

- Read this file plus [architecture/chungus-assistant.md](chungus-assistant.md) if the change involves images, assistant sessions, or the settings table.
- Adding a directory under the data dir is a three-place change: `SNAPSHOT_ENTRIES`, the restore swap, and `scripts/package.ts` (architecture/backups.md coupling 1).
- `bun run check` covers **both** halves (svelte-check over `src/`, tsc over `server/` + `shared/`). A server-only change that passes svelte-check has not been checked.
- Never edit an applied migration; append a new `MIGRATIONS` entry. Ask the user before writing any migration that rewrites existing rows.
- New setting? Decide its side first: something the process needs before it can serve, or cannot fix from inside the app, goes in `chungushub.config.json` (and then in `CONFIG_DEFAULTS`, which is what carries it into files that already exist, the Settings file section of `docs/installation.mdx`, and the portable README if it is worth stating there). Everything else is an app setting on the settings spine.
- Anything new at boot? Its place in the order is a decision, not a detail. The claim on the data folder and the restore swap both run before any database is opened, and the only thing above the claim that touches the data dir is `ensureDirs()`, which has to be there because the claim needs the folder to exist.
- New endpoint? Decide which gate applies (it inherits IP + password automatically by living under `/api/`), and whether a mutation must `broadcastSync`, and with which scope.
- New db method? Three places (method + allowlist/scope + client proxy). New column? Migration + mapper + insert/update methods + client types.

## Hand-kept couplings

1. `MUTATION_SCOPES` / `READ_METHODS` (db.ts) ↔ the client proxy methods in `src/lib/services/database.ts`. Names must match exactly. Asserted by [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts).
2. Sync scope strings: **not hand-kept.** The vocabulary is `SyncScope` in [`shared/sync.ts`](../shared/sync.ts); `MUTATION_SCOPES`, `broadcastSync`, `AssistantContext.broadcast` and the assistant registry's `EntityDef.scope` are all typed against it, and the client's handler table is a `Record<SyncScope, …>`. A scope one side cannot handle does not compile. What the compiler can't see is a declared scope nothing ever broadcasts, dead weight in the client's table; `contracts.test.ts` asserts that half.
3. `SESSION_IDLE_MS` in security.ts ↔ the dev-proxy gate in `vite.config.ts` (same value, duplicated by design).
4. WS message shapes in index.ts ↔ the client transport in `src/lib/services/transport.ts` (`t` discriminators, `id` correlation). `contracts.test.ts` asserts every discriminator the client sends has a server handler.
5. `IMAGE_CATEGORIES` in config.ts ↔ client-side category strings passed to `/api/images` and `/api/images/copy` (imageService).
6. The `settings` table is read by BOTH client stores (via the bridge) and the server directly (assistant gates), so renaming a key is a two-sided change.
7. The thumbnail extension: `THUMBNAIL_EXTENSION` in `files.ts` ↔ the same constant in [`imageService.ts`](../src/lib/services/imageService.ts). The server writes the file, the client asks for it by a path it derives itself, and the client cannot import server code. Moved on one side alone it points every picture in the app at a file nobody wrote. Asserted by [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts), which also holds the client's encoded format to the extension it names.
