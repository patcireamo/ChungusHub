# Backups & restore: architecture & maintenance

A snapshot is a **complete copy of the data dir at one moment**, kept in a store beside it, and a restore puts one back. The whole subsystem lives under [`server/backup/`](../server/backup/) plus one settings page, and it exists so that every irreversible thing in this app has a way back: there is no undo channel anywhere (architecture/ui-shell-settings.md), and an upgrade that goes wrong takes the story with it.

**Where things are.** The store is `<parent of the data dir>/backups`, a **sibling** of the data dir and never inside it: a snapshot written into the folder it is snapshotting carries every snapshot before it, so the second is twice the size of the first and the tenth is unusable. `CHUNGUS_BACKUP_DIR` moves it, as does `backupDir` in the settings file, whose `../backups` default **resolves from the data dir** and not from the file's own folder, precisely so the sibling rule survives a data dir moved somewhere else (architecture/server-core.md). [`assertBackupDirUsable`](../server/backup/paths.ts) refuses to boot when either folder contains the other (the reverse puts live data where retention prunes). Both paths resolve the env **per call**, like `resolveDataDir`, so tests can redirect them after the modules are loaded. A backup path frozen at import cannot be pointed anywhere but the real one. From source the default store lands inside the repo, which is why `backups/` is in `.gitignore`. The store carries the two privacy markers, the same pair `ensureDirs()` puts in the data dir ([`privacy-notice.ts`](../server/privacy-notice.ts)): written by the first snapshot, and by `ensureBackupStoreMarkers()` at boot for a store that already exists, which never creates the folder itself so an install that never backs up still grows no empty store. A snapshot holds every secret the live folder does, and this is the folder people zip up and send when they mean "here is my backup". The markers sit at the store's root beside the snapshot folders, where `listSnapshots()` skips them for not being directories. Each snapshot is a real, browsable directory: `<timestamp>_<kind>/` holding `manifest.json`, `index.json`, and `data/` mirroring the data dir. Not an archive, deliberately: pulling one character's portrait out of a backup should not need the app, and a folder is the only shape that allows it.

**What a snapshot carries** is the explicit list in [`paths.ts`](../server/backup/paths.ts) `SNAPSHOT_ENTRIES` and not "everything in the folder": `chungushub.db`, `images/`, `assistant-files/`, `presets/` (unsaved drafts included), `assistantSkills.json`. It is named one by one so a new data directory is a visible edit in three places rather than a silent omission that still looks backed up (coupling 1). **`security.json` and `allowlist.json` are absent from both directions**: they are the door to the app rather than the content behind it, and a restore that quietly reinstated a months-old password, or reopened a port the reader had since closed, would be a security surprise arriving under the word "restore". The database's `-wal`/`-shm` are absent for a different reason: `VACUUM INTO` writes a self-contained file that already holds what the live WAL was carrying, so copying them would pair a stale journal with a database it does not describe.

## Taking one

Three properties hold [`snapshot.ts`](../server/backup/snapshot.ts) together.

**The database is copied with `VACUUM INTO`**, which is transactional over the live file and picks up uncheckpointed WAL frames, so nothing is stopped, locked or asked to wait. The source is opened **read-write**: a read-only handle cannot create the `-shm` a WAL database needs, and the pre-upgrade snapshot runs at boot where no other process is holding one.

**Unchanged files are hardlinked from the previous snapshot** instead of copied, which is what makes keeping a year of history affordable: the marginal cost of a snapshot is the database plus whatever art arrived since the last one. Deleting any snapshot folder stays safe, since the other links keep the bytes alive. **Unchanged means the SOURCE file's `(size, mtime)` matched what `index.json` recorded last time, never "a file exists at that path"**: `images/backgrounds/` keeps human filenames, so deleting `sunset.png` and uploading a different `sunset.png` reuses the path exactly, and a path-existence test would link month-old pixels under the new picture's name. That is a wrong backup that looks right. `index.json` is that record, stays on disk and never rides the API, because a large library puts tens of thousands of entries in it. Presets and the skills file are **always copied**: they mutate under fixed names by design. A filesystem that cannot link at all (exFAT, most network shares) falls back to copying for the whole job, and says so on the row through `manifest.linked` rather than silently costing ten times the disk. That verdict is only reachable **before the job has shared anything**: Windows answers `EPERM` both for a volume that cannot link and for one file a scanner happens to be holding, so a failure after nine thousand successes is about that file, and taking it for the filesystem turns the rest of the job into full copies under a sentence that is not true of the disk.

**A snapshot is built where it will live, carrying a `.building` marker file that is deleted last**, so a snapshot that is listed is a snapshot that is whole. Building aside and renaming the directory into place is the obvious design and **must not come back**: Windows refuses to rename a directory anything holds a handle on, and a folder that has just had thousands of files written into it is exactly what a virus scanner, a search indexer, a sync client or an editor's recursive watcher is holding one on. From source the store also sits inside the repo, where the dev server would be watching it. `vite.config.ts` ignores `user-data/` and `backups/` for that reason and because neither holds a module. Deleting one small file is the commit instead. It also means `manifest.json` and `index.json` are written straight out with no temp-and-rename of their own: a torn one is swept whole at the next boot, since the marker is still there. `patchManifest` (pinning) is the exception and does rename, because it edits a snapshot that is already committed and listed, where nothing would ever sweep a torn write. A job that throws deletes its own folder; one a process died in is `sweepAbandonedSnapshots()`'s at boot, keyed on the marker so a folder somebody put in the store by hand is left where they put it.

**A snapshot is stamped when the job starts**: one instant for both the folder name and the manifest's `createdAt`. The two agreeing is the small part. The load-bearing part is that the schedule compares that stamp against when the data last changed, so a message written during the minutes a large job takes is newer than the snapshot that does not hold it, and still earns a copy of its own. Stamped at the seal, that message reads as older than the snapshot missing it and is never backed up at all.

**Ordering, then reconcile.** Files are copied first and the database second, so anything uploaded in between exists in the database's world but not in the copy. The reconcile pass asks the snapshot what it claims to own and fetches whatever is missing, then a thumbnail beside each late original (a card whose art is there but whose thumbnail is not reads as data loss). What it claims is found by **matching the shape of a stored path** (`images/<category>/<file>`) over the JSON-bearing columns, not by walking five JSON schemas ([`inventory.ts`](../server/backup/inventory.ts)). Over-matching costs one copy of a file that already exists; under-matching costs the file, and a hand-kept list of blob shapes is exactly the thing nobody updates. Preset cover art is named inside preset **documents** rather than any table, so the same pattern runs over the copied preset files too. Anything still missing was already missing from the live install and lands in `manifest.warnings`, on the row. Copied `.json` files are parsed and re-copied once if they do not read back, because `writePresetFile` and the skills save are plain `writeFileSync` with no temp-and-rename: half a preset file makes the whole preset list fail to load after a restore.

**The job runs in a CHILD PROCESS**, and both halves of that are load-bearing. It is a separate process because `bun:sqlite` is synchronous: `VACUUM INTO` on a 300 MB database blocks the event loop for the better part of a second, and larger libraries for many seconds, so an inline scheduled backup would stall token streaming and flash the outage bar on every connected device. It is a re-invocation of **this executable** rather than a `Worker` because `bun build --compile` does not carry worker entry points into the binary: `new Worker(new URL('./x.ts', import.meta.url))` runs perfectly from source and dies with ModuleNotFound in every portable build, which is the only build users have. [`service.ts`](../server/backup/service.ts) spawns `process.execPath` (plus `argv[1]` from source) with `CHUNGUS_BACKUP_JOB` set; the branch at the top of the boot block in [`index.ts`](../server/index.ts) answers it and exits. **That branch sits above `serverDb.open()` and must stay there**: opening runs the migrations, which is the one thing the pre-upgrade snapshot exists to happen before. Reporting is newline-delimited JSON on stdout; anything that is not a line of that shape is ignored, so a stray `console.log` cannot corrupt the protocol.

Two things guard the parent against a child that never comes back, and both matter because **the lock is held for the life of the process**: a wedged job means no snapshot, no restore and no delete is accepted again until the app is restarted. **stderr is drained from the first moment, never after the exit**: a child that fills the stderr pipe blocks on the write, its stdout then never ends, and the two processes wait on each other forever. And **ten minutes of silence stops the child**: it reports every phase and every 250 files, so silence is not slowness, it is a file a scanner or a network share will not release. The folder it dies in keeps its `.building` marker and is swept at the next boot, exactly as one a power cut ended.

**Progress is polled, not pushed.** The page polls `/api/backups` while a job is live and stops when it is not; completion broadcasts once on the `backups` scope so a device that is not looking still sees the row when it opens the page. A backup happens a few times a day, and a socket message shape kept in step across the bridge for that is more machinery than the problem needs.

## When one is taken

Three triggers, plus the button. **Before a schema upgrade** is the valuable one and the only one whose timing carries weight: `snapshotBeforeUpgrade()` in `index.ts` compares `schemaVersionOnDisk()` (a throwaway read-only connection, so the live handle stays shut) against `LATEST_SCHEMA_VERSION` and runs before `serverDb.open()`. A failure there **stops the boot** rather than upgrading unprotected, because "the backup did not happen" is precisely the sentence nobody reads in a log; the way past it (`CHUNGUS_SKIP_UPGRADE_BACKUP=1`) is printed on screen, so a full disk is an inconvenience rather than a wall. It passes `{ prune: false }`, since pruning reads a setting and reading a setting would open the database. **On a schedule**, described in full below. **Before a restore**, always, so restoring the wrong snapshot is a recoverable mistake.

### The schedule

One timer re-deciding from the store each minute rather than re-arming itself, so a changed interval takes effect within the minute and a machine asleep for two days takes one snapshot on waking rather than forty. It stands down entirely while a restore is claimed (see maintenance mode below). Everything else is one rule, and [`schedule.ts`](../server/backup/schedule.ts) is that rule alone, pure and tested the way `retention.ts` is:

> Take a scheduled snapshot when nothing has been snapshotted in the last interval, and something has changed since whatever was.

**Both halves hang off the same anchor: the newest snapshot in the store, whatever kind it is.** A snapshot taken because the database was about to be upgraded, or because a person pressed the button, already holds everything up to the moment it started, so the schedule has nothing to add for a whole interval after it. Anchoring the clock half on the newest **scheduled** snapshot instead writes a second identical copy fifteen seconds after every boot that upgrades, and a minute after every manual one.

**"Something has changed" is a timestamp on disk, not a flag in memory.** `broadcastSync` calls `markChanged()` for every scope but `backups`, since a finished snapshot broadcasting its own row would mark the next one as owed and snapshot an untouched install forever. The four writes that reach the data dir without a broadcast (image copy and delete, assistant file store and delete) call it themselves. Every write into the data dir says so, whether or not another device needs to hear about it. The value lands in the settings table under `dataChangedAt`, and only the **first** change after each snapshot is written there, so it costs one row per snapshot cycle and is written the moment it becomes true rather than on a timer: an app closed straight after an edit still knows the edit happened. Held only in memory the answer reads as "yes" on every launch, and an install nobody has touched then gets a full copy of itself once an interval for as long as it is owned. Compared against the snapshot's own stamp it also needs no clearing, which is what makes a change that lands **while** a snapshot is being written still read as pending: the reason `createdAt` is stamped when a job starts (see above) rather than when it seals.

**A failed attempt backs off**, doubling from five minutes and never past the interval; a full disk does not clear inside a minute, and each attempt walks the whole library and writes a partial copy before giving up. **A snapshot dated in the future stops the schedule and says so** on the page through `lastError`: neither half of the rule has an answer while the clock disagrees with the store, and a schedule that quietly stops is the failure nobody notices.

**Retention** ([`retention.ts`](../server/backup/retention.ts)) splits on a single idea: a snapshot taken because something was about to happen, or because a person asked, is evidence and is not thinned on a timer; a scheduled snapshot is a position on a timeline, and a timeline needs recent detail far more than every point on it. So manual snapshots are kept forever, before-upgrade and before-restore ones are capped by count, and scheduled ones keep the recent window whole and then collapse to one a week and one a month for a year. **A pinned snapshot of any kind is never pruned**, which is the one control the reader has over the whole policy. Retention runs after a successful snapshot and once at boot, and deliberately **not** inside a restore, where it could delete the snapshot the marker points at.

**The thinning half stands down when the clock sits behind the store.** Every rule past the count caps reads an age, and an age is only as good as the clock that produced it: a machine with a dead battery, or a first boot before any time sync, reads every snapshot as more than a year old and empties the timeline in one pass at boot. That is data loss caused by a wrong date. The count-based caps need no clock and still run.

## Putting one back

**A restore happens at boot, never in a running server, and that is a hard constraint rather than a preference.** `bun:sqlite` does not release the database file once `db.transaction()` has been used on the handle: `close()` leaves a connection SQLite still owns, and on Windows that blocks deleting the file **and** renaming it (`close(true)` reports "database is locked" outright). Migrations run inside a transaction, so every live server has an unreleasable handle from its first boot. Anything shaped like "close the database, swap the files, reopen" cannot work here, and neither can a self-relaunch: a `Bun.spawn` child does not survive its parent exiting on Windows, so the process cannot hand over to a replacement either.

What that constraint buys is the property the operation most needs anyway. A restore is many destructive steps, and a **journal** makes every one of them resumable:

1. The reader confirms. `POST /api/backups/restore` validates, raises maintenance **inside the handler** so every request arriving after it is already turned away while its own reply still travels, and returns 202.
2. `quiesceForRestore` closes every socket and aborts running assistant turns. Everything written from here would be discarded, and the reader should not spend an hour writing into it.
3. The safety snapshot runs, in the usual child.
4. `beginRestore` writes `backups/restore.json` naming the source snapshot. Nothing has been destroyed yet.
5. The maintenance page says to close ChungusHub and start it again, or to cancel. **Until the relaunch, the claim can be withdrawn**: `POST /api/backups/cancel-restore` deletes the journal and lifts maintenance, it refuses while the safety snapshot is still being written, and it is offered on both the Backups page and the maintenance page. An armed restore that could only be disarmed by executing it would be a trap, and disarming costs nothing because the claim is one small file.
6. The next boot runs `resumeInterruptedRestore()` **before `serverDb.open()`**, deletes each entry and writes the snapshot's back, restores the directory skeleton with `ensureDirs()`, and clears the marker; once the database is open, it stamps a fresh `dataEpoch` into the settings table.

The swap is per **entry**, never a rename of the data dir itself: two `fs.watch` handles stay open on that directory for the life of the process ([`watch-file.ts`](../server/watch-file.ts)), and Windows refuses to rename a directory anything has open. It is **idempotent** (every entry is removed and written afresh), which is what lets a boot that finds a half-finished swap simply run it again. Files are **copied, not hardlinked**, into the live folder: linking would make a restore instant and is safe only while nothing in the app ever rewrites an image in place, an invariant no future author would know they were holding, and the day one did, a restore would silently edit the snapshot it restored from. An unreadable `restore.json` is **fatal** rather than ignored, because "something was mid-swap" never reads safely as "carry on".

**A snapshot newer than the running app is refused**, by `restoreBlockedReason` against the manifest's `schemaVersion`: migrations only run forward, so the app cannot read its own future. Older is ordinary as far back as the schema baseline: restoring a year-old snapshot is not a special path, it is the upgrade path a user who did not open the app all year would take anyway. Below the baseline there is no path at all, since the migrations that once led up to it are not in the build, and the boot fails loudly instead of running on a schema it cannot complete. What keeps the ordinary case safe is the rule [`server/schema-upgrade.test.ts`](../server/schema-upgrade.test.ts) holds every migration to: **a migration only moves data when it was decided there**, by name on its `DATA_MIGRATIONS` list, and each entry on that list carries a case proving what it rewrites and what it leaves standing.

**`dataEpoch` is how a device finds out its world was replaced.** It rides `/api/config`; `AppShell` remembers the value it booted with and re-asks on every reconnect, reloading on a change (and never comparing before that first answer arrives: "unknown" must not read as "changed"). It cannot be a push: every socket is closed before the restore, and the process that took the decision is gone by the time it becomes true. A phone that was asleep for hours finds out the same way. The value is a **settings-table row, written once by the boot that ran a swap**, not an in-memory counter: a counter resets on every launch, which would make the first plain restart after a restore look like a second restore and reload every open page for nothing.

**Maintenance mode** turns away everything except `GET /api/config`, `GET /api/backups`, and the cancel POST above: the two reads because the Backups page is the surface that has to keep saying what is happening, and it cannot do that through a gate that refuses it; the one mutation because it is the mutation that ends the state. All three sit behind the same IP and password gates as everything else. A navigation gets `maintenancePage()`, which auto-retries only when the state ends by itself; a restore waits for a person, and a page refreshing hopefully behind that instruction would suggest otherwise. While the claim stands, the scheduled timer also **skips**: a scheduled snapshot would prune afterwards, the new snapshot shifts the retention window, and the snapshot pushed out can be the very one the journal points at, which the next boot would then refuse to start without.

## The surface

Settings → App → **Backups** ([`BackupsPage.svelte`](../src/lib/components/settings/BackupsPage.svelte)), two cards. **Automatic Backups** (`automatic-backups`) holds the switch, the interval, and the two retention counts. It deliberately carries **no prose restating the policy**: a sentence spelling those three controls back as a span of days reads as a promise, and the thinning underneath it means the span is not one. The controls say what they do, and the history below shows what actually survived. **History** (`backup-history`) holds the Back up now row, the live job, and the list: each row is when, why, what is in it, how big, with a pin and per-row Restore and Delete. Selection is a **mode** rather than a permanent column, since a checkbox on every row makes the common case (read the list, restore one) look like a form to fill in. The row folds on its own **container** width, not the viewport's, because the same panel is a narrow dock and a wide centered overlay independent of the screen.

Both deletes and the restore go through `ui/ConfirmDialog` with `destructive` set, so the reader's rung on the destructive-act ladder reaches them. The restore's message states the date and, from `serverDb.createdSince`, what goes in real counts (**messages included**, because a restore that costs "one chat" can cost every hour of writing inside it), and its hold length is scaled by that same total. It also says plainly that the app has to be closed and started again, since that is the part a reader must agree to in advance rather than discover.

The settings ride the settings spine (`backupSettings`) and the server reads the same row to run its timer, so `normalize` in [`stores/backups.svelte.ts`](../src/lib/stores/backups.svelte.ts) and `normalizeBackupSettings` in `service.ts` have to agree on the clamps (coupling 2). One consequence worth knowing: the settings table is inside the snapshot, so a restore rewinds the backup schedule along with everything else.

## Before touching this

- Adding a directory under the data dir? It needs an entry in `SNAPSHOT_ENTRIES` **and** a line in `scripts/package.ts` if it ships bundled content. Missing the first is invisible until someone restores.
- A new write into the data dir that does **not** go through `broadcastSync` has to call `backupService.markChanged()` itself. Missing it means the schedule never hears about that data, and the failure is silent in the worst direction: the file is simply never in a snapshot.
- The job-child branch in `index.ts` must stay above `serverDb.open()`, and the pre-upgrade snapshot must stay above it too.
- Never make the restore swap run in a live server "because it would be nicer". Re-read the paragraph above first; the file lock is measurable, not folklore.
- A new JSON column that can hold an image path needs an entry in `IMAGE_BEARING`; a new **key** inside an existing one needs nothing, which is the point of matching path shapes. A new image **category** needs one too: `IMAGE_PATH_RE` spells `IMAGE_CATEGORIES` (config.ts) out, and a category it does not name is a folder no snapshot ever copies.
- Snapshots hold API keys in plaintext, exactly as the data dir does. Anything that moves the store somewhere new (a sync folder, a network share) is a security decision, not a convenience one.

## Hand-kept couplings

1. `SNAPSHOT_ENTRIES` (paths.ts) ↔ the restore swap ↔ `scripts/package.ts`'s copy list: the twin of build-packaging coupling 4. One list decides what is backed up, restored, and shipped.
2. `normalizeBackupSettings` (service.ts) ↔ `normalize` (stores/backups.svelte.ts): same key, same clamps, read by both halves.
3. `MIGRATIONS_FOR_TESTS` (db.ts) is exported for `schema-upgrade.test.ts` and `backup/backup.test.ts`. Nothing else may import it.
4. The `backups` sync scope is declared in `shared/sync.ts` and typed on both ends, so a missing handler does not compile. What the compiler cannot see is that `service.ts` broadcasts through an injected callback rather than a literal `broadcastSync('backups')` in `index.ts`: the reachability scan in `contracts.test.ts` reads the pin call in `index.ts` and is satisfied by it.
5. Every write into the data dir ↔ `markChanged()` (service.ts). `broadcastSync` covers all of them but four, and those four call it directly in `index.ts` (image copy and delete, assistant file store and delete). Nothing checks this: a write that tells neither is data the schedule does not know exists.
