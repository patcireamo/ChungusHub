# Chat, message tree & chats: architecture & maintenance

The conversation model is a **tree, not a list**: `messages` rows link by `parent_id` + `sibling_index`, a chat's `active_leaf_id` picks the branch being viewed (root→leaf walk = the visible transcript), and `canon_leaf_id` optionally blesses one timeline as canonical for the story map. Multiple roots are legal (seeded greetings are root-level siblings), so the structure is really a forest. Swipes, regenerates, edits-as-branch, and forks are all "new sibling + move the leaf".

**Two stores split the work.** [`chat.svelte.ts`](../src/lib/stores/chat.svelte.ts) (`chatStore`) owns chats: the chat list, `currentChatState` (chat + tree + active path + `allMessages` + streaming state), chat creation (`createChat` **requires** a `characterId`: no UI path creates a characterless chat; rows orphaned by a character deletion are the only characterless ones. Every new-chat entry point either has a character in hand or routes through the New chat flow in architecture/ui-shell-settings.md. Auto-title `<character> - YYYY-MM-DD` off the shared `utils/date.ts` `formatDate` rather than a second date recipe: year-first is load-bearing twice over, since a title is a stored string and the chats panel's Title sort compares it as text, so this is what makes that sort group by character and run chronologically inside each one (architecture/ui-shell-settings.md, "one numeric date shape"), pin to the character's active version at birth (the only place the library's active version reaches a chat; from then on the chat's own pin decides every request it makes, see architecture/library.md), seed First Message + alternate greetings as swipeable root siblings, stored **raw**, with `{{char}}`/`{{user}}` left literal so they resolve live at display and generation and a persona change reflows the greeting), deletion (immediate and final: the chats panel's confirm dialog asks first with the chat's real message count, per the destructive-act ladder in architecture/ui-shell-settings.md; the store deletes server-first so a failed delete changes nothing on screen, and refuses only the case no dialog can cover: a reply still streaming into that chat's rows), **bulk deletion** (`deleteChats`, behind the chats panel's picking mode: a cleanup of twenty old chats is twenty menus and twenty confirms otherwise, and no delete-confirmation setting fixes the repetition around the gate. Deliberately NOT a loop over `deleteChat`: that re-routes the open chat once per row, so a batch containing the chat you are in can land you inside another chat that is itself about to go, and it would refuse the whole selection over one streaming reply. Here the streaming refusal is per row and says which one was kept, the server pass stops at the first failure with the list still telling the truth about what is left, and the routing runs once at the end. The panel's confirm states both figures, chats and messages, because the second is the one nobody counts before agreeing to lose it, and its hold scales on the message total), post-delete routing rules (`routeAfterDelete`, shared by both paths: stay within the same character's story; a living character never drops to zero chats), `goHome` (the composer's home action: a real chat close back to the boot zero state, with active id and chat state nulled, memory cleared, welcome raised; callers must check `messageStore.warnIfBusy()` first since chatStore can't import messageStore), and `syncReload` (remote-change refresh that never disturbs a local stream: a hint arriving mid-stream sets `missedSyncWhileStreaming` and replays when `endStream()` lands, because the server never repeats a hint and dropping it left the device stale until the next remote change). **The stream is owned, not ambient.** `stream` (`{ chatId, content, thinking, continuingMessageId }`, opened by `startStream(chatId)`, closed by `endStream()`) is a field of the STORE and deliberately not of `ChatState`: a generation belongs to the chat that asked for it, never to whatever the reader happens to be looking at. Three rules fall out and all three are load-bearing. Tokens land on the stream record, which already names its owner, and every transcript surface paints from `visibleStream` (the stream only while its chat is the one on screen), so a reply still arriving in a chat the reader walked out of cannot bleed into the one they walked into. The composer asks the opposite question: `messageStore.isStreaming` is `stream !== null` app-wide, not the viewed chat, so leaving a chat mid-reply never reads as idle; read off the view it unlocks the composer of wherever the user landed and lets a second generation start beside the first, over the one `abortController`, which then reaches only the newer of the two. That app-wide flag is the composer's WHOLE busy state: `ChatContainer` hands `InputArea` a single `isStreaming` prop and no separate `disabled`, because "the app is generating" and "the composer is shut" are one fact, and it is what turns Send into a Stop that reaches the running reply. And the generation paths close by refreshing the chat they were FOR (`chatStore.refreshChat(chatId)`; `refreshCurrentChat` is now that same call with the active id): a reply landing while the reader is elsewhere still has to carry its own chat up the list with its new time, and refreshing whatever is open instead re-reads a transcript nothing touched while the chat that changed keeps its old position. `refreshChat` reloads the transcript only when that chat is the one on screen, so the list row moves either way. The instant tree mutations keep `refreshCurrentChat`: they cannot span a navigation. Every door that swaps the active chat still refuses mid-generation on top of all that (`goHome`, both New chat doors). The ownership model is what keeps the state correct, the guards are what keep the user out of the situation. chatStore also owns the per-chat **feature state** (`chats.feature_state`: the last-10 spent-one-shot steering history and the Impersonate perspective; types + the pure `normalizeChatFeatureState` live in `types/chat.ts`, shared by this store and the db-sourced generation path so both normalize identically): `featureState(chatId)` is the normalized reactive read, and `updateChatFeatureState`/`pushSteeringHistory`/`setImpersonatePerspective` are read-merge-write mutations serialized per chat through `featureStateQueues` (the same idiom as the message queue). `pushSteeringHistory` records the texts of spent one-shot steering notes, newest first (`pushSteeringHistoryEntry`: exact duplicates move up instead of duplicating, cap 10), and no-ops on an empty list so a turn with no one-shot never touches the row. **Steering itself does not live here**: notes are their own rows with their own scope and their own store (architecture/engines.md), and this blob keeps only the reuse list, which is the one genuinely per-chat piece. A `steering` key left in an older blob is not parsed. [`messages.svelte.ts`](../src/lib/stores/messages.svelte.ts) (`messageStore`) owns turns: send (create user message → generate), `generateResponse` (`steeringStore.flush()` → `buildPromptMessages` → `llmService.complete` → insert assistant turn → spend the one-shot steering notes → fire-and-forget sidecar: memory maintenance). **Stop keeps what streamed**: an aborted generation comes back as an ordinary result flagged `cancelled` carrying every token that arrived before the stop (architecture/client-data-layer.md), and those are persisted as the turn like any other reply: the user watched the text arrive and stopped because they had enough of it. Only a stop with nothing to keep (no token yet, or a dead socket the server never answered through) creates no row and returns null, which is the one case the callers' abort branches still handle, edit (`save_only` / `create_branch`: the intent is picked by the button that opened the editor, Edit vs Branch, and never asked at save time; every in-place rewrite is handed to `memoryStore.invalidateMessage(chatId, messageId)` when the chat has memory enabled (it no-ops for live/off-path turns, see architecture/memory.md), while `create_branch` is exempt, since the fork is a new id the original's summary still describes), delete (`this_only` splices: children re-parent via `deleteMessageOnly`, and the view re-homes ONLY when the deleted turn was the active leaf itself: nearest sibling branch preferring a same-role variant, else a re-parented child, else the parent; a mid-path splice keeps the leaf, which survives the delete, so the user never gets yanked to another branch, and re-parented children that land off the viewed path get an explanatory toast since they'd otherwise read as deleted; subtree delete is **final**: the confirm dialog is the only gate, rows and their attachment files go together, no undo), regenerate (`replace` vs `branch` for both roles, with view-restore only when the generation produced no row: a stop that kept its partial text lands that text as the new turn and the view stays on it) and `regenerateLastResponse` (the composer's shortcut into it), sibling navigation, opening-scene generation (virtual user message, never persisted), `continueMessage` (fired from the composer hamburger menu: extends the newest assistant turn **in place**; rebuilds the turn's regenerate prompt from fresh rows and rides the turn as the assembly's continuation tail, whose instruction is the active preset's own `continuePrompt`, resolved inside assembly; it is NOT an engine and takes the primary connection like any send, see architecture/prompt-pipeline.md; streams into the existing bubble via `ChatState.continuingMessageId`; on success writes the joined text + accumulated stats through `db.applyMessageContinuation`, which deliberately never stamps `edited_at`, then hands the in-place rewrite to `memoryStore.invalidateMessage` like any edit and refires the memory sidecar; join rules (glue seam for the live preview, restatement-overlap trim for the persisted result) live in [`utils/continuation.ts`](../src/lib/utils/continuation.ts), tested in `continuation.test.ts`; a stop keeps the tail that streamed and joins it exactly like a completed continuation, while a stop with nothing to keep, or a nothing-new result, discards it and touches no row), and `insertDummyMessage`. `warnIfBusy()` is the concurrency gate: every tree mutation checks it so nothing forks the lineage a streaming turn is about to attach to.

**A chat nobody has written in is a MIRROR of the card, not a copy of it.** Its rows hold the character's First Message and alternate greetings and nothing else, so an edit to the card reaches them: `serverDb.updateLibraryEntry` calls `refreshSeededGreetings` on every save, and since every door writes through that one method (the library editor's autosave over the RPC bridge, the assistant's `manage_greetings` and its `firstMessage` field write), none of them reimplements the rule. Without it every unstarted chat quietly opens on a version of the character that no longer exists anywhere. The moment the chat holds something the user put there (a turn, a reply, a hand-edited greeting, an extra opening written by hand), it is a story, and the card stops reaching it.

**Recognition asks the CHAT, never the card's history.** Every seeding path records what the card handed over: `chats.seeded_greetings`, a JSON array, written by `chatStore.seedCharacterGreetings`, the assistant's `create_chat` and the refresh itself, and read by nothing else (which is why `mapChat` deliberately does not carry it and no client type mentions it). A chat qualifies when its rows are **exactly that list**: same count, same order, every row still an unedited root-level assistant turn with no attachment. NULL means no claim was ever made (imported chats, and every chat older than the column), and those never follow the card. **This is not the same as matching against the greetings a save happens to be replacing**, which is the obvious shortcut and is wrong: a chat holding a story while the card moves on ends up holding a text the card no longer recognises, so emptying it back down could never hand it back, and whether an emptied chat followed the card came to depend on invisible history. From outside that reads as random, which is worse than either answer.

**There is deliberately no "this chat has been used" flag.** The claim is provenance (this text came from the card), not history (this chat was played), and the difference decides the behaviour: an emptied chat follows the card again, because nothing left in it is the user's to protect. The exact match is the whole safety net: a single character the user typed anywhere in the chat breaks it, so a hand-edited greeting or an opening written by hand is never overwritten. Scope is the variant that actually changed: chats pinned elsewhere keep what they were pinned to, and a save that MOVES the active version pointer (a fork, a switch) is not a content edit at all and reconciles nothing. The rewrite is in place (row ids survive, so a reader parked on the third greeting stays on it), stamps no `edited_at` (the card wrote it, not the user; that stamp is memory's staleness signal, architecture/memory.md), leaves `chats.updated_at` alone so the chat list can't reshuffle under the cursor, and retreats the leaf to the First Message when the greeting it was on is dropped. A card that gains its first opening seeds an empty chat (which is why the claim is written even when the character has no greetings at all: an empty claim is still a claim), and a card that loses every opening empties one and nulls its pointers. **A card save that does not touch the opening never looks at a chat**, and the candidate query COUNTS each chat's messages rather than reading them, so a card edit costs nothing on the long stories of that character. Covered by [`server/greetingRefresh.test.ts`](../server/greetingRefresh.test.ts).

**Invariants to keep** (each fixed a real bug, and the steering pair was designed in from the start): a 'once' steering note is spent only after a story generation's PERSISTED success (send/regenerate/continue/opening scene), through the single `messageStore.spendOneShotSteering`: errors, stops that kept nothing, and continue's no-new-content soft returns never spend, so a failed steered turn keeps its guidance for the retry, while a stop whose partial text WAS persisted spends like any other landed turn (the guidance already shaped text now in the story; carrying it forward would apply it twice); and every one of the three build sites calls `steeringStore.flush()` before `buildPromptMessages`, so a note typed inside the debounce window can never miss its own send (the builder reads the db rows, not the store's optimistic copy). The originals: persona is locked per user message at send time (`personaId`), and the one deliberate after-the-fact rebind is the composer menu's "Set chat persona" (`messageStore.setChatPersona` → `db.setChatUserPersona`, scope `messages`), which re-attributes EVERY user turn in a chat at once so imported/legacy chats stop rendering a plain "You"; character version is NOT locked per turn: it is per chat, and repinning applies to everything the chat does from then on (architecture/library.md); sibling indexes are never reused within a parent: merging sibling sets appends after `getNextSiblingIndex`; edits of memory-archived turns drop the summary covering them (see architecture/memory.md; the archive boundary is derived, so nothing else has to move); and **no chat pointer may name a deleted row**: the leaf and the canon marker retreat to the nearest surviving ancestor, the root recomputes from surviving parentless rows. That last one is the db's own guarantee (`repairChatPointers`, architecture/server-core.md), so every delete door inherits it; this store's `repairCanon` and its leaf re-homing are the POLICY on top (which sibling the reader lands on for continuity), and they write after the delete, not instead of it.

**Pure helpers**: [`message-tree.ts`](../src/lib/utils/message-tree.ts) (tree build, active-path walk, role-agnostic sibling resolution (`findSiblings` walks every branch at a point so spliced forks stay reachable from chat), `collectSubtree` in FK-safe BFS order, `subtreeBlastRadius` for confirm dialogs, `findDeepestLeafFromNode` for navigation; tested in `message-tree.test.ts`) and [`story-map-layout.ts`](../src/lib/utils/story-map-layout.ts) (Buchheim tidy-tree layout in grid units, virtual super-root for the forest, cycle-guarded; tested in `story-map-layout.test.ts`).

**Satellites**: [`chatCast.svelte.ts`](../src/lib/stores/chatCast.svelte.ts): lightweight chatId→characterId and chatId→last-persona indexes for chat lists (names/art resolved lazily against the library); [`chatSelection.svelte.ts`](../src/lib/stores/chatSelection.svelte.ts): the live text selection the Chungus Assistant auto-attaches; [`inputDraft.svelte.ts`](../src/lib/stores/inputDraft.svelte.ts): per-chat composer drafts, debounced 500ms per chat on the shared `DebouncedWriter` (which commits them when the tab goes away), synced across devices; [`inputHistory.svelte.ts`](../src/lib/stores/inputHistory.svelte.ts): the ↑/↓ recall log, deliberately independent of the messages table; [`branch-labels.ts`](../src/lib/utils/branch-labels.ts): the fixed branch color palette (palette keys stored, not CSS values).

Deliberately NOT the same thing as the hamburger's "Set chat persona…" (`ChatPersonaDialog` → `messageStore.setChatPersona`), which re-attributes a chat's existing user turns and changes nothing app-wide; the two must stay separate entries. The **Spellcheck / Impersonate** hamburger entries (gated by their switches, disabled on an empty draft, mid-stream, or while one is already open) raise [`TransformPanel.svelte`](../src/lib/components/chat/TransformPanel.svelte): a strip mounted **in flow above the composer**, never a modal, so it shortens the transcript instead of covering the story and the draft it rewrites stays on screen underneath it. Spellcheck opens straight into `running` because it has nothing to choose, which makes its menu row the press. **The proposal is read differently per kind**: Spellcheck as an inline word-diff redline (`utils/text-diff.ts`, deliberately separate from the assistant's `utils/diff.ts`, see both file headers), Impersonate as the message itself, since a word diff between a one-line note and the message grown from it is an unreadable weave of accidental matches rather than a review. Approve replaces the draft only after recording the original into input history, and close/Escape/error leave the composer byte-for-byte untouched; **the composer is frozen while the strip is open** (textarea and Send disabled), because the proposal is against the draft as it stood at the press and approving over an edited box would throw that edit away silently. The row is the composer's shortcut to the newest reply's own Retry → "Replace current": it calls `messageStore.regenerateLastResponse('replace')`, so nothing about the retry path is re-implemented here. **The label is fixed but the behaviour follows the last turn**: a reply gets re-rolled, a user turn gets the reply it doesn't have yet. See the "Chats panel" section below for what the rows say and where the numbers come from. **Continue streaming** rides the same `chatStore.stream` record plus its `continuingMessageId`: while it is set, `MessageList` suppresses the `StreamingIndicator` bubble and instead hands the target `Message` a `streamTail`/`streamTailThinking` pair: the bubble renders `glueContinuation(stored, tail)` through the normal display pipeline (so display regex and self-refs apply to the seam too), and new reasoning streams into `MessageReasoning` after the stored block with the pulse marker. `endStream()` drops the whole record, so the id can never outlive its stream, and the persisted join happens only in the store. The component never writes. Display-scope regex rules (architecture/prompt-pipeline.md "Regex rules") are applied at render time in exactly two places (`Message` and `StreamingIndicator` run content through `regexRulesStore.forDisplay(content, role, depth)` before `renderMarkdown`), never at save time: Copy, the editor, and the stored rows always carry the original text, and the streaming token estimate deliberately counts the raw stream. **`depth` is counted by `MessageList`, not by the row**: `messages.length - 1 - index`, plus one while a fresh reply streams into its own bubble, because that bubble is a turn the stored rows don't have yet and without the offset the newest reply would flip between turn 0 and turn 1 as the stream settles. A continue writes into a row that already exists and so adds no turn; `StreamingIndicator` passes 0 outright, which is the same number the row it becomes is handed. `Message` then runs the result through `expandSelfRefs` (active persona + bound character) so raw `{{char}}`/`{{user}}` in stored content resolve live on screen. This must stay in lockstep with the generation-side expansion in `prompt-assembly.toInjectedMessage` (coupling #5). **The story text is patched into the page, not reprinted onto it.** Every transcript surface that renders model output (`Message`, `StreamingIndicator` and `MessageReasoning`) hands its HTML to the [`renderedHtml`](../src/lib/actions/renderedHtml.ts) action instead of `{@html}`, and the difference only matters while a reply is arriving, which is to say constantly. `{@html}` applies a new string by throwing the whole subtree away and building a fresh one, and everything the reader is doing inside that subtree lives on the nodes it destroys: a folding panel loses the `open` they just clicked, a text selection collapses, and worst of all the click usually never lands, because a click fires on the common ancestor of where the press went down and where it came up and a panel replaced between the two hands the event to the container instead. The action parses the new HTML into an inert `<template>` and reconciles it against what is on screen, positionally: there are no keys to be had in rendered markdown, and position is the right match anyway, since a reply grows at its end and everything above that end lines up and survives. Two rules hold it together: the HTML is trusted to have come from `renderMarkdown` and nothing there relaxes that, and **`open` on a `<details>` is never synced**, because it is the reader's state and not the text's: a panel that survives a patch keeps what they set, while one that arrives fresh is built from the source node and so still honours whatever the reply asked for.

**The message cursor is where the keyboard is in the story.** The transcript is long and Tab is not navigation, so a turn a hundred messages back has to be ADDRESSED rather than stepped to. [`chatCursor.svelte.ts`](../src/lib/stores/chatCursor.svelte.ts) is the one thing the doors share, and it holds one turn id stamped with the chat it was set in, so a cursor reads as absent in every other story and a chat switch drops it with nothing to clean up. **Marking and taking are separate facts** and the split is what makes find-in-chat work: `mark` says which turn the cursor is on and paints the ring, `goTo` also moves the keyboard, and the search bar marks every hit while the reader is still typing in its own field, where a mark that took focus would empty that box on the first match. Three doors reach it and they are the three distances: **stepping** for the near turn (⌥↑/↓ from anywhere, bare ↑/↓ once the keyboard is on a card, and ↓ past the newest hands it back to the composer, which is what makes the transcript and the box one continuous run rather than two places with a wall between), **find in chat** for anywhere in the branch (its close hands the keyboard to the hit it left the reader on, so type, Escape, E is one gesture instead of a search followed by a hunt), and **`/go <n>`** for the address, the number every turn already wears under its portrait. Escape from a turn goes back to the composer through the shell's own Escape ladder (architecture/ui-shell-settings.md), so the cursor needs no exit of its own. **Stepping is always a step, never a resume**, which is what lets one gesture both enter the story and walk it: the shape a reader reaches for is the modifier held down and the arrow tapped, so a door that resumed would answer the second tap by landing where it already was, and a key that lands where it already was reads as a dead key. **The cursor IS focus on the row**, which is the whole reason its keys can be bare letters: on a turn the keyboard sits on a card and never in a box that takes text, so nothing has to be modified to stay out of the way of typing. `Message.svelte` therefore gives the row `tabindex="-1"` (focusable, deliberately not in the tab order, since tabbing through a long transcript is not navigation), and handles the keys **only while the cursor is on that turn and the event's target is the row itself**: everything inside owns its own keys, and one of their events passing through on the way up is not this turn being addressed. **A pointer press is not one of the doors.** Clicking anywhere in a card focuses the row as well, since the browser hands focus to the nearest focusable ancestor of what was clicked, and marking from that would leave a ring on the last turn a reader touched with nothing to clear it: the ring says where the keyboard is, which is a claim a click never makes. So the row marks from its own `focus` event only while the browser reports that focus as keyboard-driven (`:focus-visible`, which never matches a click or a tap), and that one condition is also what lets the two generic keyboard doors land a cursor without knowing anything about turns, since both only focus the row: the hint labels and the focus keys (architecture/ui-shell-settings.md). The three doors above mark in the store before they focus anything, so none of them depends on it. The keys follow the ring rather than focus for the same reason: a bare `E` opening an editor on a card wearing no ring would be a key landing where nothing on screen says it lands. Every one of those keys is that row's own button and never a second path to the act, so `Delete` and `R` open the very menus the pointer opens and the confirmations gating them hold for the keyboard exactly as they do for a click. **Adding a key there adds a row to the `turns` group** in `commands/shortcuts.svelte.ts`, or it is a key nothing on screen ever mentions. `MessageList` owns the landing, and it is the same reach as the arrival mark with a different ending: a turn behind the transcript window is loaded back in first and the effect re-runs on the row that now exists, the scroll says `'instant'` (coupling 15; stepping through a stretch of story would otherwise queue one animation per press) and deliberately does not arm `programmaticScroll`, since landing mid-history SHOULD release the bottom pin. The ring rides `.message-bubble-shell::before` like the card outline, so it works in every chat style and the card's geometry is identical whether or not the cursor is on it; it sits BELOW the manuscript block in the stylesheet at the same specificity, because that block hides the ring outright and a cursor written up beside the other ring rules would be invisible in the one style that draws no card. It is dimmed while the keyboard is elsewhere and bright while the row has focus, because "where Alt+↑ comes back to" and "your keys land here" are different claims. The row also carries `data-hint`, which is what lets the hint labels reach a visible turn directly (architecture/ui-shell-settings.md).

**Commands are the composer's other mode.** Typing `/` into an EMPTY composer arms it: the shell takes the accent border and a palette opens above the box, and from there the composer is filling in a call rather than holding a message. [`commands/registry.ts`](../src/lib/commands/registry.ts) is the single list **and** the single parser, one file for the reason `macros.ts` is one: a command is declared, documented, gated and matched in exactly one place. The grammar is the whole design and it is deliberately tiny: a slash, a name up to the first space, and everything after that space as ONE verbatim argument. That is what leaves an argument with nothing to quote and nothing to escape, which is the tax a command language charges on every one-liner the moment it grows separators, variables and closures. So there are none: no chaining, no second argument, and anything that would need one gets a picker or stays a control. **Arming on an EMPTY composer is what keeps prose out of the mode**: a story line containing a slash never enters it, Escape leaves it with the text intact (consumed per the shell Esc contract, so backing out of the palette cannot also close a panel behind it), and a line naming no command closes the palette by itself so Enter sends it like any other message. There is no dead state to escape from, which is why the mode needs no exit affordance of its own. Empty means the whole composer and not just the text box: **a pending attachment blocks arming**, because `/say` writes a turn through `insertDummyMessage` and would land it with the picture still sitting behind it, silently dropped. **A command line is also not a draft** and is never persisted: drafts sync across devices and restore as ordinary text, so a command typed and abandoned would come back as a message that sends itself on the next Enter. Leaving the mode by Escape saves it, because from that press on the line really is prose and nothing else fires (leaving a mode is not an input event). **The Send button answers the same question Enter does** (`commandReady`), so it goes dead over a name still being typed, a refused command or a missing argument instead of looking live over a press that would do nothing; it is also what makes the mode work on touch, where Enter is a newline. **The list is ranked rather than filtered, and headings are for browsing only.** Matching reads descriptions as well as names, so someone who knows what they want but not what it is called still finds it, and that is precisely what makes the ranking load-bearing: descriptions are full of the words other commands are NAMED after, so a flat match puts a command the user is not spelling above the one they are. Spelling the name beats spelling part of it, which beats hitting a description, and registry order decides inside a tier. Group headings therefore appear only on a bare `/`, where the list IS the whole vocabulary: applied to a ranked list they reorder it back into registry order and put the best match under a heading below a worse one, with the highlight sitting on a row that is not the first on screen. **No command implements behaviour**: every `run` is one call into a store or into the composer's own door (`CommandHost`, which carries the three the composer owns rather than a store: Continue and Retry, wrapped differently by `ChatContainer`, and Duplicate, which raises a dialog), so a command and the control it stands in for are the same call and not a second copy of it. **The gates are handed in, never recomputed**: `canContinue`, `canRegenerateLast` and the resolvable character reach the registry through `CommandContext` as the very deriveds the hamburger's own rows read, which is what stops a command from ever being more permissive than its button; a row that cannot run stays on screen and says why in place of its description, since a command vanishing from the list reads as a typo rather than as a refusal. `/retry` and `/swipe` are the two rows behind the transcript's one Retry button and are drawn alike to say so: same call, `'replace'` against `'branch'`. Their gates differ by exactly the one exclusion `'replace'` earns, though, and `canSwipeLast` is a SEPARATE derived for that reason: Retry refuses a user turn that already holds replies because replacing there is a subtree delete, while that is precisely the turn swipe exists for. Two commands cannot reach their target directly and both hand off the one-shot way `revealTargetId` does: `/branch` sets `messageStore.branchTargetId`, which the newest turn's own row claims to open its editor in Branch mode (the editor is that row's state, so the composer may ask for it and nothing more; a row **already editing refuses out loud**, since the composer stays typeable during an edit and flipping an open editor's mode would silently turn a rewrite into a fork), and `/duplicate` mounts the Chats panel's own `DuplicateChatDialog`, so the one question a copy cannot answer for itself is asked here too. Whether there is a question at all is `duplicateAsksAboutMemory` in [`types/chat.ts`](../src/lib/types/chat.ts), read by both doors: two spellings of that rule end with one door asking and the other quietly deciding. This door differs from the panel in exactly one deliberate way: it lands you IN the copy, because the command was typed from inside the story and that is where the next turn goes. The list itself is [`CommandPalette.svelte`](../src/lib/components/chat/CommandPalette.svelte), a presentation surface holding no mode state and resolving no gate (both belong to the box being typed into); what it owns is the one thing a list must get right alone, keeping the moving highlight in view. Coverage is the contracts net alone (`contracts.test.ts`, "commands", architecture/testing.md); the mode's own behaviour is manually tested like the rest of the composer.

**A reply can also contain folding panels of story state.** Presets instruct the model to print `<details>`/`<summary>` blocks and carry regex rules that style them, so `renderMarkdown` allows those tags (plus `div`/`b`/`i`/`u`/`font`) and the disclosure is native: no script, no component, nothing to hydrate. **Their bodies are markdown**, which takes one correction to be true: CommonMark reads `<details>` as opening a raw-HTML block that runs to the next blank line, and a model writes the body on the line straight after `</summary>`, so without help the whole panel arrives as one run-on line of literal text with its list dashes intact. [`model-markup.ts`](../src/lib/utils/model-markup.ts) inserts the blank line that closes the raw block (after `</summary>`, before `</details>`, at every nesting depth, never inside a fence) and drops a `<br>` sitting at the end of a line, which is what the line ending already means once the body is markdown and which would otherwise double every gap in a hand-written or imported panel. That one has no exception: a `<br>` alone on its line empties the line, which is the blank one its author was drawing, while a `<br>` mid-line is left alone because nothing else is doing its job. What such a block may look like is **not** the preset's to decide beyond its colour: every inline `style` is narrowed to four decoration properties by [`inline-decoration.ts`](../src/lib/utils/inline-decoration.ts) and the panel's whole shape (box, padding, corners, accent bar, chevron) is drawn by `.prose details` in `app.css` from the summary's `currentColor`. The reason is the threat model, and it is worth stating plainly: the rules rewriting that reply came from a preset a stranger wrote, and a block that could size and position itself could be drawn over the interface as a fake window asking for an API key. Size and position are therefore never granted, and that list must not grow (architecture/sillytavern-interchange.md coupling 10).

**Two separate things have to go right for a preset's colour to reach the page, and each of them fails silently on its own.** The first is that the attribute has to survive sanitizing at all: `ALLOWED_ATTR` decides which attributes may EXIST, but DOMPurify then matches the VALUE of anything it does not hold to be inert against `ALLOWED_URI_REGEXP` and drops the attribute when it fails. Its inert list is fixed and contains `style` and `class` but **not** `color`, so a hex colour is read as a URL, fails the deliberately narrow `https?|mailto` pattern, and `<font color>` is deleted before any stylesheet sees it. `ADD_URI_SAFE_ATTR: ['color']` is what says a colour is a colour; the `afterSanitizeAttributes` hook remains the thing that decides whether it is a colour we accept. `target` and `rel` sit in `ALLOWED_ATTR` under the identical trap and would not survive either: nothing emits them, which is the only reason it does not matter. Adding an attribute to that list is therefore never one edit: ask what its value looks like to a URL matcher.

The second is the cascade, and it has to be said out loud in CSS because it says the opposite of what you want. A `<font color>` is a presentational hint, which ranks **below every author rule**, so the quote tint on the `.quoted-text` span **inside** it takes the colour straight back, and coloured dialogue is exactly that shape, `<font color="…">"the line"</font>`, a colour wrapped around a quoted line. It is the thing presets most want, and the tint would take it back from every one of them. One rule in `app.css` hands quote, strong and emphasis back to `inherit` under anything carrying a colour, because a preset that colours a run means the run. It matches **the elements themselves** (`font[color]`, and a `style` whose serialized declarations begin with or contain `color:`) rather than a marker attribute written during sanitizing: the colour is already in the DOM by then, so nothing outside that stylesheet has to cooperate for the rule to hold. The price is a coupling to how `sanitizeDecorations` serializes (`property: value`, joined by `'; '`), which is what lets the selector anchor tightly enough that `background-color:` is not read as a text colour; `inline-decoration.test.ts` pins that shape with the stylesheet named in the test. **The editor has no save-time menu.** `MessageEditor` takes a `mode` (`save_only` | `create_branch`) decided by the button that opened it (**Edit** rewrites this turn, **Branch** writes the text as a new sibling and leaves this one alone), and Save just saves. Three things follow. **One**: nothing is created until Save, so cancelling a Branch costs nothing. An in-place save of untouched text closes without writing; a Branch of untouched text still forks, because a verbatim alternate is a legitimate place to write into later. **Two**: `EditAction` has exactly two values. There is deliberately no "rewrite in place and delete every descendant" third one: that is a subtree delete hidden behind a Save button, and a Branch reaches the same outcome without destroying the timeline it forks from. **Three**: `create_branch` does NOT auto-generate on a user turn. The fork just becomes the leaf, which puts Generate one click away on its own toolbar, deliberate breathing room rather than a call the user never asked to spend. **An in-place save over a folded turn asks first.** A rewrite outdates the summary covering that turn, which the engine then discards and re-reads (architecture/memory.md), so Save on an archived message raises a confirmation inside the editor: the draft stays on screen above it, Keep editing returns to it untouched, and the panel states the real numbers from `memoryStore.impactOf` (which summary goes, how many pause behind it, how many turns are re-read and what triggers that). It is raised at Save rather than at the Edit button because opening an editor costs nothing and the price has to be readable beside the text it is being paid for; `create_branch` never raises it, since a branch writes a new sibling and leaves the folded turn alone. The panel offers **three doors, and the gesture separates them**: press-and-hold buys the re-read, a plain tap saves as a MINOR edit that costs nothing and leaves every summary standing (`editMessage(…, { minor: true })`, memory.md coupling 8), and Keep editing returns to the draft. The minor door is not an optimisation the app may apply on its own: no diff of two strings tells a typo from a retcon, so it is only ever the user's own answer to "does this turn still say the same thing". While the confirmation is up the editor is `locked`: it holds a SNAPSHOT of the draft, so a keystroke landing after it would be silently discarded by the commit. **Branch is offered on every message**, both roles: a user turn forks into a different thing said, a reply into a hand-written alternate to swipe between (the clone is always the same role, so this cannot mint a mixed sibling set, see coupling 1). **The transcript is the only place either button exists.** The story map reads and navigates the tree; it does not rewrite or remove turns (see the story-map paragraph below). In the Portraits chat style the message card is a two-column flex row whose portrait column is `position: sticky` against the list scrollport. This requires `overflow: visible` on the card and **no vertical padding on the `.message-list` scroller itself** (a scroll container's own padding insets the sticky constraint rect; the spacing lives on `.message-list-content`). That same `.message-list-content` is also the transcript's width: it centers at `--chat-content-max` inside the chat column, which above the dock breakpoint is a share of the screen rather than a fixed width (architecture/ui-shell-settings.md coupling 7), and the cap must stay on this content box: Portraits and Manuscript rows fill their row, so uncapped they stretch to whatever the share resolves to on a wide screen. `InputArea .input-inner` carries the same cap so the composer sits exactly over the text it feeds. `MessageList` autoscroll pins to the bottom only while the user is near it (~120px); any deliberate **upward** scroll releases the pin at once (direction-tracked against `lastScrollTop`, with a `programmaticScroll` guard so the auto-follow's own snap isn't read as intent), so a fast stream can't yank the view back mid-read; a floating "jump to latest" pill (with a "New" hint for unseen messages) restores it. That guard spends itself on ONE scroll event, which pins two rules to `snapToBottom`. It is armed **only when the snap will actually move the scroller**: a write to a scroller already at the bottom (the normal case while following a stream) fires no scroll event at all, so the guard would stay armed and swallow the user's next real scroll-up, leaving the pin set and the next token free to drag them back down. And the follow scrolls with `behavior: 'instant'`, overriding the scroller's CSS `scroll-behavior: smooth`: an animated snap fires a whole run of scroll events and only the first is covered, so the rest read as the user scrolling mid-glide. `jumpToLatest` passes `'smooth'` because that one IS a deliberate travel across a long distance. **The streaming→settled transition never snaps** (`streamSettled`): the settled turn replaces the streaming bubble in place, so a pinned reader is already at the bottom and one who scrolled up to read must not be thrown to the end by the last frame of a reply they already left behind. Auto-scroll fires only for path **extensions** (the previous leaf is still on the new path: a send/reply/dummy append) and chat opens, and "which chat" is asked of the rendered path rather than of `chatStore.activeChatId`, which names the chat being opened a flush before its rows arrive: keyed to that id the swap reads as a chat change against the PREVIOUS story's rows, and the new story's rows then read as a branch switch, the one case that deliberately does not scroll, so a chat would open wherever the last one's offset happened to survive; a path switch that replaces the tail (swipe, branch jump, delete re-homing) asks the pin **as it stood before the swap**, because that pin is part of the reading position and the effect still sees it (it runs before any scroll event the swap fires). A reader who had scrolled up keeps their offset with `nearBottom` re-baselined from real geometry, so switching into a long branch never teleports the view to its bottom and the stale pin from a short branch can't make the next stream token do it either; a reader who was AT the bottom stays pinned there, since the turn a swipe replaces is the one they were reading and the arrow they pressed sits at that turn's bottom, so holding their offset would strand them mid-message with the controls off screen. `lastScrollTop` is rewritten on both paths: the swap can shrink the content and let the browser clamp `scrollTop` by itself, and a clamp measured against a stale value reads as the user scrolling up. **The one scroll that is not autoscroll** is the arrival mark: `messageStore.revealTargetId` names a turn another surface wants read (the story map's jump is the only writer), and `MessageList` hands it to the shared [`flashTarget`](../src/lib/utils/flash-target.ts), the app's single "look here" gesture, the same scroll and accent glow the assistant points with, never a second recipe of the transcript's own (architecture/chungus-assistant.md), then clears the id back to null. **What it flashes is the CARD** (`[data-message-card]` on the bubble, resolved from the row's `msg-<id>`), never the row: a row is as wide as the scrollport, so the scroller clips its glow left and right and the following turn paints over the bottom of it, leaving a bar along the top edge and nothing else. The effect reads the path as a dependency so a target named before its branch has rendered still lands, and a target whose row never appears (deleted between the click and the jump) clears itself after a beat instead of waiting to fire under a later, unrelated branch switch. It deliberately does NOT arm `programmaticScroll`: landing mid-history SHOULD release the bottom pin, which is exactly what the resulting scroll events do. `.message-list-wrap` carries `min-width: 0` so a wide expanded thinking block scrolls inside its own panel instead of stretching every row past the viewport. **The transcript is windowed, and nothing else is.** `MessageList` renders the newest `transcriptPageSize` turns of the active path (Settings → App → General, "Long Chats": `generalSettings.transcriptPaging` / `transcriptPageSize` / `transcriptLoadMode`, on by default at 100) and reaches further back on demand. What that buys is not only a faster open: every turn on screen is a markdown parse plus a card of DOM, and the pin-to-bottom logic re-measures the whole scroller on every streaming token, so an unwindowed long branch drags every reply after it too. Three rules hold it together. **The top edge is a pinned TURN, never a count back from the newest one.** A counted window slides forward with the story: every reply that lands pushes a turn off the top, and removing content ABOVE the viewport shifts everything a reader who scrolled back is looking at, on every single turn a long session generates. So the edge is pinned on arrival and from then on only ever moves EARLIER, which makes the whole rule one line: within a visit the loaded stretch only grows, and it grows at the end the reader is already watching. Leaving the chat is what resets it (the anchor is dropped on the way out, or returning to a story would quietly revive the stretch loaded last time while a detour through a third chat would not), and it is keyed to the chat the RENDERED path belongs to, never to `activeChatId`: selecting a chat sets that id and then awaits the load, so for one flush the store names the new story while the old one is still on screen, and an anchor written there would pin the next chat's window onto a turn from the last one. The pin is state rather than an effect that resets on chat change, because an effect runs a frame AFTER the new chat has already mounted, at the previous one's size, which is the exact burst this exists to prevent. The anchor carries its index beside its id, and falls back to it when the turn itself is gone (deleted, or a branch switch replaced that stretch): the index still states how far back the reader had reached, where collapsing to the base window would yank them forward instead. **Every index a message is handed is measured against the whole path**, never against the rendered slice: the `#N` ordinal, the depth a regex rule is scoped by, `isLast` and the memory-ghost prefix all count from the start of the branch, so a window that shifted them would renumber the story and re-scope every depth-bounded rule. **The clip is on rendering alone**: `allMessages` and the active path stay whole, so the tree, prompt assembly, the story map, the chats panel and the blast radii never see it. Two doors reach earlier turns and they hold scroll differently on purpose. The reader's own (`loadEarlier`, from the top-edge button or from scrolling within `LOAD_EARLIER_PX` of the top, whichever `transcriptLoadMode` says) holds the reading position, since the turns arrive ABOVE the viewport. Three things make that correction correct rather than nearly correct, and every one of them is silent when got wrong. It is **measured against a turn**, the first row still on screen, rather than computed from the scroller's total height, which also grows when a reply lands below while the load is in flight (the reader would then be pushed down by a message they were not even looking at). Measuring is also what makes it idempotent with the browser's own scroll anchoring, which does this same job on the engines that have it and is deliberately left ON: whatever it already fixed is not in the number, so the two can never double up, and `overflow-anchor: none` would trade a late-loading image shifting the story on Chrome and Firefox for nothing at all, since Safari has no anchoring and the manual correction is needed regardless. It is written through **`scrollTo` with `behavior: 'instant'`**, which is the ONLY value that overrides this scroller's CSS `scroll-behavior: smooth`: `auto` defers to that CSS, and so does a plain `scrollTop +=`, so either one ANIMATES the correction and the reader watches the entire stretch that just loaded fly past. The button load mode is where that shows, since the reader is parked at the top edge with no gesture of their own to cut the glide short. Every scroll write on this scroller that must land rather than travel takes the same value, find in chat's re-park after a load included. And it is **announced rather than kept private**: `onContentShift` hands the whole travel (ours plus anything anchoring did) up to `ChatContainer`, whose margin-wheel target is an ABSOLUTE scroll position, so a wheel that just reached the top edge would otherwise snap back to where the content used to start and load again on the next notch. Anything else that remembers a scroll offset across a load owes itself the same correction. Find-in-chat's door (`showFrom`, through the `loadThrough` prop) deliberately does not, because the bar parks the view on its own hit afterwards. A third case only looks like a door: an auto-mode window too short to fill the viewport has no scroll for the reader to ride, so it loads until the scroller has something to scroll, and reads its own height as the condition so it settles itself. It stands down on a zero-height scroller, which says nothing about fit and would otherwise load a whole chat with nobody looking, and it re-snaps a pinned reader afterwards, since those turns arrive ABOVE and no message landed to move them: without that the story finally overflows with the reader parked at its top. A turn pointed at from outside (`revealTargetId`) is loaded back in by that same call before the flash: a row missing because the window holds it back is the one case where it does not mean the turn is gone. Reaching far back renders everything below it too, since the transcript is one continuous scroll to the newest turn; that is the deliberate trade, and it is exactly what a story-map jump into deep history has always cost. **Find in chat** ([`ChatSearchBar.svelte`](../src/lib/components/chat/ChatSearchBar.svelte)) is a floating bar `MessageList` mounts inside that same wrap (the scroller is handed to it as a prop, which is why `listElement` is `$state` and not a plain `bind:this` let): open state + query + the Match case / Whole words options live in the satellite store [`chatSearch.svelte.ts`](../src/lib/stores/chatSearch.svelte.ts), deliberately NOT in uiStore's panel choreography, since the bar is inline chat chrome that must be able to sit open beside a docked Settings or Library. It is raised from the composer hamburger ("Find in chat…") and by Ctrl/Cmd+F in `Workspace.handleKeydown`, which takes the key off the browser's find only while a chat is on screen and no overlay covers it (the story map carries its own search). The search runs over the **rendered** transcript, not the stored rows: display regex rules, self-ref expansion and markdown are already applied on screen, so DOM matching is the only way the read text and the searched text agree, and it lets a hit span inline markup. [`utils/chat-search.ts`](../src/lib/utils/chat-search.ts) holds the pure matcher (`buildSearchRegex`, tested in `chat-search.test.ts`: literal escaping restricted to regex syntax characters because every other backslash escape is a SyntaxError under the `u` flag; Unicode letter/number lookarounds instead of ASCII `\b`, which never fires beside `ş` and so would make a whole-word search for "şey" find nothing while matching "eyler" inside "şeyler"; and the dotted/dotless i fold: Unicode pairs only I↔i, so without `[iıIİ]` a search for "kapı" silently misses "KAPI") plus `findMatchRanges`, which joins text nodes **per block** so offsets map straight back onto nodes and "Ali"/"Veli" in adjacent `<li>`s can't read as one word. Hits are DOM Ranges painted through the CSS Custom Highlight API, never `<mark>` injection: the message markup stays untouched, so `renderedHtml`'s ownership of that subtree, Copy and the `chatSelection` hand-off are byte-identical. Enter / Shift+Enter cycle, Escape closes and is consumed (shell Esc contract); the match pass writes its cursor under `untrack` so a jump can't re-trigger the DOM walk. Scope is the story text only, and matches are capped at `MAX_MATCHES` with the counter showing "N+" rather than truncating quietly. **The transcript window does not bound it**: a query loads back through its OLDEST match, so the counter, the highlights and the ∧/∨ cycle are always about the whole branch. That reach is a debounced scan (`EARLIER_SCAN_MS`) of the STORED rows above the window, which carries the same asymmetry the branch list lives with (no DOM up there, so a hit that exists only once a display regex rule has run is not seen from it), and it is debounced because find-as-you-type walks prefixes that match far more of the story than the word being typed. Two consequences the bar handles by hand. Until that scan comes back the counter reads "Searching…", never "No matches", which would be a verdict on turns the search has not reached yet. And the cursor is kept by NODE IDENTITY across a load rather than by its number: turns already on screen keep their nodes (the each block is keyed, `renderedHtml` patches in place), while ranges prepended above would slide a numbered cursor onto an older hit. **Off-path branches** (the swipes, alternates and abandoned forks that aren't rendered) are searched as a deliberately separate half: `findBranchHits` matches `allMessages` minus the active path against the same regex, over the STORED text: there is no DOM for them, so no Range and no markdown/display-regex resolution; callers expand `{{char}}`/`{{user}}` first, the same call and the same reason as the story map's search (greetings store their macros raw). They surface as a collapsible "N on other branches" list at the free end of the options row (its own cap, `MAX_BRANCH_HITS`, reported as "N+" the same way), each row a one-line snippet around the first match with the turn's branch label or speaker; clicking one calls `messageStore.navigateToBranch` and sets `pendingTargetId`, which the next match pass claims to land the cursor on that turn's first hit in the freshly rendered path (cleared unconditionally, so a jump that found nothing can't fire later). Reaching a branch is a **click, never part of the ∧/∨ cycle**: a navigation key must not rewrite what the reader is looking at. The bar is centred by auto margins between pinned edges, not `left: 50%` + `translateX(-50%)`: the `.fade-in` entry animates `transform` and would override the centring translate for its whole duration. On wide screens the centered column leaves empty margins flanking it; `ChatContainer` catches `onwheel` over `.chat-content` and forwards it into the `MessageList` scroller (exposed via a `bind:scrollEl` bindable) so the reader can scroll the story from anywhere. It self-limits: an open side dock covers its margin and eats the wheel first, and a chat-covering overlay makes `.chat-host` `visibility:hidden` (so pointer-events-inert): the forward only fires over genuinely empty margin beside a live chat; over the column itself the native scroller already handles it. **It also stands down over any box in the column that scrolls itself**, and this one is not optional: `.chat-content` wraps the **composer** too, not just the transcript, so a blanket `preventDefault()` eats the wheel of every scrollable thing down there (the composer textarea once the draft outgrows its 200px cap, the persona popover's list) and scrolls the story under it instead. `consumesWheel` walks from the event target up to `.chat-content` and bails on the first real scroller (`overflow-y: auto|scroll`, or a `<textarea>`, with `scrollHeight > clientHeight`). It costs nothing on the paths that matter: a wheel over the transcript returns on the `scrollEl.contains` fast path before the walk, and one over the margin has the stop element as its own target, so the loop never enters. Non-scrolling composer chrome (the button row, the meta strip) still forwards. **Message numbers** (`appearance.showMessageNumbers`, toggle on Settings → Layout): `MessageList` passes each turn's 1-based position on the visible path (`ordinal`) through `Message` into `MessageAvatar`, which renders a `#N` badge under the portrait, purely positional, so a delete renumbers everything below; not stored anywhere, and invisible in the Manuscript style since it hides the avatar column (the streaming indicator deliberately carries no number). Its siblings `showTimestamps`/`showModelName`/`showTokenCount` (same settings card) gate the meta row by passing null props from `Message` and `StreamingIndicator`: `MessageMeta` drops the date, and its generation info icon collapses once model and tokens are both null; the reasoning block's `~N tokens` readout in `MessageReasoning` rides its OWN knob, `showReasoningTokenCount`, deliberately independent of the message-level `showTokenCount`. **One pill in that row is a door rather than a readout**: a turn carrying a lorebook trace (`message.lorebook`, architecture/lorebook.md) gets a book pill counting the entries that reached its prompt, and clicking it opens the whole scan. It appears only where a scan actually ran, which `Message` decides and hands down: a turn that consulted no book at all has nothing to report, and a pill reading zero on every reply would be noise for everyone not using lorebooks. It hangs on the REPLY and never on the user turn above it, because a swipe is its own generation with its own rolls, so a pill on the request could only ever describe one of the attempts. **Each generation also names its own kind to the scan** (`lorebookTrigger`: a send is `normal`, either regenerate is `swipe`, Continue is `continue`), since an entry may be limited to some of them and only the caller knows which one is running; a new generation that leaves it out silently reads as a plain send. The token gates sit BEFORE the lazy deriveds on purpose, so the per-message, per-stream-tick, and reasoning-text `countTokens` estimates are all skipped entirely while hidden. **Message card appearance** (Settings → Chat, architecture/ui-shell-settings.md): `Message`, `StreamingIndicator`, `MessageAvatar` and `MessageMeta` carry **no** appearance state of their own: every knob arrives as a `--msg-*` / `--prose-*` / `--avatar-*` custom property, and each declaration keeps the shipped value as its `var()` fallback so the transcript paints right before the theme store boots. Three consequences worth knowing before editing that CSS. **One**: `StreamingIndicator` duplicates the whole card recipe (radius, notch, border, shadow, padding, tail) because the live turn must be indistinguishable from the row it becomes: a var added to `.message-bubble` and forgotten on `.stream-bubble` shows up as the bubble visibly changing shape the instant a reply finishes (coupling 10). **Two**: `showAvatars` off (and Manuscript, which never drew one) removes `MessageAvatar` from the DOM in JS, not by CSS, because the `#N` ordinal and the generation timer live under the portrait, and a visibility toggle that silently kills two OTHER visibility toggles is a lie. `Message`/`StreamingIndicator` derive `avatarsHidden` and hand `ordinal`/`durationMs` to `MessageMeta` instead, which renders them inline; the meta row itself disappears entirely (`hasContent`) once nothing is left to show, rather than leaving a bare strip of padding over the prose. **Three**: knobs a chat style can't honour are hidden in Settings rather than left inert, so the CSS only has to suppress what a style genuinely owns: Manuscript keeps its own speaker label whatever `speakerLabel`/`speakerCaps` say, which is why those rules sit **before** the manuscript block in `MessageMeta` (same specificity, so source order decides). The same source-order trick carries `compactActions`: `MessageActions` reads `--msg-action-label`/`-pad`/`-gap`, and the ≤900px rule sets those same properties later, so phones stay icon-only whatever the setting is.

**The card outline lives on the SHELL, not the card** (`.message-bubble-shell::before`), and this is load-bearing: the ring paints ABOVE the card, which is the only reason it survives the Portraits style, whose card must keep `overflow: visible` for its sticky portrait. So `.message-bubble` keeps a **transparent** border of the same width purely to hold the box model, plus `background-clip: padding-box` so its translucent fill stops at that border rather than stacking with the ring into a denser edge. Consequences: the ghost's dashed treatment and every per-style radius override target the ring, not the card, and a style that wants a different silhouette moves the ring's corners alongside the card's.

**Chat styles** are four `data-chat-style` values stamped on `<html>`, and only three of them change the card. **Bubbles** is the base every rule is written against. **Flat** is Bubbles with the user turn un-mirrored and nothing else: `.message-main-user`/`.message-rail-user`/`.message-toolbar-shell-user` stop reversing, the user tail moves to the left edge with its borders, and the tight notch moves from the top-right corner to the top-left so it still sits nearest the tail. Same cards, same colors, same portrait column, both speakers on the left, which is why Settings gates card knobs on `bubbleLike` (`bubbles || flat`) and `StreamingIndicator` needs no Flat block at all (it only ever renders an assistant turn, which was already left-aligned). **Portraits** and **Manuscript** are the ones that restructure: a two-column card with a sticky in-card portrait, and no card at all, respectively. A rule keyed to `.message-*-user` in the base block is a rule Flat probably has to undo. Check it there before assuming Bubbles is the only mirrored style.

**Message timer** (`showGenerationTime`, same card): `generateResponse`/`generateOpeningScene` clock the `llmService.complete` call alone (no db awaits) and persist it as `messages.generation_ms` through `createMessage`; `MessageAvatar` renders the formatted readout under the portrait, stacked below the `#N` ordinal (alone when numbers are off or while streaming), from a `durationMs` prop: the saved value on `Message`, a 100ms-interval live elapsed in `StreamingIndicator` (ticking against mount time, which coincides with request start; the interval doesn't run while the knob is off). Like the ordinal it's invisible in Manuscript (no avatar column). Greetings, imports, dummies and user turns stay NULL. UI behavior here has no test coverage: the user tests manually.

**Story map surface.** **The map reads and navigates the tree; it never writes a turn.** There is no editor, no branch-from-here and no delete on this canvas: rewriting and removing turns belongs to the transcript alone, where the memory price of an edit or a delete is measured and confirmed before it is paid (coupling 3, architecture/memory.md). The only rows the map touches are its own annotations, the chat's `canon_leaf_id` and a message's `branch_label`, plus `active_leaf_id`, which is navigation. A control added here that changes what a turn *says* or whether it exists is the thing this rule exists to keep out; put it on the message instead. **Every message gets a node**, and a swipe nobody continued from is not an exception. It is tempting to fold childless siblings into the turn beside them (most rows in a played chat are re-rolls, and the map would shrink a great deal), and it is wrong: a swipe can be edited into something the story says nowhere else, and even an untouched one is the start of a branch that simply hasn't been written yet. Folding them draws a chat full of swipes as a single line, which is a picture of a story the user does not have. **The header counts the way the chats panel counts**: turns on the CURRENT branch (`onActivePath`, i.e. exactly the transcript's length) and the number of branches, each labelled, never the raw node total. A sixty-turn story whose forest holds 244 rows reading as "244 turns" is the same lie the chats panel's two labelled counts exist to prevent. `StoryMapView` keeps the shell's shared stacked utility-overlay header (subject: the chat, facts: the two labelled counts) and puts **nothing else in it**. Every map control lives ON the canvas as floating `.surface-float` chrome: labeled-branch bookmark chips plus the transient strip (search bar / compare-pick banner) stacked in a top column so they can never overlap, legend bottom-left (hidden ≤640px), and a bottom-right corner cluster (the search toggle, then zoom −/%/+, fit, center-on-current, minimap toggle + `StoryMapMinimap`, which auto-shows above 30 nodes on non-phones). The search toggle sits with the other tools rather than in the header for that reason: one place holds everything that acts on the canvas. **Branch names on the canvas are DOM, not SVG** (`.map-labels`, a pass-through layer that only its chips take the pointer on): SVG text has no ellipsis and no metrics, so the pill had to be sized from a guess at character width and every string the guess wasn't tuned on came out mis-sized and off its node, and scaled with the canvas the name shrinks to nothing at exactly the zoom a long story is read at. Anchored to the node's screen position, centred by `translateX(-50%)` on the browser's own measurement, constant size at every zoom. The canvas pans by left drag or middle drag (middle is pan-only: it starts already "moved" so no node is ever selected, and a `mousedown` handler cancels Chromium's middle-click autoscroll) and by two-pointer touch pinch (third state next to pan/click in the pointer handlers: a second finger kills the pending click, and lifting back to one finger re-baselines the pan). **What a plain wheel does is the user's choice** (`generalSettings.storyMapWheelPans`, default off, Settings → App → General): on it pans both axes, off it zooms around the cursor. Two gestures are fixed in BOTH modes and that is what makes the setting safe to flip: ctrl/⌘+wheel zooms, shift+wheel pans sideways. The ctrl half is not a courtesy: a trackpad pinch reaches the page as ctrl+wheel, so pinch-to-zoom would die with the setting if the modifier followed it. Two conversions hang off the same handler. **Deltas are normalized to pixels before a pan** (`wheelPixels`, the conversion `ChatContainer`'s margin wheel already uses): Firefox reports a mouse wheel in lines, and unconverted a notch nudges the canvas three pixels. And **the zoom rate is picked by the delta's own size, never by the modifier**: a pinch streams tiny deltas where a notch sends one big quantized jump, and with panning on, ctrl+wheel is a mouse's only zoom, so keying the fast pinch rate off `ctrlKey` would swing the view several times over per click. Misreading the size only makes a zoom faster or slower; it can never turn a gesture into the wrong action, which is why size is a legitimate signal here and device-sniffing to decide pan-vs-zoom is not. **A dot's size is how much was written at it** (`rOf`, square root over content length so turns running from a dozen characters to several thousand don't all bottom out at the same circle): every marker the node wears reads it (the halo, the crown's height, the branch name's offset, and the edge endpoints, which stop at each end's OWN radius). **Canon is drawn once, not twice**: the gold path and the crown on its tip say it, and a ring around every node on that path only competes with the halo that marks where the reader actually stands (a canon root with no gold edge touching it still wears the crown, so nothing goes unsaid). **Every stroke on the canvas is a screen weight** (`vector-effect: non-scaling-stroke` on edges, node rings, halos, the fork pip and the focus ring): scaled with the view, a 1.8 line is under a pixel at any zoom showing more than a few turns, so it anti-aliases away and a branch whose connector has vanished reads as a dot floating loose beside the story. A map of identical circles is a diagram of pointers; sized, the story's rhythm is in it. Turns the memory engine has folded are ghosted the way the transcript ghosts them (`memoryStore.archivedMessageIds`, so it is empty unless the active preset injects `{{memory}}` and never reaches off the active path), and the inspector says "In memory" beside them. Attachments are named in the inspector and deliberately NOT drawn on the canvas: a fifth marker on a 30px dot is clutter. Nodes carry an oversized invisible hit disc (~44px touch targets, doubles as the focus ring) and a roving tabindex: arrow keys walk the tree (up = parent, down = child preferring the active path, left/right = siblings), +/−/0 zoom/fit, and Enter / double-click / the inspector's "Open in chat" all jump: `messageStore.navigateToBranch`, `uiStore.closeOverlay()`, then `messageStore.revealTargetId = id`, deliberately landing the user in the chat (double-click is suppressed for touch; the inspector button is the touch path). **Naming the turn is not optional**: navigation reaches a BRANCH, by its deepest leaf, so a jump from a mid-story node would otherwise drop the reader at the end of a timeline they have never read, at whatever scroll offset the previous branch left behind, with nothing on screen saying where the turn they picked went. Selecting a node opens `StoryMapInspector` (a floating card, bottom sheet ≤640px), and the view auto-pans the node into the rect the card doesn't cover (`safeBox`/`ensureVisible`). **Bookmark chips and search-match cycling center instead** (`centerOn`), and centering also pulls the scale into the `FOCUS_K_MIN`…`FOCUS_K_MAX` band: a jump that only panned left the target an unreadable speck whenever the view sat zoomed out over the whole forest. A scale already inside the band is left alone, so the clamp can't fight a framing the user chose on purpose. `centerOn` sets `userMovedView`, which is what stops a later resize re-fitting the forest and throwing the focus away. The inspector is a single read view (its label draft re-seeds only on a node-**id** change, so graph refreshes from sync/streams can't eat in-progress typing): the turn's text, time/variant/model/token chips, "Open in chat", canon toggle, the branch-label editor, and "Compare…" which arms pick mode: the next node or bookmark-chip click is the second branch, and the banner offers "Use current path" when the anchor is off-path. Search dims non-matching nodes (matching runs over self-ref-expanded content + label names) and Enter/Shift+Enter cycles matches. Escape backs out one layer per press: compare pick → search → selection. Each consuming press calls `preventDefault` so the workspace doesn't also close the panel (shell Esc contract in architecture/ui-shell-settings.md); the map stands down while the compare modal owns the key, and Esc inside the inspector's name field only blurs it. Every preview surface (inspector, hover card, search) expands `{{char}}`/`{{user}}` live like `Message.svelte` (coupling 6); display-scope regex rules deliberately do NOT apply here (they stay pinned to Message/StreamingIndicator); every time on this surface goes through `formatMessageTime` like any meta row, so the map obeys the same Message Details settings (coupling 10). **The canvas holds no fixed hue**, here or in the compare modal: the reader's own turns wear `--color-accent`, the story wears `--color-text-secondary`, canon wears `--color-warning`. A map painted in a colour nobody picked is the one surface ignoring the palette behind it. Role chips are tinted rather than filled for the same reason: a solid pill needs a text colour that reads on every role hue in every theme, and no single value gives that. **Opening the map is not the same question as Fit** (`computeOpeningView`, used by the per-chat reset and by a resize, while the Fit button and `0` stay a true fit): fitting a sixty-turn story into a phone screen is arithmetic, not a view. It lands at a few percent, where the tree is a column of specks and the reader cannot tell which one they are on. So a fit that would land under `DETAIL_K` is replaced by the reader's own position at `FOCUS_K_MIN`, with the shape around it. `DETAIL_K` is the one line between "a document" and "an overview" and it also drops the on-canvas branch names, which the bookmark bar carries at that zoom. A resize re-applies the opening view only until the user pans/zooms by hand. View animations run through one rAF tween (`animateView`) that respects `data-motion='reduced'`/`prefers-reduced-motion`. That tween has two coupled rules and they stand or fall together: **scale interpolates geometrically** (a linear `k` swings the perceived zoom rate mid-move, so the view lunges then crawls), and **the pan is rebuilt each frame from the world point under the stage centre** rather than lerped from `tx`/`ty` (which are pixel offsets that mean something different at every scale: under a geometric `k` a linear `tx`/`ty` bows the target's screen path instead of running it straight). Its duration is not fixed: `moveDuration` scales it with the distance actually travelled and the zoom ratio, clamped, so a nudge to the next turn stays snappy and a flight across the forest doesn't read as a cut.

## Chats panel

The browser over the chat list ([`ChatsView.svelte`](../src/lib/components/sidebar/ChatsView.svelte), rows in [`ChatListRow.svelte`](../src/lib/components/sidebar/ChatListRow.svelte), the right half in [`ChatPreviewPane.svelte`](../src/lib/components/sidebar/ChatPreviewPane.svelte)). Everything a row shows beyond the `chats` row itself is a **server-side aggregate**. No message text crosses the wire for the list: `getChatListStats` (per chat: `path`, `total`, `lastAt`), `getChatContentGroups` (identical-chat fingerprints), `searchChatMessages` (opt-in message search), `getChatMemoryFootprint` (what a duplicate would carry). All four live in the "CHAT LIST AGGREGATES" block of `server/db.ts` and are reads, so they carry no sync scope.

**Scope is a switch, not a consequence.** A two-way segmented control under the header picks between the open chat's character and every chat there is, and it writes into `scopedCharacterId`: the SINGLE derived the list, the face each row wears and the New chat button all read, so the panel can never list one thing while its button means another. It is what makes every chat reachable from inside a story without going home first. The choice lives in `uiStore.chatsScope` beside `libraryTab`, kept across opens because a switch that resets on every visit is one the user re-flips on every visit; it names a KIND of scope and never a character, which is what lets it survive walking from one story into another, and it is a preference rather than a binding, so a panel opened with no character on screen lists everything whatever it says. Four rules hold it together. The switch is gated on the library entry **resolving**, not on the chat's character id: a chat orphaned by a character deletion keeps a dangling id, and scoping to that narrows the list to a character with no name, no face and nothing on screen saying why. Those chats browse globally. With no character there is exactly one possible scope, so the switch is hidden outright rather than shown with a permanently dead half, which is a label dressed as a choice. The header title is always "Chats", because the character's name lives in the switch and a title that shape-shifted into it would say the same thing twice, in only one of the two scopes. And a flip empties the held preview and resets the selection like any other filter change: the effect reads `scopedCharacterId` rather than the switch, so the character vanishing from the library under an open panel is covered by the same line. One consequence downstream: the duplicates filter's toggle stays rendered while its own filter is on even once the scope holds no twins, or a flip takes away the only control that can turn it back off.

**Importing chats onto a character** ([`ImportChatsDialog.svelte`](../src/lib/components/sidebar/ImportChatsDialog.svelte), raised by the header's icon button beside New chat). One or more `.jsonl` files are picked, read in the browser, and each lands as its own chat through the same `chatStore.importSillyTavernChat` the folder import calls; **no format logic lives in the panel**, the header is read by `readChatCharacterName` and the tree is built by the store. **The scope IS the target and there is no character picker**: the button renders only while `scopedCharacterId` holds somebody, every file lands on them, and the alternative is a dropdown over a library that runs to thousands of entries, which is a list nobody can find anything in. Scoped to everything there is nobody to import onto, so the button is hidden rather than shown inert, the same rule the rest of this panel follows. The target is **captured at the pick** and carried into the dialog rather than read live, so a scope that moves underneath cannot move where the files land. What each file names in its own header is still read, but only to **flag a file played with somebody else** before it lands: display-name matching is what the folder importer refuses to do unattended (architecture/sillytavern-interchange.md coupling 8), and a warning the reader can act on is not a bind. A file that names nobody is not flagged, since it has nothing to disagree with. **The pick is never claimed in the import ledger**: the reader named these files themselves, so picking one twice is two copies by intent, not the duplicate the ledger exists to prevent. Failures keep the dialog open and shrink the list to what did not land, so a retry cannot re-send what already arrived; an unreadable file is held apart from them, because it has no row to retry from and would otherwise be cleared by the next clean run. A run with nothing left over closes the dialog and **toasts the count**, since imported chats carry the dates they were played and sort into the middle of a list the reader is not looking at.

**Row anatomy**: face, title (+ the twin chip), a relative time under it, the two counts stacked at the right edge, and an always-visible row menu. The time is `lastAt`, the active leaf's own timestamp, NOT `MAX(created_at)` over the chat, which would let a swipe written on an abandoned branch date the branch you read. There is no last-message preview line: the only text a row ever carries is the snippet `searchChatMessages` cuts around a hit, shown beside the time so a search result can say why it matched. The favorite **action** lives only in the row menu; the row itself shows a star as state (`.chat-row-star`, drawn with the `heart` glyph).

**Two counts, both labelled.** `path` is the branch a reader would actually read (root→`active_leaf_id`, walked in one recursive CTE); `total - path` is everything hanging off it: swipes, alternate greetings, abandoned forks. The row stacks them (chat glyph over branch glyph, each with its own tooltip) and the preview header says "N messages on this branch". This is not cosmetic: `total` in the row and the active path's length in the preview, both unlabelled, make one chat read as 61 and 57 at once. Any new count here states which of the two it is.

**Favorites** are `chats.is_favorite` (same shape as `character_library.is_favorite`). `updateChatFavorite` / `chatStore.toggleChatFavorite` deliberately never touch `updated_at`: starring is bookkeeping, and bumping activity would reshuffle the list under the user's cursor. Favorites float into their own section above the day buckets whatever the sort, except when the Favorites filter is already on.

**Duplicate** is one server transaction (`serverDb.duplicateChat`), never a client-side loop: the chat row, the whole message forest (fresh ids, parent-first insert, same `sibling_index`/timestamps/branch labels), and the remapped `root_message_id` / `active_leaf_id` / `canon_leaf_id`, plus `settings_json`, the pinned `character_version_id` and `feature_state`. A row that turns out not to be reachable from a root fails the whole copy rather than leaving a silent partial one. The chat's own **steering notes** are re-minted under fresh ids bound to the copy (`scope = 'chat'` only: notes at the global/character/version scopes already apply to the copy through their own binding, and copying them would double-inject). Attachment paths are copied verbatim: chat images are reference-counted, so two rows sharing a file is the designed state (`dropOrphanedChatImages`). **Not** copied: `is_favorite` (a star is about the original) and the composer draft. **Memory is opt-in**: `ChatsView` asks `getChatMemoryFootprint` first and only raises `DuplicateChatDialog` when there is something to carry; saying yes runs `copyChatMemory`, which remaps every message reference in `memory_episodes` through the same id map (`source_message_ids`, `anchor_message_id`). Memory still pointing at the source's rows would resolve its coverage against a tree it no longer belongs to (architecture/memory.md). There is no cursor to remap: the copy's archive boundary derives from the copied episodes' own coverage. A reference that does **not** remap (the source's memory anchored to a message that has since been deleted) makes the whole copy **throw** `mem-copy-stale` and roll back, and the panel says so: mapping those to NULL would not reproduce the source's state, it would invent a different one that is internally valid and therefore never heals. An episode whose coverage silently shrank still claims the turns it lost, so the copy would recall a stretch it is also sending verbatim, forever. The source repairs itself on its next open; the copy would not. The memory SELECTs are `ORDER BY rowid` so insertion order survives a `created_at` tie in the copy: `memListEpisodes` breaks those ties by rowid, so reading in index order would silently re-order same-millisecond rows (architecture/memory.md coupling 6). `chatStore.duplicateChat` names the copy `<title> (copy)`, counting up on collision, and deliberately does **not** open it.

**Identical chats** are found in two stages (`getChatContentGroups`): an aggregate signature in SQL (row count + total content length) narrows the field without reading a byte of content, and only chats that collide on it get hashed. The hash is structural (a node's digest folds in its children's digests, ordered by `(sibling_index, child digest)`), so it is independent of row ids and insertion order, which a copy never reproduces; timestamps are deliberately excluded, so "same story, same text" is the whole test. Attachments are part of the digest (same words over different pictures is a different chat); `thinking` is not (reasoning is the model's scratch paper). Two never-played chats of one character genuinely ARE identical (same seeded greeting, same tree), so they get chipped too; that is the definition working, not a false positive. Chats in a group wear a count chip; hovering it lights every twin, and a filter chip narrows the list to them.

**Search** is two-state by design. Titles always match locally through `buildSearchRegex` (the same case-folding matcher find-in-chat uses). The toggle in the field adds message text, debounced 250ms into `searchChatMessages`, which searches **only each chat's active branch**: off-path hits would need a branch jump to reach, and a result you can't see is worse than no result. Its case fold (`SEARCH_FOLD` in `server/db.ts`) is applied identically in SQL (`foldSearchSql`, to narrow) and in JS (`foldSearchText`, to decide), stops at ASCII + the dotted/dotless i family and five more letters because SQLite's `LOWER()` is ASCII-only, and is one-character-for-one so a match offset still points into the untouched content for the snippet window.

**Preview pane.** Hover-driven: it opens **empty**, fills with the first row the pointer touches, and **holds that row** until the list changes under it: a query, a filter, a sort, an emptied list, or the previewed chat itself going away. It deliberately does **not** clear on the way out of a row, and that is the whole reason the pane is usable with a mouse: the trip from a row to the pane crosses the list's own padding, its scrollbar and the section labels, so a pane that empties on any of those is blank by the time the pointer arrives, and its action bar (the only copy of the row actions a mouse can reach, since rows are arrow-driven) can never be pressed. Whether it renders at all is decided by the **panel's measured width** (`singleColumn`, `bind:clientWidth`), never by a viewport media query: the panel is a fixed-width modal on desktop and a full-width overlay on phones, so a window-width query describes neither, and a CSS `display: none` would leave the pane mounted and invisible, fetching a whole chat on every row hover and holding the only tabbable copy of the row actions. The threshold is the panel body's own width (`TWO_PANE_MIN`, 640px: the two columns need 17rem + 20rem to breathe). It opens at the END of the story (the only question a preview answers is "where did I leave off"), renders in windows of 20 turns and grows upward as the reader scrolls, restoring scroll position by the height it added, which is why the scroller carries `overflow-anchor: none`, or the browser's own anchoring adds a second correction on top and throws the view a window forward. Paths are cached per `(chatId, activeLeafId)`, so a branch switch elsewhere can't serve the branch the reader left behind. Self-refs expand here exactly as in `Message.svelte` (coupling #5), with the CHAT's persona, not the app-wide active one, since this is a look at someone else's story.

**Keyboard and reach.** The search field and the list are one combobox: focus stays in the field, `aria-activedescendant` names the selected row, and ↑/↓/Home/End/Enter drive it from the window handler. Those keys are bound on the **window**, so they are gated by `listKeysActive()`: the list only gets them when nothing else has focus (the check is "is the focused thing an interactive control other than the search field"). Without that gate the handler ate every Enter in the app: pressing Enter on the preview's own Delete button opened a chat instead, and Enter in the assistant widget's composer sent the message AND opened whatever row the selection sat on. Escape is deliberately ungated. It closes layers, one per press: row menu, sort menu, rename, a typed query, then the panel. Rows and their actions are NOT in the tab order (tabbing through 200 chats to reach one is not reach), so the row menu is opened by the standard **ContextMenu / Shift+F10**, and every row action also lives in the preview pane's action bar. No destructive key is bound: focus lives in a text field, where Delete means "delete a character". The modal wrapper in `Workspace.svelte` carries `role="dialog"` **without** `aria-modal` on purpose: nothing outside is made inert, and claiming modality no focus trap backs up only lies to a screen reader.

- Read this + architecture/prompt-pipeline.md (generation) + architecture/memory.md (which tree mutations cost summaries and which are free) first; deletes also interact with chat-image ownership (architecture/chungus-assistant.md "Attachment lifetime").
- The Chungus Assistant holds three server-side replicas of this subsystem's client logic (architecture/chungus-assistant.md): `create_chat` mirrors `createChat` + `seedCharacterGreetings` (title format, version pin, raw greeting seeding, insert ordering), `add_steering` inserts a `steering_notes` row (architecture/engines.md), never `feature_state` (so `feature_state`'s "the server never parses it" contract holds without exception), and `activePathMessages` re-walks root→`active_leaf_id` the way `buildMessageTree` does, which is what every assistant read, every `seq` number and its off-branch write warning are measured against. Changing the chat-creation recipe, the title format, the steering-note shape, or how the active path is resolved must update those replicas too, except the greeting LIST, which `create_chat` takes from the db module's own `chatGreetingsOf` rather than copying, because `refreshSeededGreetings` recognises a chat by exactly the rows that list produces (coupling 12).
- Every tree mutation goes through `messageStore`/`chatStore` methods: never call `db.*` tree methods from a component, and check `warnIfBusy()` semantics before adding a new mutation path.
- Deletes are the most delicate area: attachment ownership, canon repair, active-leaf re-homing, root recompute. Trace one existing delete path end-to-end before writing a new one.

**Bulk import** (`chatStore.importSillyTavernChat`): builds a whole chat + message tree in one shot from a SillyTavern `.jsonl`, the same store-owns-the-tree pattern as `seedCharacterGreetings` (insert chat with null root/leaf → insert parent-first messages → `updateChat` sets root/leaf). The pure ST→tree map lives in [`sillyTavernChatImport.ts`](../src/lib/services/sillyTavernChatImport.ts) (`convertSillyTavernChat`, tested): each ST message emits one node per `swipes[]` entry as siblings and the ACTIVE swipe (`swipe_id`) is what the next message parents onto, so the played timeline is the active path and unpicked swipes hang off as dead-end leaves; `reasoning`→`thinking`, per-message `personaId` left null (the documented "untracked" value). **`is_system` is deliberately NOT skipped**: SillyTavern flips it true to hide/ghost a message from the prompt, but those are real conversation turns: dropping them silently deletes history. They import as normal visible turns with role from `is_user` (ChungusHub has no per-message hide-from-prompt flag). It has **two callers and they resolve the character differently**: the folder-level orchestration that feeds it in bulk ([`sillyTavernFolderImport.ts`](../src/lib/services/sillyTavernFolderImport.ts), matching a chat's folder name to an imported card's avatar-filename stem, see architecture/ui-shell-settings.md (Import page)), and the Chats panel's own picker, where the reader confirms the target on screen (above).

## Hand-kept couplings

1. Sibling navigation is **role-agnostic by design**: `findSiblings` returns every child of the parent, so the chat arrows/counter walk ALL branches at a point (same-role variants and different-role forks alike) and must keep matching the story map's unfiltered numbering (`buildMessageTree.siblingCount`). A role filter here makes spliced branches invisible outside the map; don't add one. Delete re-homing PREFERS a same-role sibling before any-role, but that preference lives in `messages.svelte.ts`, not in `findSiblings`. **A well-formed tree does not grow a mixed set directly**: both routes that would mint one are shut. A splice at a fork is refused outright (coupling 3), and **Generate/Retry are offered only on the LAST turn of the path** (`showRegenerate` in `Message.svelte` is gated on `isLast` for BOTH roles). The second is the less obvious half: "add alternate reply" on a mid-story user turn would fork a second reply under a turn that already has a child, so once a splice has parked a user turn there, the two become swipe variants of each other. To re-roll from further back the user branches that turn instead (the Branch action: the fork becomes the leaf, and Generate is offered on it), which keeps the escape hatch without the mixed set. Indirect routes remain (a lone child spliced away leaves a same-role parent/child pair a later regenerate can fork beside, see `canSpliceMessage`), and imports and older chats already carry mixed sets, which is why the walk stays role-agnostic; don't "clean them up" behind the user's back.
2. Every delete is final, chats included: no grace window exists anywhere for rows or files, and the gate is the confirm BEFORE the act (the destructive-act ladder, architecture/ui-shell-settings.md). `deleteMessageAndDescendants` collects attachment files in the same call and `deleteChat` sweeps rows, attachment files and chat-scoped steering notes in one server call (file-side contract in `server/db.ts`), so nothing may assume a grace window for either. A deferred delete must not come back: its timer dies with the page and the row resurrects on the next boot, while every other device keeps showing the chat for the whole window. The no-undo scan in `contracts.test.ts` holds this.
3. `subtreeBlastRadius` drives the confirm-dialog copy in `Message.svelte`. Keep counts honest if delete semantics change. **Memory is the second blast, and only `Message.svelte` measures it.** Deleting one summarised turn kills the summary over it and parks every summary behind it until a re-read closes the hole: real work a single-row delete has no other way of announcing, which is why `this_only` confirms at all when it costs memory. `Message.svelte` asks `memoryStore.impactOf` for the exact numbers, renders them under the message count, and sizes the press-and-hold by `messages + turns re-read + summaries paused` rather than the row count alone: one summarised turn is a heavier act than one loose reply and the gesture should say so. The copy branches in [`impact-copy.ts`](../src/lib/memory/impact-copy.ts), whose rules are in architecture/memory.md. **Every delete surface owes these numbers before it ships**, or a summarised turn goes with nothing said about what it cost. There are two: this one, and the Chungus Assistant's `delete_entity`/`edit_entity` on messages, which asks `memoryCostOfMessageChange` (architecture/chungus-assistant.md), the same `changeImpact` + `impact-copy` pair, so the two cannot word the same act differently. It also decides the delete menu's **shape**: when the `includeSelf: false` radius is zero the turn is a leaf, so "delete this only" and "delete with all responses" remove the identical single row, and the menu collapses to ONE delete rather than offering a choice with a single outcome (a menu that still names responses under a turn that has none reads as a lie about the tree). The collapsed row sends `this_only` deliberately: `allMessages` is a snapshot (coupling 4), so if a reply landed since it was taken, a splice costs one row where a subtree delete would take the whole branch with no confirm. The second shape rule is [`canSpliceMessage`](../src/lib/utils/message-tree.ts) (tested): a message that **heads a branch** (has siblings) may only be spliced while nothing hangs below it, so with descendants the menu drops "delete this only" and offers the whole-subtree delete alone. A splice merges the turn's children into its PARENT's child set, and at a fork those two sets hold opposite roles (the branches beside it answer the same turn it answers; its own children answer IT), so the merge leaves a swipe position reading user turn, then reply. Note this closes the direct route only; see coupling 1 for the ways a mixed set still arises, which is why sibling navigation stays role-agnostic. `Message.svelte` renders both shape rules; a second delete surface has to repeat them. The rule itself is **enforced in `serverDb.deleteMessageOnly`**, which throws on a branch head that holds replies, so every caller inherits it: the client store over RPC, the assistant's `delete_entity` (architecture/chungus-assistant.md), and anything added later. `canSpliceMessage` exists so the menus don't offer what the db would refuse; it is not the guard. Asserted from both doors in `server/assistant/registry/smoke.ts`.
4. `chatStore.currentChatState.allMessages` is the snapshot every mutation validates against: long operations must re-fetch (`db.getMessagesByChat`) rather than trust it.
5. Self-ref (`{{char}}`/`{{user}}`) expansion happens live, never baked into rows: display in `Message.svelte`, the story map's preview surfaces (`StoryMapView` inspector/hover/search), find-in-chat's off-path branch hits (`ChatSearchBar`), and both chats-panel surfaces (`ChatsView` row snippets, `ChatPreviewPane`), five call sites in all, and generation in `prompt-assembly.toInjectedMessage` + `renderTranscript` (macros.ts) must expand the same way, or the on-screen text and the sent prompt drift. A new surface that renders stored content owes the same call; the macro vocabulary itself is architecture/macros.md. Greetings are seeded raw (`chat.svelte.ts`); nothing re-bakes them. Every one of those five is a read-only surface, so none of them can bake an expanded name back into a row.
6. Find-in-chat has two hand-kept ends: the `data-search-text` attribute on the prose container in `Message.svelte` is the ONLY thing `ChatSearchBar` selects on (drop it and the bar silently finds nothing; it must stay on the story text and stay off the meta row, toolbar and token readouts), and the highlight registry names `chat-find` / `chat-find-current` in `ChatSearchBar` pair with the two `::highlight()` rules in `app.css` ("Find in chat"). Those rules cannot move into the component: CSS highlights are document-scoped by definition, and `::highlight()` honours only colour, background-color, text-decoration and text-shadow. No box properties.
7. `BranchCompareModal` is read-only in both its modes (side-by-side diff, side-by-side prose), and its `allMessages` read stays reactive so a turn edited in the chat behind it re-diffs live. It must not grow a write: cherry-picking a paragraph across branches is an in-place rewrite of a turn that is very often off-path and already folded into memory, and the modal has no room to state what that costs (coupling 3). Copying text out and pasting it into the transcript's own editor reaches the same result through the door that does the accounting.
8. `duplicateChat`'s message copy and `copyChatMemory` share one id map by hand: a column added to `messages` must be added to the copy's INSERT (or it silently vanishes from every duplicate), and a new memory column holding a message id must be remapped there (or the copy's memory points into the source's tree). Remapping is fail-loud by design: `remapMsgId` throws `mem-copy-stale` rather than defaulting to NULL, and `ChatsView` turns that into the "open the chat once" toast, so a new id column must not be given a silent fallback. The gate is right for MESSAGE references and ONLY for them: a provenance column whose ids are not guaranteed to survive must stay out of the remap, or the first duplicate of a chat holding a dangling one throws and rolls the whole copy back. `server/chatList.test.ts` asserts no source id survives a copy, and that a stale anchor refuses the whole copy. Extend both with the column.
9. `StreamingIndicator` mirrors `Message`'s card CSS by hand (`.stream-bubble*` ↔ `.message-bubble*`): the same `--msg-*` vars, the same fallbacks, the same per-chat-style overrides. It is a deliberate duplicate, not an oversight (the two render different content trees), but a card property changed in one and not the other makes the bubble jump the moment a stream lands.
10. Timestamps and durations format through [`time-format.svelte.ts`](../src/lib/utils/time-format.svelte.ts) only, never `toLocale*` at a call site: the locale is always the browser's (an `en-US` date beside prose in another language reads as a bug, which is what this module exists to prevent), and `hour12` is left `undefined` unless the user explicitly picked 12 or 24. Relative labels read `relativeClock.now`, ONE module-level 30s tick shared by every meta row: components must not add their own interval, and reading it outside the `format === 'relative'` guard would drag absolute rows into a re-render they don't need.
11. The chats panel's message search folds case in two places that must agree: `foldSearchSql` (narrows in SQLite) and `foldSearchText` (decides in JS), both driven by the one `SEARCH_FOLD` table in `server/db.ts`. Widening the JS side alone makes the decider accept rows the SQL pass already threw away, i.e. results that depend on which query term happened to be longest.
12. **The greeting list is built in two places and they must build it identically**: `chatStore.seedCharacterGreetings` (what a new chat lays down) and `chatGreetingsOf` in [`server/db.ts`](../server/db.ts), which is BOTH what `refreshSeededGreetings` rewrites a chat to and what the assistant's `create_chat` seeds from. The assistant deliberately holds no copy of its own, though it replicates the rest of the creation recipe. Same order (First Message, then every alternate), same trim, same drop of empties. The remaining pair cannot be collapsed: one is a client store, the other server-side. A divergence is silent in the worst way: a chat seeded under one rule records a claim its own rows do not match, so the card never reaches it again and nothing anywhere says so. A new trait that seeds a chat (`seedsChat` on `PERMANENT_TRAITS`, architecture/library.md) has to land in both.
13. **Every path that lays greeting rows down must record the claim beside them** (`setChatSeededGreetings`), in the same transaction-shaped moment: `chatStore.seedCharacterGreetings`, the assistant's `create_chat`, `refreshSeededGreetings` after its own rewrite, and `duplicateChat`, which copies the source's claim along with the rows it copies. Rows without a claim are inert (the chat simply never follows the card), so forgetting it in a new seeding path is a feature that silently does nothing rather than a crash. The reverse (a claim without matching rows) is harmless by construction: the match fails and the chat is left alone.
14. **The transcript window is a rendering budget, not a scope.** `MessageList` clips what it draws (see the window paragraph above); nothing downstream may inherit that clip. Everything that READS the story keeps reading `activePath`/`allMessages`: prompt assembly, memory, the story map, the chats panel and every blast radius. Everything that POINTS at a turn has to load it back in first, and there are exactly three doors. `messageStore.revealMessage` is the one for anything outside the transcript (the assistant's timeline rows and its approval cards): it switches branch ONLY when the turn is off the path being read, since navigating to one already on it re-homes the leaf onto whatever hangs deepest below it, which is a different timeline, and it then hands the id to `revealTargetId`. The story map writes `revealTargetId` directly, having navigated already. Find in chat gets `loadThrough`. A fourth jump that resolves `document.getElementById('msg-…')` on its own finds nothing for any turn behind the window, and on screen that reads as the turn having been deleted, which is why [`contracts.test.ts`](../src/lib/contracts.test.ts) scans for every shape of that lookup and exempts only the two transcript components that own the window.
15. **The transcript scroller glides by CSS, so a scroll that has to LAND says `behavior: 'instant'`.** `.message-list` is the app's only box carrying `scroll-behavior: smooth`, and that CSS is load-bearing twice: it is the transcript's own feel, and it is the animator `ChatContainer`'s margin wheel rides by writing `scrollTop` and letting it travel. What that costs is a spelling trap. `'auto'` does not override that CSS, it DEFERS to it, and so does a plain `scrollTop` write, so a scroll meant to land travels instead: the reading-position correction after a load then animates and the reader watches the whole stretch that just arrived fly past, worst in the button load mode, where they are parked at the top edge with no gesture of their own to cut the glide short. The deliberate travels (`jumpToLatest`, find in chat's ∧/∨ cycling, `flashTarget`) say `'smooth'` and mean it. Nothing in the type system tells the two apart, since all three spellings are a valid `ScrollBehavior`, so [`contracts.test.ts`](../src/lib/contracts.test.ts) pins that the CSS is still there and still alone, and that neither transcript component asks for `'auto'`.
