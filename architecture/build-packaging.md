# Build, dev workflow, bundled assets & packaging: architecture & maintenance

**Two-process dev** ([`dev.ps1`](../dev.ps1) on Windows, [`dev.sh`](../dev.sh) on macOS and Linux): Bun server with `--watch` on :4242 + Vite dev server on :1420 with HMR; Vite proxies `/api`, `/files`, `/unlock`, `/ws` to Bun (`xfwd` forwards the device's real IP so Bun's gates work through the proxy). **The live-sync socket is the one thing the client does not send through that proxy**: it opens straight at :4242, whose number rides the bundle through a `define` for exactly this (architecture/client-data-layer.md). The `/ws` proxy entry stays anyway, so :1420 answers the app's whole route surface (coupling 2). The launcher owns both child processes ([B] rebuilds the client for :4242, [Q] quits). The two are deliberate duplicates of one another (same processes, same keys), so a change to one belongs in the other; only the way each takes its children down differs (`taskkill /T` against the tree, a signal to the process group). Both hand their children an empty stdin, or Vite claims the terminal's keyboard for its own shortcuts and [B]/[Q] never arrive. `dev.sh` also falls back to `~/.bun/bin` when `bun` is missing from PATH: Finder runs a double-clicked `.command` without the interactive shell that the Bun installer's PATH line lives in. **Neither launcher opens a browser itself**: both print the URLs, and the one tab a dev start is allowed comes from **Vite's own `server.open`, wired to `OPEN_BROWSER`** in `vite.config.ts`. It has to be Vite rather than either half of the pair: Vite opens once it is genuinely listening and at :1420, the port that hot-reloads, while the Bun half runs under `--watch` and re-runs its whole file on every save, which would be a tab per keystroke. [`server/index.ts`](../server/index.ts) therefore skips opening whenever `process.execArgv` carries `--watch` or `--hot` and opens otherwise, so a portable double-click and a `bun run start` from source both feel like launching an app while two-process dev stays at one tab. That makes `CHUNGUS_NO_OPEN` load-bearing for anything that spawns the server from source, the two spawned-server tests included (architecture/testing.md). **[`vite.config.ts`](../vite.config.ts) takes its proxy target from `config.ts`'s `PORT`** instead of writing the number out again, or the two halves of dev drift onto different ports and the app loads and then answers nothing. **It also names every runtime dependency in `optimizeDeps.include`**, so the prebundle happens while the dev server starts. Left to discovery, a bare import is found while the module carrying it is transformed, which on a cold cache is mid page load: Vite holds those requests until esbuild is done and then force-reloads the page under an app that has already begun booting, a window tens of seconds wide on a fresh clone and the one moment a first launch is most likely to be watched. Nothing in a build or a type check notices a name missing from that list and a warm cache hides it locally, so `contracts.test.ts` asserts it against `package.json` (coupling 8). **[`vite.config.ts`](../vite.config.ts) duplicates the server's security gates for dev**: `allowlistGate()` re-implements the IP allowlist (re-reading `allowlist.json`/`security.json` per request) and the password gate for top-level documents, because every proxied request reaches Bun as loopback. The dev server always binds the LAN, because a listening address is fixed for the life of a process and Vite cannot move its socket the way Bun's `rebindNetwork()` does; `allowlistGate()` enforces the network-access switch at the socket instead, destroying every non-loopback connection before a byte of HTTP is read while the switch is off, re-read per connection so it is live in both directions with no restart (architecture/server-core.md). A denial serves the same auto-retrying denied page as the Bun server and reports the knock to Bun's loopback-only `/api/access/record-denied`, so the Settings → Security waiting list works in dev too. It imports `server/access.ts` + `server/config.ts` directly (which is why config.ts must stay Vite-loadable) and mirrors `SESSION_IDLE_MS` from `server/security.ts` by hand.

**Client build**: SvelteKit + adapter-static (SPA fallback `index.html`) → `build/`, served by the Bun server in production (single origin). Tailwind v4 via the Vite plugin. `src/app.html` is the shell; [`src/service-worker.ts`](../src/service-worker.ts) is a minimal app-shell SW: precaches the build output *and* all of `static/` (`build` + `files` from `$service-worker`, so every self-hosted font lands in the cache), **never** caches `/api/`, `/files/`, `/ws` (live data fails loud offline), version-keyed cache cleanup on activate.

**Bundled assets**: `defaults/presets/` holds the shipped presets and is **read as a folder, not a list**: every `<id>.json` in it is a default preset and an image under the same name (`<id>.png|jpg|jpeg|webp`) is that preset's cover, so shipping one is dropping the pair in and nothing else. There is no id list to edit and nothing that can fall out of step with the files. Currently `standard_chungus.json` + `standard_chungus.jpeg`, the cover written at 768×1024 because the seeded copy is drawn wherever its thumbnail would be (architecture/server-core.md). Both halves are seeded into `user-data/presets/` and `user-data/images/presets/` on first boot ([`ensureDefaultPresets`](../server/files.ts)), and a folder holding no `.json` throws: a build that seeds no preset leaves a first-run user with nothing to generate with. `defaults/skills/` holds the assistant skills the app ships, **read as a folder** the same way: every `<id>.json` is one skill in the same format a Skills export writes (`shared/skills-file.ts`), the filename is the id, and dropping a file in ships it. It seeds `user-data/assistantSkills.json` on its first read and backs the Defaults browser in Assistant Settings, where a deleted or rewritten skill is fetched back from; nothing ever writes into the folder, and a missing or empty one throws (architecture/chungus-assistant.md). `defaults/characters/` holds the example characters, **read as a folder** like the other two but seeded on a different rule: `<id>.json` is one character's content (name, tags, traits, alternate greetings, and the label its `defaultSprite` names), `<id>.<image>` beside it is the portrait, and the `<id>/` folder beside it is the sprite pack, one picture per label in SillyTavern's own layout. The card file carries **no image paths at all**, the same principle the preset defaults follow: a path is install-local, and the seed is where the files it names come into existence. It is deliberately the app's own compact shape rather than an exported card, so a field is stated once instead of twice, and so a shipped character can say which sprite it rests on, which no export can carry (there is no reader for such a pointer, see architecture/sillytavern-interchange.md). Authoring one is therefore: export the character, lift `data.extensions.chungushub`'s `identity` + `data` into that shape, drop the portrait and the sprite folder beside it. Versions and linked lorebooks do not travel, matching what an export drops for the same reason. **`ensureDefaultCharacters` ([server/default-characters.ts](../server/default-characters.ts)) runs it once per id and never again**, keeping the ids it has seeded in the `seededDefaultCharacters` setting, so a character the reader deletes stays deleted while one added to a later build still reaches an install that already exists. That is the whole difference from a preset, which is re-seeded whenever it is missing because the app must always have something to generate with; a character is somebody's library. An empty or missing folder is fine here and throws in neither direction: a build with no example character is a build without one, not a broken install. Its art is copied rather than uploaded, so it keeps the format it was authored in (webp, for the transparency a sprite is made of) and ships at the size the app draws it, with no thumbnail: `resolveImageFile` answers a thumbnail request with the original, and nothing here would be smaller for having one. `defaults/backgrounds/` is tracked in the repo (78 webp, ~48 MB), served straight from it at `/files/backgrounds/` and copied into the portable build; drop a file in to ship it. The **display name is derived from the filename** (`backgroundName` in [server/files.ts](../server/files.ts): extension stripped, `-`/`_` to spaces, title-cased), so a file lands in the picker under whatever it is called. Name it for what the image shows, not for what produced it. `static/` holds the PWA shell assets: `manifest.webmanifest`, the two drawings (`mark.svg`, `icon.svg`) and the rasters cut from them (`favicon.ico`, `icons/`), and `fonts/` (self-hosted font families, one CSS per family, lazy-loaded by [`src/lib/services/fonts.ts`](../src/lib/services/fonts.ts); app.html links only the defaults). **`fonts/OFL.txt` is a shipping requirement, not documentation**: every family there is under the SIL Open Font License, which permits the bundling on condition that the copyright notices and the license travel with the font files. It lives beside them precisely so that happens by itself, since `static/` is copied whole into `build/` and `build/` whole into the portable package. Adding a family means adding its copyright line to that file in the same piece of work. **Those two SVGs are the app's only source art**, and **which one is used is decided by size, not by surface**: `mark.svg` is the whole raccoon, linked as a vector wherever there is room to look at it (the greeting, the welcome landing), while `icon.svg` is the same animal's head and is what **every raster in the repo is cut from** by [`scripts/icons.ts`](../scripts/icons.ts) (`bun run icons`). Those rasters are the two manifest PNGs, the maskable and apple-touch tiles, the `.ico`, and `docs/logo/mascot.png`, since the docs site puts that in a navbar and reuses it as its favicon. Below roughly 48px the full body loses its face and reads as a pale smudge; the head still shows two eyes at 16, which is the size a tab, a taskbar and a home screen all live at. **The two drawings share one palette** (`#010101` line, `#ededed` face, `#636362` fur), which is what makes them one animal rather than two marks, and the head is drawn touching its box left and right on a transparent ground: it is cut straight to size, so margin left inside the drawing is margin every icon inherits and nothing downstream can trim. `images/` at the repo root is README art and not app data: the hand-made banner, the theme showcase capture and `screenshots/`, none of which anything generates and none of which the generator should be taught to overwrite. Those outputs are committed, since they are served and shipped rather than built on demand, so editing the drawing means re-running the script in the same piece of work, or the mark changes in one place and stays put in the others. The generator needs ImageMagick on PATH and throws when it is absent; it is a workstation tool, never a runtime or build dependency. Two of the tiles are **plated** rather than transparent, and that is not decoration: Android crops a maskable icon to its launcher's shape and iOS composites transparency on black. The maskable one is also inset, by a figure measured off the drawing rather than chosen: how far its furthest point reaches from its own centre decides how large it can be scaled before that point leaves the safe circle, so a redrawn mark needs that measured again. The assistant's face is a third drawing and lives inline in `AssistantMascot.svelte` (architecture/chungus-assistant.md), deliberately not here. Nothing outside the app ever asks for it.

**Packaging** ([`scripts/package.ts`](../scripts/package.ts), `bun run package`): vite build → `bun build --compile server/index.ts` (Bun runtime embedded) → `dist/ChungusHub-portable/` with the exe + `build/` + `defaults/presets/` + `defaults/skills/` + `defaults/backgrounds/` + README.txt. On Windows the compile also takes `--windows-icon` pointed at `static/favicon.ico` plus `--windows-title`, so the file in Explorer, its taskbar button and the browser tab all carry one mark; a missing `.ico` throws there rather than shipping a binary wearing the Bun logo. **On macOS the compile is followed by an ad-hoc `codesign`** against [`scripts/macos-entitlements.plist`](../scripts/macos-entitlements.plist) and then a `codesign --verify --strict` that must pass: macOS kills an unsigned arm64 binary the moment it launches, and a Bun release can write a truncated signature, so the verify is what turns "crashes on every Mac that downloads it" into a failed build here. The entitlements are the five JIT permissions Bun needs. Signing without them produces a binary that starts and then dies. The signature is ad-hoc, not an Apple developer identity, so it clears the kernel but not Gatekeeper; the packaged `README.txt` grows a macOS-only paragraph pointing at System Settings → Privacy & Security for the one-time first-launch approval. Windows gets its own, for the same reason wearing a different face: an unsigned exe downloaded from the internet meets SmartScreen's blue full-screen block, which offers no visible way past it until you press More info. Each build carries only its own platform's paragraph, since the other is noise there. The note also tells the reader to keep the folder out of OneDrive and the like: a sync client copying the SQLite file mid-write corrupts it, and a synced Desktop is the Windows default. **That README is the only place a headless install is told how to open itself up**, so its `security.json` + `allowlist.json` route has to stay true to the actual defaults, to both files being written on first boot, and to both being applied live (architecture/server-core.md): a machine with no screen cannot follow the Settings → Security steps above it, and there is nothing else in the zip to read. The backgrounds are copied in full and their absence throws: `listBackgrounds` reads that folder directly, so a build without them ships an empty picker. The compiled binary detects itself via `IS_COMPILED` (bunfs check in server/config.ts), roots everything next to the exe, and auto-opens the browser unless the settings file turns it off. The compile also carries `--define CHUNGUS_VERSION`, read from `package.json`, the only place a version is stated and a file the portable folder does not ship, so the number has to travel inside the binary; [`server/version.ts`](../server/version.ts) reads it and answers `dev` from source. Every backup manifest stamps it, which is what says later which build wrote a snapshot. `package.ts` imports **`DEFAULT_PORT` and deliberately not `PORT`**: the zip ships without a settings file, so what its note has to state is the port a fresh install will listen on, while `PORT` is whatever the machine doing the build happens to have configured (architecture/server-core.md). The note also names `chungushub.config.json` itself, since that is where a portable reader changes the port, pins the data folder or stops the browser opening, and it is written on their first run rather than shipped; importing `config.ts` at all creates `user-data/` next to the repo as a side effect (it calls `ensureDirs()` at import time), which is gitignored and harmless here. **`bun build --compile` does not carry worker entry points into the binary**: a `new Worker(new URL(…, import.meta.url))` that runs from source dies with ModuleNotFound in every portable build, which is why background work here re-invokes the executable as a child process instead (architecture/backups.md).

**Releases** ([`.github/workflows/release.yml`](../.github/workflows/release.yml)): builds the portable distribution on one runner per platform (ubuntu/macos/windows), archives each, and opens a **draft** release carrying the archives plus a `SHA256SUMS.txt`. Three entry points, one pipeline: a run started from the Actions tab **with a version** is the whole flow with nothing checked out locally, since `gh release create --target` creates the tag on the commit the run built; the same run **without** a version stops after uploading the archives to the run page, which is how packaging gets tested; pushing a `v*` tag does what filling the version in does. The release job checks nothing out, since all it does is move archives between the API and a release, so `gh` is aimed at the repository through `GH_REPO` rather than left to read a git remote. Creating the release through GitHub's own Releases form instead is the one route that breaks: it makes the tag, the tag fires this workflow, and the workflow then fails trying to create a release that exists. **The matrix is native builds, not cross-compilation, and that is the point**: `tar` on a real Unix host is what preserves the executable bit (an archive written on Windows drops it, and the download will not run), and `codesign` exists only on macOS. Windows is zipped with `Compress-Archive`, the other two `tar -czf`; both hold one top-level `ChungusHub-portable/`. The Bun version is **pinned** rather than floating, because a Bun release can regress the macOS signature and that regression surfaces on a user's Mac, not here. `actions/attest-build-provenance` signs each archive's digest against the repo, commit and workflow, so `gh attestation verify` answers whether a downloaded file came out of this repository; it is **gated on the repository being public**, since attestations are a public-repository feature outside Enterprise Cloud and the step fails rather than degrading. Nothing else is conditional on visibility, so making the repo public turns it on with no edit here. Intermediate artifacts upload uncompressed with one-day retention: they are a handoff between the two jobs, and three platforms of a build this size otherwise sit against the account's artifact quota.

**Misc repo files**: `start.bat` and `start.command` (double-click wrappers that run `dev.ps1` and `dev.sh`; the `.command` extension is what has Finder open the file in Terminal rather than an editor), `architecture/`, the subsystem docs this file belongs to (tracked in the repo, never packaged).

## Before touching this

- Anything touching auth/session behavior in `server/access.ts`, `server/security.ts`, or the gate order in `server/index.ts` must be mirrored in `vite.config.ts`'s dev gates. They are deliberate duplicates.
- `server/config.ts` is imported by Vite at config-load time. Keep it side-effect-light (it only mkdirs) and free of Bun-only APIs.
- The service worker must keep its never-cache list in step with the server's route surface (`/api/`, `/files/`, `/ws`).
- Bun is the only package manager and `bun.lock` the only lockfile; a new dependency is the maintainer's call, not a detail a change carries in with it. the packaged exe embeds no node_modules: the server must stay dependency-free at runtime (it currently imports nothing outside stdlib + bun builtins).

**Generated config**: the root `tsconfig.json` extends `.svelte-kit/tsconfig.json`, which `svelte-kit sync` writes and nothing commits, so `bun install` regenerates it through the `prepare` script. Without that, the first thing a fresh clone runs is Vite loading `vite.config.ts` through esbuild, which reads the root config, finds no base to extend and warns about it before SvelteKit's plugin has had the chance to write one.

**Type-checking**: `bun run check` is two passes: `svelte-check` over `src/` (via the root `tsconfig.json`, which extends SvelteKit's generated config and therefore covers `src/` only) and `tsc -p tsconfig.server.json` over `server/` + `shared/`. The second config exists because the first structurally cannot reach the server. The service worker falls through both passes: the root config explicitly excludes `src/service-worker.ts`, and the server pass never looks at `src/`. `shared/` is the dependency-free contract layer both halves import (relative path from `server/`, the `$shared` alias from `src/`, declared in `svelte.config.js` `kit.alias`); it is bundled into the client by Vite and into the exe by `bun build --compile`, so it must stay free of both DOM and Bun APIs.

## Hand-kept couplings

1. `vite.config.ts` dev gates ↔ `server/access.ts` / `server/security.ts` (allowlist logic, the `passwordEnabled` flag, `SESSION_IDLE_MS`, cookie name).
2. Vite proxy route list ↔ the Bun server's non-static route surface (`/api`, `/files`, `/unlock`, `/ws`). Complete even where the client goes around it: the socket takes the Bun port directly in dev, and `/ws` is proxied regardless, so :1420 is a faithful stand-in for the app's origin.
3. `defaults/presets/`, `defaults/skills/` and `defaults/characters/` are the source of truth for what ships: `ensureDefaultPresets` seeds every `<id>.json` the first holds, `listDefaultSkills` reads the second on demand, `ensureDefaultCharacters` seeds each id in the third exactly once, and `scripts/package.ts` copies all three whole. A scratch file left in any of them is a shipped default on the next boot and in the next portable build. The first two throw when empty; the third does not, since an example character is not something the app cannot run without.
4. `scripts/package.ts` copies an explicit list (build, defaults/presets, defaults/skills, defaults/characters, defaults/backgrounds). A new runtime-read directory must be added there or the portable build silently lacks it.
5. Service-worker never-cache prefixes ↔ server route prefixes.
6. `scripts/package.ts` ↔ `.github/workflows/release.yml`: the workflow only runs the script and archives `dist/ChungusHub-portable/`, so the output folder name and the fact that packaging produces exactly one folder are the contract between them. The macOS half additionally depends on `scripts/macos-entitlements.plist` existing (the script throws without it) and on the runner being a real macOS host, since `codesign` is only there.
7. `static/mark.svg` + `static/icon.svg` → every committed raster, via `bun run icons`, and `static/favicon.ico` → `scripts/package.ts`'s `--windows-icon`. That script is the only writer of those files; hand-editing one leaves it out of step with the drawing and nothing will say so. Redrawing `icon.svg` also means re-measuring the two plated tiles' insets, since both are figures taken off the drawing.
8. `optimizeDeps.include` (vite.config.ts) ↔ `dependencies` in `package.json`: every runtime dependency is named, a package with per-entry exports by the subpaths actually imported. Asserted in both directions by [`contracts.test.ts`](../src/lib/contracts.test.ts), since a warm dep cache means the cost of a missing name is paid on somebody else's fresh clone and never here.
