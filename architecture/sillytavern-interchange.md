# SillyTavern interchange: architecture & maintenance

Reading and writing SillyTavern's formats is a headline promise, and the code that keeps it is spread across ten modules that no single subsystem owns. This doc owns the **format boundary itself**: what the bytes look like, which parser claims which file, what is renamed crossing over, what rides untouched, and what deliberately does not travel at all. Everything on the far side of the boundary belongs to another doc and is not restated here: the library store, drafts and versions in architecture/library.md, the book domain model and activation engine in architecture/lorebook.md, the message tree in architecture/chat-sessions.md, the Import page's placement in the settings shell in architecture/ui-shell-settings.md. Macro names borrowed from SillyTavern (`{{char}}`, `{{description}}`, `<START>` example blocks) are a naming convention rather than a file format (architecture/prompt-pipeline.md).

## What we read

**PNG text chunks have one implementation** ([`pngText.ts`](../src/lib/services/pngText.ts)) shared by every reader and writer of a document-inside-a-picture: `buildTextChunk`, `insertTextChunk` (which drops the keywords it is replacing on the way past, so a re-exported picture never carries a stale document beside the fresh one), `readTextChunk`, and the `encodeBase64Utf8`/`decodeBase64Utf8` pair. Reader and writer live in one file deliberately (a chunk whose CRC covers the wrong byte range looks fine locally and is rejected by every real PNG reader), and CRC-32 itself lives once more in [`crc32.ts`](../src/lib/services/crc32.ts), shared with the ZIP writer.

**Character cards** ([`sillyTavernImport.ts`](../src/lib/services/sillyTavernImport.ts), `importSillyTavernCard`). Two containers: a `.json` card, or a `.png` whose card rides base64 in a text chunk. `extractCharaFromPng` is `readTextChunk(bytes, 'chara')`: the chunk table is walked without decoding the image, the **first `tEXt` or `iTXt` chunk with that keyword** wins, `tEXt` decodes latin1 while `iTXt` skips its compression flag, language tag and translated keyword and decodes UTF-8, and `decodeBase64Utf8` tolerates URL-safe alphabets, stray whitespace and missing padding, falling back to treating the payload as raw JSON when `atob` throws.

**Preset cards** ([`presetCard.ts`](../src/lib/services/presetCard.ts)) are the same trick for a preset: an ordinary PNG whose visible image is the preset's cover, with the interchange document (`presetDocument`, architecture/prompt-pipeline.md coupling 9) base64'd into a **`chungus_preset`** chunk. The keyword is ours and deliberately not `chara`: neither our own card importer nor SillyTavern's may ever mistake one for the other, and `presetCard.test.ts` pins that a preset card contains no `chara` keyword at all. The picture is always **redrawn at a fixed 3:4 portrait** (`COVER_WIDTH`×`COVER_HEIGHT`, 768×1024) rather than passed through at whatever shape the author uploaded, so every preset card is the same shape and crops the same way the app shows it. `cropToPng` centre-crops exactly like `object-fit: cover` does on screen (architecture/preset-authoring.md). This is the only way a cover travels: `meta.cover` is a path into one install's image store, so it is stripped from the document and the picture carries the cover instead; a `.json` export of the same preset is complete except that it has nowhere to keep one. Import saves the PNG itself through `imageService.saveImage(file, 'presets')` and lands the preset with that path. `readPresetFromPng` returns **null** for a picture with no preset in it (not a preset card) and **throws** for one whose chunk is present but unparseable: importing an empty preset under a success message is how somebody loses an afternoon's work without being told. Both card generations are read through one mapper: `charData = stChar.data || stChar`, so a V1 card's flat fields and a V2/V3 card's nested `data` block reach `mapSillyTavernToCharacter` identically. **`spec`/`spec_version` are typed but never read**: a V3 JSON card imports as a V2 one, and its overlapping fields land correctly; a V3-only PNG whose card lives solely in a `ccv3` chunk with no `chara` chunk **throws** `No character data found in PNG`, because `chara` is the only keyword matched. The standard field set maps onto traits with a rename at each slot (`first_mes`→`firstMessage`, `mes_example`→`exampleDialogue`, `creator_notes`→`creatorNotes`, `system_prompt`→`systemPrompt`, `post_history_instructions`→`postHistoryInstructions`, `character_version`→`characterVersion`; `description`, `personality`, `scenario`, `creator` verbatim), `name`/`tags` go to identity, `alternate_greetings` are trimmed with empties dropped, and the ChungusHub-only `background` trait is seeded empty. **The card path has no `rest`**: the mapper names every field it wants, so anything outside that set is dropped on the floor: the card's own `extensions` (`talkativeness`, `depth_prompt`, `fav`), V3 additions (`assets`, `nickname`, `group_only_greetings`, `creation_date`), `avatar`. That is the sharp asymmetry against the lorebook path below, and it is why a card is a lossy read while a book is not. **`extensions.world` is the one exception and it is not a trait**: it is SillyTavern's link from this card to a book in the same profile, named as that book's world file is named, so `readWorldName` (both card generations, trimmed, absent as null) hands it out beside the character for whoever holds the folder to resolve. A card picked on its own has no folder and leaves it alone. Reading only the embedded `character_book` and not this is how one shared book lands once per card that uses it.

**World info** ([`lorebook/sillytavern.ts`](../src/lib/lorebook/sillytavern.ts), `parseLorebook`) reads the same data in two on-disk shapes and tells them apart by structure, never by a declared type. Detection order in `parseLorebook`: an embedded `character_book` (top-level or under `data`) wins first, then `entries` **as an array** means the character_book shape, then `entries` **as an object** (keyed by stringified uid) means native World Info, and anything else **throws** rather than yielding an empty book. Native is near-passthrough because the model uses SillyTavern's field names verbatim: `fromNativeEntry` types the modelled fields and copies every other key into `entry.rest` untouched (`position`, `depth`, `role`, `group`, `sticky`, `cooldown`, `characterFilter`, `displayIndex`, all of it) while `uid` and `selective` are deliberately kept out of `rest` because they are positional/derived and regenerated on export. The matching, timing and placement fields are modelled too and therefore read on both sides: `scanDepth` (the entry's own scan window), `triggers` (the generation kinds it fires on, **every token kept**, ours or not), the `match*` source flags, which `asScanFields` reads off the one `LOREBOOK_SCAN_FIELDS` table rather than a second list of names, `sticky`/`cooldown`/`delay`/`group`/`groupOverride`/`groupWeight`/`useGroupScoring`, and `position`/`depth`/`role`. **The three recursion flags are the one group SillyTavern spells two ways** (`excludeRecursion`/`preventRecursion`/`delayUntilRecursion` flat in native World Info, `exclude_recursion`/`prevent_recursion`/`delay_until_recursion` inside a card entry's `extensions`), so `asRecursionFlags` reads **both names in both shapes** off the one `RECURSION_FIELDS` table and `recursionFlags` writes whichever name the target shape reads. A flag written under the other side's spelling is a setting that stops applying with nothing on screen to say so, which is the failure this pairing exists to prevent. `delayUntilRecursion` crosses as SillyTavern writes it, `true` or a recursion level, and a flag the file never named stays absent rather than becoming a decision its author did not make. **`position` is kept whole even though only two of its eight values name a place this app has**: 4 puts an entry at a depth in the chat, everything else reads as the `{{lorebook}}` block, and an author's-note or example-block position leaves exactly as it arrived rather than being flattened to 0. The three timing numbers default to **null, not 0**, which is SillyTavern's own default and the difference between "no window" and "a window of zero"; `ST_ENTRY_DEFAULTS` no longer carries them, since a modelled field is written from the entry. The card shape puts the real `position` enum in each entry's `extensions` while its own top-level `position` is a two-value string (`before_char`/`after_char`); the extension is the one that decides, and the string is derived from it on the way out. `character_book` is the only path that needs real translation: `keys`→`key`, `secondary_keys`→`keysecondary`, `insertion_order`→`order`, `enabled`→ inverted `disable`, `case_sensitive`→`caseSensitive`, `comment` falling back to `name`, and the modelled fields **lifted out of** the spec's per-entry `extensions` under their snake_case card names (`selectiveLogic`, `match_whole_words`, `probability`, `useProbability`, `scan_depth`, `triggers`, `match_scenario` and its siblings) so they can't drift from the modelled values on re-export; what remains of `extensions` becomes that entry's `rest`. Book-level: `scan_depth` and `recursive_scanning` are modelled tri-states where absent means inherit the global, `token_budget` and `description` are parked into `book.extensions` because the app models neither (both parse paths do it, so a card's book description survives a round-trip it has no surface for), and `liftBookOverrides` pulls our own three override keys back out of `extensions`. `asKeyList` accepts either an array or SillyTavern's comma-joined string.

**Chats** ([`sillyTavernChatImport.ts`](../src/lib/services/sillyTavernChatImport.ts), `convertSillyTavernChat`: pure, no db or stores, tested). The wire shape is JSON Lines: a `chat_metadata` header line, then one object per message carrying the active text in `mes`, every alternative in `swipes[]`, the live index in `swipe_id`, and per-swipe metadata in `swipe_info[]`. Any line holding a `chat_metadata` key is skipped, and a line that fails `JSON.parse` is skipped **individually** rather than sinking the file. That header line is also the only place the file names its character, and `readChatCharacterName` is the one reader of it: the first non-blank line, required to carry `chat_metadata`, `character_name` trimmed, null for anything else. A message's own `name` is never allowed to stand in, because on a user turn it is the persona's. Its one caller is the Chats panel's picker, and it **decides nothing there**: that import lands every file on the character the panel is already narrowed to, and this name is shown beside the filename purely to flag a file played with somebody else before it lands. Resolving a target from it would be display-name matching, which the folder importer refuses to do unattended (coupling 8); a warning is not a bind (architecture/chat-sessions.md). Per message: `is_user` decides the role, `swipe_id` is clamped into range, `extra.reasoning`→`thinking` (assistant turns only), `extra.model`→`model`, `extra.api`→`provider`, `extra.token_count`→`tokensCompletion`, and `send_date` is parsed best-effort (SillyTavern mixes ISO with `October 24, 2025 6:15pm`) falling back to a monotonic sequential clock. The active swipe's metadata lives on the message's own `extra` while the others carry theirs in `swipe_info[j]`, so the reader prefers the swipe-specific block and falls back to `extra` only for the active index. **Three generation timings come across too**, so an imported chat is not a hole in the app's own timing stats: `gen_finished` minus `gen_started` → `generationMs`, `extra.time_to_first_token` → `firstTokenMs`, `extra.reasoning_duration` → `reasoningMs` (architecture/server-core.md). The two stamps sit BESIDE `extra` rather than inside it, at the message level and inside each `swipe_info` entry, and follow the same swipe-specific-first rule as everything else here, since every swipe was its own generation with its own clock. All three are refused rather than guessed at whenever the file cannot support them: a half pair, a stamp that does not parse, a span that runs backwards, a negative or non-numeric duration. A **measured zero is kept**, because "instant" and "nobody measured" are different claims and only the second one is null. They are also never written onto a user turn, whatever the file says, since all three describe a generation. **`tokensPrompt` stays null and cannot be recovered**: the format never records it, so any figure here would have to be invented. What can be recovered is only ever the exporter's own measurement, and `reasoning_duration` is the one to watch: it has been observed equal to the whole generation on a turn whose reasoning stream cannot have run that long, so it is a looser reading of "time spent reasoning" than a turn generated here records, and a stat that averages the two together is averaging two different quantities. `personaId` imports as null, the documented untracked value. **`is_system` is deliberately not skipped**: it is SillyTavern's hide-from-prompt flag, those are real turns, and ChungusHub has no per-message equivalent, so they import as ordinary visible turns. How the emitted nodes become a branching tree is architecture/chat-sessions.md's subject.

**Personas and backgrounds** are read only as part of a folder import, and personas are the one case where a character's data is split across two files: the portrait comes from `User Avatars/<file>` and its identity from `settings.json`. `power_user.personas` maps the **avatar filename** to the display name and `power_user.persona_descriptions[<file>].description` to its description, with the filename stem as the name fallback. `readPersonaSettings` is the one reader of that shape and it lives in [`sillyTavernFolderScan.ts`](../src/lib/services/sillyTavernFolderScan.ts) rather than beside the writer, because the confirm card labels its persona rows from `names` while the run writes both, and only a module free of the store graph can be reached from both (and tested). A card that named a persona one thing while the import wrote another would be a lie nobody could see until afterwards; the fallback is shared for the same reason. Backgrounds carry no metadata at all; the bytes go straight to `imageService.saveImage(file, 'backgrounds')`.

**Regex scripts** ([`utils/regex-rules.ts`](../src/lib/utils/regex-rules.ts), `fromSillyTavernScript`) are recognized structurally too: `isSillyTavernScript` is `typeof raw.findRegex === 'string'`, nothing more. A `/body/flags` find string is unwrapped and its flags narrowed to the `gimsu` subset we allow, while a bare string compiles flagless exactly as SillyTavern runs it; `{{match}}` becomes `$&`; `placement` 1/2 become the `user`/`assistant` targets with `[2]` as the default; `disabled` inverts into `enabled`; `minDepth`/`maxDepth` cross unchanged, because both formats count turns back from the newest and the numbers therefore mean the same thing on both sides, with ST's `null` for "no bound" landing as `undefined` rather than as 0, which would silently narrow the rule to the newest turn alone; and the scope mapping carries a decision: ST's "neither `markdownOnly` nor `promptOnly`" means a **permanent rewrite of the stored message**, which we never do, so it maps to both scopes instead. The **id is preserved** when the script declares one, and the two entry points then disagree on purpose: `parseRegexRulesImport` (the Regex page) mints fresh ids because an import is a new row in this install, while `normalizeCarriedRules` (rules riding inside a preset) keeps them, because the reader's per-rule switch points at them. `parseRegexRulesImport` accepts our own envelope, a bare array, a single object, one ST script or an array of them, and throws when nothing usable is found.

**Inline styling in model output is not a format we read, it is a boundary we enforce.** A preset's regex rules rewrite the reply before it is rendered, so the HTML reaching the transcript is authored by whoever wrote the preset. [`inline-decoration.ts`](../src/lib/utils/inline-decoration.ts) reduces every `style` attribute to four properties (`color`, `background-color`, `font-weight`, `text-align`) and the legacy `<font color>` to the same colour grammar, rebuilding the attribute from what survived so nothing unparsed reaches the DOM. Size, spacing, borders, shadows and above all **position** are never allowed, which is what keeps a downloaded preset from lifting a block out of the transcript and drawing a convincing fake window over the interface; no allowed value can name an external resource, so a rule cannot phone home through a background image either. The rest of the panel (box, padding, corners, accent bar, chevron) is the app's, drawn in `app.css` from the summary's `currentColor`, so a preset that sets one colour gets a coloured panel and a preset that sets none gets an app-toned one. **This list must not grow**: adding a size or a position re-opens exactly the door it exists to keep shut.

## What we write

**A character card export is a SillyTavern V2 card** ([`sillyTavernExport.ts`](../src/lib/services/sillyTavernExport.ts)): `spec: 'chara_card_v2'`, `spec_version: '2.0'`, the canonical fields under `data`, and the six V1 fields (`name`, `description`, `personality`, `scenario`, `first_mes`, `mes_example`) mirrored at the top level for V1-only readers, exactly as real ST cards do. The **ChungusHub fidelity block** is `ExportedLibraryEntry` (shape and version in [`libraryExport.ts`](../src/lib/services/libraryExport.ts)) embedded at `data.extensions.chungushub`, where SillyTavern ignores it: it carries the surfaced version's full `LibraryEntryData` (trait labels, hidden traits, the ST-less `background` trait) plus, for an `'all'` export only, every character version and the `activeVersionId`. The same shape describes our **legacy top-level JSON export**, which has **no writer left**: `buildExportBlock` is the only producer of the block and it only ever embeds, so `ExportedLibraryEntry.image` (the inlined portrait data URL) is only ever populated by files an older build wrote, and the importer keeps reading them. `.json` is the card serialized; `.png` is the card base64'd into a `tEXt` chunk named `chara` (we write `tEXt` only, though we read both), spliced in immediately before `IEND` by `insertCharaChunk`, which **drops any existing `chara` or `ccv3` text chunk on the way through** so a re-exported portrait can never carry a stale card beside the fresh one. The chunk's CRC-32 covers type+data per the PNG spec, and a wrong range makes real readers reject the chunk, which is why `sillyTavernExport.test.ts` re-computes it with an independent implementation. The base image is the portrait, re-encoded through a canvas when it isn't already PNG, or a 512px placeholder (flat `#2a2a33`, the name's first initial in `#8a8a99`) with fixed colors rather than theme variables, since the file leaves this app's theming behind.

**A lorebook export is native World Info** ([`toNativeWorldInfo`](../src/lib/lorebook/sillytavern.ts), downloaded by [`io.ts`](../src/lib/lorebook/io.ts)), the format SillyTavern's "Import World Info" reads. Each entry is layered `ST_ENTRY_DEFAULTS` ← `entry.rest` ← modelled fields, so an imported entry's originals always win while a book authored here still exports as a complete, ST-idiomatic record; `rest` goes out through `withoutStoredRecursion` at **both** exits, so a copy an older row still keeps there cannot ship beside the resolved value and contradict it; `uid` is the array index, `selective` is derived from whether secondary keys exist, and `displayIndex` falls back to the uid. Per-key match rules are the one field SillyTavern has no shape for at all, so they ride under a name that is obviously not its own (`chungus_key_rules`) and only when a key actually overrides something; there the keys fall back to the entry's own case-sensitivity and whole-word flags, which is the closest that side has. A **regex key needs no channel of its own**: a key written `/pattern/flags` is one on both sides, so it crosses as its own text. Book-level fields (`name`, plus `scan_depth`/`recursive_scanning` **only when explicitly set**, so an inheriting book re-imports as inheriting) ride at the top level as harmless extra metadata that our own re-import recovers, and `book.extensions` rides beside them carrying everything unmodelled, `description` included. **A top-level key the import does not model lands in `book.extensions` too**, the book-level twin of an entry's `rest`: `MODELLED_BOOK_KEYS` names the six the parser reads for itself and everything else is kept, so a third-party book does not come back out with whatever wrote it stripped off. The file's own `extensions` bag wins a name it shares with a stray top-level key. `toCharacterBook` writes the other direction (spec names outside, ST-specific fields inside each entry's `extensions`, and the book's own extensions carried under the overrides exactly as the native exporter carries them, with `description` and `token_budget` going back to their real card fields instead of both places) and is fully tested, but **has no production caller**: nothing embeds a `character_book` into a card we write.

**Bundling.** A single card downloads as a bare file; anything with more than one file becomes a `.zip`: a bulk export (`characters.zip`, one card per character, always `'all'` versions) or a single character exported with its sprites or its gallery. `buildCharacterFiles` lays out one character as `<base>.<ext>`, its **sprites flat in `<base>/` named by their labels** and its **gallery art in `<base>/gallery/1.<ext>`, `2.<ext>` …**, with extensions taken from the stored path or the fetched blob's mime, and `uniqueBase` disambiguates same-named characters as `Asami`, `Asami(2)`, `Asami(3)` across one shared `usedBases` set so a character's card and its folder always agree. **That split is the format boundary, not a filing preference**: `characters/<Name>/<label>.png` is SillyTavern's sprite layout and is what both `scanSillyTavernFolder` and SillyTavern itself read a pack out of, so gallery art sharing the folder would re-import as sprites labelled "1", "2", "3" and overwrite the pack's real labels. A sprite's filename is `sanitizeFilename(label)`, run through `uniqueBase` per character so two labels that sanitize alike stay two files; that sanitizer is ASCII-only, so a non-ASCII label is what a round trip through a filename cannot carry. The archive writer ([`zip.ts`](../src/lib/services/zip.ts)) is dependency-free and **STORE-only** (PNGs are already compressed and the JSON is small, so deflate would buy nothing), with the UTF-8 filename flag (bit 11) set, zeroed mod time/date, no data descriptors and no ZIP64, meaning the format is sound for the sizes it is used at and nothing more. CRC-32 lives once in [`crc32.ts`](../src/lib/services/crc32.ts) (lazy 256-entry table, polynomial `0xEDB88320`) and is shared by the PNG chunk writer and the ZIP writer so the two can never disagree.

## The round-trip invariant

**Two `.png` claims exist and they cannot collide**: `importSillyTavernCard` reads only `chara`, `readPresetFromPng` reads only `chungus_preset`. Two of the three readers are reached from their own picker (the Library's card import and `PresetManager`'s), so neither has a claim to decide. A picture carrying neither keyword yields null/throws in the reader that was asked, never a silent empty import.

**The third reader is the assistant's file ingest** ([`server/assistant/files-ingest.ts`](../server/assistant/files-ingest.ts)), and it is the one that has to CHOOSE, because a file is dropped on a panel rather than handed to a picker. Its order is `chara`, then `chungus_preset`, then refuse, which is safe for the same structural reason the rest of this section rests on: a preset card contains no `chara` keyword at all (`presetCard.test.ts` pins it), so the first match can never be the wrong one. It reads the document and stores it as text; it imports nothing, so nothing downstream of the mappers is involved. This is also the one place [`pngText.ts`](../src/lib/services/pngText.ts) is reached from the server, which is why that file and [`crc32.ts`](../src/lib/services/crc32.ts) must stay free of `$lib` value imports. A second chunk reader on the server side would let an attached card and an imported card disagree about what a picture holds. The client makes the same claim once more, and for a different question: a dropped `.png` is routed to the file path or the image path by whether it carries either keyword (`isDocumentPng`), since MIME type cannot tell a character card from a photograph.

**Our own export must re-import through our own path, and the branch that claims a file is decided before any format-guessing runs.** A ChungusHub card is a valid SillyTavern card *first*, so both readers can parse it and only ordering decides which one is right. Get it backwards and every export silently degrades to its ST surface, losing versions, trait labels and hidden traits with no error anywhere. `importSillyTavernCard` therefore tries, in order: (1) `isChungusExport(parsed)` on the top-level object, which catches the legacy JSON export whose own `data` key SillyTavern's shape would otherwise misread as a card body and yield an empty character; (2) `isChungusExport(stChar.data?.extensions?.chungushub ?? stChar.extensions?.chungushub)`, the block embedded in a card; only then (3) the standard ST mapper as the fallback. Both of the first two route through the **same** `importChungusExport`, and the guard is one predicate (`format === 'chungushub.libraryEntry'`), so a rename of that string breaks both doors at once. The lorebook side states the same rule structurally: `parseLorebook`'s detection order is fixed (embedded book, then array-entries, then object-entries, then throw), `toNativeWorldInfo` re-emits enough book-level state for our re-import to recover the whole book, and `sillytavern.test.ts` pins the strong form. **Export → parse reaches a fixed point after one pass**, the first export being allowed to complete a sparse entry with ST defaults and every cycle after that being byte-stable. The regex importer resolves the same question in the *opposite* order (ST shape is tried before our own normalizer), and that is safe only because our rules have no `findRegex` key, so the two can never both claim a file.

## The folder importer

The folder importer is **two modules and no format logic**: [`sillyTavernFolderScan.ts`](../src/lib/services/sillyTavernFolderScan.ts) decides *what was picked*, [`sillyTavernFolderImport.ts`](../src/lib/services/sillyTavernFolderImport.ts) writes it. The browser hands the pick over as a flat `File[]` (a non-standard `webkitdirectory` input, set on the element imperatively, see architecture/ui-shell-settings.md), each file tagged with `webkitRelativePath`.

**The pick is the profile folder (`data/default-user` in a standard install) and an ancestor is refused rather than resolved.** A known folder counts only as a **direct child** of what was picked (`knownAt` looks at the second path segment, which is where the browser's own prefix puts it, and at nothing deeper), so pointing at `SillyTavern/` or at `data/` matches nothing, and the surface answers with the folder to pick instead. Resolving an ancestor for the reader is not free and must not come back: `<input webkitdirectory>` makes the **browser** walk every file under the pick before a line of ours runs, `node_modules` included, and no code here can prevent that, so being friendly about the pick costs a full checkout's enumeration on every import, for a saving of two clicks.

Three rules govern what lands where. Only **direct children** of `backgrounds`/`characters`/`worlds`/`User Avatars` count, so a `characters/<Name>/` sub-folder is never mistaken for a card: one level down it is that character's **sprites**, grouped by folder in the scan so a pack lands as one write, while chats need the intermediate folder because it names the character. **A known name only counts as the folder a file sits in, never as the file itself**: `worlds/chats` is a file inside `worlds/`, and since it carries no `.json` it is imported as nothing at all rather than read as a chat folder. And `settings.json` is taken beside those folders, never deeper. A pick holding nothing recognizable is **null**, never an empty bundle. The module is pure by contract (no stores, no db, no writes), which is what makes it testable.

The import step then calls the app's existing importer per bucket: `readLorebookFile` + `lorebookStore.addBook`, `importSillyTavernCard` + `characterLibraryStore.importFromSillyTavern` (with `importLorebook: true`, so a full migration brings each card's book along linked), `characterLibraryStore.addSprites`, `imageService.saveImage`, `chatStore.importSillyTavernChat`. **The order the phases run in is the binding order rather than a preference.** Lorebooks run first, because a card binds to the book it names; characters run next, **before** sprites and chats, both of which bind to the character their folder names through one shared resolver (avatar-filename stem first, display name as the fallback). **A sprite's filename is its label** (`joy.png` becomes "joy"), which is the whole reason the pool's vocabulary is SillyTavern's (architecture/library.md); a pack lands as one `addSprites` call per character rather than one per file, and a folder matching no library entry is reported rather than dropped.

**Chats match on the card's avatar filename stem, not its display name**, and the reason is not stylistic: SillyTavern disambiguates same-named cards on disk as `Jason.png` / `Jason_1.png` and folders their chats as `chats/Jason/` / `chats/Jason_1/`, so display-name matching collides on duplicates and strands the second character's entire history. Each imported card records its lowercased filename stem in `charByFileStem`, and the chat loop looks the folder name up there first. **A card an EARLIER run brought over is seeded into that same map from the ledger** (`cardStemFromKey` over the claims, filtered to entries the library still holds), which is what keeps filename matching working across the runs the ledger exists to enable. Without it every second run silently falls back to display names, i.e. straight into the collision this whole rule was written to avoid. Display name is the **fallback only**, for characters in the library that neither this run nor any claim accounts for; `charByName` is built over the store's `updated_at DESC` list with a first-match-wins guard, so a duplicated display name resolves to the most recently touched entry. The run is per-item fail-soft: one bad file lands in its category's `failed` list and never aborts the pass, and the `ImportReport` the page renders is per-category `imported`/`failed[]` plus `chats.skippedNoCharacter[]` (chat files whose folder matched nothing, reported so the user can import that character and re-run). "Nothing recognizable was in there" is the scan's `null` and never reaches this report.

**A profile carries one lorebook many times over, and shelving every meeting of it is what this order closes.** SillyTavern keeps a shared book as a file under `worlds/` AND embedded in the `character_book` of every card that uses it, so a shelf of twelve books arrives as forty unless something asks whether each one is already here. Two answers, in order, both through the one `BookIndex` (architecture/lorebook.md). **SillyTavern's own link first**: `extensions.world` names the book, that name is the world file's own name, and the run has already shelved that file, so the link resolves to a real row. A resolved link **stands in for the card's embedded copy**, and that is the one place this drops something the disk holds. It is deliberate and it matches the format: SillyTavern's own `getCharacterLore` gathers a character's lore from world files **by name alone** (`extensions.world` plus `charLore.extraBooks`) and never reads `character_book` at generation time, so where the two differ the embedded copy is a draft of the world file rather than a second book, and the world file is the half anybody has been editing. **Then substance**: a book whose entries say what one on the shelf already says IS that book, so the card links to it. Only a book neither answer recognizes is written. The index is seeded from the whole shelf as it stands when the run starts, so a book an earlier run or a hand import brought over counts too, and it grows as the run lands more, so the second card sharing a book meets the first one's. Two counts ride the report, because a feature whose whole effect is an absence is invisible without them: `worlds.fromCards` (books that arrived inside a card, which have no row on the confirm card since they are not files in the pick) and `worlds.linked` (characters bound to a book that was already here). Covered end to end by [`sillyTavernFolderImport.test.ts`](../src/lib/services/sillyTavernFolderImport.test.ts).

**Every file that lands is claimed in the import ledger** (`import_sources`, architecture/server-core.md), and that one table is what makes three different problems the same problem. Running a folder twice brings only what is new. A run **stopped** by the reader, or by the server going away, continues by being run again rather than by any stored resume position. That is also why there is none: a position in a list would not survive a reload, would not know a row had since been deleted, and would say nothing about the folder having grown since. The key is `sillytavern:<path inside the pick>` (`sourceKey`), a **path and not a hash of the bytes**, so a card edited in SillyTavern is that character arriving twice rather than a new one. A card's row, a persona's row and a world file's row also carry **what they became** (`entity_id`), and that pointer does two jobs. Skipping a file does not excuse the run from binding what arrives beside it: a card's chats and sprites name it by filename (see the rule above), and a later run's cards name its book by the world file's own name (`worldStemFromKey`, the mirror of `cardStemFromKey`). And **a claim that names a row is only worth as much as that row still existing**: `importRun.known` drops any claim whose `entity_id` neither shelf holds, so a character, persona or lorebook the reader deleted by hand is offered again on the next run instead of being skipped forever under a claim saying they already have it. That liveness question asks the library and the lorebooks as ONE set, since an `entity_id` names either and the only thing asked of it is whether it is still there. The kinds that point back at nothing (backgrounds, chats, sprites) store null and cannot be asked, so their claims stand and the checkbox below is the only way back to them. Three rules ride with it. Claims are written in **batches of 20 and again at the end**, never one per file (an import's chatter would double) and never once at the end (a stop would drop every claim it had earned); a batch the server refuses adds its size to `report.ledgerLost`, which the page states in real files, because it is the one failure here whose cost is paid on a **later** run. A refused batch is counted rather than thrown: reachability only turns over once a reconnect has failed, so the run may well carry on and land plenty more, and a throw would cost the reader every count of what actually arrived. A sprite pack is claimed **including its refusals**, since a label already in use is that file having arrived before. And `settings.json` is **never claimed**: it is not a library item, it is read for the persona names beside it, and a run importing one new persona still needs it. `withoutKeys` is the filter, and it drops a sprite folder whole once its whole pack is known so an untouched character is not visited at all.

**The reader can also bring less than the whole folder, and narrowing is subtraction and nothing else.** `withoutKeys` is asked a second question with the keys switched off on the confirm card, so the importer is handed a smaller bundle rather than a bundle plus instructions, and there is exactly one place where "this file is not coming over" is decided. Two rules keep the cheap path cheap. **Everything starts on and every group starts closed**, so a whole-profile migration is still the pick and one press; only somebody who wants less pays attention. And the state is kept as **exclusions, never as a selection**, which is what makes a file entering the plan later (the ledger checkbox below) arrive switched on: a stored selection would have to guess for every file nobody has touched, and would guess wrong. `planGroups` spells the bundle out as the rows that can be switched off, and **every label comes off a path**, so a pick of four hundred characters costs no reads at all: SillyTavern names a card's file after the character, folders that character's sprites and chats under the same name, and names a world file after the book. Sprites and chats are **one row per character rather than one per file**, since a pack is already one write and a story's history is the unit somebody decides about; per-file chat picking has its own surface and is deliberately not repeated here (architecture/chat-sessions.md). `strandedByChoice` then asks the importer's own binding question **before** the run: a chat or sprite folder whose character is not coming over lands nowhere, and read off the report afterwards that is a list of work that did not happen and cannot be retried without picking the folder again. **It counts only the case a tick can fix**, which is what separates a warning from noise: the character has to be a row the card is offering (`available`) and not one that would actually bind (`resolvable`). A folder whose character is nowhere in the picked profile is an orphan of SillyTavern's own making, since a card deleted there leaves its chat folder standing, and there is nothing on this card to switch on for it; the run reports those as skipped, which is the only honest thing anybody can say about them.

**The reader can ask for all of it anyway.** The confirm card carries one checkbox that ignores the ledger, and it stays reachable even when every file in the folder is known. Re-importing something deleted since is otherwise unreachable, and a one-way door with nothing on the far side is not a safeguard. Its count (`alreadyImported`) is measured against the **pick**, never against the plan, and that is what keeps the control usable: read off the plan it falls to zero the instant the box is ticked, so the number the reader is deciding about disappears at the click and the row deletes itself out from under the tick. The label says what ticking does and says it in the same words either way. The counts above are where the current state is read, and a label that swaps sentences on click makes the two indistinguishable.

## Deliberate non-goals and lossy edges

Each of these is a decision recorded in the code, not an oversight. **Lorebooks don't travel in a card export**: `ExportedLibraryEntry` carries no books and `importChungusExport` explicitly drops `lorebookIds` from both the main data and every version, because ids are install-local and a dangling one is worse than an absent link. **Pictures travel as files, never as data**: the block's `identity` is name + tags only, and there is no zip *reader* anywhere in the app, so the folders in an export are for a human, not for a re-import. The two sets differ in what that human can then do with them: a sprite folder is already in the shape both this app's folder importer and SillyTavern read a pack out of, so it re-enters either one by being put in a profile's `characters/`, while gallery art has no reader on any side and is only ever files on disk. **A character's EXTRA lorebooks are not read**: SillyTavern keeps a primary book on the card (`extensions.world`, which is read) and any others in `settings.json` under `world_info.charLore` as `{ name: <avatar filename stem>, extraBooks: [names] }`. Both reach `getCharacterLore` there, so a character with extras arrives here linked to its primary book alone. Nothing is lost, since those books still come over as `worlds/` files; only the links to them do. Adding them is one more name lookup through the same `BookIndex`, against a file this importer already reads for the persona names. **Chats are import-only**: nothing writes `.jsonl`, and there is no chat export path of any kind. **Regex rules export in our own envelope**, never as ST scripts, so that direction is a one-way read. **Non-card fields of an ST card are dropped**, per the card mapper's lack of a `rest` bucket. **`is_system` turns are imported rather than skipped**, and **ST's "permanent rewrite" regex mode maps to both scopes**, both because ChungusHub has no destructive equivalent and inventing one would be worse than the mismatch. **SillyTavern presets are not read at all**, and this is the one non-goal with a surface: an ST preset is the wrong file people bring here on purpose, so `refusalFor` ([`preset-io.ts`](../src/lib/services/preset-io.ts)) recognizes one structurally (a `prompts` or `prompt_order` array) only to name it in the refusal, and the reader is told to rebuild in the Prompt Builder rather than left reading a parse error about their own file. That is a **refusal, not a claim on the file**: it converts nothing, so it is not the second implementation coupling 7 forbids, and it must not grow into one. Reading the format would mean mapping a prompt system this app does not have, across every preset dialect in circulation. Two edges are worth knowing before they surprise someone. **`traitCategories` does not survive a round-trip for an unversioned character**: the import path lands on `LibrarySeed`, which has no such field, while a versioned `'all'` export keeps it because the full `LibraryEntryData` rides in the `versions` array. And **`isFavorite`, timestamps and entry ids never travel**: an import is always a fresh row.

## Before touching this

- Run `bun test` after any change here; this area is genuinely covered: [`sillytavern.test.ts`](../src/lib/lorebook/sillytavern.test.ts) (both import shapes, `rest` preservation, the export fixed point), [`sillyTavernExport.test.ts`](../src/lib/services/sillyTavernExport.test.ts) (card surface, PNG round-trip through the real importer, stale-chunk stripping, an independently computed CRC, archive naming and the sprite/gallery layout), [`sillyTavernChatImport.test.ts`](../src/lib/services/sillyTavernChatImport.test.ts) (swipes as siblings, per-swipe metadata, ghosted turns), [`sillyTavernFolderScan.test.ts`](../src/lib/services/sillyTavernFolderScan.test.ts) (what a profile folder yields, that an ancestor yields nothing, and what the ledger takes back out), [`sillyTavernFolderImport.test.ts`](../src/lib/services/sillyTavernFolderImport.test.ts) (a profile whose one book sits in a world file and inside four cards shelves it once, and a second run binds to what the first left), [`sillyTavernImport.test.ts`](../src/lib/services/sillyTavernImport.test.ts) (the card's `world` link, on both card generations), [`identity.test.ts`](../src/lib/lorebook/identity.test.ts) (one book read out of both shapes is one book), [`zip.test.ts`](../src/lib/services/zip.test.ts) (the archive is parsed back byte-for-byte), and the import half of [`regex-rules.test.ts`](../src/lib/utils/regex-rules.test.ts).
- **Field names stay SillyTavern's verbatim in the lorebook model.** Translation happens at the `character_book` boundary and nowhere else; a "nicer" name in `types.ts` turns the native path from a passthrough into a second mapper to keep in sync.
- A new modelled lorebook field is four edits, not one: `types.ts`, engine resolution, `sillytavern.ts` import **and** export, plus the editor. An unmodelled one rides in `rest`/`extensions` for free. Prefer that (architecture/lorebook.md).
- A new card field must be added to `traitsToCardFields`, `mapSillyTavernToCharacter` **and** `PERMANENT_TRAITS`, or it exports blank, imports blank, or never appears. The card path has no passthrough to catch it.
- Adding a reader for a new container (a V3 `ccv3` chunk, a chat `.jsonl` writer, a zip importer) means re-deciding the claim order in the round-trip section first. Write the ordering test before the parser. The assistant's file ingest is a reader too, and unlike the pickers it chooses. A new keyword has to be placed in ITS order as well.
- **Recognizing is not importing.** The assistant's file ingest names what a dropped file is (`detectFileKind`, [`files-core.ts`](../server/assistant/files-core.ts)) by the same structural tests the parsers use (`character_book` present, `entries` as an object versus an array, a `findRegex` string, a `chat_metadata` header line), but it converts nothing and writes no row. Keeping it a recognizer is what lets it live server-side without porting a single mapper; the moment it needs to actually import one of these, the mapper it needs is client code and that is a different piece of work.
- Parsers here are **fail-loud by contract**: `parseLorebook` throws on unrecognised input rather than returning an empty book, `parseRegexRulesImport` throws when nothing is usable, `extractCharaFromPng` throws on a non-PNG or a card-less PNG, and `dataUrlToFile` throws on an unreadable embedded portrait rather than importing the entry image-less under a success report. The one sanctioned softness is per-item, at the batch level: a corrupt `.jsonl` line and a failed file in a folder import are skipped and reported, never silently swallowed.

## Hand-kept couplings

1. **`ExportedLibraryEntry.version`** ([`libraryExport.ts`](../src/lib/services/libraryExport.ts)) ↔ `buildExportBlock` / `buildSillyTavernCard` (writers) ↔ `importChungusExport` (reader). Bump together and keep old versions importable: v1 files carry no `versions` array and must keep importing unchanged. Shared with architecture/library.md coupling 5; it is one coupling seen from two sides.
2. **The claim string `'chungushub.libraryEntry'`** is checked by one predicate (`isChungusExport`) against two doors: the legacy top-level JSON and the embedded `data.extensions.chungushub` block. It is a literal in the type, in the writer and in the guard; renaming it in fewer than all three makes every export re-import as a plain ST card with no error raised.
3. **The lorebook book-override extension keys** (`max_recursion_steps`, `case_sensitive`, `match_whole_words`) are written by `bookOverrideExtensions` and read by `liftBookOverrides`. Rename in pairs. Same coupling as architecture/lorebook.md rule 3, restated here because it is what makes our own World Info export round-trip.
4. **The per-entry recursion flags carry two spellings each**, paired in `RECURSION_FIELDS` and read by `asRecursionFlags` / written by `recursionFlags` (architecture/lorebook.md rule 9). Both import paths and both export paths go through that one table; adding a flag or renaming a spelling touches the table alone, and touching anything else instead drops the setting on one of the two shapes with nothing on screen to say so.
4. **The `character_book` entry-extension lift list** is a second pair: `fromCharacterBookEntry` deletes `selectiveLogic`, `match_whole_words`, `probability`, `useProbability` out of `extensions` and `toCharacterBookEntry` writes exactly those four back in. A field added to one side and not the other either duplicates into `rest` (and then wins over the modelled value on the next export) or vanishes.
5. **The chunk keyword is the contract, and there is one chunk module.** `pngText.ts` holds both directions; character cards write `chara` and read `chara` (with `ccv3` in the replace list **only** to strip, never to write; the day something writes it, the reader learns it in the same change), preset cards write and read `chungus_preset`. A new keyword means a new claim on `.png` files: decide where it sits in the round-trip order below before writing the parser.
6. **CRC-32 has exactly one implementation** ([`crc32.ts`](../src/lib/services/crc32.ts)), used by the PNG chunk writer and the ZIP writer. Both formats reject a mismatched checksum in real readers, so a fork here produces files that look fine locally and fail in SillyTavern and in Explorer.
10. **The decoration allowlist is a fixed set, not a default.** `inline-decoration.ts` names four properties and `markdown.ts` is the only place they are applied, through a DOMPurify `afterSanitizeAttributes` hook. `ALLOWED_ATTR` alone would let `style="position:fixed;inset:0"` straight through. `inline-decoration.test.ts` pins both halves: what a real panel header keeps, and that nothing which resizes, moves, or reaches off the machine survives.
7. **The folder importer must never grow format logic**, the scan must never grow writes or start searching for the profile, and **a new imported kind must claim its source file** or the folder brings it over again on every run. It also needs a group in `planGroups`, or its files are in the bundle and on the Import button's count while being unreachable from the list that claims to show what is coming over; `sillyTavernFolderScan.test.ts` pins that the rows account for every file `countFiles` counts, so that omission fails rather than ships. A kind that becomes a library entry claims its `entity_id` too, since that is what lets a deleted one be offered again. Its contract is read-and-dispatch into the same importers the single-file UI entry points use (`CharacterLibraryView`'s card picker, `LorebooksView`'s file picker, `RegexPage`'s import, `ImportChatsDialog`'s `.jsonl` picker). A parse written inline there becomes a second implementation that drifts the moment the shared one is fixed.
8. **The chat↔character binding key** is the card's **avatar filename stem**, and it has TWO sources that must agree: the character loop for cards arriving now, and `cardStemFromKey` over the ledger for cards an earlier run claimed. Changing what either records, or lowercasing on only one side, silently strands imported chats in `skippedNoCharacter`. Worse, on a duplicated display name the fallback binds them to the wrong character with no report line at all. Anything that changes `sourceKey`'s shape changes the second source, so the two move together. **A third place asks the same question and must be moved with them**: `importRun.resolvableCharacters` assembles those two plus the library's display names so `strandedByChoice` can warn on the confirm card, before the run rather than after it. It is the only restatement of this rule that is allowed to exist, it is a name set rather than a map because it decides nothing, and a resolution rule changed in the importer alone leaves that card warning about the wrong files.
9. **The card↔lorebook binding key** is the world file's filename stem, and like the chat binding above it has TWO sources that must agree: the worlds loop, which binds `stemOf(file.name)` as it shelves each file, and `worldStemFromKey` over the ledger for world files an earlier run claimed. It is the same key SillyTavern writes into a card as `extensions.world`, so all three are one name read three ways; lowercase on only one side and every card quietly shelves its own copy of a book that is already there. Anything that changes `sourceKey`'s shape changes the ledger source, so this coupling moves with #8.
