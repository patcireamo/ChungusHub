# Prompt assembly pipeline: architecture & maintenance

The path from "user hits send" to "messages array on the wire". The design splits IO from logic so the live token meters and the real generation can never disagree (one accepted exception: the lorebook's two rolls, an entry's Trigger% and an inclusion group's weighted pick, happen once per assembly, so the meter and the send, being two assemblies, can price different entry sets; within one assembly the set is fixed, see `buildMacroContext`): [`prompt-builder.ts`](../src/lib/utils/prompt-builder.ts) gathers inputs from the db (generation path), the meters gather the same inputs reactively from stores, and **both** feed the pure assembler [`prompt-assembly.ts`](../src/lib/utils/prompt-assembly.ts). If you change assembly behavior in one place, you have changed it for every surface. That's the point. Covered by `bun test` (`prompt-assembly.test.ts`, `prompt-pruning.test.ts`).

**Presets** drive everything: a preset ([`presets.svelte.ts`](../src/lib/services/presets.svelte.ts)) is an ordered list of `PromptItem`s (role + template text) plus author-defined `PromptControl`s (widgets bound to macro names), the presentation layer around them (`sections`, `bundles`, `meta`, and the `regexRules` it carries; architecture/preset-authoring.md owns all four), and three per-preset scalars: `pruneEmptyBlocks`, `exampleSeparator` and `continuePrompt` (Prompt Builder → **Preset options**, under the item and control lists). Presets are JSON files on the server (`user-data/presets/`, seeded from `defaults/presets/`); edits go to a per-preset **draft** file (`presets/temp/<id>.json`) until Save commits or Discard drops it. `getActiveEffectivePreset()` (draft-over-committed) is what both the editor and generation use. `presetService.activatePreset()` is the only active-selection writer and owns the reactive `activePresetId`; the LLM service does not mirror it. [`PresetManager.svelte`](../src/lib/components/presets/PresetManager.svelte) is shared by Prompt Builder and Preset Controls for duplicate/import/export/delete/default-restore behavior and confirmations: Prompt Builder uses its preset picker too, Preset Controls passes `showSelect={false}` and switches from its own header dropdown. Duplicate copies the effective preset, including a live draft, without committing or discarding that source draft. JSON validation/serialization lives in [`preset-io.ts`](../src/lib/services/preset-io.ts) around one `presetDocument` shape, and the three ways out of a preset (**Export card (PNG)** / **Export JSON file** / **Copy as JSON**, all in `PresetManager`) carry exactly those bytes. The card just wraps them in the cover art (architecture/sillytavern-interchange.md). One picker takes both containers back in. An export **materializes every per-preset field at its effective value**: storage stays override-only so a shipped default can still improve under an existing preset, but a shared document that silently omits a field reads as a field the preset doesn't own, and nothing in the JSON reveals it exists. `parsePresetJson` closes the loop with `asOverride`: a value equal to the shipped default imports as no override at all, so a round trip neither freezes this install's copy of a default into someone else's preset nor shows them a Reset they never earned. `DEFAULT_EXAMPLE_SEPARATOR` (macros.ts) and `DEFAULT_CONTINUE_PROMPT` (prompt-assembly.ts) are the two shipped fallbacks, each declared once and read by both the resolver and this round trip. Control **values** are global (not per-chat), stored under the `presetControlValues` settings key ([`presetControls.svelte.ts`](../src/lib/stores/presetControls.svelte.ts)).

**Macros** ([`macros.ts`](../src/lib/macros.ts)): the single registry + engine. `MACROS` is the one list (names, docs, display group, engine vs flow, structural flags); `substitute()` the one substitution primitive (single-pass, unknown names stay literal so typos surface); `expandMacros()`/`resolveMacroValues()` the context-aware engine. Engine macros resolve from `MacroContext` on every surface; flow macros ({{batch}}, …) are filled only by their flow (memory) and layered over engine values.

**Names follow SillyTavern's wherever ST has a macro for the same thing**: `{{user}}`, `{{char}}`, `{{description}}`, `{{personality}}`, `{{scenario}}`, `{{mesExamples}}`, `{{mesExamplesRaw}}`, `{{charFirstMessage}}`, `{{charPrompt}}`, `{{charInstruction}}`, `{{charVersion}}`, `{{charCreatorNotes}}`, `{{lastMessage}}`, `{{lastUserMessage}}`, `{{lastCharMessage}}`, `{{persona}}` (its plain description, no sheet), so a preset author arriving from ST writes what their fingers already know. The macros ST has no equivalent for (`{{character}}`, `{{charCreator}}`, `{{lorebook}}`, `{{chatHistory}}`, `{{chatHistoryLastN}}`, `{{memory}}`, the memory-flow set) keep the same camelCase shape, deliberately: a registry split between two naming conventions reads as two systems. What ChungusHub does NOT take from ST is the rest of its macro language: no `::` arguments, no `{{if}}` blocks, no variables, no randomness. `substitute()` stays a pure name → string map, which is what lets the meters and generation resolve the same values twice with the same answer.

One macro is **structural**: `{{chatHistory}}` injects native-role messages (with image attachments) instead of inline text; only `prompt-assembly.resolveStructural` handles it, and `injectedTurns`/`historyTurns` (macros.ts) is the one place its turn list is derived. It carries the WHOLE path minus `excludedIds` (memory-archived + budget-trimmed), newest turn included; the three `{{last*Message}}` macros are plain inline text and take nothing away from it. A second structural macro splitting the path would let turns fall through the gap between the two and let the trim price turns the other one carries. `ctx.injectsHistory` (filled in `buildMacroContext` from the ENABLED items) exists for one reason only: the budget trim can't claim to drop turns nothing renders. The structural path is not a shortcut around the ordinary one: it applies `pruneEmptyBlocks` to each text run around the tag (an item is not exempt from the preset's own pruning just because it also injects chat turns), and it splits `{{memory}}` out of the `context` bucket the same way. An item that puts `{{memory}}` next to `{{chatHistory}}` is ordinary authoring, and pricing it as Context would make the meter's Memory row vanish on exactly those presets. Injected message content is run through `expandSelfRefs` (`{{char}}`/`{{user}}` → live persona/character names) in `toInjectedMessage`, and the inline forms do the same in `renderTranscript` and `lastTurnText`. Self-refs in stored chat rows are **never baked**, they resolve live here so a persona change reflows old turns. This must match the display-side expansion in `Message.svelte` (architecture/chat-sessions.md coupling #5). `pruneEmptyTagBlocks` implements the opt-in `<tag>…</tag>` conditional-framing pruning (bottom-up, template-side, typo-safe; rules documented in the file). The per-field character macros derive from `PERMANENT_TRAITS` (a field that gains or renames a macro needs no second edit), and `contracts.test.ts` asserts every one of them is declared in `MACROS`. A field macro missing from the registry still resolves but is invisible to every macro-reference UI. `{{mesExamples}}` is special-cased (deliberately NOT a plain `CHARACTER_FIELD_MACROS` entry): `splitExampleBlocks`/`formatExampleDialogue` split the field on SillyTavern `<START>` markers, re-head each surviving block with the preset's `exampleSeparator` (default `***`), and drop the oldest `ctx.droppedExampleBlocks` (the budget-trim signal). `{{mesExamplesRaw}}` is the same field with none of that and is deliberately outside the trim, and the field is normalized inside the `{{character}}` blob too, fixed there (not trimmable). **The lorebook places itself, and the context builder is where that is decided.** Most entries join the block `{{lorebook}}` prints, but an entry can ask to sit at a depth inside the chat instead, with its own role, and then it is a splice like steering rather than part of the macro's string. `resolveLorebooks` takes `placeAtDepth`, which is the caller saying whether it CAN splice: `buildMacroContext` passes whether the enabled preset renders `{{chatHistory}}`, and every other surface leaves it false, so an at-depth entry folds back into the block rather than landing in a position nothing renders. Both halves are admitted under ONE budget allowance in `order` sequence, since the lore budget caps everything lore injects at once. **The lorebook is resolved by the context builder, not by its macro**: `buildMacroContext` calls `resolveLorebooks` once and puts the block on `ctx.lorebook`, so `{{lorebook}}` prints a string the way `{{memory}}` does. Selection is therefore one roll per assembly however many times the tag appears and however often the trim re-resolves, and the scan's own record (`ctx.lorebookTrace`, surfaced as `PromptAssembly.lorebook`) reaches the generation path, which stores it on the turn it produced (see architecture/lorebook.md).

**Regex rules** ([`utils/regex-rules.ts`](../src/lib/utils/regex-rules.ts) + [`stores/regex-rules.svelte.ts`](../src/lib/stores/regex-rules.svelte.ts), UI in Settings → Regex): find & replace rules over chat text, per-rule targeted at user/assistant turns and scoped to display, prompt, or both (never the stored rows). Two sets run: the reader's own, then the ones the **active preset carries** (`preset.regexRules`, architecture/preset-authoring.md), each at its effective switch position (the author's shipped `enabled`, unless the reader recorded a deviation in `carriedOverrides`). `rulesWithCarried` joins them and `regexRulesStore.effective` is the single getter every consumer reads; preset rules run last on purpose, so an author's presentation layer sits on top of the reader's own cleanups rather than under them. The prompt-scope application happens **once, in `buildMacroContext`**: `applyPromptRegex` rewrites `input.chatMessages` before anything derives from them, so structural injection, `recentMessages` (lorebook scanning) and the budget trim all read the same transformed turns (the trim deliberately counts `ctx.chatMessages`, not `input.chatMessages`). Sidecar flows via `live-macro-context.ts` deliberately see raw content: regex is a chat-surface concern, and memory analyzes the real story text. Display-scope application lives in the chat components (architecture/chat-sessions.md). Engine covered by `regex-rules.test.ts`; assembly behavior by `prompt-assembly.test.ts`.

**A rule can also be bounded by depth**, and that is what lets one treat the live turn differently from the ones behind it. `minDepth`/`maxDepth` are inclusive turn counts back from the newest turn, 0 being the newest, and either being `undefined` is no bound (the default, and the whole story). The case it exists for is the one a preset that prints story state cannot solve any other way: the state block is a full snapshot, so only the newest one carries information, and a prompt-scope rule at `minDepth: 2` strips it from every reply behind that. Depth 2 rather than 1 because a send appends the user's turn first, which makes the newest **reply** turn 1. **`applyRegexRules` takes the depth as a required argument**: a caller that guessed would have to guess 0, and every bounded rule would then quietly run on the text it was told to leave alone. `applyPromptRegex` reads it off the array's own tail, so the turns being priced and the turns being sent are numbered identically; the display side is counted by `MessageList` (architecture/chat-sessions.md). A range with nothing inside it (`minDepth` past `maxDepth`) is inert, and `isRuleInert`/`routingSentence` say so in the same breath as an empty target list. Both bounds cross the SillyTavern boundary unchanged, since ST counts turns back from the newest too (architecture/sillytavern-interchange.md).

**Assembly** (`assemblePrompt`): resolve each enabled item → messages + token attribution in four buckets (preset / context / memory / chat), then the **context-budget trim**: if the total exceeds `contextBudget` (from `llmService.getPromptTokenBudget(target)`, in calibrated base-estimate space; see architecture/tokenizer-debug.md), first push example-dialogue blocks out oldest-first (re-resolving with a rising `droppedExampleBlocks`), then drop the oldest contiguous `{{chatHistory}}` turns and re-resolve; `overBudget` flags when even that isn't enough. A budget too small for the whole history takes the newest turn with it: nothing shields the turn being answered; `overBudget` is the loud half of that. Examples yield before history because they teach voice, which matters less than recent turns as a chat grows. Memory-archived turn ids are excluded from history only when the preset actually injects `{{memory}}`; that archived set is derived per-path by the memory engine (architecture/memory.md), so it follows a branch switch with no round trip. The trim is the one way story text can leave the prompt with nothing recalling it (the turns it drops are live, hence by definition not covered by a summary), so `trimmedMessages`/`overBudget` are surfaced on the composer's token chip itself, not only inside its popover, **and** on the Prompt Builder's item header. That view's per-row numbers price what each item resolves to while its total prices what fits, so without the flag the two just silently disagree. Finally `applyPostProcessing` reshapes for restricted APIs (none / merge / semi-strict / strict / single-user, per-connection setting).

**Continuation tail** (`AssembleInput.continuation`, continue-in-place, and deliberately NOT an engine: architecture/engines.md): the assistant turn being extended appends after every preset item, right before post-processing (run through prompt regex + `toInjectedMessage` exactly like an injected history turn, so self-refs resolve live), and then the preset's own `continuePrompt` as a final user message. That instruction is **preset state, not app state**: absent falls back to `DEFAULT_CONTINUE_PROMPT`, an empty/blank one is skipped and leaves the trailing assistant turn as a native prefill, and `continuationTail` macro-expands it against the SAME `MacroContext` as everything else in the prompt, the reason it resolves here rather than at the call site. `chatMessages` must be the path up to the turn's parent (the same prompt that would regenerate it), never include the turn itself. The tail is fixed cost: `continuationTail` prices it and every budget-trim comparison adds `tail.tokens`, so history yields room for it; it also survives the empty-preset `systemFallback`. Both exits surface the tail turn's content as `PromptAssembly.continuationSent` (through `BuiltPrompt`), the anchor the store's restatement trim compares the model's reply against: it is the text the model actually saw, and anchoring on the stored bytes instead lets a restated macro-laden greeting through to be appended twice (architecture/chat-sessions.md owns the join rules). The meters never pass `continuation`: a continue is a one-shot action, not standing prompt state. Note the tail carries ONLY the extended turn; with a non-user parent (stacked dummy assistant turns) the turns between the last user message and the target ride `{{chatHistory}}`, which carries the whole path.

**Steering injection** (`AssembleInput.steering`, the Steering engine; architecture/engines.md): `{ notes: { text, depth, role }[], wrapper }`. The **notes arrive already resolved**: scope matching and placement inheritance happen in the pure `types/steering.ts` before assembly is called (`resolveSteeringForPrompt`; generation side reads the `steering_notes` rows fresh, meter side resolves the store's cache), gated by `featurePromptsStore.steeringEnabled` at BOTH sites identically. `buildSteeringMessages` then **groups** them: notes sharing a role AND a depth are joined with a blank line and wrapped ONCE, so a stack of five is not five turns scattered through the prompt, and a single note comes out byte-for-byte as if no grouping happened. Per group: `expandMacros` over the joined text (so `{{char}}`/`{{user}}` resolve; after the join, so one note can't be swallowed by another's trailing macro), then `substitute` on the wrapper with `{{steering}}` layered as an ad-hoc call-site key over the wrapper's own macro values (the opening scene's `{{idea}}` pattern; deliberately NOT a MACROS entry, so the macro reference stays honest for preset authors).

**Placement is SillyTavern's author's-note model**: steering always rides inside the injected chat, never after the preset's post-history blocks. `depth` counts back from the end of the injected sequence: `{{chatHistory}}`'s turns, derived in `injectedTurns` so the tag can never render a different set than a depth was counted over. 0 (the default) lands right after the newest turn, N lands N turns before it, and a depth deeper than the injected chat clamps to the front. `placeSplices` splices each group into the history at that position. It is shared with the lorebook: an entry placed at a depth builds the same `DepthSplice` shape and travels the same path, deliberately, so one placement rule serves both and the two cannot drift. Splices are carried on ctx (`splices`) so the example/history trim re-resolves place them consistently against their own filtered chat. At a shared slot the array order decides, and lore is built first, so the background sits ahead of the reader's own direction. Every position is measured against the UNSPLICED sequence and the result rebuilt in one pass, so several splices can't shift each other's target and groups landing on the same slot keep their own order. An identity-tracked fallback net appends any group at the END of the assembly whenever its position was rendered by nothing (no `{{chatHistory}}` in the preset, or the trim left nothing to inject). Steering never silently vanishes.

It is **fixed cost like the tail**: `fixedExtra = tail.tokens + Σ spliceTokens` (steering and at-depth lore together) rides every budget comparison so history yields room for it and none of it is ever itself trimmed; each group's tokens are attributed exactly once, to the `context` bucket, on either path, and every group survives the empty-preset `systemFallback` (ordered system → steering → tail). Unlike the continuation tail, the chat meter (InputArea) DOES pass steering: it is standing prompt state, and the meter must price what a send will inject; `PromptBuilderView` deliberately does not (it prices the preset, not transient composer state). Known accepted edges: a degenerate preset with `{{chatHistory}}` twice splices steering into each occurrence exactly as the history itself duplicates; a splice into a tagged-but-empty history keeps that item's framing text alive; and a group landing inside a tag-framed item **splits that item's framing across messages** (`<history>` / turns / guidance / `</history>`) unless the note's role matches the item's, which merges them back into one. That last one is accepted rather than special-cased: the alternative is a depth 0 that means something categorically different from every other depth. One-shot spending and the pre-build debounce flush are messageStore's job: architecture/chat-sessions.md.

**Sampling params** ([`config/sampling.ts`](../src/lib/config/sampling.ts)) are a sibling concern: `SAMPLING_SLIDERS` is the one list of knobs (UI range + `supportedKey` + `apiField` + neutral value), and `buildGenerationParams` / `buildGenerationTuning` build the request fields filtered by the provider's `paramPolicy` and the model's reported capabilities, kept in lockstep with the visibility helpers so **"visible === sent"** (the same invariant architecture/llm-providers.md describes from the server side).

**Who calls what**: `messageStore` (send/regenerate/opening-scene/continue) → `buildPromptMessages` → `assemblePrompt`. `PromptBuildContext.target` (default `'primary'`) is the routing point the caller would ride: send, regenerate and continue stay `'primary'`, while opening-scene passes `{ engine: id }` so its assigned connection applies to assembly exactly as it does to the call itself (architecture/engines.md coupling 4). **Which connection that resolves to is [`utils/chat-setup.ts`](../src/lib/utils/chat-setup.ts)'s `resolvePromptTarget(chat, base)` and nothing else's**: it hands back the call target plus the three things assembly needs in that connection's terms (model for token counting, context budget, post-processing/placeholder), and `BuiltPrompt.target` carries it out so the send rides the connection its budget was counted against and the review dialog names that model. The chat is handed in rather than reached for, so the generation path can import the module without closing live-macro-context.ts's cycle. Substitute-level flows (the opening scene's `{{idea}}`, the composer transforms' `{{draft}}`) build a `MacroContext` via [`live-macro-context.ts`](../src/lib/utils/live-macro-context.ts) (store-sourced twin of prompt-builder's db-sourced resolution; deliberately not used by the memory store, because of an import cycle). The Prompt Builder view and chat meters call `resolveItem`/`assemblePrompt` directly for live breakdowns.

**The prompt hold** ([`stores/promptHold.svelte.ts`](../src/lib/stores/promptHold.svelte.ts), gates declared once in [`config/prompt-hold.ts`](../src/lib/config/prompt-hold.ts)) is the one stage between a built prompt and the wire: `promptHoldStore.review(gate, messages, target)` hands the messages straight back when that gate is disarmed (the default, and free), and otherwise parks them until the reader releases the review. **What comes back is what is sent**, byte for byte, so the hold is the one place in the app where the messages assembly produced are not the messages the provider receives, and every caller passes the returned array on rather than rebuilding. Five gates, all of them a press somebody made: send, regenerate, continue, spellcheck, impersonate. Nothing that fires on its own has one, because a held background request would be a queue of prompts nobody asked to see. **Cancelling resolves to null and the caller must then have written nothing at all**, which is why the hold sits in `messageStore.prepare` above the tree mutations and inside `runComposerTransform` before the call, never beside `llmService.complete` (architecture/chat-sessions.md). The reader's edits reach only `messages`: the `lorebook` trace and `oneShotSteering` ids ride through untouched, since they record the scan and the guidance that shaped the prompt, which happened either way. Known and accepted: a hand-edited prompt can contradict the trace stored on the turn it produces, and the review shows the request one step before `llmService.complete` strips attachments for a model that takes no images, the same boundary the debug panel documents (architecture/tokenizer-debug.md). The surface itself is [`PromptReviewDialog.svelte`](../src/lib/components/chat/PromptReviewDialog.svelte) (architecture/ui-shell-settings.md); the JSON boundary it edits through is the pure [`utils/prompt-review.ts`](../src/lib/utils/prompt-review.ts), which refuses a shape it does not recognise by name rather than repairing it.

The reader-facing `PresetControlsView` uses the shell's shared stacked utility-overlay header and embeds the same preset manager as Prompt Builder, riding the subject line beside the preset switcher (`compact`, menu-only), since its menu acts on the preset the switcher names; authoring-only item/control edits remain in Prompt Builder.

Prompt Builder's preset picker, save control, and preset-action menu remain in normal document flow rather than sticking to the Settings scroller.

## Before touching this

- A new foreground generation the reader triggers by hand gets a hold gate, or the setting silently means "some of your requests". One entry in `HOLD_GATES`, one `review` call above every write that path does.
- Any change to what gets sent MUST go through `prompt-assembly.ts` (or `macros.ts`), never be patched into one caller. Otherwise meters and generation drift, which is the exact failure this design exists to prevent. Run `bun test` after.
- New macro = one entry in `MACROS` plus its resolution in `resolveMacro` (engine) or the owning flow (flow macro). Never write a bespoke `{{...}}` regex anywhere. Use `substitute`/`MACRO_REGEX`.
- New sampling knob = one `SAMPLING_SLIDERS` entry; check the per-provider allow-lists in `server/llm/providers/*` name the same `apiField`.
- Token counting anywhere in this path must use `countTokens(text, model)` with the same model id end-to-end.

## Hand-kept couplings

1. Structural macro names: **one source.** `MACROS`'s `structural: true` flag drives everything: `macros.ts` exports the derived `STRUCTURAL_MACROS` list, `resolveMacro`'s nested-expansion early-return tests against it, and both regexes in prompt-assembly.ts (`STRUCTURAL_TAG_RE` for the detect, `resolveStructural`'s scanner for the split) are built from the same derived alternation. Declaring a macro structural in the registry is the only edit.
1b. The turns `{{chatHistory}}` injects come from `historyTurns` (macros.ts) and NOTHING else: `injectedTurns` (what the tag renders + what a steering depth is counted over) and the budget trim's history token count both call it. Compute a history slice by hand at either site and the trim starts pricing a different set than the send injects, or a depth lands one turn off what the meter showed.
2. Slider `apiField` names (sampling.ts) ↔ provider profile allow-lists (server). The Mistral `random_seed` mismatch is the documented example of why. Asserted in [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts); see architecture/llm-providers.md coupling #4.
3. `buildMacroContext` (prompt-assembly), `buildLiveMacroContext` (live-macro-context.ts) and the memory store's own `macroContext` resolve character/persona/lorebooks/budget in parallel: a resolution change must land in all three. The lorebook half of that is no longer hand-kept: all three call `resolveLorebooks` (lorebook/engine.ts), the one function that scans and renders, so a surface cannot select differently from the one that sends, and all three gather the card text a scan may read through the one `lorebookScanFields`. Anything a new builder resolves by hand instead is a fork by definition. What the three DO have to pass by hand is the generation kind (`lorebookTrigger`), since only the caller knows it: absent reads as a plain send, which is right for the meters and wrong for anything else. The path's own earlier traces go the same way, through the one `lorebookHistory`, and they are what the sticky and cooldown windows are measured against.
3b. **Character-version pinning has FIVE resolution sites**, and every one of them must resolve the CHAT's pin (`chat.characterVersionId`), never the library's active version: `prompt-builder.ts` (generation, swaps in the pinned row's data from the db), `live-macro-context.ts` (the substitute-level surfaces, via `characterLibraryStore.dataForVersion`), `InputArea.svelte` (chat meter, same call), `PromptBuilderView.svelte` (builder breakdown, same call), and `memory/store.svelte.ts` `macroContext` (via `ChatCtx.characterVersionId`, which every `ChatCtx` construction site must fill). A site that reads `entry.data` directly is reading the active variant by definition, which is the bug this coupling exists to prevent: it costs the pinned chat both its card sheet AND its linked lorebooks. Neither the db path nor `dataForVersion` shortcuts "pinned == active": both always go through the version row, so a pinned chat's prompt cannot shift because the active pointer moved elsewhere.
4. Preset draft semantics: `presetService.sameContent` (client) decides draft existence; the server blindly stores what it's told. Keep "no-op edit = no draft" client-side.
5. `DEFAULT_SYSTEM_PROMPT` fallback fires when the preset is empty/missing. Behavior surfaces silently; don't remove without a replacement.
6. Preset REST mutations broadcast the `presets` sync scope; `presetService.syncReload()` replaces committed/draft maps and ticks `contentVersion` so an open Prompt Builder refreshes even when the active id did not change.
7. Every `AssembleInput` construction site passes `regexRules: regexRulesStore.effective`. Those sites are prompt-builder.ts (generation), InputArea.svelte (chat meter) and PromptBuilderView.svelte (builder breakdown). **`effective`, never `rules`**: it is the reader's own rules plus the ones the active preset carries at their effective switch positions, and it is the same getter the transcript's `forDisplay` reads, so a preset's presentation layer can never apply on one surface and not another. A site that omits the field entirely silently assembles without prompt-scope regex, and the meter/generation agreement breaks exactly when rules are active.
8. `AssembleInput.steering` parity: prompt-builder.ts (generation) and InputArea.svelte (chat meter) both build their note list through the SAME pure resolver: `resolveSteeringForPrompt(notes, steeringTargetForChat(chat), featurePromptsStore.steeringDefaults)` under the same `steeringEnabled` gate, with the same `steeringWrapper` template. They differ only in where the notes come from (fresh db rows vs the store's cache), deliberately, the way lorebook resolution differs. Fork that resolution (re-implement the scope match or the inheritance at a call site) and the meter starts pricing a different stack than the send injects. PromptBuilderView deliberately omits steering entirely (it prices the preset, not transient story state). A new AssembleInput site with live chat context must make this choice consciously. The generation side takes one thing more off those rows that the meter has no use for: `BuiltPrompt.oneShotSteering`, the `once` notes with their ids, which ride the request so the turn's commit spends exactly what the turn sent (architecture/chat-sessions.md). It is read off `activeSteeringNotes` beside the resolver rather than threaded through it, because the pure resolver deliberately hands assembly text/depth/role and no identity.
9. **Per-preset fields are whitelisted end to end, and each side now has exactly one list.** Client: `clonePresetBody` in `presets.svelte.ts`. `hydrate`, `strip`, `clone`, `duplicatePreset` and the exported `clonePreset` (which IS `PromptBuilderView`'s working copy) all route through it, and its key order is load-bearing because `strip` drives `sameContent` by comparing serialized output. Server: `presetFileShape` in `files.ts`, shared by `ensureDefaultPresets`/`readPresetDir`/`writePresetFile`, with `PresetFileData` as the type both preset PUT handlers in `index.ts` name. Interchange: `presetDocument`/`parsePresetJson` in `preset-io.ts`. A field with a shipped fallback must be written at its EFFECTIVE value there or it vanishes from the export whenever nobody overrode it, and `meta.cover` is deliberately excluded because a stored image path means nothing on another install. The fields are `sections`, `bundles`, `meta`, `regexRules`, `pruneEmptyBlocks`, `exampleSeparator`, `continuePrompt`, plus `PromptItem.note`. A new one dropped from any of the three lists is silently lost on save. See architecture/server-core.md and architecture/preset-authoring.md.
10. **One resolution of the connection a chat's prompt is built in.** `resolvePromptTarget` (chat-setup.ts) is where `model`, `postProcessing` and `contextBudget` come from, on every surface that assembles: prompt-builder.ts (generation), InputArea.svelte (chat meter), PromptBuilderView.svelte (builder breakdown), plus live-macro-context.ts for its lorebook budget. A site reaching for `llmService.getPrimaryModel/getPromptTokenBudget/getPromptPostProcessing/getPromptPlaceholder` itself is a fork by definition: the meter then trims to one context window while the send goes out on another, with nothing on screen saying so.
