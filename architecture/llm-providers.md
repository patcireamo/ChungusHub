# LLM provider layer: architecture & maintenance

All model I/O is server-side ([`server/llm/`](../server/llm)); API keys never reach the client. The client half is one façade, [`src/lib/services/llm/provider.ts`](../src/lib/services/llm/provider.ts) (`llmService`), which resolves **which Connection serves each calling point** and streams completions over the WebSocket (`llmComplete` in transport.ts). Non-streaming control-plane calls (models list, validation, endpoints, account) go over REST (`/api/llm/*`).

**Two stream clocks ride every result**, and they are measured in [`transport.ts`](../src/lib/services/transport.ts) rather than at any call site, because that is the one place every token frame passes through: a clock per call site would be a clock started at a different point per call site. `firstTokenMs` is the request leaving this page until the first streamed token **of either kind**, reasoning included, since on a model that thinks first its first thinking token IS the moment the wait ended and timing from the first content token instead would report the whole reasoning phase as dead air. `reasoningMs` is the reasoning stream's own span, first thinking token to last. Both are null when nothing streamed, which is every non-streamed call (`generation.streamResponses` off withholds `onToken`, and no token then arrives to be the first one), and `reasoningMs` is also null for a turn that produced no reasoning. A provider that buffers its reasoning and flushes it in one frame reports a span near zero, correctly: the thinking time it hid lands in `firstTokenMs`, which is where the wait actually showed. The chat's three generate paths persist both on the assistant turn beside the `generationMs` they clock themselves (architecture/server-core.md); every other caller simply ignores them.

**Connections & routing**: the user-facing selection model. A **Connection** ([`Connection` in `src/lib/types/llm.ts`](../src/lib/types/llm.ts)) is a self-contained bundle: `{ id, name, provider, model, contextSize, postProcessing, promptPlaceholder, routing, samplingParams, reasoningDialect, generation }` (full per-connection `GenerationSettings`; `samplingParams` and `reasoningDialect` are the two BYO declarations described under **Sampling Parameters** and **Declared reasoning** below, empty/`'none'` and inert for every other provider). Its secret half (API key + base URL) lives server-side keyed by `id` in `connection_credentials`, never in the object. The [`connectionStore`](../src/lib/stores/connections.svelte.ts) owns the connection list + the flat routing map, both riding the settings spine. Routing is ONE flat map (`connectionStore.assignments`, the `connectionAssignments` settings key; a point whose id is absent or dangling lands on the first connection, in the UI immediately rather than behind a hidden rule): every calling **point** carries its own concrete connection id. Those points are `primary` (the story), `assistant` (the Chungus Assistant), and each calling engine by id (`ASSIGNMENT_IDS`, registry-derived; Steering makes no call and is absent). No roles, no groups, no defaults-following, no pins, no warnings: the Connections page's **Model routing** card is the whole truth, one always-visible pill row per point with the two points the user drives directly (Primary / Assistant) lightly emphasized on top and every calling engine below the divider. A fresh install binds every point to the one Default connection; a new connection starts unused until the user points a row at it; deleting a connection moves anything routed to it onto the first remaining one (visible in the UI immediately). The Engines settings page shows the resolved connection read-only and never assigns. `llmService` is a resolver over that store: `complete(target, opts)`, `modelFor/providerFor/connectionIdFor/getGenerationTuning/routingFor/sendsImages(target)`, `resolveConnectionParams(target)` (where a `CallTarget` is `'primary'`, `'assistant'`, or `{ engine: id }`, all straight lookups in the map), and the prompt-assembly helpers (`getPromptPostProcessing/Placeholder`, `getPromptTokenBudget`, which is target-aware with a `'primary'` default, so Opening Scene assembles in its own connection's terms; `getPrimaryModel` stays primary-only for the meters and labels). Every WS/REST call carries `connectionId`; the model cache is keyed by connection id (two connections on one provider can hold different keys/base URLs → different model lists). **Sampling economics** (deliberate, and without exceptions): **every** call builds its params from its own resolved connection's `generation` block. Assigning a connection and then overriding its settings would make assigning it pointless. That includes the **Chungus Assistant**, which reaches the same builder through `resolveConnectionParams('assistant')` because its tool loop rides its own WebSocket channel instead of `complete()`; nothing in the app carries app-owned sampling, an output cap of its own, or a hardcoded context window.

The Connections page's connection list defaults to at most four visible cards; the rest sit behind its local expand control. Creating or duplicating a connection keeps the overview open, expands the list when needed, scrolls the new card into view, and pulses it with the shared Assistant navigation highlight instead of navigating into its editor.

**Registry** ([`server/llm/registry.ts`](../server/llm/registry.ts)): the only entry point the rest of the server uses, through `complete(connectionId, provider, opts)` (chat + every sidecar query) and `completeWithTools(connectionId, provider, opts)` (Chungus Assistant). It re-reads credentials from `connection_credentials` by connection id before every call (a key saved in the editor applies immediately), translates the connection's OpenRouter routing (`opts.routing`, sent per request, camelCase→snake_case via `toProviderField`), and exposes `providerMetadata()`, the capability sheet the client UI renders from.

**Profiles, not subclasses**: every provider is a `ProviderProfile` ([`providers/types.ts`](../server/llm/providers/types.ts)), a data file declaring base URL, auth, and honest capability policies: `paramPolicy` (which sampling knobs the API accepts: `'reported'` per-model / `'base-only'` / static allow-list / `'declared'` = unknowable from here, so the connection carries the list; see **Sampling Parameters**), `reasoning` (effort vocabulary + wire dialect, or `'declared'` = unknowable from here, so the connection names the dialect; see **Declared reasoning**), `media` (image parts, per-model gating, the Mistral bare-string quirk), `caching` (`'explicit'` = we place `cache_control`, `'auto'` = server-side no-opt-out), `verbosity`, `serviceTier`, plus optional hooks: `normalizeModel` (provider-specific /models field mapping), `fetchAccount` (balance ledger), `fetchModelEndpoints` (OpenRouter), `createProvider` (the registry instantiates that native implementation instead of the generic class, for Anthropic only). **The guiding invariant is "visible === sent"**: the client hides any control the profile doesn't declare, and providers translate only declared tuning, so a knob left over from another connection never leaks into a strict API's request. For the 13 providers whose API we know, visible also means *accepted*; behind a BYO endpoint it cannot, so `'declared'` hands that half to the only party who knows (below). Extensive per-provider reasoning is written as comments in each profile file. Read the profile before touching its provider.

**Base URL resolution (BYO endpoints only).** `openai-compatible` is the one profile with `baseUrlEditable`, and where under `<typed>` the API actually lives is unknowable from the string: llama.cpp and LiteLLM answer at both the root and `/v1`, LM Studio and Ollama only under `/v1`, and a gateway path can end in something else entirely (Cloudflare's `/openai`, Azure's deployment path) while carrying a `/v1` mid-path. Every string rule has a counterexample, so nothing is ever rewritten on a guess. The class asks the endpoint: `baseCandidates()` yields the typed URL, the stem of a pasted full endpoint URL (`…/models` / `…/chat/completions`), and the `/v1`-toggled twin (a URL carrying a query or hash gets no derived candidates), and `probeModels()` walks them with GET /models under evidence rules: only a **JSON model list proves** a base and pins it in `resolvedBases` (the pin derives from the response's final URL, so a redirect pins the base that really answered); a 404 **or a 200 that is not a model list** (an SPA catch-all page, a status page) means "not here, keep walking"; an auth rejection or server error is **held as the best answer but never pinned**. A later candidate with proof outranks it, and nothing sticks while the key is wrong. A pinned base that stops proving is dropped and re-walked in the same call, so a stack swap behind the same URL heals on next use instead of staying broken for the life of the process; an unreachable host throws naming the typed URL (candidates differ only in path, so reachability is host-level). When nothing serves a model list, `fetchAvailableModels()` and `validateCredentials()` fail with a message naming every URL tried; that message rides `/api/llm/validate`'s `{valid:false, error}` into `llmService.validateConnection().error` and the editor's connection-error line. Swallowing it regresses "no API found here" into a generic credentials rejection. **Generation** (`resolveBase()`, awaited by the four `/chat/completions` call sites) is more forgiving on purpose: with no proof it sends to an engaged base when one exists (the endpoint's real auth error is the truthful failure) and otherwise to the typed URL as written. An endpoint serving only /chat/completions with no /models must still get its request, with the POST's own failure as the loud signal. Because the registry reuses one instance per provider and `configure()` mutates it, every completion snapshots its base URL + headers before its first await: the probe must not let a concurrent request for another connection swap credentials under this one (`runtime()` captures the same way for profile hooks). Trailing slashes are stripped in `configure()` (a pasted `.../v1/` would otherwise request `.../v1//models`). The correction is **shown, never silent**: `resolvedBaseUrl()` (null unless the pin differs from what was typed) rides the `/api/llm/models` response to `llmService.getResolvedBaseUrl()` and the connection hero prints it under the URL field, which keeps the user's text exactly as typed. A fixed-endpoint provider has one candidate and never probes: the 13 profiles whose endpoint we know must not shift under the user. Covered in `openai-compatible.test.ts` against live local servers: `/v1`-only, root-mounted, an HTML-everywhere web UI, an auth wall, a redirecting /models, a /models-less chat-only proxy, and a mount that moves mid-process.

**Two implementations** run the profiles: [`openai-compatible.ts`](../server/llm/openai-compatible.ts) (the generic class 13 of 14 providers use: /chat/completions streaming + non-streaming, tool-calling for the assistant, inline-reasoning extraction on the **plain** completion paths via [`inline-reasoning.ts`](../server/llm/inline-reasoning.ts), which is one curated marker table (think/thinking/reasoning tags, Magistral `[THINK]`, Harmony channels, Gemma) run through one chunk-split-safe state machine for streaming and one-shot alike (tested in `inline-reasoning.test.ts` plus the live-endpoint wiring tests in `openai-compatible.test.ts`; skipped when `tuning.parseInlineReasoning === false`; orphan close markers deliberately not guessed at). The **tool-calling path deliberately skips inline extraction**: the assistant legitimately quotes marker-like text ("fix the `<think>` tag in that message"), and an unclosed marker would silently reroute the rest of its reply into the thinking channel. Structured reasoning fields still stream. **Both implementations decide streaming by one rule, on the plain path and the tool path alike: whether the caller passed `onToken`.** That is how a connection's Stream response setting reaches the wire (`complete()` withholds the callback, and the assistant loop withholds all three of them), and a non-streamed tool call therefore posts `stream:false` and reads the step's reply, reasoning and tool calls out of the one response body, with the same fail-loud guard against a body carrying nothing and no finish signal. Both SSE loops treat a mid-stream `{"error": {...}}` event (OpenRouter's 200-then-fail shape) as a thrown error (never a quietly empty "successful" completion), and a tool call that accumulates arguments without ever getting a name throws as a corrupt stream. A **user abort is the one deliberate exception to failing loud**: both loops catch it, stop reading, and RESOLVE with everything accumulated so far under `finishReason: 'cancelled'`, which is also what exempts an aborted empty stream from the closed-with-no-output guard beside it. That partial is not a courtesy: the client persists it as the turn, so a Stop keeps the text the user watched arrive (architecture/chat-sessions.md), and an abort that threw here instead would lose it. Asserted in `openai-compatible.test.ts`. Also: reasoning-field normalization, cache-token normalization across four reporting shapes, error unwrapping incl. OpenRouter's `metadata.raw` (shared by HTTP errors and stream error events) and [`anthropic-native.ts`](../server/llm/anthropic-native.ts) (real Messages API: system-block hoisting, placeholder first user turn, adaptive vs budget thinking per live /models capabilities, explicit cache breakpoints, and an **in-process `rawTurns` cache** replaying thinking+tool_use blocks the transport can't carry, so a server restart mid-assistant-conversation loses those, by design). All network I/O rides the hardened primitives in [`net.ts`](../server/llm/net.ts) (header deadlines, per-chunk idle timeouts, body caps, one shared SSE parser). Never call `fetch` directly in a provider. Image attachments travel as `images/<category>/<file>` paths and become bytes only at request-build time via [`media.ts`](../server/llm/media.ts) (path-traversal guarded).

**Adding a provider** = one profile file in `providers/`, one line in [`providers/index.ts`](../server/llm/providers/index.ts) (display order), and the `PROVIDER_NAMES` array in [`src/lib/types/llm.ts`](../src/lib/types/llm.ts) (the client's `ProviderName` derives from it) plus the `ProviderName` union in [`server/llm/types.ts`](../server/llm/types.ts). Model lists are always fetched live from /models: no hardcoded fallbacks, a dead endpoint fails loudly. **A list is never the whole truth, so the picker takes a typed id too** ([`ModelPicker`](../src/lib/components/settings/ModelPicker.svelte)): typing anything not already in the list offers it verbatim on a row pinned below the scrolling list (never inside it, where a few hundred matches would bury it), and `Connection.model` stores it unchanged. That is the only way to reach an endpoint serving /chat/completions and no /models at all, which `resolveBase()` deliberately still posts to, and it is also how OpenRouter's `:nitro`/`:floor` shortcuts get used, since those work on any model without being listed. The connection editor says "Not in the loaded model list" only when a list exists to contradict; with no list the hero's red "no API here" verdict carries a line saying requests still go to the URL as typed, because a mistyped URL is the likelier cause and must keep shouting.

**Client façade** (`llmService`): a resolver over `connectionStore`, holding only provider metadata and the per-connection model cache. It owns no generation state of its own: provider, model, context size, sampling, output cap, streaming, post-processing and routing are all fields on the resolved Connection, for every caller including the Chungus Assistant (architecture/chungus-assistant.md). Active preset state deliberately belongs only to `presetService`; `llmService` neither caches nor writes it. `complete(surface, opts)` resolves the surface's connection, builds tuning via `buildGenerationTuning` from that connection's `generation`, and strips `images` unless `sendsImages(surface)` (connection toggle + provider media policy + model modality) passes, the same gate the assistant panel and chat both use. `getPromptTokenBudget()` (primary connection) converts the real-token budget (context − response − margin) into the tokenizer's estimate space via per-model calibration (see architecture/tokenizer-debug.md). Param building lives in [`src/lib/config/sampling.ts`](../src/lib/config/sampling.ts) (part of the generation-settings UI contract; read it together with `paramPolicy`).

**Sampling Parameters** (a connection editor's Sampling card, Settings → Connections → open a connection): the sliders edit the connection's concrete `GenerationSettings` sampling fields directly, with no abstraction between the UI and the stored blob. Visibility comes from `sliderVisible` per the connection provider's `paramPolicy` ("visible === sent"), and each slider double-click-resets to its `DEFAULT_GENERATION_SETTINGS` value. These settings apply to **every** call that connection serves, story, engine or assistant alike: point Memory at a connection and Memory runs on that connection's temperature and response length; point the Chungus Assistant at one and its tool loop runs on that connection's sampling, Max tokens, Context Size and Stream response toggle. Nothing overrides them.

**Declared params (BYO endpoints only).** `openai-compatible` is the one profile whose accepted params nothing on our side can know: the user supplies the base URL, those stacks (llama.cpp, LM Studio, vLLM) serve exactly the RP knobs (`min_p`, `top_k`, `repetition_penalty`) that a `'base-only'` policy hides, and their `/models` never reports `supported_parameters`, so `'reported'` would degrade to base-only too. Falling back to the safest set would present "we don't know" to the user as "your endpoint hasn't got these". Its profile declares `paramPolicy: 'declared'` and the allow-list lives on the connection (`Connection.samplingParams`), written in the Sampling card's **Accepted by this endpoint** chip row by the person who stood the endpoint up, the only party who knows. [`resolveParamPolicy`](../src/lib/config/sampling.ts) collapses `'declared'` into that plain allow-list at the two sites that resolve a policy (ConnectionEditor, `getGenerationParams`), and everything downstream runs the SAME allow-list branch the static-list providers already use, which is why "visible === sent" needs no second proof here. The helpers take `ResolvedParamPolicy` (`ParamPolicy` minus `'declared'`), so forgetting to resolve is a compile error instead of a silent fall-through to the `'reported'` branch. An empty declaration behaves exactly like `'base-only'`, and that is the state every connection stays in until its owner says otherwise: nothing is assumed on the user's behalf. The vocabulary `DECLARABLE_PARAMS` is derived from `SAMPLING_SLIDERS` (every non-base slider plus `seed`); temperature is absent because it is the universal knob, always sent and never declarable. Scope is deliberate: the other 13 profiles keep their literal policies, because we DO know what those APIs accept and opening them to a user declaration would be a regression. Known non-goal: the declaration picks WHICH knob is sent, not what it is named, so a stack that wants `repeat_penalty` rather than `repetition_penalty` (LM Studio documents exactly that name) still needs a per-knob field-name override that does not exist yet. Declaring that knob there sends a field such a server ignores, silently.

**Declared reasoning (BYO endpoints only).** The same problem in a different vocabulary, and the same answer. These stacks disagree on which request field carries the thinking settings (vLLM, Ollama, llama.cpp and NVIDIA NIM read a flat `reasoning_effort`; gateways built on OpenRouter's request shape read a nested `reasoning: {effort, exclude}`), /models never reports it, and guessing would either hide a control that works or send a field that 4xx's. So `openai-compatible` declares `reasoning: 'declared'` and the connection names its dialect (`Connection.reasoningDialect`), written in the Response card's Reasoning section by the person who stood the endpoint up. [`resolveReasoningPolicy`](../src/lib/config/sampling.ts) collapses the pair into a plain `ReasoningPolicy` at the three sites that resolve one (ConnectionEditor's three visibility deriveds, `buildGenerationTuning`), and everything downstream runs the SAME branch the 13 known providers already use, which is why "visible === sent" needs no second proof here. The helpers take `ReasoningPolicy | null`, so forgetting to resolve is a compile error rather than a control that renders and sends nothing. `REASONING_DIALECTS` is the one table: the editor's Select renders from it and the resolver reads from it, so a dialect cannot be offered without a translation behind it, and its effort levels are the documented ones rather than a superset (vLLM takes low/medium/high plus `none` to disable, Ollama rejects `minimal`, llama.cpp acts only on `none`). **The resolved policy rides `GenerationTuning.reasoningPolicy`**, not a field of its own beside `routing`: tuning already travels every path verbatim (chat, engines, the assistant's tool loop) and the prompt debug panel flattens it field by field, so the assistant leg and the audit trail cannot drift out of sync by omission. `applyTuning` reads it **only** when the profile says `'declared'`; a provider whose dialect we do know must never be overridable from the wire. The declaration promises sending, never effect: nothing here can check that the endpoint honours the field, which is why the UI says so. `'none'` (where every connection stays until its owner says otherwise) shows no control and sends nothing. Scope is deliberate: the other 13 profiles keep their literal policies. Known gap: `chat_template_kwargs: {enable_thinking}` (Qwen3-style templates on vLLM/SGLang/llama.cpp) is not offered. It needs boolean wire values where `efforts` maps strings, a per-template key name, and an "on" level the effort ladder has no room for, while its off-case is already covered by `reasoning_effort: "none"` on all three; it is one row in `REASONING_DIALECTS` plus that vocabulary when someone needs it.

## Before touching this

- Read the target provider's profile file comments first: most "bugs" here are deliberate omissions with documented reasons (e.g. Mistral seed, Gemini top_k, DeepSeek penalties).
- Never bypass net.ts guards or the registry entry points.
- A new tuning field must be wired end-to-end: `GenerationTuning` (both type copies) → profile policy declaration → both provider implementations' translation → client `buildGenerationTuning` → the settings UI. Partial wiring silently violates "visible === sent".
- A new sampling slider joins `SamplingParamKey` (types/llm.ts) + `SAMPLING_SLIDERS`; it enters the BYO declaration vocabulary for free, since `DECLARABLE_PARAMS` is derived from that list rather than hand-kept beside it.
- A new BYO reasoning dialect is one row in `REASONING_DIALECTS` plus its literal in the `ReasoningDialect` union; the contract test fails on either half alone. A wire shape the existing `ReasoningPolicy` cannot express needs more: an `effortField` value on BOTH type copies and a branch in `applyTuning`, and a policy field added to one copy only is caught by the same test.
- One documented exception: `parseInlineReasoning` skips the profile-policy step on purpose. It drives our own inline-marker extraction, not a wire param, so it is provider-agnostic (set per connection in the editor's Reasoning section, carried only when off).

## Hand-kept couplings

1. Provider vocabulary. On the client `PROVIDER_NAMES` (`src/lib/types/llm.ts`) is the single source and `ProviderName` derives from it (`typeof PROVIDER_NAMES[number]`): adding a provider there is the only client edit. The server keeps its own `ProviderName` union (`server/llm/types.ts`) and `PROVIDER_PROFILES` (providers/index.ts) because neither side imports the other; both are asserted against the client list in [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts). Note `ProviderProfile.name` is typed `string`, so the profile list is bound by that test rather than by the compiler.
2. Policy/metadata types mirrored by hand: `ReasoningPolicy`+`ProfileReasoning`/`MediaPolicy`/`CachingPolicy`/`ParamPolicy`+`ResolvedParamPolicy`/`GenerationTuning` in server types ↔ `src/lib/types/llm.ts`; `ProviderMetadata` (registry.ts) ↔ `ProviderMeta` (client provider.ts). Three of them are asserted equal on both sides in [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts): the param-policy vocabulary, `ReasoningPolicy`'s fields and wire values, and `GenerationTuning`'s fields. A literal that exists on one side only is a policy that mis-branches silently; a tuning field that does is a control the client shows and the type boundary drops. `ReasoningPolicy` itself lives in `server/llm/types.ts` beside the `ReasoningEffort` that keys it, re-exported from `providers/types.ts` for the profiles. The same test holds `REASONING_DIALECTS` to the `ReasoningDialect` union, since a dialect with no row resolves to null: a stored declaration that quietly stops sending anything.
3. `RoutingConfig` exists in registry.ts (server, exported) and `src/lib/types/llm.ts` (client): same fields, camelCase. A connection owns its routing; the client sends it per request in the WS `llm`/`assistant` message (`transport.ts` → `index.ts` handlers → registry), and `toProviderField` translates it to snake_case server-side. There is no global routing setting.
4. Param names in profile allow-lists must match the `apiField` names `config/sampling.ts` sends verbatim (documented Mistral `random_seed` exclusion is the canonical example). Asserted in [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts): every entry in a static allow-list is either a slider `apiField` or one of the known non-sampling request fields (`max_tokens`, `max_completion_tokens`, `seed`).
5. `connectionId` rides every model call: the WS `llm` message + `AssistantRequest` + the four `/api/llm/*` POST bodies all carry it (`transport.ts` ↔ `server/index.ts` ↔ `server/assistant/loop.ts`); the registry reads the key from `connection_credentials` by that id.
6. `llmService.sendsImages()` is the single image-send gate: chat, assistant panel, and message stripping all call it; don't fork the logic.
7. The resolved base URL rides the **`/api/llm/models` response** (`{ models, baseUrl }`): `ChatProvider.resolvedBaseUrl?()` (optional, since only the BYO-capable implementation has one) → `registry.resolvedBaseUrl()` → the endpoint → `llmService.getResolvedBaseUrl()` → `ConnectionEditor` → `ConnectionHero`. Dropping any link turns a visible correction back into a silent one. The failure leg matches: a `validateCredentials` throw rides `/api/llm/validate`'s `{ valid: false, error }` → `llmService.validateConnection().error` → the editor's connection-error line. Dropping it shows a generic credentials rejection for an endpoint that has no API at all.
8. `MAX_CONTEXT_SIZE` / `MAX_RESPONSE_TOKENS` (`src/lib/types/llm.ts`) bound the connection editor's two token fields and nothing else: the store accepts any positive integer and no provider clamps either value, so they are UI sanity caps, not capability claims.
