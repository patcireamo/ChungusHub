# Macros: architecture & maintenance

`{{name}}` substitution: [`macros.ts`](../src/lib/macros.ts) is the single registry **and** the single engine, one file on purpose: a macro is declared, documented and substituted in exactly one place, rather than in seven that each carry their own copy of the same regex. Macros are **global**: every macro-resolving surface (preset items, the opening scene, the steering wrapper, the composer transforms, the sprite prompt, memory templates, lorebook entry content) resolves the shared engine macros from the same `MacroContext`, then layers its own values over that record and calls `substitute` once. That is also why an engine template that needs a slice of the story writes `{{chatHistoryLast3}}` rather than growing an excerpt builder of its own: the shared vocabulary already answers it, and it answers it as an author's choice instead of a constant. Two rules hold everywhere: **flow values win on a name collision**, and **a macro whose data doesn't exist where it is used stays literal**, visible in the prompt and never silently gated. Where a `MacroContext` comes from, and what assembly does with the expanded text, is architecture/prompt-pipeline.md.

**The registry.** `MACROS` is the one list. A `MacroDef` carries `name` (no braces), `description` (the only copy any UI shows), `group` (one of `names` / `context` / `character-field` / `memory`, ordered and labelled by `MACRO_GROUPS`, which is the reference panel's display order and nothing else) and three flags. `engine: true` means "resolved from `MacroContext` on every surface" and derives `SYSTEM_MACROS`; `structural: true` means "injects native-role messages instead of inline text" and derives `STRUCTURAL_MACROS`; `parameterized: true` means "the registered name is a shape, not a resolvable name" and **subtracts** the entry from `SYSTEM_MACROS`. All three exist so no consumer ever spells the names out again: declaring the flag in the registry is the only edit.

**Four classes of macro, and only two of them live in `MACROS`.** This is the distinction the file exists to hold, and the one a new macro has to pick from:

1. **Engine macros** (`engine: true`). `resolveMacro` answers them from `MacroContext` on every surface, and it answers them **first**, so a preset control reusing an engine name is ignored rather than allowed to shadow it. Cost: one `MACROS` entry plus one branch in `resolveMacro`, and it must resolve to *something* everywhere (empty string when its data is absent), because the same registry backs generation, the token meters, memory and the composer alike.
2. **Flow macros** (registered, no `engine` flag) are today exactly the memory pipeline's set (`{{batch}}`, `{{sceneLength}}`, `{{deepMemory}}`, …). Declared here so the picker can list them under a group whose hint says they stay literal anywhere else, but filled only by their owning flow (`memory/prompts.ts`, `memory/recall.ts`, architecture/memory.md coupling 4). Cost: the name is reserved app-wide but resolves in one pipeline only, so an author who writes `{{batch}}` into a preset item ships a literal `{{batch}}` to the model.
3. **Call-site substitution keys.** `{{idea}}` (opening scene, `messages.svelte.ts`), `{{steering}}` (the wrapper, `buildSteeringMessages`), `{{draft}}` / `{{perspective}}` (`composerTransformService.ts`), `{{labels}}` (the chat character's own sprite labels, `spriteService.ts`). Deliberately **not** registry entries: `MACROS` is the vocabulary the macro reference advertises to **preset** authors, and each of these resolves in exactly one template that is not a preset, so registering them would advertise names that resolve nowhere an author can reach. Every one is layered as an ad-hoc key over `resolveMacroValues(template, ctx)` before `substitute`, which is what keeps `{{char}}`/`{{user}}` working inside those same templates; the key is documented in its engine's `prompts` hint instead (architecture/engines.md). `{{idea}}` is the worked example of why the classes must not blur: calling it `{{scenario}}` would have shadowed the character-card macro that resolves in that very template.
4. **Author-defined preset-control macros.** `{{pov}}`, `{{tense}}`, `{{voice}}`, whatever a preset author binds a `PromptControl` to. `resolveCustomControl` matches the name against `ctx.controls` and formats the widget's value through `formatControlForPrompt` ([`prompt-controls.ts`](../src/lib/utils/prompt-controls.ts)) against `ctx.customFields`, which is **one preset's** values (`presetControlValuesByPreset`, keyed by preset id then macro name; architecture/preset-authoring.md). Whoever builds the context owes `controls` and `customFields` off the same preset, or a macro expands to a value some other document's knob set. It is the **last** resolution step, so a control can never shadow anything above it, and the Prompt Builder refuses the name up front (`macroError` tests against every `MACROS` name, flow macros included).

A new macro joins class 1 if it can answer from story/chat state on every surface, class 2 if only one internal pipeline can fill it but authors should still see it exists, class 3 if it resolves in exactly one non-preset template. Class 4 is never yours to add: it is what a preset author does.

**The substitution primitive.** `substitute(template, values)` replaces every `{{key}}` in ONE pass, through a function replacement so a literal `$&` inside a value is not treated as a replacement pattern; single-pass is what stops a value that contains `{{...}}` (injected story text, a lorebook entry, a control's text) from being re-scanned as macros. `MACRO_REGEX` (`/\{\{(\w+(?:\.\w+)?)\}\}/g`) is the one shape. The dotted `{{a.b}}` form it accepts has **no producer and no resolver anywhere in the app** today, so a dotted name simply stays literal. `extractMacroNames` returns the unique names in a text, `resolveMacroValues(text, ctx)` resolves exactly those and omits the ones it cannot answer, and `expandMacros` is the two composed. Unknown names get no entry and stay literal, so a typo lands in the prompt where you can see it rather than vanishing. `{{chatHistoryLastN}}` is the one entry whose registered name is a **shape** rather than a resolvable name: `cappedHistoryTurns` parses `chatHistoryLast<digits>`, so the literal name copied from the picker resolves to nothing while `{{chatHistoryLast20}}` resolves. That is what `parameterized: true` is for: it drops the placeholder out of `SYSTEM_MACROS`, and the Prompt Builder's unbound-macro lint runs `cappedHistoryTurns` before its set lookup, so the numbered form passes and the placeholder is flagged. A lint that only compared literal names against the registry would say the exact opposite.

**Structural macros** are prompt-assembly's business alone: `resolveMacro` returns `''` for anything in `STRUCTURAL_MACROS` purely as a nested-expansion fallback, so a structural name reached through some other macro's content cannot inject a stray inline copy. `{{chatHistory}}` is the only one; the detection and split live in prompt-assembly (architecture/prompt-pipeline.md coupling 1).

**Helpers that live here rather than in assembly**, each because more than one caller must produce the exact same bytes: `expandSelfRefs` (`{{char}}`/`{{user}}` inside stored content, case- and whitespace-tolerant for imported cards, and shared by the prompt side with five display surfaces: `Message.svelte`, `StoryMapView`, `ChatSearchBar`, `ChatsView`, `ChatPreviewPane`; architecture/chat-sessions.md); `pruneEmptyTagBlocks`, whose bottom-up rules are stated in full in the file and depend on `substitute`'s stay-literal behaviour to keep a typo's block alive; `splitExampleBlocks` / `formatExampleDialogue`, shared by `{{mesExamples}}`, the `{{character}}` blob and the trim's block count; `renderTranscript`, which backs `{{chatHistoryLastN}}`; `cappedHistoryTurns`, the one definition of the parameterized shape; `historyTurns`, the one derivation of the turns `{{chatHistory}}` injects; and the `MacroContext` / `PromptCharacter` types every builder fills. The module has no store, no Svelte, no db import and must keep it that way: memory's otherwise-pure core imports `substitute`, and prompt assembly is pure by contract. `renderTranscript` and `formatExampleDialogue` are module-internal; everything else in that list is exported.

**`CHARACTER_FIELD_MACROS` is derived, not declared**: built by inverting `PERMANENT_TRAITS.character`'s own `macro` field, so a card field that gains, loses or renames a macro reaches resolution with no second edit (architecture/library.md coupling 1). `SPECIAL_FIELD_MACROS` is the single exception list and holds exactly `mesExamples`, filtered out because `resolveMacro` formats that field itself; a plain map entry would hand back the raw text and double-resolve it. `{{mesExamplesRaw}}` and `{{persona}}` never enter the map at all: the first has no trait of its own, the second belongs to `PERMANENT_TRAITS.persona` and resolves through `formatPersona`.

**Naming policy.** Names follow SillyTavern's wherever ST has a macro for the same thing, so a preset author writes what their fingers already know; the ones ST has no equivalent for keep the same camelCase shape rather than inventing a second convention (prompt-pipeline.md enumerates which is which). What is deliberately **not** taken from ST is the rest of its macro language: no `::` arguments, no `{{if}}` blocks, no variables, no author-facing randomness. That is not conservatism: `substitute` being a pure name → string map is exactly what lets the meters and generation resolve the same text twice and get the same answer. The one nondeterminism in the system is the lorebook's Trigger% roll, and it sits OUTSIDE this engine: the block is resolved once when the context is built and `{{lorebook}}` only prints it, so two resolutions against the same context always agree (architecture/lorebook.md).

**The picker.** [`MacroReference.svelte`](../src/lib/components/ui/MacroReference.svelte) is the user-facing "Available macros" reference: groups and chips rendered from `MACRO_GROUPS` + `MACROS` (so it cannot drift from what resolves), a `structural` tag from the flag, click-to-copy, an optional dynamic group for the open preset's own control macros, and at its foot the tag-block pruning rules **in words** (the "Prune empty blocks" toggle itself only demonstrates them, via `PruneEmptyBlocksMockup`). It is mounted in exactly one place: [`PromptBuilderView.svelte`](../src/lib/components/promptBuilder/PromptBuilderView.svelte), which passes the preset's controls in. Nothing else mounts it: `PresetControlsView` is reader-facing and shows values rather than vocabulary, and `EngineDetail` builds its own flow-key chips by scraping the shipped default template instead. So a macro's discoverability is the registry entry plus that one mount.

## Before touching this

- Never write a bespoke `{{...}}` regex. Use `substitute` / `MACRO_REGEX` / `extractMacroNames`. The three that already exist are named in coupling 5 and are not a precedent.
- Keep `substitute` a pure name → string map, and keep resolution deterministic: two resolutions of the same text against the same context must agree, because a meter and a send do exactly that. **The clock macros are the one exception**, and only because SillyTavern's are: `{{time}}` and its four siblings read the clock as they substitute, so a meter and the send after it can land either side of a minute and price a character apart (`9:59 AM` is seven, `10:00 AM` is eight). Replicating ST's behaviour was worth that; nothing else may read anything the context does not carry.
- Every macro resolves on every surface or resolves empty. No silent gating, no surface-specific special cases inside `resolveMacro`.
- `macros.test.ts` holds the clock macros and nothing else, because they are the one group whose output is not a function of the context alone. With no instant to inject there is no exact string to assert, so it pins the SHAPE SillyTavern presets are written against and the 1-based month `Date` invites getting wrong. Every other macro's coverage rides `prompt-pruning.test.ts` (the pruning rules, unit and integration), `prompt-assembly.test.ts` (expansion inside real assembly) and `contracts.test.ts`. Run `bun test` after any change here.

## Hand-kept couplings

1. **A macro not in `MACROS` is invisible.** Resolution and the reference are separate mechanisms: `CHARACTER_FIELD_MACROS` derives from `PERMANENT_TRAITS`, so a new card field resolves with no edit here, but the registry list is hand-written and the picker reads only that. A field macro missing from `MACROS` resolves correctly and cannot be discovered by anyone who doesn't already know it exists. Asserted in [`contracts.test.ts`](../src/lib/contracts.test.ts) ("every character field macro is documented in the macro registry"). The same rule holds for every other macro, with no test behind it.
2. `SPECIAL_FIELD_MACROS` ↔ `resolveMacro`'s own `mesExamples` branch: the name is filtered out of the derived map *because* this file formats it. Drop either half and the field either double-resolves or loses its `<START>` block formatting.
3. The three flags drive derived consumers only: `structural` → prompt-assembly's detect and split regexes (prompt-pipeline.md coupling 1); `engine` minus `parameterized` → `SYSTEM_MACROS` → the Prompt Builder's unbound-macro lint. A parameterized entry also needs its parser wired into that lint (`cappedHistoryTurns` is the only one), or every numbered spelling of it false-flags. A flow macro added without a fill site is a picker entry that resolves literal, and nothing warns.
4. **Flow-value layering is by hand at four sites.** Opening scene (`messages.svelte.ts`), steering wrapper (`prompt-assembly.ts`), composer transforms (`composerTransformService.ts`), memory (`memory/prompts.ts`, via the store's `globals`/`cards`). Each spreads `resolveMacroValues(...)` first and its own keys second. Reverse a spread and the flow's own value loses to an engine macro of the same name; memory is the live case, since it deliberately overrides `{{character}}`/`{{persona}}` with its "(no character sheet bound)" fallbacks.
5. Three `{{...}}` replacements exist outside `substitute`, all intentional and all invisible to the registry, the picker and the lint: `expandSelfRefs`' case-insensitive pair (it must match card variants `substitute` would not), `formatControlForPrompt`'s `{{value}}` (a control-template placeholder, not a macro; `prompt-controls.ts`), and `EngineDetail`'s `flowKeys` scrape of the shipped default template (which lists call-site keys and engine macros side by side without distinguishing them).
6. `DEFAULT_EXAMPLE_SEPARATOR` is declared here and read by both `resolveMacro` and the preset export/import round trip (`preset-io.ts`); see prompt-pipeline.md coupling 9.
