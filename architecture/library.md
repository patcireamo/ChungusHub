# Character & persona library: architecture & maintenance

One store owns it all: [`characterLibrary.svelte.ts`](../src/lib/stores/characterLibrary.svelte.ts) (read the section you're touching, they're clearly banded). Entries live in the `character_library` table as `{ identity, data }` JSON: **identity** (name, portrait `imageUrl`, tags, `gallery`) is never versioned; **data** ([`types/library.ts`](../src/lib/types/library.ts) `LibraryEntryData`: `traits` + labels/hidden/categories + `alternateGreetings` + `lorebookIds`) is what character versions snapshot. `PERMANENT_TRAITS` is the field registry: each field's editor label, its per-field prompt macro, whether it joins the `{{character}}`/`{{persona}}` blob, and whether it seeds the chat (First Message). A new card field starts there (plus `CharacterTraits` in the same file) and reaches macro resolution with no second edit, but **not** the editor: `EntryFormFields.svelte` derives every field's label, hint and "Not sent to AI" badge from the registry yet places each one explicitly by key in its template, so a registry entry nothing places is simply invisible. The assistant's data model is separate (`server/assistant/registry/entities.ts`, see architecture/chungus-assistant.md).

**Editing is write-through**, the same shape the lorebook and steering stores use, so there is one answer in this app to where typed text goes: the editor writes onto the entry and the shared `DebouncedWriter` (500ms, keyed per entry, see architecture/client-data-layer.md) carries it to the server. Typing rides `scheduleIdentityEdit`/`scheduleDataEdit`; **a discrete action never sits in a timer**: a tag, a portrait, a gallery pick, a lorebook link and a version switch all write at once through `updateIdentity`/`updateData`/`updateEntryImage`. `flushEntry` sends what is still waiting and is called before anything that reads the server's copy: leaving the editor, forking or switching a version. There is no separate draft row and no "unsaved" state to reconcile: the editor header's saving indicator is `hasPendingWrite`, which is just the writer's own timer, made reactive. Two rules keep a reload from moving text backwards under the caret: `refresh` flushes before it refetches, and an entry whose write is *still* pending after that flush was typed into during the refetch, so its on-screen copy wins over the row that came back. Image uploads land on the entry immediately (`imageService.saveImage` already writes this entry's own copy), which is why deleting an entry only has to sweep what its identity names. Brand-new entries (`createCharacter`/`createPersona`) are committed rows tracked in `_unconfirmedNewIds`: the editor offers Save/Discard instead of autosave until confirmed, where Discard is a plain `deleteEntry` (row and files together).

**Character versions**: named variants, not history. The entry's `data` is always the **active** variant's content; the server mirrors every save into the active row (`updateLibraryEntry` in server/db.ts) and `persistEntry` mirrors it into the client's cached `_versions` row (the `library` sync broadcast skips the device that wrote, so nothing else would). First fork materializes an "Original" baseline and pins every existing chat of that character to it (`pinUnpinnedChatsToVersion`, which runs once, at opt-in). `deleteVersion` refuses while chats are pinned; `switchActiveVersion` parks pending edits into the outgoing row first.

**The active version is an authoring pointer, and only that.** It decides which variant the library editor writes to, and nothing else at all: it does not reach a chat, not even at birth. What a new chat is pinned to is `characterLibraryStore.chatVersionSeed` (the character's own `defaultVersionId` while that version still exists, else the first one ever made, else null for an unversioned character), asked by every door that mints a chat and asserted by `contracts.test.ts`. Letting the editing pointer answer it means opening another variant to read it quietly changes what every story started afterwards is played against. Which variant a chat *plays* is `chats.character_version_id` alone, repinned from the Version row of the composer's `ChatSetupChip`, and every request that chat makes (story turns, memory, opening scene, the token meters) resolves that pin. Both resolvers, `dataForVersion` (store) and prompt-builder (db), always read the pinned **row**, with no "pinned == active, just read `entry.data`" shortcut, and both throw on a dangling pin rather than fall back to a different variant. `load()`/`refresh()` therefore assign `_versions` **before** `_entries`: an entry becoming findable is what makes readers resolve its version row. There are no per-turn version stamps: a chat has exactly one variant at a time. **The opening is the one card field whose edit reaches existing chats**: `serverDb.updateLibraryEntry` carries a changed First Message or alternate-greetings list into the chats that are still nothing but that opening, scoped to the variant that actually changed, so an unstarted chat can never sit on a version of the character that no longer exists. Every other field is read at request time and needs no such carry. The recognition rule, the corner it fails on and what it refuses to touch are in architecture/chat-sessions.md.

**Portrait framing** (`identity.portraitFocus`, [`portrait-focus.ts`](../src/lib/utils/portrait-focus.ts)): a focal point (0..1 across and down the picture) plus a zoom over the cover fit, never cropped bytes. One portrait is drawn at several ratios at once (2:3 and 1:1 chat avatars, 3:4 browse cards, a 60x80 list row) and the chat's silhouette is a setting the reader can change long after the framing was authored, so a baked rectangle would be right in one box and re-cropped by every box that disagrees with it, with the original gone. `portraitFocusStyle` turns the three numbers into `object-position` + `transform-origin` + `scale`, carried inline by every cover-fit portrait `<img>`; `portraitFocusAim` is the same minus the transform, for the two browse cards whose portraits already scale on hover and compose the two in `.browse-card-portrait` (app.css). An inline transform there outranks the hover rule and freezes the drift. `cover` guarantees the picture is at least as large as its box on both axes, so no focal point in 0..1 at any zoom >= 1 can leave a gap; pinned by [`portrait-focus.test.ts`](../src/lib/utils/portrait-focus.test.ts), along with the fact that `portraitFocusFromDrawOffset` (what a drag writes) inverts `portraitDrawRect` (what the dialog draws) exactly. Absent means the shipped centred cover, so an unframed entry renders as it always did and there is nothing to migrate. **The framing belongs to the picture**: `updateEntryImage` drops it whenever the portrait is replaced or removed, because coordinates chosen for one picture mean nothing on the next; it is not versioned for the same reason the portrait isn't, and `duplicateEntry` carries it alongside the copied file. It does **not** travel in an export (the block's identity carries name and tags only), so a reimported character is framed again. Authoring is [`PortraitFramingDialog.svelte`](../src/lib/components/library/PortraitFramingDialog.svelte), reached from the crop button on either editor's portrait; `.portrait-overlay-action` (app.css) is what keeps those corner buttons reachable on a touch screen, which has no hover to reveal them with. Its three lenses are the **narrowest and widest boxes the app draws a portrait in, plus the circle**. A framing that reads in both reads in everything between, which is what makes one framing enough for every surface; an avatar silhouette added outside 2:3..1:1 needs a fourth lens or that guarantee stops holding. The full-size viewers (`PortraitViewer`, and `ImageLightbox` over the gallery, see architecture/ui-shell-settings.md) deliberately show the picture uncropped: that is where the original is looked at, not the frame.

**Tags on a browse card go through one component** ([`TagList.svelte`](../src/lib/components/library/TagList.svelte)): it measures chips against the strip's real width and shows as many whole ones as fit, collapsing the rest into a `+N` badge and truncating a single chip only when not even one fits. A hardcoded chip count is wrong on every surface at once, since the same strip is a phone's list row in one place and a docked gallery card in another. Widths come from an off-screen mirror of bare spans, which is why a real chip carries no whitespace around its label: a collapsed space either side makes it wider than what was measured. The two tones differ in colour alone (`overlay` for chips drawn over a portrait, where the surface tokens have no surface to read against), so one mirror serves both, and neither is accent-tinted: a tag names the character, it does not claim anything is active. The **Gallery** card always draws it. The **List** row draws it behind a switch (`listTags` on `browseViewPrefs`, offered as the View Options popover's Show Tags switch, which is on screen in list mode alone), and that switch is **off by default**: the strip costs the preview line its second row, and which of the two is worth more is the reader's call, not a default's. The grid **tiles** have no strip at all, since name-only density is the whole reason that mode exists. In the list row the preview line drops from two lines to one whenever tags are on screen: the row's height is its 60x80 portrait's, and a content column that outgrows it takes with it the uniform row height a long list is scanned by. That column is also **held to the portrait's height from below**, so the name starts at the same place in every row: the row centres its items, and a column left to be as tall as its content sinks the name down the row whenever the preview is short. There is deliberately **no second switch for pressing a chip**: a strip the reader turned on is one they can press, and a visible control that only turns a control off is noise. A chip is a **button in the List row alone** (`onTagClick`, wired to `CharacterLibraryView`'s `toggleTag`, which resets the page as any other filter change does): the Gallery card is a portrait with a caption laid over it, so a press target inside that caption competes with the card's own. `PersonasView` has no tag filter to toggle and passes nothing, so its rows are labels too, and the row drops the handler while selecting, since a chip that filtered would move entries out from under the selection just made. **A press target cannot be grown past the chip**: the strip clips to its own box to cut the tags that do not fit, so anything a button adds vertically is cut off top and bottom.

**Sprites are their own image set** (`identity.sprites`, a `{ path, label }[]`, plus `identity.defaultSprite`; the pure model is [`sprites.ts`](../src/lib/utils/sprites.ts), unit-tested in [`sprites.test.ts`](../src/lib/utils/sprites.test.ts)). **A path is in `sprites` or in `gallery`, never both**: the two grids sit one under the other in the same editor, so a picture in both would draw twice and either grid's X would take the file out from under the other. That disjointness is why neither grid can hand a picture to the other: which set a picture belongs to is settled by the section it was uploaded into, and moving one is uploading it again into the other. It is also what keeps the Gallery about the character's art when a pack of forty arrives, and what makes the editor's `gallery images` count and the export's two picture checkboxes mean what they say. Labels are free text with a suggested vocabulary (`SPRITE_LABEL_SUGGESTIONS`, SillyTavern's emotion set, which is also what pack filenames use) and are **unique per character, matched case-insensitively**. The engine answers with one label and expects one picture back, so two sprites sharing a label would make the second unreachable with nothing on screen admitting it; `findLabelConflict` refuses the collision at the point of naming instead. **A character with sprites always has a default** (`resolveDefaultSprite`, run over the result of every write that can move the list): the first upload sets it, removing it hands the role on, the last removal clears it. That invariant is what lets the chat draw a picture the instant the engine is switched on rather than after the next reply, which would read as broken; it is the persona floor's doctrine applied to a pointer: kept true at write time, never repaired at read time. Writes are `addSprites` / `setSpriteLabel` / `removeSprite` / `setDefaultSprite`, all on the immediate path since every one is a discrete click, and `addSprites` uploads a whole pack in **one** write (returning the labels it refused) because a write per file is a broadcast per file. `duplicateEntry` copies the sprite files as their own set and carries the labels onto the copies. A filename becomes a label through one function, `labelFromFilename`, and the default pointer is settled by one function, `resolveDefaultSprite`. **Both live in [`shared/sprites.ts`](../shared/sprites.ts)**, re-exported by `sprites.ts` for the client, because three doors put a pack on a character and one of them is not client code: the Sprites upload, the SillyTavern import, and the example character the server seeds on first boot (architecture/build-packaging.md). A copy on the server side would let the same pack label itself two ways, or land holding sprites with no default, depending on which way in it took. What the engine does with them: architecture/engines.md.

**One picture, one meaning per corner.** [`CharacterSprites.svelte`](../src/lib/components/library/CharacterSprites.svelte) is a fourth collapsible section of `EntryFormFields` beside the Gallery, and the corner **X deletes the picture and its file** exactly as the Gallery's does: same glyph, same corner, same act, so neither grid teaches a habit the other punishes. A tile's own press opens [`SpriteLabelDialog.svelte`](../src/lib/components/library/SpriteLabelDialog.svelte), which **only renames**: it is mounted once, by `EntryFormFields`, so there is one answer in this editor to what a legal label is. The heading carries the grid's **display order** (`SPRITE_SORT_OPTIONS`: upload order, A → Z, Z → A) at its right, and only once there are two sprites to order, since a control over one picture is noise. It rides outside the collapse button, since a control nested in it would fold the section on every press. The choice is app-wide and persisted ([`spriteSort.svelte.ts`](../src/lib/stores/spriteSort.svelte.ts) on the settings spine), because re-picking it per character is exactly the work it exists to save. **Sorting is a view and never a write** (`sortSprites`): the stored list keeps the order the files arrived in, which is what makes upload order a place to come back to and what stops a sort from moving `resolveDefaultSprite`'s first-one-in. With the engine off the section says so and deep-links to Settings → Engines, but only once there is a sprite to say it about, since on an empty set it is an error message about nothing. That pointer is the whole reason the engine can ship off without becoming a trap. Tiles are **3:4 and contained, never cropped**: sprites are drawn tall, and a square cover crop takes the face off the top of one. They draw the ordinary thumbnail, which carries the transparency a sprite is made of because every thumbnail is webp (architecture/server-core.md). The chat's sprite layer is the one surface that reads the stored file instead, since it draws the picture at a height no thumbnail is written at (architecture/ui-shell-settings.md).

**Turning one kind into the other is a copy, never a flip of `type`** ([`convertEntry`](../src/lib/stores/characterLibrary.svelte.ts), offered by both ⋯ menus, the editor header's and every browse card's: "Save as persona…" on a character, "Save as character…" on a persona, worded once in `CONVERT_ACTION` so the two menus cannot say it differently). Chats name their character by id, version rows hang off that id, and every user message carries the id of the persona it was sent with, so a row that changed kind under them would leave all three pointing at something that no longer answers; the persona floor and the active pointer would have to be re-litigated on top. The source is left exactly as it is. What travels is the name, the portrait (copied into the new kind's own folder, framing included, since it is the same picture) and the linked lorebooks, which both kinds carry. Nothing character-shaped does: versions, greetings, sprites, gallery, tags and the card metadata stay where they were authored. A character's descriptive fields fold into the one field a persona has through [`personaDescriptionFromCharacter`](../src/lib/utils/entry-conversion.ts) (Description + Personality summary, each under its own heading; a lone field folds verbatim, since a single heading over a single block is noise), and the reverse direction carries the persona's description into Description. **The fold is a proposal, not a result**: [`ConvertEntryDialog.svelte`](../src/lib/components/library/ConvertEntryDialog.svelte) puts the text on screen to edit before anything is created, and names what is being left behind, so a dropped scenario or greeting is never a discovery made later. The new entry lands committed (no Save/Discard rung: the dialog already was the confirmation) and a new persona is **not** made active, since who you play is app-wide and no menu item gets to change it silently. Pinned by [`entry-conversion.test.ts`](../src/lib/utils/entry-conversion.test.ts).

**Image ownership**: an entry's portrait/gallery/sprite files are exclusively its own. `duplicateEntry` and cross-entry adoption always `copyImage`, and deletes remove the files (portrait, gallery, sprites) with the entry. An upload is on the entry the moment it is picked, so what the row names is the whole set. This complements the chat-attachment refcount rules in architecture/chungus-assistant.md; library art lives in `images/characters/` / `images/personas/` and is never touched by the chat sweep.

**The library is not empty on a fresh install**: the server seeds the example characters `defaults/characters/` ships (currently one, with a full sprite pack) straight into `character_library` at boot, before any client connects, so they are ordinary rows from the first paint and no surface here knows they were shipped. **Seeded once per id and never again** (`ensureDefaultCharacters`, architecture/build-packaging.md): deleting one is a plain `deleteEntry`, row and files together like any other character, and it does not come back. There is deliberately no restore-defaults control anywhere for them, which is why the ledger is what enforces this rather than a rule the UI has to remember. They land **unversioned** and with no linked lorebooks, the same two things an export drops, so nothing here has a shape a hand-made character could not have.

`load()`/`refresh()` take DB rows as-is: no load-time normalization, so a malformed row surfaces as breakage instead of being silently rewritten.

**The editor's foot states what a card amounts to** ([`CharacterStatsBar.svelte`](../src/lib/components/library/CharacterStatsBar.svelte), a third row of `LibraryEntryEditor` outside the scrolling form, so it is on screen whatever the user is editing): chats, messages, versions, alternate greetings, gallery images and sprites (the two picture counts are separate because the two sets are), then **two token figures that answer different questions and neither replaces the other**. *Card* is every field of the active version, summed per field (a joined string would price its own separators). *Prompt* is what the ACTIVE preset actually places, so a field no macro reaches costs nothing, the same rule the editor's "Not sent to AI" badges are drawn from, asked here through the real macro engine (`extractMacroNames` over the ENABLED items, then one `resolveMacroValues` for the card's own macros alone) so the figure cannot drift from what assembly would produce, and so pricing a character never selects a lorebook or walks a chat history. A macro two enabled items place is counted twice, because the prompt really does carry it twice. The macro set is derived from `PERMANENT_TRAITS.character` + `BLOB_MACRO`, with `mesExamplesRaw` written out by hand as the one name with no trait behind it. A future synthetic macro needs adding there or its field prices as free. Both figures go through `countTokens` under the primary model, the app's one counter (architecture/tokenizer-debug.md). The message figure is the branch each chat is open at (`getChatListStats().path`), the same number the chats panel shows, with the all-branches total in its tooltip; a figure that looked like that one and meant something else would be a trap. Characters only: `PersonaEditor` has no such bar.

**Satellites**: [`persona.svelte.ts`](../src/lib/stores/persona.svelte.ts), the persona new chats start as (`activePersonaId` settings key). It is the app's answer and nothing reads it directly except the resolver: which persona a story is PLAYED by is that chat's own claim falling back to this one, resolved in [`utils/chat-setup.ts`](../src/lib/utils/chat-setup.ts) and asserted by `contracts.test.ts` (architecture/ui-shell-settings.md, "A chat claims what it can name"). `setActive` takes a real id and never clears: its callers are `PersonasView`/`PersonaEditor` here and the first-run greeting. **A character names what its new chats start on**: `defaultPersonaId`, `defaultConnectionId` and `defaultVersionId` (`ChatDefaultKey`), set from the character editor's **New Chat Defaults** panel and written through one setter, `setChatDefault`. Each is a seed and nothing more: it stamps a chat at birth and has no say afterwards, so moving one never touches a story already under way. The persona seed outranks the app's answer and is itself outranked by the New chat flow's persona step, which is somebody choosing for the chat being made right now; the connection seed outranks nothing, since no other door carries a connection into a new chat; the version seed answers the question every chat has to answer, above. All three are stored as **siblings of `data`** in the entry payload (server/db.ts `CHAT_DEFAULT_KEYS`, each written only when set), so none mirrors into a version row or reaches a card export. **The panel sits at the foot of the identity pane, closed** (`EntryFormFields`'s `identityExtra` snippet slot): what a chat starts on belongs beside who the character IS rather than among the card fields, and it is read far less often than any of them. It deliberately does not wear the accent section headings those fields carry, since it is not part of the card and the eye should not read it as one more of them. When the grid stacks it rides up with the identity pane and lands between the tags and the card, still closed, still one quiet line. It says on screen that nothing in it is written into an exported card, and only `buildExportBlock`'s explicit shape keeps that line true (architecture/sillytavern-interchange.md), so a seed added to the entry payload is a seed this panel now claims for. Each row's "nothing set" option is named for what answers it and not for the answer itself: **Default** for the persona (the word the library badges the app's own persona with) and for the version, **Global** for the connection, since a connection can BE named Default and an option naming one of the rows under it is a trap. Which version "Default" means is answered where the versions are listed: the header's `CharacterVersionMenu` badges it, off the same `chatVersionSeed`, so the two can never name different variants. **A seed naming something deleted is left standing**: nothing sweeps one (deleting a persona moves the app's pointer and touches no character; deleting a connection or a version touches none either), so the row names the state and its select keeps showing that something IS set rather than blanking to a value nobody chose, while new chats fall back exactly as if the row were empty. Pinned by [`server/perChatSetup.test.ts`](../server/perChatSetup.test.ts). [`chatCast`](../src/lib/stores/chatCast.svelte.ts) resolves names/art lazily against this store.

**The library always holds at least one persona, and the active pointer always names a row that exists.** Both halves live in one place, `serverDb.deleteLibraryEntry` (server/db.ts), because that is the one door every delete goes through (this store over the RPC bridge and the assistant's `delete_entity` in-process), and a rule the assistant can walk around is not a rule. It refuses the last persona outright and, when the deleted one was active, hands the role to the most recently touched survivor and returns it; both callers announce that move on the `settings` scope (architecture/server-core.md), which is what re-reads `activePersonaId` on every device including the one that deleted. **The pointer is kept true at write time, never repaired at read time**: a fallback that resolved "no active persona" to some persona would make the stored value's wrongness invisible, and `activeEntry` returning null is supposed to mean something. The first persona is written by the first-run greeting, which gates on there being none (architecture/ui-shell-settings.md). That is the only door that creates one from nothing, which is why it has no Skip. Two consequences ride along: **Personas has no empty state**, since the list can only run out behind a filter; and the last persona's delete is **inert on screen, not hidden**. `PersonasView` and `PersonaEditor` pass `deleteBlockedReason` (`LAST_PERSONA_REASON`, exported from the persona store so two surfaces cannot word it differently) and both menus, `LibraryEntryMenu` and `LibraryEditorHeader`, mute the item, hand it that sentence as its tooltip and refuse the press. **This is deliberately the opposite of the hide-it rule** the settings pages follow (architecture/ui-shell-settings.md), and the difference is what the control is missing: a knob with nothing left to style has no subject, so it is noise, while this one has its subject in front of the reader and is held back by a rule they have not met yet. Removing it answers "why can't I delete this" by deleting the question. The press is refused with the same sentence as a toast rather than silently, because a tooltip is unreachable on touch and a row that does nothing at all on a tap is the very dead button hiding it would have avoided. The `|| 'User'` fallbacks in macro resolution and memory are what an app with no persona at all lands on, which now means an outage during that greeting and nothing else. Pinned by [`server/personaFloor.test.ts`](../server/personaFloor.test.ts). **Import** ([`sillyTavernImport.ts`](../src/lib/services/sillyTavernImport.ts)): PNG `chara` tEXt/iTXt chunk or JSON; SillyTavern V2/V3 cards map onto traits verbatim-ish, embedded `character_book` becomes a standalone linked lorebook (user-confirmed). The Settings **Import** page's bulk SillyTavern-folder migrator ([`sillyTavernFolderImport.ts`](../src/lib/services/sillyTavernFolderImport.ts), architecture/ui-shell-settings.md) rides this same path: it calls `importFromSillyTavern` (with `importLorebook: true`) per character card and `savePersona` per User Avatar (name+description pulled from the folder's `settings.json`), so library import logic stays single-sourced. **Export** ([`sillyTavernExport.ts`](../src/lib/services/sillyTavernExport.ts)): produces a SillyTavern **V2 card** as `.json` (imageless) or `.png` (portrait as art, card in the `chara` tEXt chunk, re-encoding non-PNG portraits and generating a placeholder when there's no portrait). ChungusHub-native fidelity (all versions, trait labels, hidden traits, the ST-less `background` trait) rides in `data.extensions.chungushub` (the `ExportedLibraryEntry` shape, minus its `image`; the card's own art carries the portrait), which SillyTavern ignores; the importer reads that block back through the SAME `importChungusExport` path as the legacy top-level `chungushub.libraryEntry` JSON. The "which version" choice only sets the card's surface: **All versions** shows the active version in the standard fields and embeds every version; a single version shows and embeds just that one. Lorebooks **don't** travel: the entry's `lorebookIds` are dropped and no book rides along. Shared download/image plumbing + the `ExportedLibraryEntry` type live in [`libraryExport.ts`](../src/lib/services/libraryExport.ts). **Bulk export** (several selected characters) bundles one card each (always 'all' versions) into a single `.zip` via `exportEntriesAsSillyTavernZip`; the archive is a dependency-free STORE-method writer ([`zip.ts`](../src/lib/services/zip.ts)), and CRC-32 (PNG chunks + ZIP entries) is shared in [`crc32.ts`](../src/lib/services/crc32.ts). **Both picture sets travel, each opt-in via the dialog when any target has one** (`includeSprites`, `includeGallery`), and either one turns a *single* character's export into a `.zip` (card at root + the character's own folder) instead of a bare file. Per-character layout is `buildCharacterFiles`, which mints one base name per character via `uniqueBase`: same-named characters (their card **and** folder) disambiguate as `Asami`, `Asami(2)`, `Asami(3)`. **Sprites take the flat `<name>/` folder, because that is SillyTavern's own sprite layout**: one picture per label, filename = label (`sanitizeFilename`, and `uniqueBase` again so two labels that sanitize alike stay two files). Dropped into a profile's `characters/` it is that character's sprites to SillyTavern and to this app's own folder importer alike, labels intact. **Gallery art therefore sits one level deeper, in `<name>/gallery/`**, where neither reader looks for a sprite: a flat pile of both sets re-imports as sprites labelled "1", "2", "3" and takes the pack's real labels with it. Filenames come from `exportBaseName`: a nameless character uses the same UI fallback ("Unnamed Character"), never a bare "entry", and `sanitizeFilename` keeps spaces ("Unnamed Character.png"). A missing gallery file surfaces (fail-loud fetch), like a broken portrait. Export UI: `ExportDialog.svelte` takes `targets: ExportTarget[]` (format toggle always; per-version picker only for a single target, else the zip note; an "Include gallery images" and an "Include sprites" checkbox, each shown only when a target has that set), opened from **(a)** a browse card's ⋯ menu (`LibraryEntryMenu`'s `onExport`, threaded through `LibraryCompactCard`/`LibraryGalleryCard`/`LibraryListRow`), **(b)** the bulk-selection bar's Export button, or **(c)** `LibraryEditorHeader`'s overflow menu inside the editor. It's character-only, so `PersonasView` omits `onExport`; **(a)** and **(b)** share `CharacterLibraryView`'s dialog (keyed by `exportIds`, so a mid-dialog library reload stays consistent), while **(c)** is `LibraryEntryEditor`'s own instance aimed at the entry it has open. **UI** (`src/lib/components/library/`): `LibraryView`/`CharacterLibraryView`/`PersonasView` shells (character select opens/creates that character's chat, and a pick made while an entry editor is open also exits the editor first, gated by the nav guard (`uiStore.guardBlocksNav`) so an unsaved brand-new entry isn't silently dropped; when the library can't dock beside the chat (`!viewport.canDockSettings`), it also closes the library so the overlay doesn't cover the chat it just opened; while the New chat flow is armed (`uiStore.newChatStep`, see architecture/ui-shell-settings.md), a character pick instead advances the flow to the Personas tab, a persona pick completes it with a fresh chat, and `LibraryView` shows the step banner), `LibraryEntryEditor`/`PersonaEditor` (draft-driven), `CharacterVersionMenu`, `CharacterGallery`, browse/sort prefs in `browseViewPrefs` + `browse.ts`. In-editor deletes of one saved thing ride the armed-press rung of the destructive-act ladder (architecture/ui-shell-settings.md): `CharacterVersionMenu`'s trash and the alternate-greetings modal's X both arm red on the first press and delete on the second. A greeting can be a whole authored opening riding the editor's autosave, so a single misclick must not be able to take it.

## Before touching this

- Every write goes through this store's own methods, never a bare `entry.identity =` from a component: they are what schedule (or cancel) the pending write, and an assignment that skips them shows on screen and reaches no disk.
- **Typing debounces, a click does not.** A new editor control that fires per keystroke belongs on `scheduleIdentityEdit`/`scheduleDataEdit`; one that fires on a discrete action belongs on the immediate methods. Put a click on the debounce and the action can still be in flight when the user leaves; put typing on the immediate path and every character is an RPC and a broadcast.
- **A delete sends the row first and sweeps afterwards.** `deleteEntry` calls `db.deleteLibraryEntry` before it unbinds chats or removes any image, because that call is the only step that can refuse (the persona floor): a sweep that ran ahead of it strips the portrait off an entry still sitting in the library. The assistant's `remove` (server/assistant/registry/entities.ts) is ordered the same way and for the same reason.
- `persistEntry` cancels the entry's pending write, because it sends the whole row anyway. Any new immediate write must go through it rather than calling `db.updateLibraryEntry` itself, or the debounce fires afterwards and repeats the same row to every device.
- A new surface that draws a portrait in a cover-fit box renders it through `portraitFocusStyle`, or that box is the one place in the app aimed somewhere else. The box needs `overflow: hidden`. Every current one has it, and a zoomed portrait bleeds out of one that doesn't.
- A browse surface that draws tags renders `TagList` rather than slicing the array itself, and the list row's content column stays inside the portrait's 80px, its own top padding included: a name, one preview line and the tag strip fit; a second preview line beside tags does not, and the rows stop being one height.
- A new field on `browseViewPrefs` is coerced in `normalize` and written in `persist`, or it reads as its default forever and the next write of any other field drops it from the stored blob. Both surfaces share the class, so a field only one of them offers still rides in the other's key; that is the price of one store, not a reason to branch it.
- Version invariants: entry.data === active row content (server row AND client `_versions` cache); identity is never versioned; pinned chats block version deletion; the chat's pin is the only input to which variant a request uses.
- Any new write that can move `identity.sprites` runs its result through `resolveDefaultSprite`, or a character can end up with sprites and no default, which the chat surface reads as "nothing to draw" and shows an empty corner until the next reply.
- A new door that puts a picture on an entry decides ONE set for it, `sprites` or `gallery`. A path written into both draws twice in the editor and dies twice over: whichever grid is used to remove it deletes the file and leaves the other one naming bytes that are gone.
- A bundled example character is content, never a fixture the code knows by name: nothing may branch on its id, its name or its presence, or deleting it (which the reader is entitled to do on day one) breaks whatever branched.
- A new sweep over an entry's files names all three sets: portrait, gallery, sprites. Nothing else can reach `images/characters|personas/` (the boot sweep is scoped to `images/chat/`), so a set missed here sits on disk forever. Both doors are ordered row-first: `deleteEntry` here and the assistant's `remove` (server/assistant/registry/entities.ts).
- Bulk paths (`deleteEntries`, `setFavoriteMany`, `addTagsMany`, `removeTagsMany`) hit the DB per entry but assign the reactive `_entries` array exactly once at the end, and fetch chat lookups once rather than per entry. A per-entry assignment turns a 100-entry selection into 100 store re-renders.
- Import changes: our own export must keep round-tripping. `isChungusExport` guards **both** the legacy top-level `chungushub.libraryEntry` JSON (its `data` key would otherwise be misread as a card body) **and** the `data.extensions.chungushub` block embedded in an exported ST card; both route through `importChungusExport`. A ChungusHub-exported card is a valid ST card first, so the standard-field ST mapper is the fallback when no block is present.

## Hand-kept couplings

1. `PERMANENT_TRAITS` macros → `CHARACTER_FIELD_MACROS`: **derived, not declared.** `CHARACTER_FIELD_MACROS` (`src/lib/macros.ts`) is built from `PERMANENT_TRAITS.character` by inverting each trait's own `macro` field, so a field that gains, loses or renames a macro reaches resolution with no second edit. The one exception is explicit: `mesExamples` is listed in `SPECIAL_FIELD_MACROS` and filtered out, because `resolveMacro` handles it itself (SillyTavern `<START>`-block formatting via `formatExampleDialogue`, see architecture/prompt-pipeline.md) and a plain map entry would double-resolve it. The editor teaches that format through a per-field `hint` on `exampleDialogue` (`EntryFormFields.svelte`). Still hand-kept: a field macro also needs an entry in the `MACROS` reference list, or it resolves correctly but is invisible in every macro-picker UI (asserted in [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts)).
2. Character deletion is two calls from the Library views: this store's `deleteEntry`/`deleteEntries` (rows, cascaded version rows, files, and the DB-side chat unbind) and then `chatStore.unbindCharacterFromChats` with the chat ids it returns. That second call is what mirrors the unbind in memory *and* clears `chatCastStore`'s index. Skip it and both keep pointing at a gone entry until the next reload.
3. The assistant edits the same entries through `server/assistant/registry/entities.ts` field defs: a new library field the assistant should reach needs a `FieldDef` there too (architecture/chungus-assistant.md).
4. Export block version (`ExportedLibraryEntry.version`) ↔ `importChungusExport`: bump together, keep old versions importable. The type lives in `libraryExport.ts`; `buildExportBlock` produces the block and `buildSillyTavernCard` embeds it into the card (both `sillyTavernExport.ts`), and `importChungusExport` (`sillyTavernImport.ts`) consumes it. All of them move together.
