# Chat memory: architecture & maintenance

A long-term memory layer for roleplay chats. As a chat grows, old messages are summarised scene by scene and dropped from the verbatim prompt, so the token cost of context stays roughly flat no matter how long the story runs, and nothing is lost: every message is either still shown raw in the prompt **or** covered by a summary that is recalled on every turn, never in between.

**The one thing to internalise before touching anything here:** the archive boundary is **not stored**. Nothing in the database says where memory ends and the live prompt begins; `resolveCoverage` ([`branching.ts`](../src/lib/memory/branching.ts)) works it out from the episodes themselves on every single read, and every rule below follows from that.

## One tier, on purpose

Memory stores **episodes** (`memory_episodes`) and nothing else. Layer 0 holds one summary per extraction batch. When a layer fills past `maxPerLayer`, its oldest `promoteCount` episodes are merged by the LLM into a single tighter summary one layer up. The top layer compacts **in place**, so even it stays inside its cap. Recent history is detailed, distant history is compressed, and the NUMBER of episodes is bounded; their total SIZE is not, which is the subject of the last section.

**Every episode above layer 0 is a merge.** Opening a fresh layer is not a special case: it consumes `promoteCount` adjacent episodes like any other promotion, and an empty layer above simply leaves that merge with no already-compacted context to write around. A step that relabels a single episode upward instead spends no call and compresses nothing, and it takes the OLDEST, so the story's opening rides to the top of the ladder at raw layer-0 length, carried up untouched at every layer it passes through, sitting beside blocks that hold a hundred turns each. The one part of the story with the most to gain from compaction is the one part that never gets any.

**Promotion merges only ADJACENT episodes** (`oldestAdjacentRun`, engine.ts). `Coverage.active` is the tiling chain, so a run of consecutive entries covers one unbroken span, and being at the same layer is *not* adjacency. Once a hole is re-folded in front of an already-promoted region, that region's higher-layer block sits between the fresh layer-0 episode and the rest of layer 0; merging "the first N at this layer" jumps straight over it and writes an episode whose coverage has a hole. A layer with no adjacent run long enough simply stays over its cap, which is a cost, not a corruption.

**A second tier of durable "facts" must not land here.** It is the feature that looks obviously right on paper (one-clause statements with categories, subjects, a supersede/deprecate lifecycle, a participant roster to attribute them to), and every reason it fails is still live:

- **The question has no answer.** Asking the model to split what it read into "durable facts" and "narrative" has no ground truth, so the answer swings with the model: the same scene yields five facts on one and fifteen on another, with no way to say which is correct. Instability like that is not a tuning problem, it is what an ill-posed question looks like. "What happened in these messages" is well-posed, and models converge on it.
- **The prompt pays for it.** Defining that boundary eats more than half the extraction template and still fails to define it, and the definition has to live in several places at once (taxonomy, template, extractor contract), which then contradict each other.
- **It is the unbounded half.** Episodes have a promotion ladder; facts have no consolidation, no aging, and only exact-string dedup, so they grow monotonically with chat length while every extraction prompt carries the whole list: cost quadratic in the story.
- **The durability it reaches for is bought more cheaply.** Precise detail is what summarisation loses first, so the templates name what must survive verbatim (names, numbers, dates, sums, open threads, lasting state changes) instead of routing it into a separate store.
- **Its manual half already exists elsewhere.** A hand-written durable truth is a chat-scoped steering note or a lorebook entry, both authored by a person, so both deterministic by construction, and both with a real editor behind them.

## The boundary is derived, not stored

The **archive boundary** is computed on every read by `resolveCoverage` (branching.ts): tile the active path from the root with the episodes' own `sourceMessageIds`, stop at the first gap, and stop again before the verbatim tail. The last covered message is the boundary. Everything up to it is *archived* (ghosted in the UI, sent as memory, not as raw text); everything after it is *live* (sent verbatim).

Deriving it is what makes memory branch-aware, and the reason is one sentence: **a stored boundary can only describe one path.** Every branch change has to rewrite it, and because a retreating boundary would otherwise strand the episodes past it, every rewrite deletes them. Walking to a branch and back costs real summaries and real money, permanently. A derived boundary answers "what is folded" differently for each path from the same rows, so walking back restores the deep answer exactly, having written nothing. There is no `cursor_message_id` column and nothing may reintroduce one.

`verbatimTail` is a hard floor on the live zone, with a **minimum of 1**, not 0, in `BOUNDS` (config.ts) and in the panel's sliders alike. At zero the boundary can reach the leaf, which is the turn being answered: it rides `{{chatHistory}}` like every other turn, and `{{chatHistory}}` filters archived ids (`historyTurns`, architecture/prompt-pipeline.md), so archiving it drops the turn out of its own prompt with only a summary standing in for the very message the model is replying to. Raising the tail is free and reversible: the episodes it pushes past go dormant.

That floor has a second, **derived** half, because the configured minimum of 1 assumes the leaf *is* the last user turn. On a path ending in assistant or system turns it is not, and a tail of 1 archives the last user turn anyway, reachable from the composer menu (insert a dummy assistant turn, then regenerate) and from Continue, whose path ends on an assistant turn by definition. The real invariant is not a number, it is **the last user turn is always live**: `effectiveTail` (branching.ts) raises the tail to clear the trailing run of non-user turns rather than trusting the configured one. It is applied where coverage is resolved, so `resolveCoverage`, `nextBatch` and `pendingCount` all agree about where the window ends.

## Three standings, and only one of them deletes

Against the path you are looking at, a stored episode is:

- **active**: its turns are on this path, inside the tail window, and part of the gap-free run from the root. It is recalled; its turns are ghosted.
- **dormant**: good, just not applicable here. Its turns are on another branch, or inside the verbatim tail, or past a hole this path has. Kept untouched, excluded from recall, and it applies again the moment the path comes back to it.
- **dead**: it can never apply again. A turn it covers no longer exists anywhere in the chat, was rewritten (`edited_at`) after the summary was written, or its coverage has a *hole* in the path it otherwise sits on. The summary describes text nobody can read (or, in the third case, nothing the tiling walk can use). Reaped.

**A gappy on-path episode is dead, not dormant, and the difference is a whole chat's memory.** Dormant means "will apply again on its own"; this one never will, since closing its hole means folding past the very index it sets as the fold ceiling. One such row makes the fold window zero-width for as long as it exists: `nextBatch` returns null, `canSummarise` goes false, the panel reads "Up to date / Summarized 0", and nothing but a rebuild or a forget recovers it, at any path length, through any amount of play. Reaping costs one re-read of its turns and restores forward progress. Nothing the engine writes should ever be gappy (see promotion, above); this is the guarantee that a bad row from anywhere else (an import, a hand-edited row, a repaired copy) cannot become permanent.

**Only genuine loss deletes.** Reaping is the only delete that is not part of a step replacing what it removes (extraction supersedes the dormant summaries it overwrites, promotion consumes its sources), and the panel's Forget and its Forget-and-rebuild are the user asking for it outright. Nothing else is destructive: branch changes, swipes, and every slider in the panel are pure reads. Reintroducing a delete on a branch change is the regression this whole design exists to prevent.

**Order comes from coverage, never `created_at`.** `Coverage.active` is in story order because the tiling walk builds it from the root; `buildRecall` and `episodesAtLayer` consume that order and sort nothing. Write time does not track story position, because holes are re-foldable: the pass that re-reads a stretch after a deleted turn writes the newest row for the oldest turns. Sorting by `created_at` prints the middle of the book after its ending, and lets promotion merge two spans with a gap between them, producing a merged episode whose coverage is non-contiguous and can therefore never apply again, taking its sources' coverage down with it.

**Folded implies recalled.** `buildRecall` renders *every* episode it is handed, and callers hand it `Coverage.active`. There is no second cap on top of the layer caps, and that is load-bearing rather than incidental: a recall cap hides episodes whose messages have already been dropped from the live history, so a band of the story ends up neither shown verbatim nor recalled, permanently invisible to the model from roughly the hundredth message onward. Bounding happens in exactly one place, the layer caps. `memory.test.ts` asserts the invariant directly, in both directions: nothing archived is uncovered, and nothing active covers a turn that is still being sent verbatim.

Because a message's ancestors are immutable (each message has exactly one parent), an episode's span is contiguous on every path that contains all of it. That is the key that makes the tiling walk sound.

## Branching (the hard part)

There is no global sequence: the chat is a tree and memory follows the **active path**.

- **Branch/swipe in the live zone** (the common case: regenerating the last reply, swiping an alternate) happens after the boundary, so nothing changes standing. Zero work.

- **Branch/edit before the boundary** (a "deep" change) puts part of the archived prefix on another branch. Those episodes go **dormant**: excluded from recall, their turns back in the live prompt, rows untouched. The boundary retreats to the last still-contiguous covered turn, and further if the shorter path would put it inside the verbatim tail. Walking back restores everything, for nothing.

- **Deleting** turns is the one branch-shaped action that costs summaries, because it has to: a subtree delete removes the rows, so the summaries of those turns describe text that exists nowhere. They are reaped. What survives either side of the cut is kept.

**Holes and the fold ceiling.** Reaping a mid-prefix episode leaves a hole, and the tiling walk stops at the first hole, so everything after it goes dormant until the hole is filled. Two rules make that converge:

1. Extraction never folds *over* an on-path dormant episode (`Coverage.foldCeilingIndex`). Those come back on their own, so re-folding their opening turns would destroy a summary that was about to apply again, and pay for the privilege.
2. When the window is capped by that ceiling rather than by the tail, a **short** batch is allowed, sized to close the hole exactly. Without it a hole left by one deleted turn is `batchSize - 1` wide (narrower than a batch), so it could never be filled, every summary after it would stay dormant forever, and a long chat would quietly revert to sending its entire history verbatim.

In-place content edits keep the same id and the same tree, so pure path-membership cannot see them. Two layers handle it:

1. **Systemic**: every content update stamps the row's `edited_at`, and an episode created before that stamp is **dead** (coupling 8 keeps the two halves of that rule in step). This is the real mechanism: rewrites nobody told memory about (the Chungus Assistant's server-side edit, another device, an edit made while memory was switched off) are caught by the ordinary reconcile pass, whenever it next runs.

   It has one blind spot by construction, and the engine closes it separately: **a batch in flight is judged stale against when it was READ, not when it was written.** An edit that lands *between* a batch being read and its summary being committed predates that summary, so `edited_at >= createdAt` reads it as fresh, forever, with every later pass agreeing. The extraction loop therefore stamps each batch with the `editedAt` values it was read with, re-reads the tree (`ProcessOptions.latest`) **before** `applyBatch`, and drops the summary unwritten if any of them moved. `invalidateMessage` cannot cover this: at edit time no episode covers that id yet, so it returns false and cancels nothing.
2. **Immediate**: `memoryStore.invalidateMessage` does the same reap synchronously for the two callers that need it to have happened by the time they return: the editor, so its toast is truthful, and Continue (coupling 8).

**Consistency guards.** Extraction is fire-and-forget, so writes race branch changes, cancels and other devices. The database-level overlap invariant (coupling 2) covers all of it, and a promotion additionally verifies that every episode it is about to merge still exists. A rejected write raises `mem-op-superseded`, which the store treats as "superseded, resync", not a failure. Reaping needs no guard at all: plain deletes, no boundary to keep in step, idempotent. A batch that commits but doesn't move the boundary (the user rewrote one of its turns while the model was answering) ends the run rather than re-folding the same span; the next pass reaps the stillborn episode and re-reads it.

## Where it plugs in

**Who calls memory:**

- `chatStore.loadChatState` → `memoryStore.loadForChat` + `syncForPath`. `syncForPath` hands the store the current tree (`this.ctx`), reaps dead episodes, and, only when something was actually reaped, kicks the ordinary automatic pass, since a reap hands every turn it uncovered straight back to the live prompt (one deleted turn measured at 47 of them at once, covered by nothing) and nothing else triggers extraction on a delete. The ghost boundary moves in the same tick as the assignment because it is derived. A branch change performs **no writes at all**.
- `messageStore.generateResponse` → `triggerMemoryMaintenance` → `maintainAfterTurn`: fire-and-forget extraction, gated by the per-chat `autoExtract` flag and capped per turn (see **Extraction** and **Promotion** below).
- `messageStore.editMessage` / `continueMessage` → `memoryStore.invalidateMessage(chatId, messageId)` on every in-place rewrite while the chat has memory enabled. It reaps only the episodes actually covering that turn and returns whether it did: the editor toasts only then. This is the *immediate* half; the systemic half is `edited_at` (coupling 8), and it is the one that catches rewrites nobody told memory about, including off-path ones.
- `sync.ts` handles the `'memory'` sync scope → `memoryStore.syncReload` (another device's fold/reap/panel edit refreshes this device's episodes; the boundary redraws itself from them). A local in-flight run is left alone.
- `buildPromptMessages` (prompt-builder) → `memoryStore.getRecall(chatId, path)`: reads fresh from db and resolves coverage against the exact path it is handed, so generation is branch-consistent by construction and there is no persisted boundary that could still be catching up. The recall text enters the prompt only via the `{{memory}}` macro; archived ids are excluded from `{{chatHistory}}` only when the preset injects `{{memory}}` (see architecture/prompt-pipeline.md), and that exclusion is what holds the token count flat: without it the recalled prefix ships twice.
- The panel ([`MemoryView.svelte`](../src/lib/components/memory/MemoryView.svelte)) drives enable/build/rebuild/forget/summarise, in-place **episode editing** (`memUpdateEpisodeContent`), the **turn span** each summary was written from (`memoryStore.episodeRanges`, printed under its ordinal in the transcript's own `#N` numbering so a summary can be checked against its source without counting), the recall preview, the **dormant list** ("N summaries belong to other branches"), and config. Its action row names the work rather than the machinery: **Summarize waiting** carries the same figure the composition bar prints as Waiting, and becomes *Merge older summaries* when merges are all that is owed, since that count is not turns; the from-scratch pass is **Forget and rebuild**, because a name that reads as a refresh puts a discard of every summary in the chat one unconsidered click away. Its one-glance reading of where the story stands is a **single segmented bar** over three keyed figures, off `memoryStore.composition`: summarised / waiting / verbatim are stages of one process rather than three unrelated stats, so separate tiles left the reader adding them up to learn the only thing they wanted. `composition`'s `verbatim` band is a **remainder**, never `config.verbatimTail`: `effectiveTail` raises the tail on a path ending in assistant turns and turns stranded behind a hole are reachable by no pass, so quoting the slider would print its own value back and disagree with the bar it labels. The ladder's shape and the per-turn cost sit below a rule, since they describe the store rather than the story. It is **embedded in the Memory panel** ([`MemoryPanel.svelte`](../src/lib/components/memory/MemoryPanel.svelte), chat-area overlay `memory`), raised by the TitleBar's Memory button, which is dropped from the nav cluster entirely while the memory engine is globally off. Settings → Engines → Chat Memory holds only the global config (app-wide switch, model tier/provider, prompt templates); see architecture/engines.md.
- The **TitleBar's Memory button** ([`MemoryNavStatus.svelte`](../src/lib/components/memory/MemoryNavStatus.svelte)) is the second reader of that state and the only one visible with the panel closed, which matters because every trigger here is a background one: a pass after each assistant turn, another chasing a reap, a whole backlog ground down for minutes after Enable or Summarize. It **owns the brain glyph** rather than styling one the TitleBar rendered, so the lit glyph and the corner mark cannot drift apart into two files: the glyph goes accent, lit and breathing while a run is in flight, a static mark sits in the button's corner while work waits or after a failure, and the outstanding call count replaces that mark past a couple of passes, **latched**, so a job big enough to be quoted counts all the way down instead of blinking out the moment it crosses back under the threshold, which is what a bare comparison does to a three-call Re-read on its very first committed pass. **The mark belongs to `behind` and `error` alone**, never to a run: a backlog is worth flagging only while nothing is being done about it, and that dot over a pass grinding the same backlog down asks the reader to go and look at the work already fixing itself. Anything gating on "not idle" rather than naming those two states reintroduces it, and only late in a long run, once the count has fallen far enough to hand the slot back. The breath is the state's only motion, and it is what makes a long silence legible: a local model can sit minutes inside one summary, and a still button reads as a crash.

  Both it and the panel's status row render **`memoryStore.standing`**, one line and one of four standings (`idle` / `working` / `behind` / `error`), derived once. A second hand-kept copy of that text parts from the first the moment either changes, and the button starts describing something the panel disagrees with. Two rules ride with it. It is **silenced by the three gates**, since an inert engine owes nothing and a chat with memory switched off must never read as behind, but a run **already in flight** is reported ahead of them, because it re-asks `active` only between model calls and is genuinely spending money the gates cannot take back. And the store holds one chat at a time, so the button always speaks for the **open chat** and never claims more.

**Recall** is the engine-owned `{{memory}}` macro, placed in a preset like `{{lorebook}}` or `{{character}}`. It is never force-injected: placement is the author's call via the Prompt Builder, and the Standard Chungus preset ships with a Memory item by default.

**Extraction** is triggered fire-and-forget after each assistant turn, after a reap, and on demand from the panel. It never blocks generation. The automatic pass is capped at a few batches (`AUTO_MAX_BATCHES`); ordinary play never reaches the cap, but a deleted stretch that leaves a long backlog would otherwise spend dozens of sequential calls unasked, on a trigger as small as sending a message. A per-chat **auto/manual** toggle (`memory_state.auto_extract`, default auto) gates only this automatic trigger: in manual mode nothing is folded until the panel's Summarize, while reaping runs unconditionally. The loop re-reads the tree between batches (`ProcessOptions.latest`), because a build over a long backlog runs for minutes and the user keeps playing, branching and deleting through it. Without that it would summarise turns that no longer exist.

**Promotion is priced and bounded like extraction**, because it is the same money. It answers to the layer caps rather than to the backlog, so dragging `maxPerLayer` from 60 to 3 owes dozens of merges *at once*, on no trigger at all. Uncapped, the next ordinary reply pays for all of them. A run carries one shared merge budget (`ProcessOptions.maxPromotions`, `AUTO_MAX_PROMOTIONS` on the automatic path) spread across every batch in it, the count rides `ProcessProgress`, and `plannedWork` quotes extractions *and* merges before Enable / Summarize / Re-read spend anything. Compaction also runs once **outside** the extraction loop: promotion owed by a lowered cap must not have to wait for a batch that may be a dozen turns away.

`plannedWork`'s extraction half counts the turns nothing covers (`Coverage.onPathCoveredIds`), not the pending count: `pendingCount` stops at the fold ceiling, because that is as far as the *next* batch may reach, so one hole prices a two-dozen-pass backlog at a single pass.

**Off by default, per chat.** Enabling on an existing chat runs a one-time **build** over the backlog; the panel states the number of passes (`plannedWork`) and confirms first whenever the quote reaches `CONFIRM_ABOVE` (3), so a one-pass build is not put behind a dialog. All state is chat-scoped and cascades on chat delete.

**Three gates, one flag**: `memoryStore.active = enabled && featurePromptsStore.memoryEnabled && macroPlaced`. The third is load-bearing: recall reaches the model only through `{{memory}}`, so a preset without that item makes the engine inert everywhere (no recall, no extraction, no ghosts, full live history) instead of paying for output nothing reads. Because `coverage` is `$derived` off `active`, flipping ANY of the three moves the whole surface in the same tick; caching the ghost set as `$state` and refreshing it only on a sync pass would leave the chat painting ghosts on turns it is sending verbatim every time the engine is toggled or a preset swapped. Stored episodes and per-chat flags survive all three being off. See architecture/engines.md.

A run in flight re-asks that flag before every model call (`ProcessOptions.stillActive`). The engine can only see the chat's own `enabled` row, so without it, switching the app-wide engine off (or editing `{{memory}}` out of the preset) leaves a build spending paid calls with its own Stop button already unmounted behind it (`MemoryPanel` swaps `MemoryView` out and the TitleBar drops the button), escapable only by switching chats or reloading.

## Module layout

The core is **pure** and tested: [`engine.ts`](../src/lib/memory/engine.ts) (orchestration), [`branching.ts`](../src/lib/memory/branching.ts) (coverage resolution), [`recall.ts`](../src/lib/memory/recall.ts) (block rendering), [`prompts.ts`](../src/lib/memory/prompts.ts) (LLM message building, parsing, the loop detector), [`config.ts`](../src/lib/memory/config.ts) (clamped tunables), [`types.ts`](../src/lib/memory/types.ts) (the ports). No Svelte runes, no I/O, and no `$lib` value imports except `substitute` in `recall.ts` and `prompts.ts`, which render templates, plus `parseJsonObject` in `prompts.ts`, both pure. That parser lives in [`utils/json-extract.ts`](../src/lib/utils/json-extract.ts) rather than here because the Sprites engine asks for structured output too, and two engines inventing their own tolerance is how they end up disagreeing about what a valid answer looks like. A constraint the server build leans on too (coupling 9). The core talks to the world through exactly two ports, a `MemoryDb` (persistence) and an `LlmFn` (the model), which is what keeps it unit-testable under `bun test` with in-memory fakes.

[`db-adapter.ts`](../src/lib/memory/db-adapter.ts) is the single `$lib`-touching persistence shim (→ the `mem*` RPC methods, SQL in server/db.ts). [`store.svelte.ts`](../src/lib/memory/store.svelte.ts) wires everything to the app: one `$derived` `Coverage` that every UI surface reads (ghosts, panel stats, recall preview, composer meter), one `$derived` `standing` that both status surfaces read (the panel's row, the nav button's indicator + tooltip), one `$derived` `composition` that partitions the path into the panel's three bands, run lifecycle with abort/ownership guards, and the LLM port. **Memory rides the Memory engine's own connection and that connection's generation settings, `source: 'memory'`** (deliberately not overridden: what the user set on the Connections page is what runs). That includes its **Stream response** setting, which nothing here may work around: the port reads no tokens, but the request still takes the wire shape the connection declares, because a non-streamed one carries no sign of life and a summary on slow local hardware then has nothing bounding it but a guess at how long that hardware takes (architecture/llm-providers.md). The port **refuses an empty reply itself** instead of handing `''` to the parser, and names the cause from the two channels the pure core never sees, `thinking` and `finishReason`: a reasoning model whose thinking never closes inside the output cap leaves the whole answer in the thinking channel, so content comes back empty through no fault of the prompt. Quoting that `""` back and retrying spends a second identical call and names nothing.

**Import-cycle rule**: memoryStore must never import chatStore or `live-macro-context` (both import memory). Callers hand it a `ChatCtx` (`chatId`, `allMessages`, `leafId`, `characterId`, `characterVersionId`, `personaId`, `presetId`); it builds its own MacroContext. `presetId` is the chat's preset CLAIM, resolved through `presetForClaim`, and it decides both the controls a template expands against and whether `{{memory}}` is placed at all, so reading the app's preset here would run the engine for a chat whose own preset never injects recall. `personaId` is the chat's persona CLAIM, resolved through `personaEntryFor` (utils/chat-setup.ts) exactly as the prompt resolves it, and it travels for the same reason the version pin does: without it the summaries a chat playing as somebody else produces are written about, and in the voice of, whoever the app starts new chats as. It is also what an unstamped user turn (imported, pre-feature) reads as in `toMemory`. That `characterVersionId` is load-bearing, not decorative: `macroContext` resolves it through `characterLibraryStore.dataForVersion`, and it is the only thing keeping the `{{character}}` sheet (and the character's linked lorebooks) on the variant the chat actually plays instead of whatever the library's active version happens to be. Three construction sites must fill it: `chatStore.refreshMemory` (the `loadChatState` tail), `messageStore.triggerMemoryMaintenance`, and `MemoryView.ctx()`. See architecture/prompt-pipeline.md coupling 3b.

`ChatCtx` is held as `$state.raw` on purpose: it carries the chat's whole message array, and deep-proxying it on every refresh would cost more than everything derived from it. It is replaced wholesale, never mutated in place: a mutation would not be observed.

`MemoryView` renders no header of its own and owns no scroll/footer, since `MemoryPanel` supplies the overlay chrome (architecture/ui-shell-settings.md): the stacked header naming the open chat, with the per-chat switch beside that name. The header switch renders only the control: flipping it calls `MemoryView`'s exported `requestToggle`, the same flow behind the intro's enable button, so the enable cost-confirm guards every door and the panel never re-spells it.

## Before touching this

- Run `bun test`: `memory.test.ts` + `memory.integration.test.ts` cover the engine with in-memory fakes and with real SQL; keep the core pure so they stay meaningful. `server/chatList.test.ts` covers the copy path, including a **merged** ladder. The branching block's centre of gravity is the **absence** of writes: branch away and back must restore the boundary having deleted nothing and spent nothing.
- The db side (`memApplyBatch` / `memApplyPromotion` / `memReapEpisodes` in server/db.ts) owns ids, timestamps and transactionality. The engine deliberately owns none of the three. Never bypass them with a raw write path.
- Extraction fails loud on an unparseable **or looping** model response (retry once, then throw; nothing is written). Never reintroduce a placeholder-episode fallback, and never commit an episode with a long verbatim repeat (a run of 12+ words re-emitted verbatim, the classic small-model failure under a length target): it becomes permanent canon and every compaction preserves it faithfully. The same doctrine covers templates: `assertTemplate` (engine.ts) refuses before spending a call when `{{batch}}` is missing, and the store's `assertTemplates` pre-flight checks both templates before a build starts.
- There is no user-facing `memDeleteEpisode`, on purpose. Deleting a summary by hand would uncover turns without freeing them; only the engine knows when a summary has genuinely become unusable. Editing an episode's prose is safe and supported (`memUpdateEpisodeContent` changes text without touching coverage), and that, not the panel's rebuild, is the fix for a single bad summary. Forget and rebuild is the from-scratch fallback. **The split between prose and coverage is the whole permission model**: writing text can neither open a gap nor move the boundary, so it needs no guard and is offered to the panel and to the assistant alike; writing coverage can do both, so it belongs to the engine and has no method anywhere.

## Naming the cost before it is paid

Editing or deleting a folded turn is cheap, self-healing and completely invisible, which is the problem: the ghosts retract, the boundary jumps back, and nothing on screen says why. Two pure functions in branching.ts close that. `episodeSeqRanges` maps an episode's coverage onto the path's 1-based positions (the same `#N` the transcript prints), so a summary can be pointed at the turns it was written from, in the panel (under its ordinal), in `read_memory_state`, and in a confirmation. `changeImpact` prices a rewrite or a delete against stored coverage before it happens: which summaries die, how many pause behind the resulting hole, how many turns must be re-read, and what that costs in passes. [`impact-copy.ts`](../src/lib/memory/impact-copy.ts) renders it as one sentence for the cost, one for what happens next, and a third only when stored summaries outside the chain go too.

**Every sentence has to describe something the engine will actually do**, and four mechanics make that harder than it looks:

- **A delete re-reads only the survivors, re-positioned against the SHORTENED path.** A subtree delete removes a suffix, so the turns just above the cut land inside the verbatim tail, where no pass reaches them. Counting those as re-read promises work that never happens, on the most ordinary delete there is. A span deleted whole leaves no hole at all: the path shortens and the summaries either side keep tiling.
- **Foldable is not the same as folded.** A run shorter than `batchSize` folds only when something covered sits after it (the short-batch exception), so `passes` follows `plannedExtractions`' rule (ceil when the run is bounded by coverage, floor when it is bounded by the tail) and can honestly be zero while `reread` is not.
- **Who re-reads differs, and how fast.** A delete's reap kicks the pass itself (`syncForPath`), so it heals immediately; a rewrite is reaped by `invalidateMessage`, which does NOT kick extraction, so it waits for the next reply; in manual mode neither fires and the panel's Summarize is the only trigger; and a backlog past `AUTO_MAX_BATCHES` takes several replies whatever the mode. That constant lives in config.ts, not the store, because the copy has to respect it.
- **Paused is not lost, and dormant is not "another branch".** Everything behind the hole keeps its row and returns the moment the hole closes. `Coverage.dormant` mixes three unrelated reasons (off-path, pushed out by the tail, stranded past a hole) that come back on entirely different terms, so `droppedStored` counts them and classifies none of them: saying they go is true of all three, saying more is not.

The chat surfaces both: an in-place save over a summarised turn confirms inside the editor, and a delete that costs memory confirms in the delete menu, with the press-and-hold scaled by re-read + paused rather than the row count (architecture/chat-sessions.md coupling 3).

**The editor's confirmation offers a third door, and the gesture is the difference.** Holding buys the re-read the sentences just quoted; a plain tap ("Save quietly") saves as a MINOR edit, which costs nothing and leaves every summary standing (coupling 8). It exists because the commonest rewrite of a folded turn is a typo, and paying a model call to re-read a comma is the kind of tax that makes people stop fixing typos. Its note has to state the CONDITION, not the mechanism (the user is answering "does this turn still say the same thing", not choosing a storage strategy), and nothing may infer that answer from the text. It is also the one control here that wears no error tint, because it is the save that costs nothing and the two must not read as variations of the same risk.

## Hand-kept couplings

1. Extraction/promotion prompt templates live in [`featurePrompts.svelte.ts`](../src/lib/stores/featurePrompts.svelte.ts) (`featurePromptsStore.promptFor('memoryExtract' / 'memoryPromote')`), edited in exactly one place, `EngineDetail`'s Prompts card, which reads its field descriptors from `engines/registry.ts` (architecture/engines.md). The Memory panel's gear does not mount a second editor, it deep-links to that same detail page; shipped defaults still originate in `memory/prompts.ts`. The recall framing is NOT editable (fixed `DEFAULT_RECALL_TEMPLATE` in prompts.ts, by design). Renaming those `FeaturePromptKey`s breaks memory. The **required macros** are declared twice by hand: `EnginePromptField.requires` in `registry.ts` (the editor's warning) and `REQUIRED_EXTRACT_MACROS`/`REQUIRED_PROMOTE_MACROS` in `engine.ts` (the refusal). Keep them in step; the editor warning without the refusal is a suggestion, and the refusal without the warning is a failed generation with no explanation.
2. **No two episodes of a chat may cover the same message.** Enforced by `memAssertNoOverlap` inside every transaction that writes coverage: `memApplyBatch` and `memApplyPromotion` (server/db.ts), each time after that step's own deletes. It is what makes a derived boundary well-defined, since the tiling walk assumes at most one episode begins at any point on the path. `resolveCoverage` degrades gracefully if the invariant is ever violated from outside (it takes the longer span and leaves the loser dormant rather than guessing), but nothing in-app may rely on that.
3. The ghost rendering + "waiting" counter in chat UI read `memoryStore.archivedMessageIds` / `pending`; the same archived set must reach prompt assembly via `getRecall().archivedIds`: one boundary, two consumers, both derived from the same `resolveCoverage`. `MessageList` adds no gate of its own: the store empties the archived set whenever the active preset drops `{{memory}}` (`memoryStore.active`, off `macroPlaced`), the exact condition `prompt-assembly.buildMacroContext` uses to filter `{{chatHistory}}` (`memoryReferenced`), so the UI never claims a turn left the prompt while it is still being sent verbatim.
4. Memory flow macros ({{batch}}, {{sceneLength}}, {{deepMemory}}, …) are declared in `src/lib/macros.ts` MACROS but filled only by `prompts.ts` (extraction/promotion) and `recall.ts` (`{{deepMemory}}`/`{{recent}}`, into the recall template). Keep names in sync.
5. `MemoryConfig` fields: types.ts + `DEFAULT_MEMORY_CONFIG`/`BOUNDS` (config.ts) + the panel's `SLIDERS`. All five are exposed; the panel's **upper** bounds are the narrower ones on purpose (BOUNDS guards stored/foreign values, the sliders guard what a person can reach by dragging), while every minimum matches `BOUNDS` exactly (`verbatimTail`'s especially, which must be ≥ 1 in both, see the note above). The panel's sliders commit on **release** (`onchange`), reading a local draft while dragging and flushing that draft on unmount: committing per tick fires one server write and one cross-device sync broadcast per pixel, through a read-merge-write with no ordering between them, so the value that lands is whichever round trip finished last rather than the one released on.
6. `memListEpisodes` orders by `layer, created_at` **with a rowid tiebreak**, and `copyChatMemory` re-reads `ORDER BY rowid` so insertion order survives same-millisecond ties into the copy. Those are there for determinism; recall and promotion take story order from `Coverage.active`. Do not re-derive order from the query.
7. A merged episode inherits `MAX(created_at)` of the episodes it replaces (`memApplyPromotion`). Recall and promotion take no order from it, but the panel's episode timeline still sorts by it (`MemoryView`). That inheritance is what places a merged block among the layer-0 episodes it replaced instead of at the end. Nothing else may rely on it.
8. The edited-after-fold rule pairs `resolveCoverage`'s staleness check (`MemoryMessage.editedAt` ≥ episode `createdAt`) with the server stamping `edited_at` in `updateMessageContent`. Every path that maps app messages into the engine (`store.toMemory`, `getRecall`) must carry `editedAt` through, or in-place rewrites go undetectable. **A MINOR save is the one rewrite that deliberately does not stamp it** (`updateMessageContent(id, text, { minor: true })`): the user is asserting the turn still says the same thing, so the summary over it stands and no re-read is bought. The touch is recorded in `minor_edited_at` instead (a content change with no trace anywhere is worse than the re-read it saves), and the transcript's edited mark reads either stamp. Two rules keep it honest: the mode is the CALLER's assertion and is never inferred from the text (no diff can tell a typo from a retcon, and guessing quiet leaves memory describing a scene that no longer happened), and `messageStore.editMessage` must skip `invalidateMessage` for it too, or the immediate half would reap what the systemic half was told to keep. The check is built over **all** messages, not just the active path, so an off-path rewrite invalidates that branch's summary too. The assistant's `edit_entity` is the one surface that can make one, since the transcript only ever edits the turn on screen. `applyMessageContinuation` deliberately does NOT stamp `edited_at`, which is exactly why `continueMessage` calls `invalidateMessage` explicitly.
9. The Chungus Assistant reads memory through `read_memory_state` and writes exactly one thing through `edit_memory_episode` (both in server/assistant/registry/chat-reads.ts): **a summary's prose, never its coverage**. The same split as the panel's episode editor, for the same reason: text can neither open a gap nor move the boundary. Each reported summary carries its id and its seq range, which is what makes the write usable: the assistant reads those exact turns back with `read_chat_messages` and corrects only what they contradict. Two rules ride with it, stated once in the `edit_memory_episode` schema itself, which the model reads on every turn. **A dead summary refuses the write**: one whose turns were edited or deleted under it is about to be reaped and re-read, so a rewrite would be discarded with it, and the tool says so instead of writing. **Whether fixing the messages and fixing the summary combine depends on which door the message went through**, and that split is the same one the editor's confirmation offers a person: an ordinary edit discards the summary, so rewriting that summary too is thrown away by the engine's own re-read; a MINOR save leaves it standing, so `edit_memory_episode` is then the second half of the job, and the only cheap way to carry a rename all the way into memory, since the summaries hold the old name too. The assistant reaches the quiet door through `minor: true` on `edit_entity`/`set_entity` (messages only, content only). It is the caller's assertion in both surfaces and is never inferred from the text. That file **imports the pure core** (`src/lib/memory/branching` + `config`) to derive the boundary and the seq ranges: one implementation, deliberately, because a hand-written second derivation would rot the first time the rules change. Keep `branching.ts`/`config.ts` free of `$lib` value imports or the server build breaks.
10. `duplicateChat`'s `copyChatMemory` remaps every **message** id through the same map as the message copy; there is no cursor to remap, and the copy's boundary derives from the copied episodes' own coverage. Memory rides a duplicate only when the user opts in (`duplicateChat({ includeMemory })`), and the dialog that asks is raised only when `getChatMemoryFootprint` says there is memory to ask about. Remapping stays fail-loud (`mem-copy-stale`): a NULL fallback would invent a coverage set that is internally valid and therefore never heals. The gate is right for message references and **only** for them: a column naming rows the promotion deletes in its own transaction is dangling by construction, so putting one through the same gate would throw on every copy of a chat past its first merge and roll the whole thing back. Nothing may introduce one.
11. `memSetState` **merges** the config patch server-side, and `memoryStore.updateConfig` sends only the field that changed. Sending the whole cached object makes every slider release a read-merge-write from a client snapshot that can be minutes stale, so two devices editing different sliders each write the other's change away, worse while one is mid-build, since `syncReload` skips when busy.
12. The panel's slider `commit` compares against the **stored override**, not `memoryStore.config`. The latter is post-clamp, so releasing a slider on a value the clamp itself produced (`promoteCount` pinned to `maxPerLayer`) reads as "no change", writes nothing, and lets the old stored number resurface the moment the clamping limit is raised. The `promoteCount` track is capped at `maxPerLayer` for the same reason.

## Recall has no token budget, and that is the decision

Recall has **no token budget**, unlike the lorebook (`budgetPercent`) and the examples. `prompt-assembly.ts` treats the memory block as fixed cost the trim can never touch (`assemblePrompt`'s context-budget trim drops `{{chatHistory}}` turns and nothing else), so when `preset + context + memory` exceeds the budget, `historyBudget` goes negative and *every* live history turn is dropped while the memory block ships whole.

**This fires on shipped defaults.** The layer caps bound the episode COUNT, not their size, and size compounds: the promote template asks for "roughly half the length of the input" while merging `promoteCount` episodes, so episode length is geometric in `maxLayers`, and the top layer compacts in place under an unchanged cap, so top-layer episodes double each time it fills. A saturated three-layer ladder on the shipped config runs to **several thousand tokens** (the ladder fills at around 2,000 messages), which blows the budget on a small context; the panel's sliders reach six figures. Measured: a 6,003-token memory block against an 800-token budget drops all 38 live turns and still ships memory whole.

**Decided (2026-07): nothing yields, and recall is not capped.** The context size is the user's own setting on the Connection page, and the layer sliders are theirs too; a configuration whose memory alone outgrows its budget is a configuration to change, not one for the engine to paper over. Both alternatives were weighed and rejected: capping the block by size means compacting harder, which spends merge calls to make memory worse; letting memory yield under pressure means dropping episodes whose turns are archived and therefore not sent verbatim either, which is exactly the band-of-story-invisible hole the folded-implies-recalled rule above exists to prevent.

What the app owes instead is visibility, and it has it: the composer chip and the Prompt Builder header both flag the trim and the over-budget case, and the panel's per-turn cost figure (the bottom line of its composition card, weighted for it) shows the block's real size. Do not reintroduce a recall cap without changing this note first.
