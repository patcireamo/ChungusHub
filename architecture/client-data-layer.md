# Client data layer & cross-device sync: architecture & maintenance

Everything the client persists or streams goes through exactly two files: [`transport.ts`](../src/lib/services/transport.ts) (the only place that talks to the network) and [`database.ts`](../src/lib/services/database.ts) (a thin typed proxy over the server's SQL). No store or component fetches directly. If you find yourself writing `fetch(` outside `transport.ts`, stop.

**Transport** ([`src/lib/services/transport.ts`](../src/lib/services/transport.ts)): REST helpers (`apiGet` / `apiSend` / `apiUpload`) with shared error handling: 403 throws `AccessDeniedError`, 401 hard-reloads the page (lands on the server's unlock screen), and a 503 flagged `maintenance` throws `MaintenanceError` carrying the server's own headline and detail, since an install holding itself for a restore is answering rather than failing and is the only side that knows what the reader has to do about it. `dbRpc()` posts `{ method, args, clientId }` to `/api/rpc/db`. `fileUrl(rel)` maps a stored relative path to `/files/<rel>` for `<img>`/CSS use. The WebSocket (`connectWs`) is a single shared connection carrying multiplexed channels. **In dev it is the one request that does not ride the Vite proxy**: `wsUrl` opens it straight at the Bun server's port, which `vite.config.ts` bakes into the bundle for that purpose alone. A proxied upgrade rests on the JavaScript runtime's own upgrade path, and a runtime that stops emitting that event leaves the handshake hanging with no error, no close and nothing to report, which is the one failure shape a client cannot tell apart from a dead host. Production is untouched (the origin serving the page is already that server), and going direct also hands the server the device's real address in place of the proxy's loopback. There are request/response ones, each a pending-map keyed by request UUID, plus server-pushed feeds: LLM completions (`llmComplete`, with token/thinking callbacks + cancel via `AbortSignal` → `llm-cancel`; a cancel deliberately does **not** settle the promise on the spot: every provider answers an abort with a normal `llm-done` carrying everything it streamed before the stop, flagged `finishReason: 'cancelled'`, so the request waits for that frame and the caller receives the partial reply. Rejecting on the spot would drop that frame on the floor, and a reply the user stopped mid-stream would lose every token they had watched arrive. A 5s timer settles it as a clean abort if the server never answers, and an `llm-error` arriving after a cancel settles the same way rather than surfacing the abort restated as a failure), assistant turns (`assistantStream`, with the same cancel grace and 5s timer, so the closing `assistant-done` still delivers the turn's real usage and context accounting), assistant the assistant running-turn query (`assistantStatus`), sync hints (`onSync`), the **assistant event feed** (`onAssistantEvent`), and the debug prompt-log feed (`onPromptLog` + `onPromptLogClear`, gated by `setPromptLogEnabled` which tells the server whether to capture at all).

**The assistant channel is addressed by SESSION, not by request.** `assistantStream` returns a promise (it is the one thing only the page that started the turn can know: a pre-flight throw, a dropped socket) but carries no streaming callbacks; every delta, tool-call progress frame, tool result and finish arrives on `onAssistantEvent` tagged with its `sessionId`, so a page that reloaded mid-turn (or a second device with the same tab open) renders the turn it never asked for. `assistantStatus(sessionIds)` asks which of those sessions are running and returns each one's timeline so far; the server builds and sends that snapshot in one synchronous step, so no delta can slip between it and the frames that follow and the caller can append straight onto what it was handed. `assistantCancel(sessionId)` stops a turn with no request of one's own: turns are session-keyed server-side, so it lands from a page that reloaded after the turn began. Reconnect is a 2s retry loop, and **one failed pass of that loop is what flips `isReachable()` / `onReachabilityChange(fn)`**, the signal behind the standing connection bar (architecture/ui-shell-settings.md). A drop is deliberately not reported the moment the socket closes: a sleeping laptop, a wifi hiccup and a dev-server restart all heal on the first retry, so reporting the close itself would flash the bar on each of them until the reader stopped seeing it, and the ~2s wait is what makes "the host is unreachable" safe to print. A socket goes down through exactly one path: `handleSocketDown`, called by `onclose` **and** by the heartbeat, and a no-op once a newer socket has taken over, so a late close event cannot reject the new connection's work. The heartbeat exists because a socket whose peer vanished without a close frame (what a sleeping laptop leaves behind) stays `OPEN` forever and would silently stop receiving sync: a `{t:'ping'}` on a quiet socket must draw an answer or the socket is declared dead, and **how long that takes IS the connection bar's latency**. Neither number is a constant, because they are not the same kind of number. **How long to wait for an answer** decides false positives and honestly spans three orders of magnitude (a couple of ms on a LAN, seconds on bad cellular), so it is **measured**: the TCP RTO estimator (Jacobson/Karels, smoothed mean + 4 deviations) over the pong round trips, which widens itself on a jittery link and tightens on a steady one. **How often to probe** decides how stale our knowledge may get and rides the same measurement (`8 × srtt`). Both are clamped, and **the floors carry more weight than the estimate**: a 2ms LAN round trip would put the window in single-digit milliseconds, where one blocked event loop on either end reads as a dead server, so the floor is sized against a stalled main thread rather than a packet. Two rules keep an aggressive window safe. **Any inbound message counts as the answer**, not just the pong, so a socket delivering tokens is never torn down for a reply queued behind them and the probe only ever fires against a genuinely quiet socket (which is also why the probe timer tests elapsed quiet on fire instead of being reset per token). And **silence must happen twice**, the second time with double the window: tearing a socket down rejects every in-flight request, so one hiccup during a long wait for a model's first token would otherwise kill the reply it was waiting for. Returning to a **visible** tab discards the estimate and clears the strikes, since a throttled tab fires its timers in a burst on wake and can expire a window whose answer was frozen in the same queue. The connect attempt carries its own 5s cap for the same family of reasons: a host that is off, asleep or firewalled never answers the SYN and the OS sits on that for ~20s with no error and no close, which would put the bar behind a TCP timeout instead of a human one. **That cap bounds one attempt and never the app's patience**: a rejection from `connectWs` is a fact about five seconds, not about the host, so the one caller that cannot proceed without a socket (boot, architecture/ui-shell-settings.md) loops over it at the reconnect loop's own cadence rather than reading the first rejection as the answer. `onReconnect(fn)` fires on every open **after** the first: the server keeps no per-device queue, so hints broadcast while a device was away are gone and the only correct answer is a full re-read (see Sync below), which for the assistant means re-asking `assistantStatus` (the deltas that fired while the socket was down are gone too). **A generation is NOT rejected when the socket goes down**, and neither is a Stop already in flight against one. The server keeps running it and holds what it streamed (architecture/server-core.md), so the pending stays in the map and `reattachGenerations` claims it on the next open, before the scope handlers, each request naming how many characters of each stream it already applied so the answer carries the remainder alone and the transcript picks up mid-word instead of repainting. A claim the server cannot honour comes back `llm-attach-miss` and rejects, which is the truth (the request died in the socket it was written to, the process restarted, or the answer waited past its window) and is what keeps the composer from staying locked on nothing. **A Stop pressed while there is no socket splits on `isReachable()`**, and the two cases need opposite answers: a blip parks the cancel on the pending and sends it the moment a socket lands, because settling locally would leave a reply generating with nobody able to stop it; a host that has already failed a reconnect settles as the abort it asked for, because waiting would leave the composer holding a button that does nothing. **A request that lived through a drop reports neither stream clock**: both are measured from frame arrival and this page was not there for the frames, so either would carry the length of the disconnection inside it (architecture/llm-providers.md). On a socket going down every other pending request is rejected: the assistant rejection is marked `detached` (the turn keeps running server-side, so the tab stays busy showing what it has until the reconnect's status query re-adopts the live turn or clears it; the store commits nothing and offers no Retry for it), except a Stop already in flight on either channel, which settles as a clean abort. The `clientId` is sent with every RPC and on the WS handshake's query string so the server can skip echoing a mutation's hint back to whoever caused it. It identifies a **page, not a device**, minted per page load, never persisted: any store tabs share (localStorage) makes two windows of the app mutually blind, each suppressing the other's changes as its own echo.

**Database proxy** ([`src/lib/services/database.ts`](../src/lib/services/database.ts)): one method per server db method, same names, same arg order. Pure passthrough via `dbRpc`, exported as the `db` singleton. **The server side is the source of truth**; see architecture/server-core.md for the three-place rule when adding a method (server method + allowlist/scope entry + this proxy). `initialize()` only ensures the WS is up before stores start reading, and its rejection is one failed 5s attempt rather than a verdict on the server, which is why boot retries it. **A store must never loop a per-row proxy method over a set the user's data sizes.** Each call is a round trip, an autocommit and a sync broadcast, and the sequence is atomic per row rather than as a whole, so an interrupted run leaves a half-written state behind: `db.importChat(chat, messages)` exists for exactly that reason and is the shape any future bulk write takes (architecture/server-core.md).

**Sync** ([`src/lib/services/sync.ts`](../src/lib/services/sync.ts)): the server broadcasts coarse scope strings after mutations; `initSync()` (called once at app boot) maps each scope to targeted store reloads: `chats`/`messages` → chatStore + chatCastStore, `library` → characterLibraryStore, `lorebooks` → lorebookStore, `steering` → steeringStore (the whole note list; it is small enough that refetching beats diffing rows), `presets` → presetService (committed files, drafts, and active-selection validation), `settings` → personaStore + presetControlsStore + every synced-setting store, `assistant` → assistantSessionStore + the assistant skills registry, `drafts` → inputDraftStore (active chat only), `inputHistory`, `memory` → memoryStore (active chat only, and skipped while a local memory run is in flight: that run's own teardown re-reads). A scope this build has no handler for (version skew across devices) is logged as an error rather than dropped silently. Hints are applied strictly one at a time in server order (a promise queue in `initSync`). Some scope pairs depend on it, e.g. a `presets` hint must land the preset that a following `settings` hint activates. `initSync` also subscribes to `onReconnect`: coming back from a drop replays **every** handler (`resyncAll`, in `HANDLERS` declaration order, which is why `presets` is declared above `settings`), because the hints that fired while the socket was down are not repeated. Without it a laptop that slept through a batch of changes shows yesterday's state until the user reloads the page by hand; a new scope joins the replay for free, since the typed `Record` forces an entry. **Adding a new scope is a three-sided change**: the entry in `shared/sync.ts`, the server broadcast (db.ts `MUTATION_SCOPES` or an endpoint's explicit `broadcastSync`), and a handler here. The typed `Record` forces the handler; nothing forces the broadcast: a file-backed endpoint that mutates and never calls `broadcastSync` works locally while every other device goes stale until reload.

**Synced settings primitive** ([`src/lib/services/syncedSetting.ts`](../src/lib/services/syncedSetting.ts)): the pattern for any per-user preference that should follow the user across devices. `readSetting(key, fallback)` / `writeSetting(key, value)` ride the server `settings` table (JSON-encoded), and `registerSettingsReload(fn)` hooks the store's reload into the `settings` broadcast. It returns a disposer, which boot-time stores ignore and a mounting component must call. Stores that use it: theme, ambient, background, browse view prefs, etc. **A store that reads a settings row but never registers a reload is the quiet bug this primitive keeps producing**: the write side broadcasts, so the other device is told, and nobody listens. Anything reading a settings row directly through `db.getSetting` owes the same registration: lorebook global settings, the token-calibration factors and the Assistant Settings page all carry one. `writeSetting` failures are surfaced (console + toast) rather than swallowed: the store has already moved, so a lost write means this device shows a value nothing else will ever agree with. **Do not use localStorage for user preferences**: what is left there is per-device viewport geometry (sidebar collapse, the assistant widget's placement), nothing a user would call a setting, plus one thing that is not a preference at all. The theme's **first-paint cache** (`chungushub:paint`, written by `applyTheme()` and read by an inline script in `app.html`) is a mirror of what THIS device last painted, kept because the look itself rides this spine and nothing can read the spine before the app has booted; a device that has never run the app has nothing there and falls through to app.css's defaults. That is the shape a new localStorage key has to have to be allowed: a cache of something the spine already owns, never the only copy of anything (architecture/ui-shell-settings.md). Note the deliberate contrast with `readSetting`'s corrupt-value fallback (a busted JSON pref is harmless) versus the server's fail-loud state files.

## Before touching this

- Read this file + architecture/server-core.md (the two describe one seam from opposite sides).
- New persistent data? Decide: relational (db method through the bridge) vs file-backed (REST endpoint in server files.ts) vs a mere preference (`syncedSetting`). Don't invent a fourth path.
- Anything that mutates shared state must end up broadcasting a sync scope, and that scope must have a handler in sync.ts.
- **Debouncing a write? Use [`DebouncedWriter`](../src/lib/utils/debounced-write.ts), never a hand-rolled timer.** One instance per store, at module scope, constructed with a delay and a `commit(key)` that reads the store's own current state, so a burst of edits writes the newest value exactly once, and `schedule` / `cancel` / `pending` / `flush` mean the same thing everywhere. It owns the two rules a hand-rolled timer keeps losing. **One:** it commits through [`flushOnHide`](../src/lib/utils/flush-on-hide.ts) by construction, because `pagehide` alone misses a backgrounded tab, whose timers freeze and then fire on wake, writing pre-sleep text over whatever another device changed meanwhile. **Two:** a commit only ever runs for a key with a pending timer, since every write broadcasts a sync scope and writing unprompted lands this device's copy on all the others. Users today: lorebook books, steering notes, composer drafts, regex rules, library entry drafts. A store that wants a toast on failure catches inside its own callback; the writer deliberately lets errors surface.

## Shared contracts

The client and the Bun server never import each other: the client is bundled by Vite, the server runs (and compiles) under Bun alone. What they must both know lives in [`shared/`](../shared/): dependency-free modules imported by relative path from `server/` and through the `$shared` alias (declared in `svelte.config.js`) from `src/`. Today that is [`shared/sync.ts`](../shared/sync.ts), the live-sync scope vocabulary. Anything that is genuinely one contract with two consumers belongs here rather than in two hand-matched declarations.

## Hand-kept couplings

1. Proxy method names in `database.ts` ↔ `ALLOWED_DB_METHODS` on the server (= `READ_METHODS` + the keys of `MUTATION_SCOPES`), asserted by [`src/lib/contracts.test.ts`](../src/lib/contracts.test.ts): every `this.call('x')` must be on the allowlist, or the typo surfaces only at runtime as "Unknown db method". The reverse is deliberately not checked: the server exposes methods only the in-process assistant uses.
2. Sync scope strings: **not hand-kept.** `SyncScope` (shared/sync.ts) types both `MUTATION_SCOPES`/`broadcastSync` on the server and the `HANDLERS` table in `sync.ts` (a `Record<SyncScope, …>`, so a missing arm fails to compile). The contract test only checks the leftover direction the compiler cannot see: a declared scope nothing ever broadcasts.
3. WS message `t` discriminators + payload shapes ↔ `server/index.ts` websocket handler (both directions). The discriminator half is asserted in the contract test (every `t` the client sends has a server handler; `sync` is server→client only). **Payload shapes are still hand-matched**: the obvious next `shared/` module.
4. `PromptLog*` types exist in both `transport.ts` and `server/promptLog.ts`, kept structurally identical by hand. Really one Request shape plus one Result shape, and two different merged "entry" views of them (`PromptLogEntry` in [`src/lib/debug/types.ts`](../src/lib/debug/types.ts) and in `server/promptLog.ts`); a `shared/` module would collapse it.
5. `AssistantStreamRequest` / `AssistantToolResult` shapes ↔ `server/assistant/loop.ts` (`AssistantRequest`) and the registry's `ToolOutcome`. The attached-file half is NOT hand-kept: the row shape both sides speak lives in [`shared/assistant-files.ts`](../shared/assistant-files.ts), and the request carries only `files: string[]`, ids of rows the upload already stored, so a turn binds them to its user message rather than shipping any content.
6. Assistant step accumulation exists twice, by necessity: `assistantSessionStore.applyEvent` builds a tab's live timeline from the event feed, and `recordLiveEvent` (server/index.ts) builds the same timeline server-side so a page joining mid-turn can be handed it. They must fold an event identically, or a reloaded page's timeline disagrees with one that watched from the start. Neither side can import the other, and the shapes they build (`AssistantStep`) are declared on both sides already. **Three events are deliberately outside the mirror.** `assistant-tool-progress` describes a call that has not returned, so it is not a step and the server records none. The client folds it into its own ephemeral `runtime.running` list instead, and a reloaded page re-draws that row from the next frame (architecture/chungus-assistant.md, *Watching a call write itself*). `assistant-approval` and `assistant-question` are not steps either but are not ephemeral: a card stands until answered, so it lives on `LiveTurn.pending` server-side and on `runtime.pending` client-side (one slot on each end, since a turn waits on one card at a time), and `assistantStatus` hands it to a page that joined mid-wait, since a delta that will never be re-sent cannot be recovered from the next frame. `assistant-attachments` (the resolved record of what rode with the user turn) is not a step and needs no snapshot slot: the server persists it on the user row before the event fires, so a page that joined mid-turn reads it from the transcript, and the event only spares the sender's optimistic bubble a db round-trip. Anything that IS a step must stay folded on both sides.
7. Reading a settings row ↔ registering a reload for it. Nothing in the type system ties the two together, so the contract test walks `src/lib` and requires every file that reads a row to also carry a `registerSettingsReload` or the `syncReload` that sync.ts calls by name. Two files are exempt and say why (`database.ts`, which *is* the read, and `utils/prompt-builder.ts`, which reads per build). A new reader with no reload path is a failing test rather than a device that quietly disagrees with the others.
